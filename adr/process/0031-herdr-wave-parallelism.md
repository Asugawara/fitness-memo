# ADR-0031: Herdr の波状並列でファイル所有権を分けて実装する

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: process
- **関連**: [ADR-0030](0030-adversarial-review-before-implementation.md)

## 背景

実装は Herdr（ターミナルマルチプレクサ）のペインに `claude` を複数立てて並列で進める。並列化の単位をどう切るかが問題になる。

複数のエージェントが同じリポジトリの作業ツリーを共有するので、**2 つが同じファイルを同時に編集すると片方の変更が消える**。git のマージ機構は働かない（コミット前の作業ツリーだから）。

一方でファイルを完全に分ければ、依存関係の順序を守る必要がある。`views/today.rs` は `core.rs` と `model.rs` が無いと書けない。

## 決定

**波（Wave）ごとに担当を決め、各ワーカーに「所有ファイル」を排他的に割り当てる。ファイル集合は互いに素にする。**

| 波 | 担当の分け方 |
|---|---|
| Wave 0（直列） | ツールチェーン導入。全ワーカーの前提なので並列化しない |
| Wave 1 | worker-a = `Cargo.toml` / `src/{lib,main,model,presets,core}.rs` ／ worker-b = `index.html` / `public/*` / `scripts/*` / `playwright.config.mjs` / `.githooks/` |
| Wave 2 | worker-a = `storage.rs` / `views/{mod,today}.rs` / `styles.css` ／ worker-b = smoke テスト |
| Wave 3 以降 | 画面ごとに 1 ファイル 1 ワーカー（`chart.rs`+`progress.rs` / `calendar.rs` / `menu.rs`） |

**Wave 2 の冒頭で `views/mod.rs` に `calendar` / `progress` / `menu` / `chart` を stub ファイル付きで宣言しておく。** これで Wave 3・4 の複数ワーカーが `mod.rs` を同時編集する衝突が構造的に消える。

モデルは基本 `claude-opus-5`、難易度に応じて下げ、`--effort` は毎回明示する。実装ワーカーは `--permission-mode acceptEdits`、調査専用ペインは `plan`（書き込み不能を保証できる）。

**`git commit` はオーケストレータが行い、ワーカーはしない。**

## 理由

- **ファイル単位の排他が、共有作業ツリーで唯一機能する分割である。** ロックもマージもないので、「同時に触らない」以外の防御手段がない。所有ファイルを明示的に列挙し、それ以外を触らないことを指示に含める。
- **`mod.rs` の stub 先出しが要点である。** Rust ではモジュールを親で宣言しないとファイルがビルドに含まれない。つまり新しい画面を追加する各ワーカーが `mod.rs` を編集する必要があり、**そこが構造的な衝突点になる**。stub を先に置いて宣言を確定させれば、以後 `mod.rs` は誰も触らない。
- **`git commit` を 1 箇所に集めると、pre-commit が 1 回で済む。** pre-commit は 25〜50 秒かかる（[ADR-0029](../deploy/0029-ci-in-pre-commit.md)）。ワーカーが各々コミットすると、他ワーカーの未完成な中間状態を巻き込んで落ちる。加えて `cargo` の target ロックで待ちが増える。
- **波で区切るのは依存関係のため。** Wave 1 の `core.rs` が無ければ Wave 2 の画面は書けない。逆に Wave 1 の 2 ワーカー（Rust 側 / アセット側）は互いに依存しないので並列にできる。
- **`--effort` を毎回明示するのは、難易度が波ごとに大きく違うため。** Wave 2 の `storage.rs` + `views/mod.rs`（`visibilitychange` × debounce flush × 日付再評価 × キーボード対策が絡む）は本アプリで最難で `xhigh`。Wave 1 のアセット系は仕様が計画で確定文になっており機械的なので `medium` で足りる。

## 運用上判明した注意点

実際に触って分かったことを記録する。同じ構成を再現するときに必要になる。

1. **分割直後のペインに `herdr agent start` を打つと `agent_pane_busy` で失敗する。** シェル初期化中のため。4〜6 秒待つか `herdr pane read --source visible` でプロンプトを確認してから起動する。
2. **エージェント名は小文字のみ。** `worker-A` は `invalid_agent_name` で拒否される。
3. **rustup 導入後、既存セッションの Bash は PATH を更新しない。** rustup は `~/.zshenv` と `~/.config/fish/conf.d/rustup.fish` を正しく書くので**新規ペインでは通る**が、rustup より前に起動していたセッションでは `cargo: command not found` になる。
4. **`herdr agent prompt` はテキストと Enter を同時に送るので、指示は必ず 1 行にする。** 改行を含めると途中で送信されて指示が壊れる。
5. **`--model` / `--effort` は起動時 argv。** 波ごとに変えるにはそのペインの `claude` を終了して `herdr agent start` を打ち直す。
6. **cargo の target ロックは待つだけで壊れない。** 2 ワーカーが同時に `cargo build` すると `Blocking waiting for file lock on build directory` と出る。ボトルネックになったら `CARGO_TARGET_DIR` を分ける。
7. **ワーカーを止めるときは新規起動ではなく `claude --resume <session-id>` で再開する。** transcript は `~/.claude/projects/<sanitized-cwd>/<session-id>.jsonl` に残り、`rg -m1 'あなたは worker-[ab] です' <id>.jsonl` で誰かを特定できる。
8. **⚠ resume しても「既に作り終えたファイルへの訂正」は自動では適用されない。** 実際に踏んだ: worker-b は resume 後、未着手の 6 ファイルは作ったが、プロンプトに含めた「既存ファイルへの訂正 5 点」を反映しなかった。エージェントは自分の TODO の続きから再開するため、完了済みタスクの手直しは指示に含めても落ちやすい。**訂正は独立したタスクとして投げ直す。**
9. **成果物の受け入れ検証は自分でやる。** 「変更したファイル一覧」の自己申告は当てにならない。要となる不変条件（`sw.js` に `.put(` が無い、`startsWith('fitness-memo-')` がある）を `rg` で機械的に確認する。

## 実際に起きた失敗と教訓

### 1. pre-commit が 23 コミット走っていなかった（`core.hooksPath` の設定漏れ）

`scripts/setup.sh` が `git config core.hooksPath .githooks` を実行する設計にしてあったが、**実際には実行されておらず、23 コミットのあいだ pre-commit が一度も発火していなかった。** ワークフローファイルを書かない構成（[ADR-0026](../deploy/0026-no-workflow-files.md)）では pre-commit が唯一の自動検証（[ADR-0029](../deploy/0029-ci-in-pre-commit.md)）なので、その期間 `cargo fmt` / `clippy` / `cargo test` / `trunk build` / Playwright のどれも自動では走っていなかった。発覚は worker-a の総点検である。

気づけなかった理由は 2 つある。**`core.hooksPath` はローカル設定なのでリポジトリから見えない**（`.githooks/pre-commit` が存在することと、それが有効であることは別）。そして**フックが走らないときの症状は「何も起きない」**で、失敗と区別がつかない。ワーカーは手元で `cargo test` を通してから完了報告するので、成果物の品質からも異常が見えなかった。

**教訓: CI の仕組みを作ったら、それが実際に発火することを最初に確認する。** 「設定するスクリプトを書いた」は「設定された」ではない。確認は 1 コマンドで済む（`git config core.hooksPath` が `.githooks` を返すか、わざと整形を崩した 1 行をコミットして落ちるか）。[ADR-0029](../deploy/0029-ci-in-pre-commit.md) に「clone しただけではフックが効かない」というトレードオフを書いていたが、それが「一度も有効化されない」形で顕在化した。書いてあるリスクは、書いただけでは防げない。

### 2. インラインスタイルの削除を、引き取る CSS より先にコミットした

`views/calendar.rs` は Wave 3a の時点で、`styles.css` の衝突を避けるためレイアウト宣言をインライン `style=` に置いていた（下記トレードオフの 1 点目の運用）。これを CSS へ移す作業が 2 ワーカーにまたがった。

- `de0edeb` が `calendar.rs` から**インライン `style=` を 12 箇所削除**した。このコミットは `calendar.rs` と `mod.rs` だけを含み、`styles.css` を含まない
- その時点の `styles.css` の `.cal-grid` は `padding-top: 2px` だけで、**`display: grid` も `grid-template-columns: repeat(7, 1fr)` も持っていなかった**。`.cal-dot` も同様で、「色は `Group.color` 由来なので background は calendar.rs のインラインが持つ」という前提のコメント付きで `flex: none` だけを持っていた
- 結果、`de0edeb` と次の `76bcf79` の **2 コミットで月グリッドが `display: block` の 42 セル縦積み、ドットは 0×0 で不可視**という状態だった
- `396ab9d` が `styles.css` に 63 行を足して解消した

**この間 E2E は緑だった。** 日付セルの click も日別詳細の表示も機能としては動くので、`data-testid` を辿るテストは 7 列でなくても通る。気づいたのは worker-c の申し送りと、再検証ハーネスの準備で `display: block` / `grid-template-columns: none` を実測したときである。

**教訓: 1 つの変更が複数ファイルにまたがるとき、片方だけコミットすると壊れる組み合わせがある。ファイル所有権で分業していると、この依存関係がワーカー間の申し送りでしか伝わらない。** 所有ファイルが互いに素であることは「同時編集で上書きが起きない」ことだけを保証し、**意味的な依存**は保証しない。「A から消して B へ移す」形の変更は、2 ワーカーにまたがるなら**両方の完了を待ってから 1 コミットにまとめる**か、移設先が入っていることを検証してから削除する。

### 3. 後片付けで他ワーカーの `static-server` を kill した（worker-d）

検証で起動した静的サーバを止めた後、`static-server.mjs` のプロセスが 1 つ残っているのを見て `kill` した。それは自分の割り当てポート（4395〜4397）ではなく、**他ワーカーの Playwright が `webServer` として起動していたものだった**。実害は出なかった（相手は再実行で通る）が、他人のテストを落としうる操作である。

同じ根の失敗をもう 1 度踏んだ。検証ハーネスの出力を `head` にパイプしたところ EPIPE で node が落ち、**子プロセスのサーバが孤児化した**。2 度目は `lsof -nP -iTCP:<自分のポート> -t` で PID を取り、`ps` でコマンド行が `static-server.mjs` であることを確認し、かつ自分の割り当てポートであることを根拠にしてから止めた。

**教訓: 共有資源（ポート、`dist` ディレクトリ、プロセス）は所有権を分けても衝突する。自分が起動したものだけを PID で記録して止める。** ファイル所有権は `src/` には効くが、ポート番号・ビルド出力・OS のプロセステーブルには効かない。`spawn` の戻り値の `pid` を保持して停止し、`pkill -f static-server` のようなパターン一括停止は使わない。

## うまくいった点

失敗と対で記録する。いずれも「ファイル所有権」の考え方を、ファイル以外の共有資源と検証に広げたものである。

- **`dist` を `--dist` で分離した。** 当初は共有の `dist/` を使っていたので、自分のビルドが他ワーカーの Playwright が読む成果物を差し替えてしまう経路があった。`trunk build --dist <自分専用のディレクトリ>` にし、静的サーバの `STATIC_ROOT` をそこへ向け、ポートも 4395 / 4405 番台のように割り当てを分けた。**これで並行ビルドの汚染は完全に消えた**（`cargo` の target ロックによる待ちは残るが、待つだけで壊れない）。ファイル所有権と同じ発想をビルド出力とポートにも適用しただけである。
- **実機相当のスクリーンショット検証が、単体テストと E2E で捕まらない実バグを 4 件見つけた。** ① 今日タブの「種目を追加」シートがボトムタブに隠れて最下部の種目が押せない ② バックドロップがタブバーを覆わず、シート表示中にタブを押すと別画面へ飛ばされる ③ `target-select` が WebKit で 23px（`min-height: 44px` を宣言しているのに UA が上書きする。**Chromium では 44px なので Chromium だけの E2E では原理的に見えない**）④ グラフの Y 軸ラベルが viewBox 外に出て `2,954,576` が `954,576` と読める。**4 件とも `cargo test` と E2E が緑のまま潜んでいた。** 共通点は「機能は動くが見え方が壊れている」ことで、`data-testid` を辿るテストの盲点である。上記の失敗 2（カレンダー崩壊）も同じ経路で見つかった。判定は `elementFromPoint` / `getBoundingClientRect` / `getBBox` で数値化できるので、目視の代わりに機械化して 38 状態を 1 コマンドで回せる形に落とせた。
- **退行テストを「修正前の状態で実際に落ちること」を確認してから採用した。** 検証ハーネスを修正が入る前のビルドに当てて FAIL することを見てから、修正後に PASS することを確認した（`target-select` は 23px で FAIL → `height: 44px` で 44px になり PASS、Y 軸ラベルは `x=-11.6` で FAIL → 短縮表記 `2.2M` で PASS）。**落ちない退行テストは何も守らない**ので、この順序は省略できない。同じ理由で worker-b はシート z-index の退行テストを追加している。

## 結果（トレードオフ）

- **`public/styles.css` が構造的な衝突点として残った。** 各画面が CSS を必要とするのに、ファイルが 1 つしかない。Wave 3 以降は「CSS は書かず、必要なクラス名と CSS を完了報告で列挙し、オーケストレータがまとめて入れる」運用にした。**追加の往復が発生し、ワーカーは自分の画面の最終的な見た目を確認できないまま完了報告する**という明確なコストがある。CSS Modules のような仕組みがない素の CSS 1 ファイル構成（[ADR-0001](../architecture/0001-rust-leptos-csr-trunk.md) の方針）の代償である。
- **ワーカーが他ワーカーの壊れた中間状態でビルドが落ちる。** 実際に Wave 3 で `menu.rs` の担当が `trunk build` を回したところ `calendar.rs`（別ワーカーが編集中）のコンパイルエラーで落ちた。自分のファイルにエラーが無いことを `cargo check 2>&1 | rg 'menu.rs'` で確認し、リトライで待つ運用になる。**「ビルドが通る」を完了条件にすると他人に依存する。**
- **オーケストレータが検証のボトルネックになる。** ワーカーの自己申告を信用できないので、成果物を毎回自分で `rg` で確認する必要がある。並列度を上げるほど検証の負荷が上がる。
- **波の境界で待ちが発生する。** Wave 1 が終わるまで Wave 2 は始められない。ファイル所有権が互いに素であっても、依存関係は残る。
- **stub 先出しは「宣言だけあって実装が無い」期間を作る。** その間 `trunk build` は通るが画面は「Wave 4 で実装」と表示される。中間状態が正常に見えるので、実装漏れに気づきにくい面はある。
- **「壊れた中間コミット」ができやすい。** 上記の失敗 2 がその実例で、意味的に 1 つの変更を 2 ワーカーが別々のコミットで入れると、その間のコミットは動くが壊れている。**単一エージェントで直列に進めれば起きない種類の欠陥**であり、並列化の直接のコストである。オーケストレータが「このコミットは単独で成立するか」を毎回見る必要がある。
- **共有資源の分離を、ファイル以外にも明示的に設計する必要がある。** ポート・`dist`・プロセスは所有権の割り当て表に入っていなかったため、上記の失敗 3 を踏んだ。担当表を作る時点でファイルだけでなく**ポート番号とビルド出力先も割り当てる**のが正しい。
- **検証ハーネス自身の可用性が問題になる。** 38 状態を回すハーネスを書いたところ、1 箇所の click 失敗で全体が中断し、例外でレポートが書かれず、`--only` 実行が他チェックのスクリーンショットを消すという欠陥を順に踏んだ。状態ごとに try/catch を置き、レポートは `finally` で書き出す必要がある。**検証する側が落ちると何も分からなくなる**ので、ハーネスは本体より壊れにくく作る。

## 検討した代替案

**単一エージェントで直列に実装する**: 衝突が原理的に起きず、検証も 1 箇所で済む。しかし独立した作業（Rust のロジック / アセットとテスト基盤 / 画面 4 つ）を順番にやるのは待ち時間が長い。ファイル集合が明確に分かれる構造なので並列の利益が大きいと判断した。

**git worktree でワーカーごとに作業ツリーを分ける**: ファイル衝突が完全に消え、`cargo` の target も自然に分かれる。しかし**統合が git のマージになる**ので、`views/mod.rs` や `styles.css` のような共有ファイルでコンフリクト解決が必要になり、しかもコンフリクトは全ワーカーの作業完了後にまとめて現れる。作業ツリー共有 + ファイル所有権のほうが、衝突を「起こさない」方向で解ける。加えて `target/` が worktree ごとに数 GB 必要になる。却下。

**ファイルではなく機能単位で分ける**: 自然な分割に見える。しかし機能はファイルを横断する（「アーカイブ機能」は `model.rs` / `menu.rs` / `progress.rs` / `today.rs` に触る）。同時編集が必ず発生する。却下。

**ワーカーにもコミットさせる**: 各自の作業が独立して履歴に残る。しかし pre-commit が他ワーカーの中間状態を巻き込んで落ちるので、`SKIP_HOOKS=1` が常態化する。それは [ADR-0029](../deploy/0029-ci-in-pre-commit.md) の唯一の防波堤を無効化することになる。却下。

**`styles.css` を画面ごとに分割する**: 衝突点が消える。しかし `index.html` の `data-trunk` リンクが増え（そこが新たな衝突点になる）、CSS 変数の共有をどうするかという問題も出る。「素の CSS 1 ファイル」という方針を並列実装の都合で変えるのは順序が逆と判断し、報告経由の運用を選んだ。
