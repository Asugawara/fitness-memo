# ADR-0008: 「1日1種目1ログ」を不変条件にする

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: data-model
- **関連**: [ADR-0005](0005-session-keyed-by-local-date.md), [ADR-0006](0006-at-optional-same-day-only.md), [ADR-0021](../ux/0021-copy-button-only-when-empty.md)

## 背景

`Session` は `Vec<ExerciseLog>` を持ち、`ExerciseLog` は `exercise_id` と `Vec<SetEntry>` を持つ。この構造だと同じ日に同じ `exercise_id` のログを 2 つ作れる。

これを許すと「前回の記録」の型が決まらない。

```rust
pub fn last_log_before(db: &Db, ex: ExerciseId, before: NaiveDate)
    -> Option<(NaiveDate, &ExerciseLog)>;
```

重複を許すなら戻り値は `Vec<&ExerciseLog>` になり、呼び出し側（今日タブの「前回」表示、「前回をコピー」、種目別グラフ）がそれぞれ「複数あったらどうするか」を決めることになる。合算するのか、最後だけ見るのか、判断が 3 箇所に散る。

## 決定

**「1 日 1 種目 1 ログ」を `Session` の不変条件として明文化する。**

```rust
pub struct Session {
    /// 不変条件: `exercise_id` は重複しない（core::migrate が正規化する）
    pub logs: Vec<ExerciseLog>,
    pub body_weight: Option<f32>,
    pub note: String,
}
```

守り方を 3 層に置く。

1. **UI**: 「種目を追加」シートで既にログがある種目を選んだら**新規カードを作らず既存カードへスクロールする**
2. **書き込み**: `write_log` は `logs.iter_mut().find(|l| l.exercise_id == ex)` で既存を探し、あれば `sets` を差し替える。無いときだけ push する
3. **復元**: `core::migrate()` の `dedupe_logs` が重複ログをマージする（セットを出現順に連結、`at` は `Some` の最大値、初出の順序を保つ）

## 理由

- **`last_log_before` が単一の `ExerciseLog` を返せる。** これが今日タブの「前回 3日前 60×10 60×8 55×8」表示、「前回をコピー」（[ADR-0021](../ux/0021-copy-button-only-when-empty.md)）、種目別グラフの 1 点、の全てを 1 つの関数で支えている。判断が 1 箇所に集まる。
- **`exercise_series` の 1 日 1 点が自明になる。** 重複を許すと「同じ日の 2 点」をグラフでどう置くかという問題が生まれる（X 軸は時間軸に比例配置なので同一 X に 2 点が重なる）。
- **実際のトレーニングと合っている。** 「ベンチプレスを 3 セット、他の種目を挟んで、またベンチプレスを 2 セット」は起こるが、それは**同じ種目の 5 セット**として記録するのが自然で、2 レコードに分けたい理由がない。指標（volume）も合算が正しい。
- **UI 側の解決が「既存カードへスクロール」で済む。** エラーを出す必要がなく、ユーザーは自分がやりたかったこと（その種目にセットを足す）をそのまま続けられる。禁止ではなく誘導になっている。
- **復元時に正規化するので、過去に壊れたデータが入っていても不変条件が回復する。** 別バージョンや手作業で重複が入り込んでも、次の起動でマージされる。捨てずにマージするのでデータは失われない。

## 結果（トレードオフ）

- **同じ日の同じ種目を「午前の分」「午後の分」に分けて記録できない。** 2 部練で同じ種目をやった場合、セットが 1 つのログに連結される。`at` は最大値（最後の入力時刻）だけが残るので、午前のセットの時刻情報は失われる。[ADR-0005](0005-session-keyed-by-local-date.md) の「朝と夜のトレーニングは同じ日に合流する」と同じ割り切りの延長である。
- **不変条件が型で表現されていない。** `Vec<ExerciseLog>` は重複を許す型なので、コンパイラは守ってくれない。`BTreeMap<ExerciseId, ExerciseLog>` にすれば型で守れたが、**セットの表示順（種目を追加した順）が失われる**ため採らなかった。順序は今日タブのカードの並びそのものなので捨てられない。結果として「3 層で守る」という運用に頼っている。
- **`migrate` のマージ規則を決める必要があった。** セットは出現順に連結、`at` は `Some` の最大値、`None` と `Some` が混ざったら `Some` を残す、初出の順序を保つ。「捨てる」より複雑だが、データを失わないことを優先した。5 パターンをテストしてある。
- **E2E で「同じ日に同じ種目をもう一度追加してもカードが 2 枚にならない」を検証する必要がある**（`smoke.spec.mjs` ケース 10）。UI 層の防御はテストしないと簡単に退行する。

## 検討した代替案

**`BTreeMap<ExerciseId, ExerciseLog>` にして型で守る**: 重複が構造的に不可能になり、`log_of` が O(log n) になる。しかし**種目カードの表示順が `ExerciseId` 順に固定される**ため、「今日はまず脚をやってから胸」という順序が表現できない。順序は UI にとって本質的な情報なので却下。

**重複を許して合算する**: 書き込みが単純な push だけになる。しかし `last_log_before` が複数を返すようになり、判断が呼び出し側 3 箇所に散る。合算のロジックがグラフ・前回表示・コピーでずれる余地が生まれる。却下。

**重複を許して最後のログだけを使う**: 実装は簡単だが、古いログが不可視のまま容量を食い続け、しかも「入れたセットが消えたように見える」。データを黙って無効化するのは最悪の挙動。却下。

**UI で重複を拒否してエラーを出す**: 不変条件は守れるが、ユーザーは「では何をすればいいのか」を自分で考えることになる。既存カードへスクロールすれば、そのまま目的の操作を続けられる。
