# ADR-0024: カレンダーの空日からも記録を追加できるようにする

- **状態**: 採用（導線は [ADR-0035](0035-record-tab-calendar-with-day-editor.md) で改訂）
- **日付**: 2026-08-08
- **カテゴリ**: ux
- **関連**: [ADR-0006](../data-model/0006-at-optional-same-day-only.md), [ADR-0005](../data-model/0005-session-keyed-by-local-date.md)

> **改訂。** 「記録が無い日にも必ず追加導線を出す」という判断は生きているが、その導線は
> 「この日に記録する」ボタン経由ではなく、**日セルをタップした時点で下の入力欄がその日の
> ものになる**形に変わった。ボタンとタブ遷移は不要になっている。
> → [ADR-0035](0035-record-tab-calendar-with-day-editor.md)

## 背景

要件の文言は次のとおりである。

> カレンダーに、どの日付にどの筋トレ項目をしたかを**追加**・閲覧できる

動詞が「閲覧」だけでなく「**追加**」であることが重要である。当初のカレンダー設計は「実施日にドットを打ち、タップするとその日のサマリを出す」という閲覧中心のものだった。この設計では**記録がない日をタップしたときに何も起きない**。

しかし最も典型的な利用場面はこれである。

> 昨日トレーニングしたが記録し忘れた。カレンダーで昨日を開いて入れる。

記録がない日から追加できなければ、要件の動詞が満たされない。

## 決定

**記録がない日をタップしても「記録なし」と「この日に記録する」を必ず表示する。**

```rust
// ★ 記録が無い日でも必ず「記録なし」と「この日に記録する」を出す。
<span class="muted" data-testid="cal-empty">"記録なし"</span>
// …
{move || if trained.get() { "この日を編集" } else { "この日に記録する" }}
```

記録がある日はサマリ（種目・セット・指標・体重・メモ）と「この日を編集」を出す。**どちらのボタンも今日タブをその日付で開き、過去日バナー付きモードに入る。**

```rust
pub fn open(&self, date: NaiveDate) {
    if self.selected.get_untracked() != date { self.selected.set(date); }
}
```

## 理由

- **要件の動詞を満たすための必須動線である。** 「閲覧できるが追加できない」カレンダーは要件の半分しか実装していない。しかも欠けている半分が、日常的に最も使う機能である。
- **入力画面を今日タブに一本化した。** カレンダー内に別の入力 UI を作らず、日付コンテキストの `selected` を変えて今日タブへ送る。セット入力・前回参照・「前回をコピー」（[ADR-0021](0021-copy-button-only-when-empty.md)）が過去日でもそのまま使える。入力 UI が 2 つあると、片方だけに機能が付く事故が必ず起きる。
- **「この日に記録する」と「この日を編集」でラベルを出し分ける。** 遷移先は同じだが、ユーザーの意図が違う。同じ文言だと「編集」が空日に出て違和感になる。
- **過去日モードを視覚的に区別する。** ヘッダを別スタイルにし（`.day-head.past`）、「8/1 を編集中 — 今日へ戻る」バナーを常時表示する。区別しないと**過去日を開いたまま今日の記録を入れてしまう**という、静かで気づきにくいデータ破壊が起きる。
- **`at` は書かない。** 過去日への入力は `is_today == false` なので `ExerciseLog.at` が `None` のままになる（[ADR-0006](../data-model/0006-at-optional-same-day-only.md)）。これにより「最後のトレーニングから」が「たった今」に化けない。**この動線と `at: Option<i64>` は同じ問題の表と裏である**。バックフィルを正面からサポートすると決めたからこそ、時刻の真実源を分ける必要が生じた。
- **visible 復帰で当日へ強制的に戻す。** `DateCtx::resync(force = true)` が `selected` を今日に戻す。過去日を開いたままアプリを閉じ、翌日に開いて入力してしまうのを防ぐ。

## 結果（トレードオフ）

- **過去日を開いたまま入力し続けられる。** バナーは出るが、入力自体は止めない。読まなければ間違った日に入る。強制的に止める（過去日は読み取り専用にする）と、そもそもこの機能が成立しないので、警告表示が上限である。
- **visible 復帰で当日へ戻す挙動が、意図的な過去日編集を中断する。** 昨日の記録を入れている途中に別アプリへ切り替えて戻ってくると、今日タブに戻っている。安全側に倒した結果だが、**入力途中に戻されるのは体験としては悪い**。入力済みのデータは保存されている（[ADR-0013](../storage/0013-flush-on-visibilitychange.md)）ので失われはしないが、続けるにはカレンダーからもう一度開く必要がある。
- **バックフィルした記録は時間粒度を持てない。** 「昨日 20 時にやった」という情報は入力できず、`Days` 粒度になる。存在しない情報を偽装するより正直と判断した（[ADR-0006](../data-model/0006-at-optional-same-day-only.md)）。
- **空日をタップして何も入れずに閉じた場合、セッションを作らない。** `write_log` と `ConditionRow::commit` が「ログも体重もメモも無い日は `sessions` から remove する」ので、閲覧しただけの空セッションが残らない。これがカレンダーの「実施日」判定（`logs` 非空）を汚さないための条件になっている。
- **カレンダーから今日タブへ画面が飛ぶ。** タブが自動で切り替わるので、「カレンダーを見ていたのに別の画面になった」と感じる可能性がある。過去日バナーが文脈を保つ役割を担っている。
- E2E で空日からの追加を検証する（`smoke.spec.mjs` ケース 8）。ドットの有無だけを見るテストではこの動線の退行を検出できない。

## 検討した代替案

**閲覧専用のカレンダーにする**: 実装が単純で、日付を間違える事故も起きない。しかし要件の動詞「追加」を満たさず、最頻の利用場面（昨日の記録し忘れ）が成立しない。却下。

**カレンダー内に専用の入力フォームを作る**: 画面遷移が起きないので文脈を保てる。しかしセット入力・前回参照・コピーの UI を二重に持つことになり、片方に機能が付き忘れる事故が構造的に起きる。却下。

**今日タブの日付を直接編集できるようにする（日付ピッカー）**: カレンダーを経由せず過去日に入れられる。しかし「どの日に記録があるか」を見ながら選べないので、記録し忘れた日を探す作業に向かない。カレンダー経由のほうが目的に合う。両方あってもよいが、v1 では動線を 1 本に絞った。

**過去日への入力時に `at` を「その日の 12:00」などで埋める**: 時間粒度を保てる。しかし嘘の時刻を書くことになり、「最後のトレーニングから」の計算が偽の精度を持つ。却下（[ADR-0006](../data-model/0006-at-optional-same-day-only.md)）。

**visible 復帰で当日へ戻さない**: 入力途中で中断されない。しかし過去日を開いたまま何日も放置され、次のトレーニングを過去日に記録する事故が起きる。バックアップ手段がない v1（[ADR-0014](../storage/0014-defer-export-import.md)）では、間違った日に入った記録を直すのも手作業になる。安全側を選んだ。
