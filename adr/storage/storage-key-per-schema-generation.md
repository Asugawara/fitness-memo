# 保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: storage
- **関連**: [localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md), [パース失敗時は上書きせず退避する](quarantine-on-parse-failure.md), [JSON エクスポート/インポートを v1 に入れない](defer-export-import.md), [指標を種目の属性ではなくグラフの表示設定にする](../data-model/metric-is-a-view-setting.md)

## 背景

[指標を種目の属性ではなくグラフの表示設定にする](../data-model/metric-is-a-view-setting.md) で `Exercise.kind` を削除した。アップグレード方向（旧 JSON → 新モデル）は serde が未知フィールドを無視するので通る。**問題は逆方向。**

`kind` は `#[serde(default)]` の無い必須フィールドだったので、**新版が書いた JSON を旧版は `missing field 'kind'` で拒否する**。そこで何が起きるかを追うと:

1. `core::migrate` が `Err` を返す
2. `storage::load` が raw を `.bak-<epoch>` へ退避し、プリセット入りの空 `Db` を返す（[パース失敗時は上書きせず退避する](quarantine-on-parse-failure.md)）
3. 画面には「以前のデータを復元できませんでした」と初期状態のプリセットが出る
4. ユーザーが 1 操作すると `save` が本体キーを空 `Db` で上書きする
5. 退避キーから読み戻す UI は無い（[JSON エクスポート/インポートを v1 に入れない](defer-export-import.md) でエクスポート/インポートを先送りしている）

つまり **ユーザーには全記録が消えたようにしか見えない。**

旧版が動く経路は塞げない。GitHub Pages のロールバック（[`release` を `main` から派生させ orphan 運用にしない](../deploy/release-branch-from-main.md)）、SW の更新失敗、`?sw=off` 後に古い HTTP キャッシュを掴む、のいずれでも起きうる。

## 決定

**保存キーを schema 非互換の変更のたびに切り、旧キーは読み取り専用で残す。**

```rust
/// 現行の保存キー。書き込みは常にここだけ。
const KEY: &str = "fitness-memo/v2";

/// 旧世代のキー。**読むだけで、書き戻さない。** 新しいほうから順に並べる。
const LEGACY_KEYS: &[&str] = &["fitness-memo/v1"];
```

- `load()` は現行キー → 旧世代キーの順に探し、最初に中身が入っていたものを採用する
- 旧世代から読んだときは現行キーへ写す（`Effect` の 400ms 保存を待たずに確定させる）
- **旧キーは消さない**
- 退避キーは読んだキー側に付ける（`fitness-memo/v1.bak-…`）

`model::SCHEMA` を上げるときは `storage::KEY` も切ること、を両方のコメントに書いてある。

## 理由

**旧版へ戻ったときの被害を「その世代の時点まで巻き戻る」に限定できる。** v1 が生きているので旧版は自分が読める最後の状態を表示する。全損と巻き戻りでは回復可能性が違う。

**エクスポート機能が無い今、これが唯一の退路。** [JSON エクスポート/インポートを v1 に入れない](defer-export-import.md) で先送りしている以上、ユーザー自身がバックアップを持つ手段が無い。せめてアプリ側が過去世代を捨てないようにする。

**キーを分けるコストはほぼゼロ。** 定数 1 つと `load()` のループだけで、保存経路は変わらない。

## 結果（トレードオフ）

**新版で追記した分は旧版から見えない。** ロールバック時、v2 に書いた記録は表示されない（消えてはいない）。全損よりはるかに軽いと判断した。

**localStorage を二重に消費する。** 1 セット ≈ 30 bytes・10 年で約 1.1MB の見積り（[localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md)）なので、世代が数個増えても Safari の約 5MB 上限には当たらない。世代が増え続けたら古いものを落とす判断が要る。

**「引き継ぎ」と「初期化」の区別がテストでしか担保されない。** `e2e/pwa.spec.mjs` の「旧キー v1 の記録を引き継いで v2 に書き、v1 は消さない」が、v1 のデータが見えること・v1 が残ること・プリセットで上書きされないことの 3 点を見ている。

## 検討した代替案

**消したフィールドに `#[serde(default)]` を残しておく。** 今回のケースは救えるが、それは「旧版が持っていた」定義であって後から足せない。フィールドを消す側は常に前方互換を壊せる立場にある。

**ロールバック禁止を運用ルールにする。** 人間の記憶に依存するうえ、SW の更新失敗のような自動的な巻き戻りは防げない。

**退避キーから復元する UI を作る。** 本質的な解だが、これは実質エクスポート/インポート機能で、[JSON エクスポート/インポートを v1 に入れない](defer-export-import.md) の判断を覆すことになる。キーを切るほうがはるかに小さく、しかも「ユーザーが操作する前に」効く。
