# JSON エクスポート/インポートを v1 に入れない

- **状態**: 履行済み（v1 では入れず、次リリースで実装した）
- **日付**: 2026-08-08
- **カテゴリ**: storage
- **関連**: [localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md), [パース失敗時は上書きせず退避する](quarantine-on-parse-failure.md), [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md), [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](share-sheet-over-download.md), [ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](../ux/install-guide-banner-and-sheet.md)

> **この ADR が「次リリースの必須項目」と書いた約束は果たされた。**
> 実装は [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](share-sheet-over-download.md)（書き出しの経路）と
> [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md)（先行条件だった ID の作り直し）にある。
> 本文の「検討した代替案」のうち **Web Share API に関する評価は [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](share-sheet-over-download.md) が覆した** —
> Web Share とファイルダウンロードを 1 つの選択肢として束ねて却下したのが誤りで、
> 前者は Promise で成否が返り、後者は検知できない。

## 背景

v1 のスコープを決める際、追加機能の候補を利用者に提示して選んでもらった。選ばれたのは「部位ごとの経過時間」と「体重・体調メモ」で、**JSON エクスポート/インポートと推定 1RM は選ばれなかった**。

つまりこの決定は利用者が明示的に選択したうえで外したものである。ただし外した結果として、**このアプリにはデータのバックアップ手段が一切なくなる**。データはブラウザの `localStorage` 1 キーの中だけに存在する（[localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md)）。

## 決定

**v1 では JSON エクスポート/インポートを実装しない。** ただし次の 2 点を同時に決める。

1. **エクスポート/インポートは「初回リリース後の推奨」ではなく、次リリースの必須項目に格上げする。**
2. その代わりに [パース失敗時は上書きせず退避する](quarantine-on-parse-failure.md)（パース失敗時の退避）は v1 で必ず実装する。バックアップが無い構成では、これが唯一のデータ保護機構になる。

## 理由

利用者の選択を尊重するが、リスクの実像は記録しておく必要がある。データが消える経路が 3 つある。

### 1. Safari のタブと standalone PWA は `localStorage` が別物

iOS では Safari のタブとホーム画面に追加した standalone PWA で `localStorage` / Service Worker / Cookie が**共有されない**。つまり次の最も自然な流れを踏むと記録が消えたように見える。

- まず Safari で開いて数日使い、記録を付ける
- 良さそうなのでホーム画面に追加する
- **PWA 側は空の DB で起動する**（実際は Safari 側に残っているが、本人には区別がつかない）

バックアップ機能がなければ、Safari 側のデータを PWA 側へ移す手段がない。エクスポート/インポートがあれば 2 タップで解決する問題である。

対策として、`matchMedia('(display-mode: standalone)').matches` が false のとき今日タブ最上部に控えめなバナーを出す。

> 記録を付ける前にホーム画面に追加してください。Safari のタブで付けた記録は引き継がれません

これは**注意書きであって解決策ではない**。読まなかった人は同じ穴に落ちる。

> [!NOTE]
> この注意書きは [ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](../ux/install-guide-banner-and-sheet.md) で改訂した。押せるバナーになり、図解つきの手順シートが開く。トーンは枠線を `--warn` に上げた一方、位置は記録タブの最上部から**末尾**（「種目を追加」より下）へ移した。出す条件も「Android を除く」形に変えて、iPad の desktop-class UA を取りこぼさないようにしてある。
>
> **ただしこの段落の結論は変わっていない。** 手順を書いたことで「読んだが実行できない人」は減るが、読まなかった人は同じ穴に落ちる。下に挙げた 3 つの経路はどれも閉じていない。解決策はこの ADR が必須項目に格上げしたエクスポート／インポートである。

### 2. WebKit の 7 日ルールは「対象外」ではなく "we do not expect"

iOS Safari のストレージ削除規定は、WebKit 公式ブログいわく「**サイトを操作しないまま Safari を 7 日使用**」した場合に script-writable storage を消す（カレンダー 7 日ではない）。ホーム画面に追加した後は Safari と別カウンタになるので実質的に対象外になる。

ただし Apple の文言は "We do not expect ... to have its website data deleted" であって、**保証ではない**。「期待していない」と書かれた挙動に 10 年分のトレーニング記録を預けている状態である。

### 3. 通常の操作でも失われる

「履歴とWebサイトデータを消去」、iOS の空き容量確保、機種変更。どれも普通に起こる。

## 結果（トレードオフ）

- **v1 のリリース時点で、データを失う経路が 3 つあり、いずれも回復手段がない。** これがこの ADR の状態を単なる「採用」ではなく「採用（リスク受容）」にしている理由である。
- **実運用に入る前の追加を推奨する。** 「使い始めてから足す」では、足すまでの期間に溜まった記録が守られない。順序が逆にならないよう、次リリースの必須項目として索引に明記した。
- **後から足すコストは小さい。** `src/storage.rs` を薄い 1 モジュール（4 関数・116 行）に閉じ込めたので、エクスポート/インポートは 30 行程度で足せる。JSON は既に `Db` の直列化そのままなので新しい形式を設計する必要もなく、インポート側の検証は `core::migrate()` を再利用できる。
- **`Db` の JSON がそのままエクスポート形式になる**という前提を維持するため、`Db` に UI 都合のフィールドを足さない方針が必要になる。現状 `Db` は `schema` / `next_id` / `groups` / `exercises` / `sessions` だけで、表示状態は一切持っていない。
- 推定 1RM も同時に外れたが、こちらは失うものがない（後から計算できる派生値であり、データを失うリスクとは無関係）。

## 検討した代替案

**利用者の選択を覆して v1 に入れる**: リスクは消えるが、明示的に選ばれなかった機能を勝手に入れることになる。リスクを説明したうえで判断は利用者に残し、代わりに「次リリースの必須」という形で記録に残す方を選んだ。

**エクスポートのみ入れてインポートは後回し**: バックアップは取れるが、取ったファイルから戻せないので Safari → PWA の移行が解決しない。半端な機能で「守られている」と誤認させるほうが危険。却下。

**Web Share API / ファイルダウンロードで自動バックアップ**: iOS の standalone PWA からのダウンロード挙動が安定せず、検証コストが高い。手動エクスポートより先に入れる価値はない。

**Safari のタブでの利用を検知してストレージを移行する**: そもそも別オリジンストレージなので PWA 側から Safari 側を読む手段がない。技術的に不可能。バナーによる注意喚起が現実的な上限だった。
