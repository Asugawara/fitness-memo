# ADR-0012: パース失敗時は上書きせず退避する

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: storage
- **関連**: [ADR-0011](0011-localstorage-single-key-json.md), [ADR-0014](0014-defer-export-import.md), [ADR-0038](0038-share-sheet-over-download.md)

> **追記（ADR-0038 時点）**
> - **退避データを UI から読めるようにした。** 本文が「iPhone 単体では実質的に救出不可能」
>   と自認していた穴を、種目タブの「データの書き出し / 読み込み」の一覧で塞いだ
>   （中身を見る → そのまま取り込み直す / 削除する）
> - **「壊れている」と「新しすぎる」を分けた。** 未知 schema は `.newer-<v>-<epoch>` へ
>   退避し、「新しい版に戻せば読める」と伝える。同じ文言で通知すると、無傷のデータを
>   前に利用者が諦めてしまう
> - **取り込み前の自動退避 `.pre-<epoch>` を足した。** こちらは直近 3 件に剪定する。
>   `.bak-` は「二度と手に入らないかもしれないデータ」なので機械的には消さない

## 背景

起動時に `localStorage` の `fitness-memo/v1` を読んで `Db` に復元する。JSON なので失敗しうる。

- スキーマ変更で必須フィールドが増えた
- 書き込み中に容量超過やプロセス kill で途中まで書かれた
- 手動でストレージをいじった
- 将来のバージョンが書いた形式を古いコードが読んだ

素直な実装は「パースに失敗したらプリセット入りの `Db` で始める」である。しかし [ADR-0014](0014-defer-export-import.md) でエクスポート/インポートを v1 対象外にしたため、**このアプリにはバックアップ手段が一切ない**。プリセットで上書きするとその瞬間に全損が確定し、復元経路が消える。

## 決定

**`core::migrate()` が `Err` を返したら、raw 文字列を `fitness-memo/v1.bak-<epoch ms>` に退避してからプリセット入りの `Db` にフォールバックし、起動時に一度だけ通知を出す。**

```rust
match core::migrate(&raw) {
    Ok(db) => (db, None),
    Err(_) => {
        let backup_key = format!("{KEY}.bak-{}", Local::now().timestamp_millis());
        let saved = store.set_item(&backup_key, &raw).is_ok();
        let msg = if saved {
            "以前のデータを復元できませんでした（退避済み）"
        } else {
            "以前のデータを復元できませんでした（退避にも失敗しました）"
        };
        (presets::seeded_db(), Some(msg.to_string()))
    }
}
```

**元のキー `fitness-memo/v1` は退避時点では書き換えない。** 上書きされるのは、この後ユーザーが何か操作して debounce 保存が走ったときである。

## 理由

- **これが v1 で唯一のデータ保護機構である。** バックアップも同期もエクスポートもない構成では、「壊れた JSON をプリセットで黙って上書きする」は全損の確定を意味する。退避しておけば、少なくとも JSON テキストとしては残り、後から手で救い出せる。
- **退避キーに epoch ms を含めるので、退避が複数回起きても上書きされない。** 破損したまま何度も起動されるケース（起動 → 通知 → 何もせず終了 → 再起動）で、最初の退避が 2 回目に潰されない。
- **通知を「退避済み」と「退避にも失敗しました」で書き分ける。** 容量超過などで退避自体が失敗することはありうる。同じ文言にすると、救えるデータがあるのか無いのかを利用者が判断できない。
- パース失敗の判定を `core::migrate()` に一本化した。`migrate` はターゲット非依存の純関数なので `cargo test`（ホスト）で `Err` になる条件を直接テストできる。実際に空文字列・不正 JSON・`null`・配列・必須フィールド欠落の 6 パターンをテストしている。
- `Db` を返す関数が「通知メッセージ」も一緒に返す形（`(Db, Option<String>)`）にしたのは、`storage` が UI に依存せずに済むため。`views::App` が受け取って `data-testid="restore-notice"` のバナーとして 1 度だけ出す。

## 結果（トレードオフ）

- **退避データを UI から読む手段がない。** 救出には DevTools か Safari の Web Inspector が必要で、iPhone 単体では実質的に不可能である。「全損を避ける」までしか達成しておらず、「利用者が自力で回復できる」には届いていない。エクスポート/インポートを次リリースの必須項目に格上げした理由の 1 つ（[ADR-0014](0014-defer-export-import.md)）。
- **退避データが容量を食い続ける。** 削除する仕組みを入れていないので、退避が繰り返されると `localStorage` を圧迫し、最終的に本体の保存が容量超過で失敗しうる。破損が繰り返される状況自体が異常なので v1 では放置するが、エクスポート機能と同時に「退避データの一覧と削除」を入れるのが正しい。
- **空文字列は破損として扱わない。** `load()` は `filter(|raw| !raw.trim().is_empty())` で空を弾いて「初回起動」に落とす。空文字列を退避しても意味がないため。ただしこれは「本文が消えてキーだけ残った」ケースを初回起動と区別できないということでもある。
- 通知は 1 回きりで、閉じると再表示されない。閉じた後で「何が起きたのか」を確認する画面はない。
- 破損 JSON の検証は 2 層で行う。`cargo test` で `migrate` が `Err` になること、重い側 E2E（`pwa.spec.mjs`）で実際に破損データを注入して**退避キーが生成され通知が出ること**。軽い側（pre-commit）は 60 秒制約があるので重い側へ振った。

## 検討した代替案

**プリセットで黙って上書きする**: 最も単純で、コードも 1 行減る。バックアップ手段のない v1 では全損を確定させる動作なので却下。

**破損時は起動を中断してエラー画面だけを出す**: データを絶対に触らないので最も安全。しかし「アプリが一切使えない」状態になり、しかも iPhone 単体では復旧できないので、実質的に文鎮化する。記録を続けられるほうが実用的と判断した。

**`Db` のフィールドを全て `#[serde(default)]` にして部分復元する**: パース失敗をほぼ起こさなくできる。しかし「壊れた部分が空になった `Db`」が正常データとして保存され、次の書き込みで**壊れた状態が確定してしまう**。失敗を失敗として扱ったほうが救える。なお `archived` / `at` / `body_weight` / `note` のような後付けフィールドには個別に `#[serde(default)]` を付けており、意図した後方互換だけは効くようにしている。

**退避してから元のキーを即座に削除する**: 「退避済みなのに元キーも残っている」という二重状態を避けられる。しかし削除に失敗した場合に退避と本体の両方を失う経路ができるので、消さずに放置して次の保存に任せる方を選んだ。
