# 推移タブの対象を「部位 + 種目」の 2 セレクタにする

- **状態**: 採用
- **日付**: 2026-08-25
- **カテゴリ**: ux
- **関連**: [UI の状態に `Db` の ID を置いてよい条件を決める（寛容な受け口と既定への受け皿）](../storage/db-ids-in-ui-state-behind-a-fallback.md)（最後の選択を保存する根拠）, [指標を種目の属性ではなくグラフの表示設定にする](../data-model/metric-is-a-view-setting.md), [体重を推移グラフの第2軸に常時重ねる](body-weight-second-axis-always-on.md), [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)（同じ「部位で畳んで届かせる」判断）, [グラフの座標計算を `chart_layout` に切り出してテスト可能にする](../architecture/chart-layout-as-a-testable-module.md)

## 背景

推移タブの対象セレクタは単一の `<select>` で、`<optgroup>` 3 つ（部位 / 種目 / アーカイブ済み）に候補を**平坦に**流し込んでいた。プリセットは 6 部位 28 種目あるので、使い込むほど 1 本のリストが縦に伸びる。iOS のネイティブピッカーは開いた瞬間に選択中の項目を中央に置くので、**下のほうの種目を選ぶには毎回スクロールが要る**。筋トレ中の片手操作ではこの 1 手が効く。

部位と種目は `Exercise.group_id` で親子関係を持っているのに、UI がそれを潰して 1 列にしているのが原因である。[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) が設定タブで解いたのと同じ問題が、推移タブに残っていた。

加えて、タブを往復するたび・アプリを開き直すたびに対象を選び直す必要があった（`Progress` はタブ切替のたびに作り直され、既定の「記録がある先頭の種目」に戻る）。

## 決定

**対象セレクタを「部位」と「種目」の 2 つに分け、横に並べる。最後に選んだ組を保存する。**

| 部位 | 種目 | 種目セレクタに並ぶもの | グラフ |
|---|---|---|---|
| すべて | すべて | 全部位の種目 | **出さない**。「部位か種目を選んでください」 |
| 胸 | すべて | 胸の種目だけ | 胸の全種目を日ごとに合算した 1 本 |
| 背中 | 懸垂 | 背中の種目だけ | 懸垂の系列 |

遷移の規則は 3 つ。

- **種目を選ぶと部位が自動で埋まる**（その種目の所属部位）
- **部位を切り替えたとき、選択中の種目がその部位に属していなければ種目は外れる**
- **部位を「すべて」に戻すと種目も必ず外れる**

**状態は `core::Pick { group, exercise }` の 1 シグナルで持ち、不変条件「`exercise` が `Some` なら `group` はその種目の所属部位」を型に閉じる。**

引き続き**記録がある種目だけ**を出す。アーカイブ済みも記録があれば末尾の `<optgroup>` に出す。

## 理由

- **部位は「種目リストの絞り込み」と「対象そのもの」を兼ねる。** 別々の概念にして絞り込み用のフィルタを足すと、セレクタが 3 つになって元の問題（縦に伸びる）を別の形で作り直す。部位を選んだだけのときはその部位の合算を出す、という改修前からの意味づけをそのまま使えば、UI は 2 つで足りる。
- **複数系列にはしない。** 「部位を選んだら所属種目を全部重ねて描く」も考えられるが、`Chart` は単一系列 + 体重の第 2 軸という前提で作られており（`chart_layout::Layout` の `polyline: String` / `pts: Vec<Pt>` が 1 系列ぶん）、複数化は `Chart` / `chart_layout` / 統計 / 記録テーブル / `.chart-line` の 1 色固定にまで波及する。**部位の合算 1 本という既存の意味が要件を満たしているのに、描画の土台を作り直す理由がない。**
- **不変条件を型に閉じ、シグナルを 1 本にした。** 部位と種目を別の `RwSignal` にすると、「部位を変えたら属さない種目を落とす」と「種目を選んだら部位を埋める」が `Effect` で追随し合って循環する。さらに 2 回の `set` の間に render effect が同期で走るので、**新しい部位で絞った候補に古い部位の種目が選ばれている**中間状態が DOM に出る（`<option selected>` がどれにも当たらず、ブラウザが先頭へ落とす）。`batch()` は `ImmediateEffect` 専用で render effect には効かないのでこの経路では防げない。**組で 1 つのシグナルにすれば `set` が原子的になり、循環も「2 回の set の間の中間状態」も無くなる。**

- **`<option>` の選択は `prop:selected`（IDL property）で書く。** content attribute の `selected` は、**HTML の dirtiness が立った `<option>`（＝利用者が一度でも選んだもの）では selectedness を動かさない**。leptos は候補が変わっても要素を作り直さず属性を差し替えるので、`selected=` のままだと「背中を選ぶ → すべての部位に戻す → 懸垂を選ぶ」で部位セレクタが「すべての部位」を表示したまま `pick` は `{背中, 懸垂}`、という食い違いが実際に出る（Chromium / WebKit の両方で再現）。**これはシグナルの原子性とは別の DOM 層の問題で、`Pick` の 1 本化では消えない。** 退行テストは「その option を先に一度選んでおく」手順を含めないと守りにならない（触っていない option だけを通る手順では通ってしまう）。
- **部位の「すべて」は絞り込みの解除ではなくリセットにした。** 「種目は残したまま一覧だけ全部位に広げる」ほうが操作は 1 手短いが、**部位=すべて / 種目=懸垂**という、横に並んだ 2 つの select が食い違って見える状態ができる。上の不変条件も崩れる。1 手増える代わりに、画面のどの瞬間を切り取っても 2 つの select が整合する。
- **どちらも「すべて」ならグラフを出さない。** 「全部位の合計」を描く選択肢もあったが、要件に無い集計を足すことになる。何も選ばれていないことを言葉で言うほうが、意味の分からない 1 本を描くより正直である。**この状態は種目を選べば部位が埋まる仕様のおかげで、「部位を明示的にすべてへ戻したとき」にしか現れない**（記録が 1 件も無いうちはセレクタの上の空状態のほうが出る）。
- **既定は改修前と同じ「記録がある先頭の種目」。** この画面の主眼は種目別の仕事量なので、開いた瞬間に何か 1 つの種目が出ているほうがよい。
- **候補の絞り込みと並べ替えを `core` へ移した。** `core::progress_candidates` が「記録がある種目だけを、部位の順 → 部位内の順、アーカイブ済みは末尾」で返す。画面側に置くと**既定値の規則（先頭）とセレクタの並びが 2 箇所に分かれ**、片方だけ直したときに「既定は先頭の種目」が静かにずれる。[グラフの座標計算を `chart_layout` に切り出してテスト可能にする](../architecture/chart-layout-as-a-testable-module.md) と同じく、`views/` は wasm32 gate の内側でホストの `cargo test` が届かないという事情もある。
- **横に並べた。縦に積まない。** 2 つ目の select を縦に足すと 44px + 8px ぶんグラフが下がる。**この改修の起点（下の項目が押しにくい）を、セレクタを 1 本増やして作り直すことになる。** 部位名は短く（胸 / 背中）種目名は長いので、幅は 2:3 に振ってある。
- **最後に見た組を保存する。** タブの往復とアプリの再起動の両方に耐える。`Progress` はタブ切替のたびに作り直されるので、コンテキストに載せるのではなく**マウントごとに保存値から読み直す**形にした。真実源が `localStorage` 1 箇所で済み、`App` に「`storage::load` の後で `Db` 依存の検証をやる」順序制約も作らない。読むのはマウント 1 回きりなので、打鍵ごとに走る `HistoryCtx` とは事情が違う。ID を UI 状態に置ける根拠は [UI の状態に `Db` の ID を置いてよい条件を決める](../storage/db-ids-in-ui-state-behind-a-fallback.md) にある。
- **両方「すべて」は保存から復元しない。** 案内文だけの画面を復元して見せる価値がない。既定へ倒す。

## 結果（トレードオフ）

- **タップが 1 回増える場面がある。** 別の部位の種目へ移るには「部位を選ぶ → 種目を選ぶ」の 2 手が要る（改修前は 1 つのリストの中で 1 手）。ただしその 1 手はリストの短縮とスクロールの消滅を買っている。**同じ部位の中で種目を替えるとき（実際に多い操作）は改修前と同じ 1 手**で、しかも候補が数個に減っている。
- **対象が選ばれていないときは体重の第 2 軸も出ない。** [体重を推移グラフの第2軸に常時重ねる](body-weight-second-axis-always-on.md) の「常時」は**グラフが出ている前提**の決定なので、グラフごと出さない状態が増えたことと矛盾しない。体重だけの折れ線を見せる画面ではない。
- **画面の横幅を 2 つの select で分け合う。** 長い種目名（「インクラインベンチプレス」）は幅に収まらず末尾が切れる。**`text-overflow: ellipsis` が効くのは Chromium だけで、WebKit（iOS 実機）は `…` を出さず文字の途中で切れる。** 開けば全文が読めるので選択はできるが、閉じた状態で読み切れない種目が出る。1 本の select が画面幅を独占していた改修前より読みにくい。
- **`data-testid` が変わった。** `target-select` は `group-select` / `exercise-select` になった。E2E の 4 箇所を書き換えてある。`smoke.spec.mjs` の「指標セグメント」のテストは、既定が既に 胸 なので「部位に 胸 を選ぶ」が no-op になっていた。種目を外して部位合計にする形へ直してある（機械的に置換すると何も検証しないテストになる）。
- **保存値が `Db` の ID を持つ。** 種目が消えれば宙に浮くが、マウントごとの `core::restore_pick` が受け皿になる（載っている間の `Db` の変化には候補を購読する `Effect` が備える）。詳細と条件は [UI の状態に `Db` の ID を置いてよい条件を決める](../storage/db-ids-in-ui-state-behind-a-fallback.md)。
- **所属部位が消えた種目では部位が「すべて」になる。** `migrate` / `merge_db` は宙に浮いた参照を残すので、`group_id` がどの部位も指さない種目は実在しうる。その ID を部位に入れるとどの `<option>` にも当たらず、セレクタが黙って先頭へ落ちて `pick` と食い違う。`Pick::with_exercise` が `Db` に無い部位を `None` に落とすので、表示と選択は一致する。種目自体は候補に残す（消すと過去データが推移タブから参照不能になる）。

## 検討した代替案

**単一 select のまま、種目を部位ごとの `<optgroup>` に切る**: 見出しが増えるだけで実装は最小。しかし**リストの総行数は減らない**（むしろ見出しのぶん増える）ので、「下のほうが遠い」という問題そのものは解けない。却下。

**種目の選択を `<dialog>` のピッカーシートにする**（記録タブの `add-sheet` と同型）: 部位のアコーディオンをそのまま流用でき、検索も足せる。しかし**開く → 部位を開く → 選ぶ → 閉じる**でタップが増え、筋トレ中に見るだけの画面には重い。却下。

**部位をセグメント（`.segmented`）にする**: タップ 1 回で切り替わり、今どの部位かが常に見える。しかし 6 部位 +「すべて」で 7 分割になり、1 枠 50px 前後まで潰れて 44px のタップ規約を割る。部位はユーザーが増やせるのでさらに厳しい。却下。

**部位を選んだら所属種目を全部重ねて描く（複数系列）**: 「その部位の中でどの種目が伸びているか」が 1 画面で読める。しかし `Chart` / `chart_layout` / 統計 / 記録テーブル / 系列の色まで波及し、6 種目ぶんの凡例を 320×160 の viewBox に載せる設計から始めることになる。要件は「部位を選んだら全体の推移が見える」で、合算 1 本がそれを満たしている。却下（将来やるなら独立した ADR で）。

**部位の「すべて」で種目の選択を残す**: 別部位の種目へ移るときに案内文の画面を経由しない。しかし 2 つの select が食い違って見える状態ができ、`Pick` の不変条件も崩れる。却下。

**どちらも「すべて」で全部位の合計を描く**: 空の画面が存在しなくなり、粒度が 全身 → 部位 → 種目 と連続する。しかし要件に無い集計を足すことになり、`core` に合算関数がもう 1 本増える。「全身の総ボリューム」に意味があるかはこの ADR で決められる話ではない。却下。

**部位・種目を別々の `RwSignal` にし、`Effect` で追随させる**: 素直に見える。しかし相互追随が循環し、中間状態が DOM に出る（理由節を参照）。却下。
