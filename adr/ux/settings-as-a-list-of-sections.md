# 設定タブの入口を節の一覧にし、中身は 1 階層下ろす

- **状態**: 採用
- **日付**: 2026-08-16
- **カテゴリ**: ux
- **関連**: [保存したメニューから始める（種目タブを設定タブに改める）](start-from-a-saved-routine.md) / [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) / [ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md) / [フォーカスリングを明示し、記録タブの見出しを 1 本の階層にする](focus-ring-and-heading-order.md)

## 背景

[保存したメニューから始める（種目タブを設定タブに改める）](start-from-a-saved-routine.md) で「種目タブ」を「設定タブ」に改め、トレーニングメニューの節を足した。結果、この 1 画面に 4 つの独立したものが縦積みになった。

1. データの書き出し / 読み込み（sticky のボタン）
2. ホーム画面への追加のしかた
3. トレーニングメニュー（一覧 + 追加）
4. 種目（6 部位のアコーディオン + 部位を追加 + アーカイブ済み）

**4 が縦に長い。** 6 部位が閉じていても 6 枚のカードがあり、開けば 28 種目が伸びる。そこにアーカイブ済みの節も付く。上下の関係で言うと、3 のメニューを 1 本足すために 4 を跨いでスクロールすることはないが、逆——4 の種目をいじってから 3 に戻る、その往復が毎回スクロールになる。1 と 2 も 3・4 の上にあるので、下へ行くほど「今どの節を見ているのか」が分かりにくい。

節を足すたびにこの縦積みは伸びる。**入口の設計が限界に来ていた。**

## 決定

**設定タブを押して最初に出るのは節の一覧だけにする。** 各行を押すと、その節だけの画面に入る。

```
設定
  データの書き出し / 読み込み        ›   → シートを開く
  トレーニングメニュー          2   ›   → 節へ入る
  種目                        28   ›   → 節へ入る
  ホーム画面への追加のしかた         ›   → シートを開く
```

- 節の中は左上に「‹」（設定へ戻る）を置き、**h1 はその節名**にする
- 右端に件数を出す（`トレーニングメニュー 2` / `種目 28`）
- 開いている節は `SettingsPageCtx` が持ち、**タブを往復しても戻らない**
- 「ホーム画面への追加のしかた」も同じ行の見た目にする（中身が節ではなくシートというだけ）

## 理由

### なぜアコーディオンではなく別画面か

「種目」の中身が既に部位のアコーディオンである（[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)）。トップもアコーディオンにすると**折りたたみの入れ子**になり、「今どの階層のどれを開いているか」を利用者が数えることになる。1 段目を画面の切り替えにすれば、開閉は 1 段目に 1 つだけ残る。

### なぜ件数を行に出すのか

出さないと「入ってみて初めて 0 件だと分かる」になる。メニューを作ったつもりが保存できていなかった、というときに**入らずに気づける**のが速い。0 件でも出す。

### なぜ開いている節をタブ往復で保たないといけないのか

`OpenGroupCtx` とまったく同じ理由（同 ADR）。`match tab.get()` はタブを切り替えるたびに `Settings` を作り直すので、コンポーネント内のシグナルにすると記録⇄設定の往復のたびにトップへ戻される。せっかく部位の開閉を保っているのに、その部位に辿り着く 1 タップが毎回増えては意味がない。**それでも永続化はしない**のも同じで、プロセス内の寿命に留める。

### なぜ「ホーム画面への追加のしかた」を節の中に埋めないのか

iOS で Safari のタブと standalone PWA の `localStorage` が別であることを伝える**唯一の常設導線**だから（[ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md)）。記録タブのバナーは ✕ で消せるので、消したあとはここしか残らない。2 タップ先に置くと、必要な人ほど辿り着かない。

### なぜ「データの書き出し / 読み込み」が先頭なのか

縦積みだった頃の sticky ボタンと同じ意図で、**データを失う前に見つけてもらう**必要がある。節の並びとしては最後でもよさそうだが、それは平時の理屈で、この行を探す人は平時ではない。

### 見出しの階層

トップは `<h1>設定</h1>`、節の中はその節名が `h1`。**画面に h1 は常に 1 つ**を保つ（[フォーカスリングを明示し、記録タブの見出しを 1 本の階層にする](focus-ring-and-heading-order.md)、E2E が `main h1` の個数を固定している）。節の中でトップの「設定」を h1 のまま残して節名を h2 にする案もあったが、そうすると画面の主題が見出しから読めない。

## 結果（トレードオフ）

- **種目を触るのに 1 タップ増えた。** 種目マスタをいじるのはトレ中の操作ではないので受け入れる。増えた 1 タップは、開いている節を往復で保つことで「戻ってくるとき」には返している
- **設定タブのスクリーンショットが 4 行だけになった。** 中身が写らないので README の本文が説明を持つ。撮影スクリプトの `expand`（部位を 1 つ開いてから撮る）は使い手がいなくなったので消した
- **E2E は節へ入る 1 手が増えた。** `openSettingsSection(page, which)` に畳んである。★ このヘルパは「入っていない」だけでなく**「違う節に入っている」**も扱う必要がある（節はタブ往復で戻らないので）。最初それを見落として、別の節に居るテストが素通りした
- 節を移る口（`go`）で編集シートを閉じているが、シートは modal なので開いている間は背景が inert で、この経路は今の UI からは踏めない。**保険として残す**（ページを替える口がここ 1 つなので、非 modal な導線を足した人が壊さずに済む）

## 検討した代替案

**トップもアコーディオンにして、その場で開く**: 戻る操作が要らないが、「種目」の中が既にアコーディオンなので入れ子になる（上記）。却下。

**節を別タブにする（ボトムタブを増やす）**: [保存したメニューから始める（種目タブを設定タブに改める）](start-from-a-saved-routine.md) で既に却下済み。トレ中に押すのは記録タブだけなので、タブを増やすと記録タブの標的が狭くなる。却下。

**縦積みのまま、節の見出しを sticky にする**: スクロール中も「今どの節か」は分かるようになるが、跨ぐスクロール量は 1px も減らない。却下。

**「ホーム画面への追加のしかた」を 4 つ目の行にせず、一覧の下に小さく置く**: 設定の節とヘルプが同格に見えるのを避けられるが、行が 3 つしかない画面で 1 つだけ見た目を変える理由が弱い。実際に並べてみると、4 行とも「押すと先がある」もので揃っている。却下。
