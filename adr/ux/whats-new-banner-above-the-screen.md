# 新機能のお知らせバナーを画面最上段に置く

- **状態**: 採用
- **日付**: 2026-09-09
- **カテゴリ**: ux
- **関連**: [ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md)（★ 常設導線を必須とした相手。下の一般化で決着をつける）, [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md)（フラグの置き場所。「回復手段の要否は失ったときに何が起きるかで決まる」の論法を借りる）, [シートをネイティブ `<dialog>` にし、手動の重なり順から降りる](native-dialog-for-sheets.md)（シートの器。`<Sheet>` を条件の外に置く理由）, [プリセット名は初回投入の言語で固定し、ユーザーデータとして扱う](../storage/preset-names-are-user-data-seeded-once.md)（`Names { ja, en }` の形の前例）

## 背景

リリースのたびに機能を足しているが、**利用者がそれを知る手段が今のアプリに一つも無い**。ホーム画面 PWA は再起動されないまま何日もレジュームされるので、ブラウザを再訪して変化に気付くような契機もない。黙って機能が増えていくだけで、README や GitHub を能動的に見に行かない限り誰も気付かない。

調査で分かった前提が 2 つある。

1. **このアプリに上部固定ヘッダーは無い。** タブは画面下部（`<nav class="bottom-tabs">`）にあり、各画面が自分の `<h1 class="screen-title">` を持つ。`.app` 直下の最上段には `.notice`（起動時通知）だけがある。「一番上」とはここを指す。
2. **アプリ内にバージョン情報が無い。** `env!("CARGO_PKG_VERSION")` の参照は `src/` に 0 件、git タグも無く、manifest にも書いていない。よって**リリースを識別する ID はこの機能で新規に定義する**（`Cargo.toml` の version にも SW の BUILD_ID にも紐付けない。理由は後述）。

既存の [ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md) が、構造・トーン・永続化の雛形になる。あちらは「バナー + シート」の 2 段構成で、`Db` とは別キーに既読フラグを持ち、`<button>` の入れ子を避けて「開く」と「閉じる」を兄弟ボタンに分けている。

## 決定

**画面最上段に細いバナーを出す。押すと未読のリリースをまとめて 1 枚のシートで見せる。閉じたら（✕ でもシートを閉じても）そのリリースまでを既読にし、二度と出さない。**

構成要素と、崩してはならない不変条件を以下に固定する。

- **お知らせ本文は `RELEASES` という 1 本のリスト**（`src/i18n.rs`）に持つ。**言語ごとにリストを分けない** — `ReleaseNote { id, date, ja, en }` の中でエントリごとに言語を分岐させる（`presets::Names` と同じ形）。表を JA/EN の 2 本にすると、片方への追記漏れがコンパイルを通ってしまう。
- **新しい順・`id` は厳密減少。** `id` は「**お知らせ番号**」であって、デプロイやリリースタグと 1:1 である必要はない。**各機能 PR が自分のエントリを `RELEASES` の先頭に足す**（`date` はマージ日）。同じデプロイに 2 本入っても、この機能の「複数リリースをまとめて見せる」がそのまま吸収する。
- **`release_seen: Option<i64>` を `UiState`（`fitness-memo/ui/v1`）に 1 フィールド追加する。** `Option<u32>` にしない。`lang` / `history` と同じ理由で、範囲外の値が入ると `UiState` 全体のパースが落ちて他のフィールドまで巻き添えで消える。切り出し（未読の prefix 判定）はホストの `cargo test` が届く `core::unseen_releases` に任せる。
- **`release_seen == None` は「全部既読」に倒す。** 新規利用者にも、この機能が乗る前からの利用者にも過去分は一切出さない。**基準値の書き込みは起動時に 1 回だけ**（`whatsnew::bootstrap`、`App` 本体の中）。ここを怠ると `None` が永久に残り、以後どのリリースも出なくなる。
- **`<Sheet>` は表示条件の外に常時置く。** バナーの `<div>` だけを `(!dismissed.get()).then(...)` で条件付きにし、`<Sheet>` 自体は無条件でレンダーする（`views::routine::SaveDayAsRoutine` と同じ形）。理由は次節。
- **常設の読み返し導線は意図的に作らない。** バナー以外に「新機能一覧」を開ける場所を持たない。

### なぜ `<Sheet>` を条件の外に置くのか

[ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md) の `InstallHelpSheet` は条件の**内側**（バナーが出ている間だけ存在する `<div>` の中）に置かれている。しかしそれは、あちらが「✕（今後表示しない）」と「シートを閉じる」が**別々の状態**（`dismissed` と `open`）に属していて、シートを閉じても `dismissed` は変わらない＝バナーの表示条件が動かないから成立している。

この機能は「シートを閉じる ＝ 既読が確定する ＝ バナーが消える」という設計そのものなので、同じ形にすると `on_close` の中で `dismissed` が真になった瞬間にバナーの表示条件が偽へ切り替わり、**開いている（退場アニメーション中の）`<dialog>` ごと DOM から消える**。これは [シートをネイティブ `<dialog>` にし、手動の重なり順から降りる](native-dialog-for-sheets.md) が「常時マウントする」と明記した理由（top layer に載った要素を DOM から外すと `close` イベントが飛ばず、退場の `translate` 0.22s も中断し、`on:close` 側のフォーカス復帰も走らない）と同じ不具合クラスに直接落ちる。表示条件にできるのはバナーの `<div>` だけで、シートは常に描く。閉じた `<dialog>` は UA の `display: none` が効くので、残しても見た目には何も出ない。

### 常設導線の非対称の正当化

[ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md) は「もし層 2（設定タブ冒頭の常設リンク）が無ければ ✕ は入れられない」という論法で、常設の読み返し導線を必須にしていた。この機能はその常設導線を持たない。矛盾しないための一般化はこうなる。

**常設導線の要否は、見逃したときの被害の大きさで決まる。**

- ホーム画面追加の案内は、見逃すと Safari のタブで記録した分が**不可逆に失われる**（エクスポート手段はあるが、失われたことに気付けなければ使えない）。だから層 2 が必須。
- このお知らせは、見逃しても機能そのものは UI にそのまま残り、README や GitHub にも記録がある。**知る手段を失うだけで、機能を失うわけではない。** だから常設導線は任意であり、今回は持たない。

**再検討トリガー**: お知らせの本数が増えて 1 枚のシートで読み切るのがつらくなったとき、または「見逃した」という要望が来たとき。そのときは設定タブへの常設行を検討する（下記の却下案を参照）。

## 理由

- **一番上に置くのは、確実に見えるようにするため。** [ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md) は逆に「記録の導線を邪魔しない」ために末尾へ落としたが、あちらの主目的は「気付かせる」で、この機能の主目的も同じく「気付かせる」である。ただし対象が違う：あちらは**継続して記録する人には毎回不要**な警告なので隠す価値があったが、こちらは**1 回読めば永久に消える**ので、隠して見逃されるコストのほうが高い。
- **1 タップで永久に消えるので、最上段を占めるコストの上限が小さい。** 初回に「1 目視 + 1 タップ」を払えば、以後は 1px も画面を占めない。露出が多い（＝全タブの最上段）ほど早く消えるので、結果的に「うるさい期間」は短くなる。
- **未読を「まとめて」1 枚のシートに出すのは、リリースのたびにモーダルを出すと連打で読み飛ばされるため。** 複数回分たまっていても縦スクロール 1 回で全部読める形にし、閉じる操作は 1 度だけにする。
- **既読は「開いた時」ではなく「閉じた時」に確定する。** 開いた瞬間に確定させると、シートを開いた直後にアプリを kill されたら最後まで読んでいなくても既読になる、が実際に起きるのはまだましな方で、**開いてすぐ閉じずに離脱した場合も既読になってしまう**上、常設の読み返し導線が無いのでそのお知らせは永久に読めなくなる。閉じた時点で確定させれば、読み切らずに離脱したときは「未読のまま次回も出る」という安全側に倒れる。
- **`RELEASES` を 1 本のリストにするのは、構造体リテラルの強制力を保つため。** `src/i18n.rs` の設計原則（フィールドを 1 つでも書き忘れるとコンパイルが通らない）を守るには、JA/EN を同じエントリの中に持たせる必要がある。2 本のスライスに分けると「日本語だけ足して英語を足し忘れる」がコンパイルを素通りする。
- **`id` をデプロイや `Cargo.toml` の version と紐付けないのは、意味の異なる数字を UI 側の既読の単位に流用しないため。** `env!("CARGO_PKG_VERSION")` は `src/` から 1 度も参照されておらず、package のバージョニングと UI の既読管理は今まで無関係だった。無理に結び付けると、typo 修正だけの版とお知らせ入りの版を同じ次元で数えることになり、混乱の元になる。**「触ると Service Worker の BUILD_ID が変わるから」は理由にしない** —— `scripts/stamp-sw.sh` は wasm を含む配信物一式をハッシュするので、`RELEASES` を触ろうと触るまいと BUILD_ID はどのリリースでも変わる。ここは不変条件の独立性の話であって、ビルドの副作用の話ではない。
- **常設の読み返し導線を意図的に作らないのは、上の非対称の正当化のとおり被害が軽いため。** 導線を増やすと設定タブの行がまた 1 つ増える。今のところ増やす理由が無い。

## 結果（トレードオフ）

- **全タブの最上段を 1 行占める。** 記録・推移・設定のどのタブを開いても、既読になるまで必ず視界に入る。コストの上限は「初回の 1 目視 + 1 タップ」で、露出が多いほど早く消えるという理屈で全タブに出す判断をしたが、**「毎回目に入るのがそもそも煩わしい」という感想は用意していない**。
- **誤タップで閉じると二度と読めない。** 常設の読み返し導線が無いので、✕ を触ってしまった場合の救済策は無い（README / GitHub には記録が残るが、アプリ内には残らない）。
- **複数リリースを途中まで読んで閉じても、全部まとめて既読になる。** 1 枚の縦スクロールシートで「閉じる」という単一の明示操作しか持たないため、部分既読という状態を作れない。読み切らずに閉じるのは利用者の選択として許容する。
- **`fitness-memo/ui/v1` が失われたときの挙動が、このフィールドだけ他の 4 つと逆向きになる。** [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md) は「このキーは失われても害がない。読めなければ案内がもう一度出るだけ」と書いているが、`release_seen` はその逆で、**失われると基準値が起動時に書き直されて、そのとき未読だったお知らせが出なくなる**方向に働く（次のリリース以降は普通に出る）。データが失われるわけではないので致命的ではないが、「読めなければ案内が復活する」という同ファイルの他のフィールドの直感には反する。
- **起動時の書き込みは、型が壊れた `fitness-memo/ui/v1` を `Default` で上書きして確定させる。** これは [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md) が定めた「読めなければ `Default` で始める」の範囲内の挙動だが、**上書きが起きる契機がこれまでの「利用者がボタンを押したとき」から「アプリを開いたとき」に変わった**。他の 4 フィールドは明示的なクリックがない限り書き直されないが、`release_seen` は起動するだけで書かれうる。

## 検討した代替案

**`scripts/release.sh` に「`RELEASES[0].date` が `origin/release` より新しくなければ警告する」チェックを足す**: 足し忘れをリリース手順そのもので検知できる。しかし typo 修正だけの release でも誤検知し、[README を英語で正とし、日本語版を `README.ja.md` に置く](../process/readme-in-english-with-japanese-mirror.md) が「片側だけが正しい変更で誤検知するチェックは `SKIP_HOOKS=1` の常用を招く」と却下した論法がそのまま当てはまる。却下。

**シートを開いた瞬間に既読にする**: 実装が 1 行減る。しかし「結果（トレードオフ）」で述べたとおり、読む前に離脱すると常設の読み返し導線が無いため永久に読めなくなる。却下。

**`release_seen` を `Option<u32>` にする**: `id: u32` と型が揃って自然に見える。しかし `UiState` の他のフィールド（`lang` / `history` / `progress_group` 等）がすべて「範囲の広い型で寛容に受けて、丸めや検証をホストの `cargo test` が届く `core` 側に任せる」規則を敷いており、`u32` にすると `9999999999` のような手で壊れた値の deserialize が失敗し、**`UiState` 全体が `Default` に落ちて `lang` まで巻き添えで消える**。既存の規則に反するので却下。

**`release_seen` だけ寛容なデシリアライザ（`#[serde(deserialize_with = ...)]`）を書く**: 型を `u32` のまま保てる。しかし `Option<i64>` で受けて `core` 側で丸める既存の 3 フィールド（`history` / `progress_group` / `progress_exercise`）と扱いが割れ、次にフィールドを足す人がどちらの規則に従えばよいか迷う。却下。

**`src/releases.rs` を新設してお知らせ本文を置く**: `i18n.rs` が肥大化しない。しかしお知らせ本文は利用者に見える文言そのものであり、「表示用の日本語リテラルは `i18n.rs` の外に置かない」規約（`presets::Names` は文言ではなくデータという例外）に当てはまらない。新設すると規約の検証コマンド（`rg '"[^"]*[ぁ-んァ-ヶ一-龠]' src/ -g '!src/i18n.rs'`）がこのファイルを見逃す穴になる。却下。

**リリース識別子に `Cargo.toml` の version や Service Worker の `BUILD_ID` を使う**: 新しい概念を増やさずに済む。しかし前者は `src/` から一度も参照されておらず UI の既読管理に流用する必然性が無く、後者は「決定」節で述べたとおり配信物全体のハッシュなので typo 修正でも変わる。**「触ると変わる」ことと「お知らせの単位である」ことは無関係**であり、意味の違う数字を借りると将来の読み手を混乱させる。却下。

**記録タブだけに限定して出す**: 実装コストは変わらないが表示回数が減る。しかし推移・設定タブしか開かない使い方（体重だけ記録している、等）をする利用者にお知らせが届かなくなる。全タブに出すコストは「初回の 1 目視 + 1 タップ」しかないので、絞る理由が無い。却下。

**N 日で自動的に消す（読まなくても一定期間で消滅）**: 誤タップの被害を減らせる。しかしお知らせは「読んだかどうか」が本質であって「一定期間表示したかどうか」ではない。自動消滅は「読まずに消えた」という一番防ぎたい事態を自ら起こす。却下。

**`.notice` に相乗りさせる**: 実装が最小で済む。しかし `.notice` は `storage::load` の復元通知専用の枠で、`App` が `Option<String>` 1 本で駆動しており、破損復元の通知とお知らせを同時に出せない。トーンも「緊急の通知」と「気付かせるだけのお知らせ」で異なる。[ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする](install-guide-banner-and-sheet.md) が同じ理由で `.notice` の再利用を却下しているのと同じ論法で却下。

**設定タブに常設の読み返し行を足す**: 見逃した後の救済になる。しかし「常設導線の非対称の正当化」で述べたとおり、見逃しの被害が「知る手段を失うだけ」に留まるこの機能では、行を 1 つ増やすコストに見合わない。**再検討トリガー**（お知らせの本数が増えた／要望が来た）に達したら改めて検討する。却下（今回は）。
