# ADR-0044: 体重を推移グラフの第2軸に常時重ねる

- **状態**: 採用
- **日付**: 2026-08-09
- **カテゴリ**: ux
- **関連**: [ADR-0004](../architecture/0004-no-chart-library-hand-rolled-svg.md), [ADR-0033](../data-model/0033-metric-is-a-view-setting.md), [ADR-0045](../architecture/0045-chart-layout-in-core.md)

## 背景

体重は `Session.body_weight` として日ごとに記録できるが、**どこにも描かれていなかった**。
`core.rs` に体重の系列関数は無く、推移タブの `Target` も `Group` / `Exercise` の 2 択だった。

そのため「ベンチの重量は伸びたが、体重も一緒に増えていたのか」がアプリの中で判断できない。
増量期なのか純粋に強くなったのかが読めず、[ADR-0033](../data-model/0033-metric-is-a-view-setting.md)
で「どの軸で見るか」を閲覧時に選べるようにした指標の解釈が、片手落ちのままだった。

要望は **「毎日登録する体重は、常にグラフに表示してほしい。メインの指標の第2軸を作るようなイメージで、
また点線でそんなに目立たないように、体重の遷移が常に一緒に見られる必要がある」**。

## 決定

**指標の折れ線に、体重を第2軸（右）の破線として常時重ねる。表示トグルは作らない。**

```rust
// core.rs — データの関数
pub fn body_weight_series(db, from, to) -> Vec<(NaiveDate, f64)>
pub fn aggregate_weekly_avg(series) -> Vec<(NaiveDate, f64)>   // 合計ではなく平均
pub fn weight_band(lo, hi) -> (f64, f64)                       // 0 起点にしない帯
```

5 つの規則を置いた。

- **右軸は 0 起点にせず、データにぴったり合わせる**（0.5kg 刻みで丸め、最小 1.0kg 幅）
- **横のグリッド線は 3 本のまま両軸で共用**する。左ラベルが指標、右ラベルが体重を指すだけ
- **X のドメインは両系列の合併**にする
- **「全期間」の体重は合計ではなく週平均**で集約する
- **描画点が 45 を超えたら描画だけ週平均に落とす**。読み取り欄は実測値のまま

## 理由

**トグルを作らないのは要件が「常に」だから。** 出したり消したりできると、消した状態が既定に
なった人には機能が無いのと同じになる。第2軸は指標の解釈を助ける文脈であって、単独で見る
情報ではないので、対象や指標のセレクタと並べる理由もない。

**0 起点にしないのは、そうすると体重が読めないから。** 主軸と同じ `0〜max×1.1` にすると
60〜65kg が画面上端に貼り付いた平線になり、遷移が一切見えない。第2軸を作る意味が消える。

**帯を「データにぴったり」にしたのは利用者の選択。** 最小幅 2kg のような緩い軸も検討したが、
「小さい変化も見えるほうがいい」という判断だった。副作用として日々の水分変動（±0.4kg 程度）が
拡大表示される。これは下の「結果」に書いた。

**目盛りの区間数を偶数に強制しているのは、中央ラベルを 0.5 の倍数に乗せるため。**
そうしないとグリッド 3 本の真ん中が `62.45` のような値になり、軸として読めない。

**平坦な系列を帯の中央へ寄せるのは、下端に貼り付くと主軸の 0 グリッド線と重なるから。**
毎日同じ体重を入れている人のグラフで、体重の線が軸そのものに化けて見える。

**X を合併ドメインにするのは、体重が毎日でトレーニングが週数回だから。**
主系列の両端で軸を切ると、最後にトレした日から今日までの計量が軸の外へ落ちる。
毎日計量する人には**常に**起きるので、「今日の体重が見えない」が既定の状態になってしまう。
合併にすると右端が実質「今日」に固定され、最後にトレした日から今日までが右の空白になる。
これは [ADR-0004](../architecture/0004-no-chart-library-hand-rolled-svg.md) の
「X を時間軸に比例配置して休んだ期間を空白として見せる」の延長で、方針として一貫している。

**週集約を平均にしたのは、合計だと体重が 400kg になるから。** 既存の `aggregate_weekly` は
指標の合計用で、体重をそこに通すと数値が意味を失う。一方で**週キーは指標側と一致させる**
必要がある（ズレると 2 本の線が別の日付軸に並ぶ）ので、`week_start` は共有し集約の仕方だけ変えた。

**密なときに描画だけ週平均へ落とすのは、破線が潰れるから。**
1Y × 毎日計量 = 365 点をプロット幅 ~250px に描くと 0.68px/点。日々の揺れが帯いっぱいに
振れるので、破線（周期 10px）が完全に潰れて**灰色の帯**になる。「目立たないように」の真逆である。
一方で読み取り欄に週平均を出すと「記録した数字と違う」ので、**線だけ滑らかにして
読み取り欄は実測のまま**にした。カーソルの丸も、線の上に実際に点がある日にしか打たない
（存在しない観測値を点として捏造しない）。

**「目立たなさ」は色では作れない。** 当初 `--muted` を使えば控えめになると考えていたが、
実測すると `--accent` とコントラスト比がほぼ同じだった。

| | ライト（対 `--surface`） | ダーク（対 `--surface`） |
|---|---|---|
| `--muted` | 4.83:1 | 6.75:1 |
| `--accent` | 4.88:1 | 6.93:1 |

従属性は **`stroke-width`（2.0 → 1.25）・破線・ドットを描かないこと・メイン線の背面に置くこと**で
作っている。`opacity` は使わない（非テキストの 3:1 基準を割るうえ、ダークモードで消える）。
破線パターンは `.chart-cursor` の `3 3` と変えて `6 4` にした（同じ `--muted` なので、
周期まで同じだと縦のカーソル線と読み違える）。

## 結果（トレードオフ）

**日々の水分変動が拡大表示される。** 帯をデータにぴったり合わせた直接の帰結で、
1M（日次のまま描く期間）では体重の線が細かくジグザグする。破線と細さで従属はしているが、
「静かな線」ではない。3M 以降は週平均に落ちるので滑らかになる。

**2 本の線の傾きは比較できない。** 第2軸を持つグラフに本質的な誤読リスクで、
指標が上がったのと体重が上がったのが同じ角度に見えても、意味のある比較にはならない。
体重を従属的に描いている（細い破線・ドット無し・背面）ことで「同格の 2 系列ではない」と
示しているが、目盛りを読まずに角度だけ見れば誤読は起きる。

**メイン指標の線が画面の全幅を使わなくなる。** 合併ドメインの帰結。最後にトレした日から
今日までが右の空白になるので、「何日空けたか」は読めるようになるが、指標の線は短く見える。

**タップは「トレした日」にしか吸着しない。** ヒット帯をメイン系列の日付から作っているため。
体重（毎日）から作ると 3M で 1 本 3px になり、[ADR-0004](../architecture/0004-no-chart-library-hand-rolled-svg.md)
の 44px 規約に反する。毎日計量していればトレした日には必ず体重があるので実害は小さいが、
「休養日の体重を読む」はできない。

**メイン指標が空の期間は体重だけのグラフになる。** 「常に一緒に見られる」を厳密に守った結果。
左軸ラベルは出さない（`y_max` が 1.0 に化けて `1 / 0.5 / 0` が並び、体重の目盛りだと誤読されるため）。
この状態では帯を体重から作るので、ヒット帯が上の 44px 規約を満たさない。劣化状態として許容した。

**体重の入力に上限が無いことが露呈した。** `day.rs` の commit も `core::migrate` も
`is_finite() && > 0.0` しか見ていないので、`f32` の上限（3.4e38）まで素通りする。
1 点でも混じると帯が f64 の丸めで潰れ、`(v-lo)/(hi-lo)` が NaN になり、
**折れ線が丸ごと描かれなくなる**（SVG のパースエラーで、例外も出ない）。
グラフ側は `body_weight_series` の範囲外し（`0 < w <= 999.5`）と `weight_band` のガードで
自衛したが、**「70 のつもりで 700」というもっともらしいタイポは範囲内なので通り、グラフを潰す**。
入力側で塞ぐのは別課題として残っている。

## 検討した代替案

**体重を `Metric` の 4 つ目の選択肢にする。** 既存のセグメントに 1 つ足すだけで実装は最小。
しかし `log_value(m, l)` は `ExerciseLog` を取るのに体重は `Session` にあるので式が合わず、
何より**切り替えないと見えない**ので「常に一緒に見られる」を満たさない。却下。

**体重を `Target` の 3 つ目にする。** 単独のグラフとしては素直だが、これも切り替え式なので
「ベンチが伸びたとき体重も増えていたか」を 1 画面で見られない。却下。

**表示トグルを付ける。** 邪魔なときに消せる。しかし要件が「常に」であり、消した状態が既定に
なると機能が無いのと変わらない。状態を永続化するかの判断も増える。却下。

**帯に最低幅（2kg / 5kg）を設ける。** 日々の変動が誇張されず「静かな線」になる。
しかし小さな変化が読めなくなる。利用者が「データにぴったり」を選んだので採らなかった。

**常に 7 日移動平均で描く。** 体重のトレンド線としては最も素直で、期間によらず滑らか。
しかし短い期間（1M）でも実測から離れた線になり、読み取り欄の数字と線の位置が常にズレる。
点数が多いときだけ落とす方式なら、1M は実測そのままで見られる。却下。

**X を主系列の範囲のままにし、体重をそこへ切り詰める。** 既存の見た目が 1px も動かない。
しかし毎日計量する人には直近の体重が常に切れるので、要件を満たさない。却下。
