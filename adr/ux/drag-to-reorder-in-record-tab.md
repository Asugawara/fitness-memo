# 記録タブのカードとセットをドラッグで並び替え、`Vec` の並びをそのまま保存する

- **状態**: 採用
- **日付**: 2026-08-13
- **カテゴリ**: ux
- **関連**: [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md), [「1日1種目1ログ」を不変条件にする](../data-model/one-log-per-exercise-per-day.md), [`at` を `Option<i64>` にし当日入力時のみ埋める](../data-model/at-optional-same-day-only.md), [種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](../data-model/notes-on-logs-and-sets.md), [セット削除は確認を挟まない（カード削除の確認は残す）](set-delete-without-confirmation.md), [破壊的操作は静止時に警告色を持たない（カード削除をフッタへ畳む）](destructive-affordance-quiet-at-rest.md), [localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md), [グラフの座標計算を `chart_layout` に切り出してテスト可能にする](../architecture/chart-layout-as-a-testable-module.md)

## 背景

記録タブでは、その日の種目カードの並びは `Session::logs` への push 順、セット行の並びは
`ExerciseLog::sets` の `Vec` 順で決まり、**一度入れた順番を後から変える手段が無かった**。

トレ中に足す順は実際にやる順と食い違う。先にやる予定だった種目を後から思い出して足す、
セットを打ち間違えて消して足し直すと末尾へ落ちる。直す手段は「消して入れ直す」しかなく、
消せば入力した数字ごと消える。**記録タブは上から順に消化する画面**なので、順が違えば
毎セット目で探すことになる。

### 却下済みの ADR との切り分け

[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)
は「ドラッグ&ドロップで並び替える」を明示的に却下している。**却下の対象は種目タブの
種目マスタ（`Exercise.order` / `Group.order`）で、本 ADR は記録タブ（その日の `logs` /
`sets` の並び）である。** 却下理由の 2 つを個別に処理する。

- **「iOS のタッチ操作で確実に動かすのは実装も E2E も難しい」— 今も生きている。**
  本 ADR はこれを「掴む場所を絞る」「長押しで誤爆を塞ぐ」「幾何を純モジュールに出して
  ホストでテストする」「E2E は永続化に集中する」の 4 つで受ける。下記の各節がその中身。
- **「そもそも並び替えの実用価値が低い」— 記録タブでは逆転する。** あちらは自分で
  「1 部位 4〜5 種目でセクション内スクロールが発生しないため実効影響は小さい」と書いて
  いるとおり、**マスタ一覧の見せ方**の話だった。記録タブの並びは**その日にどの順で
  やるかという計画**そのもので、上から順に消化する画面の読み順を決めている。

**種目マスタの並び替えは今も持たない。** あちらの決定は 1 文字も覆っていない。

## 決定

**記録タブに限り、種目カード（`.card-head`）とセット行（`.set-no`）を掴んでドラッグで
並び替えられるようにし、その並びは新しいフィールドを一切足さず `Session::logs` と
`ExerciseLog::sets` の `Vec` の並びそのものとして保存する。**

不変条件は 6 本。

- **ドラッグ中は signal の `Vec` を入れ替えない。** `transform` だけで見せて、指を離した
  1 回で確定する
- **セットの並びは既存の `commit()` が書く。`log.sets` を添字で並べ替える経路は作らない**
  （`commit` は `parse_reps` が `None` の行を落とすので、`rows` と `log.sets` は添字が
  対応しない）
- **カードの並びは `core::reorder_logs(db, date, order)` が書く。`sets` / `note` / `at` には
  触らない**
- `reorder_logs` は **`order` に無いログを落とさず末尾へ相対順のまま残し**、ログの無い ID は
  飛ばす
- **`commit()` からも毎回 `reorder_logs` を呼ぶ。** これで「`logs` の順 == `cards` の順」が
  単一の書き込み口で保たれる
- **`core::dedupe_logs` の「初出順を保つ」はこの機能の前提**であり、変えると次回起動で
  利用者の並びが黙って戻る

`SCHEMA` は据え置き。フィールドを 1 つも足さず、`Vec` の並びは既に保存形式に含まれている。

```
┌─────────────────────────────┐
│ ベンチプレス          胸    │ ← 見出し行を 250ms 押してからカードを動かす
│ 前回 3日前  60×10  60×8     │
│  1  [ 60 ]kg × [ 10 ]   ✕  │
│  2  [ 60 ]kg × [  8 ]   ✕  │ ← 番号を掴んで行を動かす（待ち時間なし）
└─────────────────────────────┘
```

## 理由

### 掴む場所を既存要素にする（44px のボタンを 1 つも足さない）

セット行は左端の番号、カードは見出し行。どちらも既にそこにある。
[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)
が並び替えを消した最大の理由は「44px のボタンが一覧の役目を潰す」ことで、`.set-row` は
既に 番号 / 重量 / kg / × / 回数 / ✕ / メモ の 7 要素が 393px に入っている。グリップを
足すと 1 日あたり最大 40 個（8 カード × 5 行）増える。

**番号をハンドルにしたのは、番号がそのまま順番だから。** 掴んで動かす対象と、それが
表しているものが一致する。1.4em @12px = 16.8px は細いので、`::before` の絶対配置で
**レイアウトを 1px も動かさずに**ヒット領域だけ約 29 × 46px へ広げてある。

見出し行を `<button>` にはできない。`<button>` の content model は phrasing content なので
`<h3>` を入れると不正な HTML で、`role="button"` にすると children presentational で
見出しが a11y ツリーから消え、[フォーカスリングを明示し、記録タブの見出しを 1 本の階層にする](focus-ring-and-heading-order.md)
が守っている階層（月 h1 → 選択日 h2 → 種目 h3）が壊れる。

### `.card-head` だけ長押しにする（今回いちばん重い判断）

`touch-action: none` を当てた要素からは**ページのスクロールを始められなくなる**。
`.set-no` は約 29px 幅なのでそこを起点に縦フリックが始まる確率は低く、待たせるほうが
損になる（トレ中はセットの並び替えのほうが頻度が高い）。

一方 `.card-head` は**全幅 × 約 24px の帯**が 5〜8 枚ぶん並ぶ。ここを即時開始にすると:

- スクロールのつもりのフリック（100〜300px）が閾値（隣のカードの半分 ≈ 87px）を確実に超える
- **画面が動かないまま種目の順だけが黙って入れ替わる**。取り消し導線は無い

250ms + 移動許容 10px なら、フリックは**何も起きない**で終わる。「たまにスクロールが
効かない帯がある」ほうが「気づかないうちに種目の順が変わる」より明確にましである。
掴めたことは持ち上げ（枠が `--accent` になる）で必ず見せる。**指が止まっていても
掴めたと分かる**必要があるので、これは長押しの必須条件。

### ドラッグ中に `Vec` を入れ替えない

`translateY(dy)` の基準は「掴んだ瞬間のレイアウト位置」なので、`<For>` が DOM を move した
瞬間に基準が 1 スロット飛ぶ。飛んだ先で測り直すと逆向きの閾値を割るので戻る、を繰り返し、
**高さがバラバラだと進み幅と戻り幅が一致せず振動が収束しない**。

加えて tachys の keyed diff（`apply_diff`）は move 対象を `insertBefore` で入れ直すので
pointer capture を落としうるうえ、A↔B の入れ替えで**どちらが move されるかは LIS ベースの
diff が決めるのでこちらから指定できない**。「ブラウザ実装に依存する」という状態そのものが
却下理由として十分である。

transform だけで見せる形なら、測るのは掴んだ 1 回だけで済む（ドラッグ中に
`getBoundingClientRect` を呼ばない ＝ レイアウトを強制しない）。

### 閾値は「掴んだ箱の進行方向の辺 vs 相手の箱の中心」

中心 vs 中心にすると閾値が `(h_from + h_k) / 2` になり**掴んだ側の高さに依存する**ので、
380px のカードを動かすのに常に 200px 超の指移動が要る。辺 vs 中心なら閾値は
`h_k / 2 + 隙間` ＝ **相手の高さだけで決まり**、「相手が半分隠れたら入れ替わる」と目で
読める。箱が重ならず文書順に並ぶなら閾値は単調増加なので、**ヒステリシスが要らない**。

### タップで並びが変わらないことを、しきい値ではなく構造で保証する

指を離した先が元の位置なら `rows` / `cards` にも `db` にも触らない。触ると打鍵して
いないのに `storage` の 400ms debounce が再武装される。`drop_index` は `dy == 0` のとき
定義上 `from` を返し、`to != from` になる最小の |dy| はセット行で 25px 以上・カードで
87px 以上あるので、指ブレ（1〜3px）とは 1 桁違う。

### 幾何を `src/reorder.rs` に出す

[グラフの座標計算を `chart_layout` に切り出してテスト可能にする](../architecture/chart-layout-as-a-testable-module.md)
が立てた規則の適用である。`core` が `Db` を、`chart_layout` がグラフの寸法を、`reorder` が
並びの寸法を知る。`views` は wasm32 の cfg gate の内側にあってホストの `cargo test` が
一度も触れないので、`remove` してから `insert` する式の添字ずれのような事故が検出されない
（`core::short_elapsed` の doc にある `ms / 86_400_000` がその前例）。

座標は **document 基準**（`rect.top + scrollY`）にした。iOS は慣性スクロール中の
`pointerdown` で `pointercancel` を送らないことがあり、ドラッグ中にページが動くと
viewport 基準のスナップショットは陳腐化する。document 基準なら毎 `pointermove` で
`scrollY` を足し直すだけで整合が保てる。画面端の自動スクロールが成立するのも同じ理由。

### ドラッグ中の番号は「見えている位置」を描く

`Vec` を入れ替えないので模型の添字と見えている位置がずれる。そのまま描くと
**2 番目に見えている行に「1」と書いてある**状態になり、番号をハンドルにした前提
（番号 ＝ 順番）が指を離すまで嘘になる。`reorder::visual_index` を通すと、掴んだ番号が
中点を越えた瞬間に変わり、落ちる先が先に読める。

### 押しのけのトランジション

`public/styles.css` には既に `.sheet` の出入り（0.22s）と `prefers-reduced-motion` の
ガードがあるので、これが初の例外ではない（`.grp-toggle` に「この CSS には transition が
1 つも無い」という古いコメントが残っていたので併せて直した）。

**transition は「ドラッグ中の親」にだけ生やす。** 無条件に `.card` / `.set-row` へ置くと、
指を離した瞬間に「`<For>` の DOM move」と「transform の除去」が同時に起きて、要素が
1 スロット飛んでから 120ms かけて滑って戻る（FLIP のジャンプ）。親の `data-dragging` が
同じ反応フラッシュで外れれば、変化後のスタイルに `transition-property` が無く、遷移が
そもそも開始されない。

**掴んでいる要素は `:not([data-drag])` で除外する。** `.set-row[data-drag="lift"] {
transition: none }` を別に書く形では詰む — 親側のセレクタ（詳細度 0,3,0）のほうが強くて
打ち消せず、**掴んだ要素まで 120ms 遅れて指について来る**。実装中に実際に踏み、E2E で
「掴んだ行が押しのけた行の位置に居る」を見て気づいた。

`prefers-reduced-motion` では `0s` にする。`.sheet` の 0.1s に揃えないのは、あちらが
上下動をやめても黒幕のフェードが残るのに対し、こちらは**動きそのものが全部**だから。

## 結果（トレードオフ）

- **`.set-no` と `.card-head` からは画面のスクロールを始められなくなった**
  （`touch-action: none`）。`.card-head` を長押しにしたのは、その代償を「何も起きない」に
  落とすため。`.set-no` は細いので即時のままにした
- **セットの並び替えは `at` を今に更新する。** `commit()` を通す設計の直接の帰結。
  `is_today` のガードがあるので**同じ暦日を出ない**ため
  [`at` を `Option<i64>` にし当日入力時のみ埋める](../data-model/at-optional-same-day-only.md) が守った
  不変条件は無傷で、現在の UI では `Elapsed.ms` が `days == 0` でしか読まれず
  `before_today` が今日のセッションを外すので**観測できない**。
  **将来「今日 ＝ 時刻粒度」を出す画面を足したら、`commit` に「並び替えのみか」を渡す
  必要がある**（条件付きの負債）
- **カードの並び替えは `at` を触らない。** 非対称なのは、カードのドラッグが**触っていない
  他種目のログ**を巻き込むから。全ログの `at` を今に揃えるのは「並べ替えただけの種目を
  22 時に実施した」という捏造で、`copy_day` が `ExerciseLog` を clone せず `at` を明示的に
  渡しているのと同じ理由で許されない
- **`commit()` が 1 打鍵ごとに `reorder_logs` を呼ぶ。** `write_log` の新規枝は `logs.push`
  なので、並び替えたあと「まだログの無いカード」に 1 文字目を打つと**そのログだけ末尾に
  生える**。これを塞ぐには書き込みのたびに揃え直すしかない。コストは `Vec<ExerciseLog>` の
  move が最大 10 回で、`write_log` が既に `sets` を丸ごと差し替えているのに比べて誤差
- **`merge_db` に多重集合のガードを足した。** `same_sets` は `zip` で位置を比べるので、
  セットを並べ替えただけの同じ記録が食い違い扱いになり、`log_rank` の第 3 要素が位置依存な
  ぶん勝ち負けが実質任意に決まって、**並びが黙って戻るうえ負けた側のセットメモが消える**。
  **この機能が新しく開けた穴**なので同じ変更で塞いだ。中身が同じで並びだけ違うときは
  取り込み先を残し、`Conflict` も出さず、位置が対応しないのでセットメモの補完もしない
- **`core::dedupe_logs` の「初出順を保つ」が仕様になった。** 読み込みのたびに通る場所なので、
  ここを並べ替える実装に変えると次回起動で利用者の並びが黙って戻る。doc にその旨を書き、
  書き出し → 読み込みの round-trip テストで釘付けにした
- **保存されない行を動かしても何も起きない。** 空行・メモだけの行は `parse_reps` が `None` を
  返して `commit` に載らない（既存仕様で、行内の `note-orphan` がその理由を出している）。
  動かしても JSON は 1 バイトも変わらず、リロードでその行自体が消える。**E2E で「空行を
  動かして順序が残る」を assert してはいけない**
- **単一ポインタでのドラッグ以外の経路は持たない。** キーボードの `Alt` + ↑↓ は既に
  フォーカスできる要素（セットの入力欄 / カード）に載せてあり WCAG 2.1.1 は満たすが、
  **2.5.7（ドラッグ操作）が求める「ドラッグを伴わない単一ポインタの代替」には
  なっていない**。長押しメニューで代替を足すことはできるが（下記の却下案）、1 人用の
  個人アプリという前提でここは開けたままにする
- **キーボード経路の発見可能性が無い。** `help.rs` はホーム画面追加の案内専用で一般的な
  ヘルプ面が無く、`aria-keyshortcuts` を入力欄に付けると打鍵のたびに読み上げが伸びる
  （トレ中のホットパス）。E2E の安定した経路としての価値のほうが大きいと判断した
- **`data-drag` / `data-dragging` が CSS のフックであり E2E の待機条件でもある。**
  `aria-expanded` を回転のフックにした
  [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)
  と同じで、属性が黙って落ちれば見た目とテストの両方が同時に壊れて気づける
- **タッチ操作そのものは E2E で検証できていない。** `page.mouse` は Chromium / WebKit とも
  本物の `PointerEvent` を出すので実装は通るが、`touch-action` の効き・長押しの
  コールアウト・慣性スクロール・ソフトキーボードは Playwright では再現しない。
  合成イベント（`dispatchEvent`）では `setPointerCapture` が `NotFoundError` になり、
  実装が意図どおり「掴まない」ので検証にならない。**ここは実機確認に依存している**
- **web-sys の feature が 2 つ増えた**（`PointerEvent` / `KeyboardEvent`）。どちらも tachys が
  自分で有効化しているので宣言しなくてもコンパイルは通るが、その「偶然」に寄りかからない
  という `Cargo.toml` 冒頭の方針に従った。`setPointerCapture` / `scrollBy` /
  `getBoundingClientRect` は `Element` / `Window` / `DomRect` の側にあるので増えていない

## 検討した代替案

**`ExerciseLog.order: u32` / `SetEntry.order: u32` を足す**: `#[serde(default)]` にすれば
`SCHEMA` を上げずに済む。しかし真実源が「`Vec` の添字」と「`order`」の 2 つになり、
`write_log` の `push` / `copy_day` / `merge_db` / `dedupe_logs` / `merge_same_day` の全部が
`order` を維持する義務を負う。1 箇所忘れると並びが黙って壊れる。`Group.order` /
`Exercise.order` が既にその形で、
[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)
の `renumber_exercises` と `set_archived` の事故が実際に起きている。却下。

**`SetEntry` に安定 ID を持たせる**: `<For>` のキーにも並び替えの表現にも使える。しかし
1 セット約 25 バイトに 12 文字の ID が乗って JSON が 1.5 倍になり、
[localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md) の
容量見積りに直接効く。`same_sets` / `log_rank` / `PartialEq` も全部 ID を意識することになる。
行の一時 ID（`Row.key`）で足りている。却下。

**記録タブに ↑↓ ボタンを置く**: E2E が確実に書けて iOS の実装リスクがゼロ。しかし
`.set-row` は既に 7 要素が 393px に入っており、2 個足すと入力欄が潰れる。
種目タブで却下した理由（44px のボタンが一覧の役目を潰す）が、入力欄がある分もっと強く
効く。却下。

**長押しメニューから「上へ / 下へ」**: ボタンを増やさずに済み、WCAG 2.5.7 の
「ドラッグを伴わない単一ポインタの代替」にもなる。しかし 3 種目を並べ替えるのに
長押し → メニュー → 選択 を n 回で、「筋トレ中に最短距離で」に反する。**2.5.7 を満たす
必要が出たらこの形で足す。** 今回は却下。

**「直近に記録した順で自動的に並べる」**:
[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)
が「矢印を戻すのではなくこれを検討する」と名指しした案。しかし記録タブの並びは
**今日この順でやるという計画**であって履歴の集計ではない。スーパーセットや「先に上げて
から追い込む」順は履歴から導けないうえ、入力中に勝手に並びが変わるのは最も嫌われる。
却下（**「種目を追加」シートの並びには今も有効な案**なので、そちらの将来案として残す）。

**並びを `fitness-memo/ui/v1` に持つ**: `Db` を汚さない。しかし
[UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md) が
「`Db` を参照しない。ID も日付キーも入れない」を性質として課しており、
`(日付キー → ExerciseId の列)` はその境界を**二重に**越える。書き出し / 取り込みで
並びが失われる。却下。

**ドラッグ中に signal の `Vec` を入れ替える**: 実装が素直で、押しのけの transform を
自分で計算しなくてよい。しかし基準点が飛んで振動が収束せず、pointer capture の生存が
ブラウザ実装依存になる（上記「理由」を参照）。却下。

**`.card-head` も即時ドラッグ開始にする**: セット行と揃って一貫する。しかし全幅の帯で
`touch-action: none` なので、スクロールのつもりのフリックが**画面を動かさないまま**
種目の順を変える。一貫性より、黙って壊れないことを採る。却下。

**画面端の自動スクロールを入れない**: rAF ループと再入防止が要らず、実装がいちばん小さい。
しかしカードは 5〜8 枚 × 150〜400px に対し可視域が約 660px で、**画面内では端まで届かない
ケースが構造的に存在する**。1 枚目を末尾へ運ぶのに「動かす → 離す → スクロール」を数回
繰り返すことになる。却下（セット行には入れていない — 1 カード最大 8 行 × 約 50px なので
カードが見えていればリスト全体が入る）。
