# 体重の線を 3M / 6M / 1Y ごとに日ごと / 週平均から選ぶ設定にする

- **状態**: 採用
- **日付**: 2026-09-21
- **カテゴリ**: ux
- **関連**: [体重を推移グラフの第2軸に常時重ねる](body-weight-second-axis-always-on.md)（決定 5 と結果の「3M 以降は週平均」を改訂）, [グラフの座標計算を `chart_layout` に切り出してテスト可能にする](../architecture/chart-layout-as-a-testable-module.md), [ドロップセットの段はメインセットの下の箱に出し、推移では既定で外して注記で開示する](drop-sets-as-a-box-under-the-main-set.md)（「推移の見せ方」設定の先例）, [前回までの記録を日付で出し、何回分出すかを表示設定にする](past-records-by-date-with-a-count-setting.md)（`.segmented` の設定サブページ）, [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md), [設定タブの入口を節の一覧にし、中身は 1 階層下ろす](settings-as-a-list-of-sections.md)

## 背景

[体重を推移グラフの第2軸に常時重ねる](body-weight-second-axis-always-on.md) は、体重の破線が
`WEIGHT_DENSE_POINTS`（45 点）を超えたら**描画点数だけを見て**自動で週平均に落としていた。
既定期間は 3M で、毎日計量する利用者は 3M の範囲（約 90 日）で必ずこの点数を超えるため、
黙って週平均に切り替わっていた。注記（`weekly-note`）は「全期間」にしか出さない設計なので、
3M で線がまとめられていることの理由が画面のどこにも無かった。

利用者の報告：「3M を選ぶとまとめられていて日付単位の推移がわからない」。

`X0 = 40` / `X1_DUAL = 286`（`src/chart_layout.rs`）なのでプロット幅は **246px**。
1Y × 毎日計量 = 365 点を描くと 0.67px/点で破線が帯に潰れる（[体重を推移グラフの第2軸に常時重ねる](body-weight-second-axis-always-on.md) の「密なとき」の根拠そのもの）が、
その閾値は利用者から見えない量であり、期間という見える量と結び付いていなかった。

## 決定

**「日ごとに描くか週平均に落とすか」を、3M / 6M / 1Y それぞれについて設定で選べるようにする。**
点数トリガは廃止し、`chart_layout::layout` は呼び側が `core::WeightLine`（`Daily` / `Weekly`）を
明示する。点数では二度と決めない。

- **期間ごとの 3 トグル**（3M / 6M / 1Y）。**1M は常に日ごと**、**「全期間」は常に週集約**のまま
  （`views::progress` の `weight` Memo が先に集約しており、これは変えない）
- **既定は 3M = 日ごと、6M = 日ごと、1Y = 週平均**
- `UiState` に `weight_weekly_3m|6m|1y: Option<i64>` を持つ（`0` = 日ごと / `1` = 週平均 /
  `None` = 既定）。保存先は `Db` ではなく `fitness-memo/ui/v1`
- **2 点以上ある週が 1 つも無ければ、`Weekly` を選んでいても日ごとのまま描く。** 週内の平均は
  実測と同じ数字になるので、点を週開始日（日曜）へ動かす意味が無い。`WeightLayer.aggregated` の
  意味は「実際に平均へ落としたか」のまま変えない（`drawn.len() != weight.len()` で判定する）
- **画面に注記は出さない。** 「全期間」の `weekly-note` のような文は追加しない。事実は
  `aria-label`（`chart_summary` の `smoothed`）と `data-weight-smoothed` に残す

## 理由

**点数は利用者に見えない量で、期間は見える量である。** 「45 点を超えたら」は利用者が
コントロールできる操作（計量の頻度、期間の選択）と 1 対 1 に対応しない。期間ごとのトグルに
すれば、利用者が選んだ「3M を見ている」という状態と設定が直接結び付く。

**2 択（「密なら常に週平均」/「常に日ごと」）にも、「どの期間から週平均にするか」の 4 択にも
しなかったのは利用者の選択。** 前者は 6M と 1Y で挙動を分けられず、後者は「6M から」を選ぶと
3M は必ず日ごとになり、6M と 1Y が常に同じ扱いになる制約が残る。3 期間を独立に選べる形を
利用者が選んだ。

**1Y の既定を週平均にしたのは、365 点を 246px に描くと破線が帯になるため。**
0.67px/点は「線が細かく揺れる」を超えて「灰色の帯」になる領域で、[体重を推移グラフの第2軸に常時重ねる](body-weight-second-axis-always-on.md) が
既に検証済みの閾値をそのまま引き継いだ。

**6M の既定を日ごとにしたのは利用者の選択で、正直に言うと閾値論では決めていない。**
6M（約 182 日）を毎日計量で描くと 1.35px/点。1Y の 0.67px/点と 1M の約 8px/点の中間で、
「潰れて帯になる」とまでは言えないが「間隔が詰まって見える」領域ではある。利用者は
「6M はまだ日ごとで見たい」を選んだ。閾値で機械的に決めるなら 6M も週平均寄りに倒す余地は
あるが、そうしなかった判断をここに正直に残す。

**2 点以上ある週が無ければ日ごとのままにするのは、平均を取っても数字が変わらないから。**
週 1 回計量する人が `Weekly` を選んでも、各週の平均はその 1 点の実測と同じ数字になる。
それでも「日付を週開始日（日曜）へ動かす」処理だけは効いてしまい、読み取りの丸
（`Band::w_y`）が消える副作用だけが残る。実益の無い副作用を避けるため、系列全体で
2 点以上の週が 1 つも無いときは `drawn` を生データのまま通す。

**設定を `Db` に置かないのは「推移の見せ方」だから。** [ドロップセットの段はメインセットの下の箱に出し、推移では既定で外して注記で開示する](drop-sets-as-a-box-under-the-main-set.md) の
「含めるか」と同じ性質で、記録そのものではなく表示の選択なので `fitness-memo/ui/v1` に置く。

## 結果（トレードオフ）

- **日ごとにした 1Y は線が潰れうる。** 利用者が 1Y を日ごとに切り替えれば、0.67px/点の
  帯へ戻ることを許容する。設定なので選んだ結果として受け入れる。
- **1Y 既定 = 週平均 は、週 2 回以上計量する人の点を週開始日（日曜）へ吸着させ、読み取りの丸
  （`w_y`）を消す。** 点数トリガを捨てた代償で、週 1 回以下の人は fallback 規則により
  日ごとのまま変わらない。
- **fallback は系列単位（全か無か）である。** 週 1 回だけ計量している系列に、ある週だけ
  2 点目が入ると、**その系列全体**が日曜へ吸着する（1 週だけ吸着するわけではない）。
  `weekly.len() == weight.len()` で系列全体を 1 回だけ判定しているため。週によって
  日ごと / 週平均が混在する形にはしていない — 混在させると `w_y` の判定・X ドメインの
  「左端は描画系列から取る」規則の両方が「その週だけ特別扱い」を要求し、複雑さが釣り合わない。
- **設定トップが 9 行になった。** [設定タブの入口を節の一覧にし、中身は 1 階層下ろす](settings-as-a-list-of-sections.md) の
  「トップは 1 画面に収まる」は 9 行でも保たれている。
- **週平均を選んでも、週 1 回以下の計量なら絵が変わらない。** 「設定を変えたのに何も
  起きない」ように見える。注記は出さない方針にしたので、この事情はマニュアルで説明する
  （`src/i18n.rs` のマニュアル章）。

## 検討した代替案

- **2 択（密なら常に週平均 / 常に日ごと）で 3 期間まとめて** — 選択肢が 1 つで済むが、
  6M と 1Y で挙動を分けられない。1Y だけ帯にしたくない・6M は日ごとで見たい、という
  利用者の要求に応えられない
- **「どの期間から週平均にするか」の 4 択（1M から／3M から／6M から／1Y から）** — 段階的で
  分かりやすいが、「6M から」を選ぶと 1Y も自動で週平均になり、3 期間を独立に選べない
- **点数を px 密度で判定する（`points / plot_width`）** — 点数の絶対値より画面の実際の密度に
  近いが、判定基準が利用者にさらに見えなくなるだけで「見えない量で決まる」問題の根本は変わらない
- **全期間も layout 側の `Weekly` 選択に寄せる**（`progress.rs` の事前集約をやめて
  `chart_layout` に一本化） — 一貫はするが、全期間の帯が日曜に吸着し、その日に計量が無いと
  読み取り欄の体重が消える。既存の「全期間は先に週平均済みの系列を渡す」経路のほうが
  読み取りの安定性で勝る
- **`Weekly` を無条件に適用する**（fallback 規則を持たない） — 実装は単純になるが、
  疎な計量（週 1 回以下）でも点が日曜へ動くだけで、実測日と違う日付に点が描かれる
  副作用だけが残る。実益が無いので却下した
- **2 点以上ある週だけ丸めて、1 点の週は実日付のまま**（週単位で日ごと / 週平均を混在させる） —
  「週 1 回の人は絵が変わらない」を週の粒度でも実現できるが、週キー = 日曜という不変条件と
  「X ドメインの左端は描画系列から取る」規則が、混在する系列では両方崩れる。指標側の週集約
  （`aggregate_weekly_points`）ともキーが揃わなくなり、2 本の線が別の日付軸に並ぶ危険がある。
  複雑さに見合わないと判断し、系列単位（全か無か）の fallback を選んだ
