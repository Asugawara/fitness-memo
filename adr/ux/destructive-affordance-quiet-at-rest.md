# 破壊的操作は静止時に警告色を持たない（カード削除をフッタへ畳む）

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: ux
- **関連**: [記録タブをカレンダー + 選択日エディタの単一画面にする](record-tab-calendar-with-day-editor.md), [セット追加は直前行の重量をコピーして回数欄へフォーカスする](set-entry-prefill-and-focus.md)（拡張）

## 背景

種目カード末尾の「この種目を外す」は、静止しているだけで主張が強すぎた。

カードは 1 日に何枚も並ぶので、**カードの枚数だけ橙色の行が縦に並ぶ**。めったに使わない破壊的操作が、常時いちばん目立つ色で出ていた。

この形は誤タップ対策の帰結である。元はカード見出しの右端に ✕ があったが、そこは「種目を追加」を探して下スクロールする指が最初に触る位置で、**追加しようとして種目ごと消す**経路になる。カード末尾のテキストリンクへ移して確認を挟んだ。

実際に `trunk serve` で測ると、問題は色だけではなかった（カード幅 612px の実測値と 390px 幅の計算値）。

| 項目 | 値 |
|---|---|
| 文字色 | `--warn`（ダーク `#e2a06a` / ライト `#b4560c`）。コントラスト比はダークで約 8.5:1 |
| 文字サイズ | **15px**。`.card-foot` の 13px、`.group-name` の 12px より大きい |
| `+ セット` 下端 → `外す` 上端 | **41px**。しかも**右端が完全に一致**（並べた 3 枚とも） |
| 最後のカードの `外す` と sticky「種目を追加」 | 縦に **9px 重なる**。横は 390px 幅で約 **7.5px** |

わかったのは次の 3 つ。

**`--warn` を静止状態で使っているのはここだけだった。** 行削除の ✕ は `.icon-btn` = `--muted` で、警告色は `.row-confirm`（確認）にしか出ない。**カード削除だけがアプリ内の規則を破っていた。**

**位置は動かしたが「列」は動いていなかった。** 旧事故地点（見出し右端）も `+ セット` も `外す` も、すべてカードの右端。上下には動かしたが左右は同じ列に置いたままだった。

**最後のカードでは sticky の「種目を追加」と斜めに 7.5px しか離れていない。** `.add-wrap` のグラデ帯は `pointer-events: none` なのでタップは下へ抜ける。1 種目終えて次を追加する、いちばん多い場面での近接だった。

あわせて、**セットが 1 つも入っていない空カードでも「この日の記録が消えます」と出ていた**。消えるものは無いので嘘になる。行削除は「空行は消えるものが無いので確認しない」（[セット追加は直前行の重量をコピーして回数欄へフォーカスする](set-entry-prefill-and-focus.md)）と決めてあるのに、カード削除だけその規則から外れていた。

## 決定

**1. 破壊的操作の入口は、静止状態で警告色を持たない。**

`--warn` を持ってよいのは確認 UI（`.warn-box` / `.row-confirm`）だけ。**入口は常に `--muted`。**
カード削除の入口も `--muted` / 13px（`.card-foot` と同じスケール）にする。

**2. 入口を `.card-foot` に畳み、左端へ置く。**

```
─────────────────────────────
この日から外す            今日  1,080
```

専用の行（`.card-remove`）を廃止する。カード 1 枚が 31px 縮む（44px + margin 2px の行が消え、フッタが 29px → 44px）。

左端に置くのは、カードの右端が「行の ✕ → `+ セット` → sticky の種目を追加」という**動線の列**だから。破壊的操作をその列に置かない。

**3. 保存済みセットが 0 のカードは確認を挟まず外す。**

[セット追加は直前行の重量をコピーして回数欄へフォーカスする](set-entry-prefill-and-focus.md) の「空行は確認しない」をカードへ広げる。

**維持する制約**: `.card-head` には削除導線を置かない。旧事故の教訓はそのまま。E2E の `card-head button` が 0 件であるアサーションも残す。

## 理由

**そろえるのは作法であって、見た目ではない。** 「行削除と同じ ✕ アイコンに統一する」案は検討して却下した。カード末尾の右端に ✕ を置くと、直上にある「行の ✕」と**同じ列・同じグリフ**になり、1 セットとカード全体のどちらが消えるのか読めない。スコープの違う破壊的操作に同じ見た目を与えてはいけない。一貫させるべきは「静かな入口 → 押したときだけ警告色の確認」という規則のほうで、そこは完全にそろった。

**色を落とすだけでは原因が残る。** 最小の修正は `danger` クラスを外す 1 行だが、それだと右端の列にも sticky ボタンの 7.5px 隣にも居座ったままになる。症状だけ薄めることになる。

**空カードの削除がいちばん多い用途。** 「シートで種目を押し間違えた」「並べたが結局やらなかった」はどちらもセットが空。ここに確認を挟むのは邪魔なだけで、しかも表示する文言が嘘になる。

**行が 1 本減るのはトレ中の実利。** 5 種目並べば約 155px スクロールが減る。

**新しい色を増やさない。** `--muted` は `.card-foot` と行削除の ✕ が既に使っている。コントラストは概算でライト 4.8:1 / ダーク 6.9:1 で、13px の通常テキストに求められる AA 4.5:1 を満たす。タップ標的は `.link-btn` の `min-height: 44px` のまま縮めない（**静かにするのは色と文字サイズだけで、当たり判定ではない**）。

## 保証するので、破る入力のテストを書く

「静止時に警告色を持たない」と宣言する以上、それを破ったときに落ちるテストが要る（このリポジトリで一度踏んだ失敗）。`e2e/smoke.spec.mjs` に 4 本置いた。

- 入口の色が `.card-foot` および行削除の ✕ と**同じ**で、確認（`.warn-box`）とは**違う**こと。トークン値をベタ書きせず色同士を比較するので、ライト / ダーク両方で成立する
- 空カード・重量だけ入って回数が空のカードが、確認なしで外れること
- 入口が `+ セット` と**同じ列に無い**こと（`boundingBox` 比較）。タップ標的が 44px 以上あること

`src/lib.rs` が `views` を wasm32 に cfg ゲートしているため `cargo test` はこの経路を通らない。**E2E がこの決定の唯一のカバレッジ。**

## 結果（トレードオフ）

**フッタの高さが 29px → 44px になる。** 中に 44px のタップ標的が入るため。行を 1 本消しているので差し引きは 31px の短縮。

**ラベルを「この種目を外す」→「この日から外す」に変えた。** カード内なので主語（種目）は自明で、本当に曖昧なのはスコープ（種目マスタから消えるのか、この日から外れるだけか）だった。実装は後者。`data-testid` は据え置きなので、文言だけ独立して戻せる。

**重量だけ打って回数が空のカードは「空」扱いで確認なしに消える。** 打った重量は失われるが、そもそも保存されていない（`parse_reps` が `None`）。[セット追加は直前行の重量をコピーして回数欄へフォーカスする](set-entry-prefill-and-focus.md) の行の規則と同じ扱いにそろえた結果として受け入れる。

**確認 UI 自体は変えていない。** `.warn-box` + 青い `primary` の「外す」は `menu.rs` の部位削除と同じ「エンティティ級の確認」の作法。今回の指摘は静止時の主張についてで、確認は押したときにしか出ない。直すなら 2 箇所そろえて別途。

## 検討した代替案

**色だけ `--muted` に落とす（位置はそのまま）。** CSS 1 行で済むが、右端の動線列と sticky ボタンとの近接が残る。上記のとおり症状だけの緩和。

**行削除と同じ ✕ アイコンに統一する。** スコープが読めなくなる。上記のとおり却下。

**見出し右端に `⋯` を置き、インライン展開でアクションを出す。** 静止時の主張はゼロにでき、旧事故地点に**無害な入口**を置く発想は筋が良い。ただしアプリのどこにも無いオーバーフローメニューという概念が増え（`menu.rs` はシートとインライン編集で通している）、削除まで 3 タップになる。**操作 1 つのために新しいパターンを 1 つ足すのは割に合わない。** 今回の変更で存在感がまだ強いと分かったときの次の一手として残す。

**スワイプ / 長押しで出す。** wasm 側でタッチ処理を書くことになり、Playwright で検証できず、iOS のテキスト選択・コンテキストメニューと競合し、発見性が最も低い。
