# 記録タブの「種目を追加」シートを部位のアコーディオンにし、1 つだけ開く

- **状態**: 採用
- **日付**: 2026-09-08
- **カテゴリ**: ux
- **関連**: [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)（★ この ADR が「記録タブの追加シートは畳まない」とした前提を覆す）, [メニュー編集シートの「選択中」をドラッグで並べ替え、種目ピッカーを複数開けるアコーディオンにする](routine-editor-drag-and-accordion.md)（★ 同じ。CSS は `.fold-group` で共有する）, [記録タブのカードとセットをドラッグで並び替え、`Vec` の並びをそのまま保存する](drag-to-reorder-in-record-tab.md)（「直近順で自動的に並べる」を将来案として残した ADR）, [記録タブをカレンダー + 選択日エディタの単一画面にする](record-tab-calendar-with-day-editor.md), [シートをネイティブ `<dialog>` にし、手動の重なり順から降りる](native-dialog-for-sheets.md), [プリセット名は表示時に言語へ追従させ、改名したものだけ据え置く](preset-names-follow-the-ui-language.md), [フォーカスリングを明示し、記録タブの見出しを 1 本の階層にする](focus-ring-and-heading-order.md), [UI の状態に `Db` の ID を置いてよい条件を決める（寛容な受け口と既定への受け皿）](../storage/db-ids-in-ui-state-behind-a-fallback.md)

## 背景

記録タブの「種目を追加」シートは、6 部位 28 種目（プリセット）を**全部同時に平坦へ並べていた**。部位ごとの `<h3>` 見出しはあるが、所属種目の `.pick-list` が常に開いている形である。

同じ形は既にこのアプリの中に 2 つあり、どちらも折りたたみへ移していた — 設定タブの種目一覧（[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md)、1 つだけ開く）と、メニュー編集シートの種目ピッカー（[メニュー編集シートの「選択中」をドラッグで並べ替え、種目ピッカーを複数開けるアコーディオンにする](routine-editor-drag-and-accordion.md)、複数開ける）。**残っていたのはこの 1 枚だけ**で、両 ADR は明示的に「ここには当てない」と書いていた（`public/styles.css` の `.rtn-group` のコメントも同じ）。その根拠は「1 タップで 1 種目を出して閉じる画面で、往復しないので畳む理由が無い」である。

**往復しないのは今も正しい。** 覆したのは別の 2 点である。

- **28 個のボタンから目当てを目で探すことになる。** 実測（Playwright / iPhone 15 Pro 相当 393×659）で `.sheet-body` の中身は **963px**、可視域は **464px**。**28 種目のうち 14 種目（胸 5 / 背中 5 / 肩 4）しかスクロールなしで届かない。**
- **同じ種目でも毎回違う位置に出る。** 部位ブロックの高さは種目名の折り返しで決まり（実測 胸 170 / 背中 120 / 肩 120 / 腕 170 / 脚 170 / 体幹 120）、種目を足したり改名したりすると下の部位が全部ずれる。**手が場所を覚えられない。**

[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) がこのシートの並びを「トレ中の唯一のホットパス」と呼んだのはそのとおりで、だからこそ**位置が動かないこと**が効く。

## 決定

**部位の行を押すとその場で種目が開く。同時に開くのは 1 つ。シートを開くたびに全部閉じた状態から始まる。種目が 0 件の部位は出さない。**

```
┌─ 種目を追加                    ✕ ┐
│ ›  ● 胸                     5 種目 │  ← 閉じた 6 行 = 341px（1 画面に収まる）
│ v  ● 背中                   5 種目 │
│    [ 懸垂 ] [ ラットプルダウン ]    │
│    [ ベントオーバーロウ ]           │
│ ›  ● 肩                     4 種目 │
│ ›  ● 腕                     5 種目 │
│ ›  ● 脚                     5 種目 │
│ ›  ● 体幹                   4 種目 │
└────────────────────────────────────┘
```

不変条件は 5 本。

- **開閉は `views::day` の `DayEditor` ローカルの `RwSignal<Option<GroupId>>`。`OpenGroupCtx` を使わない**
- **`sheet.set(true)` の側で `None` へ倒す。`on_close` ではない**
- **`open_group` を読むのは部位ごとの内側 closure だけ**
- **中身が 0 の部位は `filter_map` で落とす**
- **見た目の CSS は `.fold-group` でメニュー編集シートと共有し、開ける数だけが違う**

## 理由

- **排他にするのは、この画面が「1 種目を出して閉じる」画面だから。** [メニュー編集シートの…複数開けるアコーディオンにする](routine-editor-drag-and-accordion.md) が複数開けるようにしたのは、**メニューを 1 本組む間に胸と脚を行き来する**のが普通の使い方だからである。追加シートは 1 タップで閉じるので往復しない（覆されなかったほうの前提はここで生きる）。排他なら常に「ヘッダ 6 行 + 開いた 1 部位」で、**部位の全体像が消えない**。別の部位へ移るのも 1 タップで済む（複数展開だと「閉じる + 開く」の 2 タップか、散らかったまま）。
- **開くたびに畳むのは、`<dialog>` が常時マウントだから。** [シートをネイティブ `<dialog>` にし、手動の重なり順から降りる](native-dialog-for-sheets.md) のとおりシートは閉じても DOM に残るので、畳まないと**前回開いた部位が開いたままで出る**。既定が毎回同じであることは、位置が動かないという今回の買い物そのものでもある。
- **畳む場所を `on_close` ではなく `sheet.set(true)` 側にしたのは、退場が見えるから。** `on_close` は ✕ / Esc / 背景タップに加えて `pick()` の `sheet.set(false)`（Effect → `d.close()` → `close` イベント）も通るので**機能はする**。しかし `.sheet` は退場に `translate` 0.22s を持ち（`display` / `overlay` を `allow-discrete` で保つ）、**滑り落ちる間もシートは見えている**。高さが中身なので、閉じ際に畳むと上端が 123px 落ちるのが見える。`sheet.set(true)` は `views::day` の 1 箇所しか無いので、開く側で塞げば全経路が閉じる。
- **`OpenGroupCtx` を共有しないのは、設定タブへ漏れるから。** [メニュー編集シートの…複数開けるアコーディオンにする](routine-editor-drag-and-accordion.md) が同じ理由で却下している（アプリ全体で 1 本の signal なので、ここで開いた部位が設定タブの種目一覧でも開く。逆も同じ）。E2E で 1 本固定した。
- **`views::settings` の `GroupBlock` を再利用しないのも同じ ADR と同じ理由。** あれは private な `Editor` enum を prop に取っていて、部位を改名する鉛筆と「＋ 種目を追加」が付いてくる。シートの中からさらにシートが開くことになる。
- **`<h3>` は残し、中に `<button>` を置く。** `<button>` に置き換えると部位ぶんの見出しが a11y ツリーから消える（[フォーカスリングを明示し、記録タブの見出しを 1 本の階層にする](focus-ring-and-heading-order.md) が整えた階層が崩れる）。`<button>` は phrasing content なので `<h3>` の中に置けて、WAI-ARIA APG のアコーディオンも「見出し > ボタン」を求めている。`<details>` / `<summary>` を使わない理由と `aria-controls` を付けない理由は [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) が整理済み。
- **中身が 0 の部位を出さないのは、押しても何も開かない的を作らないため。** 設定タブは 0 件でもヘッダを出すが、あちらは開くと「＋ 種目を追加」が出るので**行き止まりにならない**。このシートには開いて出せるものが 1 つも無い。副産物として E2E のヘルパが「開けば必ず 1 個以上出る」に依存できる。
- **`scroll_into_view_if_needed` は入れない。** [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) があれを必須にしたのは、**プログラムからの自動展開**（末尾に作られる新規部位、一覧最下部のアーカイブ復帰）が「画面の外で開く」からだった。このシートに自動展開の契機は 1 つも無く、開くのは必ず押した行 ＝ 定義上画面内である。**前提が成立しないので手当ても要らない。**
- **`open` を `Memo` にしないのは、外側の closure が `db` を購読しているから。** ピッカー全体はセットを 1 文字打つたびに作り直されるので、`Memo` を 6 個作り直すほうが高い。`views::settings` の `GroupBlock` が `Memo` なのは、あれが `Db` の変更をまたいで生きるコンポーネントだからである。**`open_group` を読むのは内側の closure だけ**にするのは [メニュー編集シートの…](routine-editor-drag-and-accordion.md) と同じで、外側で読むと 1 部位開くたびにピッカー全体が作り直される。
- **`.rtn-group` を `.fold-group` に改名して共有した。** 中身は「見出しを折りたたみ用に整える」規則だけで、メニュー編集シート固有のものは 1 つも無い（`.rtn-grab` / `.rtn-picked` / `.rtn-save` は本当にあの画面固有）。カンマで 2 名前を抱えさせる案は、`h3` の打ち消しが**詳細度 (0,1,1) でソース順に依存する**繊細な形なので却下した。

## 結果（トレードオフ）

- **タップ数が 2 → 3 に増えた。しかも「常に得」ではない。** 上の実測のとおり**胸 / 背中 / 肩の 14 種目はスクロールなしで届いていた**ので、そこは**純粋に 1 タップの後退**である。得になるのは折り返しの下にあった腕 / 脚 / 体幹の 14 種目で、そちらは「2 タップ + スクロール」が「3 タップ」に置き換わるだけ。**買ったのはタップ数ではなく、行位置が毎回同じであることと、部位の全体像が常に見えること。** この非対称を承知で採る。
- **「3 タップは常に 3 タップ」は完全には成立しない。** 3 行に折り返す部位（胸 / 腕 / 脚）を開くと、実測で `.sheet-body` は 464px に対して 497px になり **33px はみ出す**。最終行に届くのにスクロールが 1 回入る。2 行の部位（背中 / 肩 / 体幹）は収まる。
- **部位を開くと押した行が約 123px 上へ動く。** `.sheet` は `inset: auto 0 0` の下端貼りで高さが中身なので、開くと上端が上がる（実測 391px → 514px）。設定タブ（通常フロー・上端基準）とは**逆向き**で、メニュー編集シートも同じ構造だが [メニュー編集シートの…](routine-editor-drag-and-accordion.md) はこれに触れていない。`#add-sheet-body` に `min-height` を当てて高さを固定する案を実測のうえ検討したが、**閉じた状態に 123px の余白が入って「6 行がぴたりと収まる」という今回の買い物を自分で潰す**ので採らなかった。開いた種目は押した指の位置に現れるので、次のタップとしては素直である。
- **`.added`（その日すでに追加済み）が閉じた部位の中に隠れる。** 開いた部位の中では今までどおり効く。`pick()` は追加済みを押しても重複カードを作らず既存カードへスクロールするので**誤った結果にはならない**（失うのは 1 タップ）。その日に何が入っているかの正典は**シートの裏に並んでいるカード列**で、開く直前まで見ていた画面そのものである。部位ヘッダに「追加済み N」を足す案は、52px の行に意味の違う数が 2 つ並んで**閉じた 6 行を舐める速度が落ちる**ので却下した。
- **所属種目を全部アーカイブした部位は記録タブから消える。** 28 種目すべてをアーカイブするとシートが空白になり、そのときの案内文は持っていない。到達には意図的な 28 操作が要る（`core::merge_db` は追加のみで種目の物理削除の経路は無く、`storage` は起動時に欠けたプリセットを補う）ので、文言より先に他の要件が来ると判断した。
- **`Group.order` の意味が変わった。** [種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) が「部位セクション順とその中の種目順」と書いた前者は**閉じた 6 行の順**になり、後者は開いた 1 部位の中だけに効くようになった。同 ADR が「将来ここが不満になったら矢印を戻すのではなく直近順を検討する」と書いた案は、**そのときも採らなかった**（下記）。
- **副産物として再描画が軽くなった。** シートは常時マウントで中身が `db` を購読しているので、セットを 1 文字打つたびに 28 個の `.pick` と 28 本の `class:added` closure が作り直されていた。全部閉じていれば 6 行だけになる。
- **平坦版の `.sheet-group` が消えた。** 改修後は 2 つの利用箇所（`views::day` / `views::routine`）が両方とも `.fold-group` になり、`.sheet-group` の 3 規則は全部打ち消される形になったので、**打ち消される側ごと削除した**。`.fold-group > h3` に残るのは `font-size: inherit`（冒頭の `h1, h2, h3` は `font-size` を触らないので UA の `1.17em` が生きる）と `font-weight: inherit`（`600` を継ぐと件数まで太る）の 2 つだけ。
- **E2E は「全部開く」ができなくなった。** 排他なので `openAllPickGroups`（メニュー編集シート用）の手が使えず、「見つかるまで順に開く」ヘルパに変わった。**部位名の表を持たない**ので英語 UI（`i18n.spec.mjs`）やテスト中に作った種目にもそのまま効く。**押す前に `aria-expanded` を見るのが必須**で、無条件に押すと開いている部位を閉じてトグルし、同じシートで 2 回呼ぶテストが固まる。`pick-exercise` を踏む 8 spec を全部直した（`e2e/` は spec 単体で読める作法なので共有モジュールは作らず、正典コメントを `smoke.spec.mjs` に置いてコピーした）。
- **testid が増えた。** `pick-group`（`<section>`）/ `pick-group-toggle` / `pick-group-name`。シートの器が `add-*`、中身が `pick-*` という既存の分け方に従った。`smoke.spec.mjs` のローカル `pickGroup`（メニュー編集シート用）は `routinePickGroup` へ改名した。
- **「無いこと」の確認は部位を絞ってから数える必要がある。** 畳んだだけで `pick-exercise` は 0 件になるので、シート全体で数えるテストは**改名やアーカイブが効いていなくても通ってしまう**。既存の 2 箇所を、開いた部位の中で数える形と「部位ごと消えること」を見る形に強化した。

## 検討した代替案

**ドリルダウン（部位を押すと種目だけの画面に切り替わる）**: 種目一覧がシートの高さを全部使えて、一度に見えるものが減るので迷いにくい。しかし「戻る」ボタンと見出しの差し替えを新規に作ることになり、**間違えた部位を開いたときのやり直しが 2 タップ**になる。アコーディオンなら次の部位を押すだけで前が閉じる。加えて他の部位が見えなくなるので、「今どこにいて他にどこがあるか」が同時に読めない。却下。

**複数の部位を同時に開けるようにする**（メニュー編集シートの規則を継ぐ）: 規則が 1 つで済み、signal も `Vec` で揃う。しかし全部開けば元の 963px に戻り、**改修が黙って無効化される**（[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) と同じ論法）。あちらが複数開けるようにした「1 本組む間に胸と脚を行き来する」事情は、1 タップで閉じるこの画面には無い。却下。

**直近の部位（その日の最後のカードの部位）を自動で開く**: 同じ部位を続けて足す間は 2 タップのままにできる。しかし外れたときは「開いていた部位を閉じてから目当てを開く」で**4 タップ**になり、しかも開き方が毎回違うので**手が場所を覚えられない** — それが今回の買い物そのものである。既定が毎回同じで予測できるほうを採る。却下。

**開いている部位を `fitness-memo/ui/v1` に永続化する**: [UI の状態に `Db` の ID を置いてよい条件を決める](../storage/db-ids-in-ui-state-behind-a-fallback.md) が条件つきで `GroupId` を許したので、[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) が挙げた「置き場が無い」はもう理由にならない。却下の理由は**満たす必要が無い**ことである（同 ADR の「結果」節が `OpenGroupCtx` について書いたのと同じ）。1 回の追加操作はシートを開いて閉じるまでで完結し、前回の続きから始める要求が無い。むしろ「毎回全閉」を要件として決めている。却下。

**`OpenGroupCtx` を共有して設定タブと 1 本にする**: signal が増えない。しかしアプリ全体で 1 本なので、**追加シートで開いた胸が設定タブの種目一覧でも開きっぱなしになる**（逆も同じ）。[メニュー編集シートの…](routine-editor-drag-and-accordion.md) が同じ理由で却下している。却下。

**`views::settings` の `GroupBlock` をそのまま使う**: 実装がゼロで済む。しかし private な `Editor` enum を prop に取っており、部位を改名する鉛筆と「＋ 種目を追加」が付いてくる。却下（[メニュー編集シートの…](routine-editor-drag-and-accordion.md) と同じ）。

**ピッカーを「直近に記録した順」で自動的に並べる**: [記録タブのカードとセットをドラッグで並び替え](drag-to-reorder-in-record-tab.md) が「『種目を追加』シートの並びには今も有効な案」として残し、[種目タブを部位の折りたたみ一覧にし、1 つだけ開く](menu-groups-as-single-open-accordion.md) が「矢印を戻すのではなくこれを検討する」と名指しした案。**部位の色と名前という既にある構造を捨てる**ことになり、「今日は胸」と決めて開いた人が胸の種目を履歴順のリストから探すことになる。折りたたみは構造を残したまま縦を畳むので、まずこちらを入れた。**この案は今も却下していない**（部位の中の並びに当てる形なら共存する）。

**部位ヘッダに「追加済み N」を出す**: 閉じていても `.added` の情報が読める。しかし 52px の行に意味の違う数が 2 つ並び、閉じた 6 行を上から下へ舐める速度が落ちる。追加済みを押しても壊れない（重複カードは作られない）ので、隠れても誤りにならない。却下。

**開いた部位を `scroll_into_view_if_needed` で画面に入れる**: 設定タブが必須にした手当て。しかしあちらの前提は**プログラムからの自動展開**で、この画面には 1 つも無い（押した行は必ず画面内）。加えてセクションが容器より高いとき `block: nearest` は押した見出しを上端の外へ押し出しうる。却下。

**`#add-sheet-body` に `min-height` を当ててシートの高さを固定する**: 部位を開いても押した行が 1px も動かなくなる。しかし閉じた状態に 123px の余白が入り、**「閉じた 6 行がぴたりと 1 画面に収まる」という今回の買い物を自分で潰す**。実測して見比べたうえで却下した。

**`.rtn-group` のセレクタにカンマで新クラスを足す / 記録タブ用に別クラスを作る**: リネームの差分が出ない。しかし 6 セレクタが 2 名前を抱えることになり、`h3` の打ち消し（詳細度が同じ (0,1,1) なので**位置に依存する**）を 2 倍に増やす。別クラスの重複は規則が drift する。却下。

**`e2e/helpers.mjs` を作ってヘルパを共有する**: コピーが 8 本にならない。しかし `e2e/` は spec 単体で読める作法で通しており（`exactText` / `blurActive` / `addExercise` / `cardOf` が意図的にコピーされている）、ここで作ると**既存ヘルパの移設という機能と無関係な構造変更**が同じ PR に混ざる。却下（作るなら別途、全ヘルパをまとめて）。
