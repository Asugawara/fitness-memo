# 数値入力に `type="number"` を使わない

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: ux
- **関連**: [キーボード表示中はボトムタブを隠す](../pwa/hide-tabs-when-keyboard-open.md), [`visibilitychange` の hidden で debounce を flush する](../storage/flush-on-visibilitychange.md)

## 背景

セット入力は重量（小数あり）と回数（整数）の 2 つの数値欄からなる。iPhone でテンキーを出したいので、素直な選択は `<input type="number">` である。

保存モデルは `SetEntry { weight: f32, reps: u32 }` だが、**編集中の値をこの型で持つことはできない**。空欄が表現できず 0 に落ちてしまい、「まだ何も入れていない行」と「0 と入れた行」が区別できない。そこで編集中は文字列の signal で持つ設計にした。

```rust
struct Row { key: u32, weight: String, reps: String }
```

ここで `type="number"` と文字列 signal が両立しない問題が出る。

## 決定

**`type="text"` + `inputmode` を使う。`type="number"` は使わない。**

```html
<!-- weight -->  <input type="text" inputmode="decimal" pattern="[0-9]*([.,][0-9]*)?">
<!-- reps   -->  <input type="text" inputmode="numeric">
```

パースは自前で行い、UI 層の 2 関数に閉じる。

```rust
/// `"6."` は Rust の f32 パーサが 6.0 として受けるので中間状態でも壊れない。
/// iOS のテンキーは小数点がロケール依存で `,` になることがあるので置換しておく。
pub fn parse_weight(s: &str) -> f32 {
    s.trim().replace(',', ".").parse::<f32>().ok()
        .filter(|w| w.is_finite() && *w >= 0.0).unwrap_or(0.0)
}

/// **空欄と 0 は「行なし」として扱う。**
pub fn parse_reps(s: &str) -> Option<u32> {
    s.trim().parse::<u32>().ok().filter(|r| *r > 0)
}
```

## 理由

- **WHATWG の number 入力は sanitization アルゴリズムを持つ。** 値が有効な浮動小数点数でない場合、**DOM の `value` は空文字列を返す**。つまり `"6."` と打っている途中の状態が読み取れない。WebKit ではさらに正規化された値が返ることもある。生の文字列が取れないので、「文字列 signal で中間状態を保持する」という設計と原理的に両立しない。
- **`"6."` の中間状態は普通に発生する。** 62.5kg を入力するとき、`6` → `62` → `62.` → `62.5` と進む。`62.` の時点で `value` が空文字列になると、その瞬間に signal が空になり、`commit()` がその行を「レップ数だけの行」あるいは「消えた行」として扱う。1 文字打つごとに保存する設計（[`visibilitychange` の hidden で debounce を flush する](../storage/flush-on-visibilitychange.md)）なので、中間状態がそのまま永続化される経路がある。
- **`inputmode` でテンキーは出るので、UX は変わらない。** iOS のキーボード種別は `type` ではなく `inputmode` で決まる。`decimal` は小数点付きテンキー、`numeric` は数字のみ。利用者から見た挙動は `type="number"` と同じである。
- **Rust の `f32` パーサは `"6."` を 6.0 として受ける。** つまり中間状態のまま保存されても値として妥当で、そのあと `"6.5"` まで打てば 6.5 になる。パーサ側で特別扱いが要らない。
- **小数点のロケール差を吸収できる。** iOS のテンキーは地域設定によって小数点が `,` になる。生の文字列が取れるので `replace(',', ".")` で吸収できる。`type="number"` だと sanitization の段階で弾かれ、アプリ側で救えない。
- **`type="number"` のスピナー（増減矢印）が不要である。** デスクトップでは邪魔で、`appearance: none` で消すのが定番になっている。`type="text"` なら最初から出ない。

## 結果（トレードオフ）

- **バリデーションを全部自前で書く必要がある。** `min` / `max` / `step` によるブラウザ側の検証が効かない。実際に必要だったのは「負値と非有限値を弾く」「レップ 0 と空欄を行なしとして扱う」の 2 つで、`parse_weight` / `parse_reps` に閉じている。
- **不正な文字を入力できる。** `pattern` は `:invalid` の判定に使われるだけで、入力自体は止めない（フォーム送信をしないので検証も走らない）。`"abc"` と打てば `parse_weight` が 0.0 を返し、`parse_reps` は `None` を返して行が保存されない。クラッシュはしないが、**「打ったのに保存されない」という静かな失敗になる**。テンキーしか出ないので実機で踏む確率は低いが、正直に言えば弱点である。
- **`reps == 0` の行を保存時に破棄する規則が必要になった。** 空欄を 0 として保存すると、`0×0` の行が「前回をコピー」で複製され続ける（[「前回をコピー」はセットが空のときだけ出す](copy-button-only-when-empty.md)）。`parse_reps` が `Option` を返すことでこの規則を型に載せている。
- **`Weighted` で `reps > 0 && weight == 0` の行は保持する。** 重量の入力忘れを黙って指標減少にしないため、行に「重量未入力」を小さく表示して残す。破棄すると入力したセットが消えるので、警告して保持するほうが安全と判断した。
- **CSS で `input { font-size: 16px }` を守る必要がある。** 16px 未満だと iOS がフォーカス時にページごとズームする。`type` とは無関係だが、数値欄は幅が狭いのでフォントを小さくしたくなる誘惑がある。全体規則として `styles.css` に置いた。
- E2E で中間状態を検証する（`smoke.spec.mjs` ケース 12）。`6.` を打った状態でクラッシュせず、`6.5` まで打つと指標に反映されること。この検証がないと `type="number"` に戻す変更が通ってしまう。

## 検討した代替案

**`type="number"` + `valueAsNumber` を読む**: sanitization の影響を受けにくいが、`NaN` が返るケースの扱いが必要で、しかも**中間状態は依然として表現できない**（`"62."` は `valueAsNumber` でも 62 になり、次に `5` を打ったとき DOM 側の文字列が失われている経路がある）。却下。

**`type="number"` + 確定ボタン方式**: 入力中に signal を触らないので中間状態の問題が消える。しかし 1 セットごとに確定操作が増え、「最短手数で回す」という要件に反する。しかもセット行が複数あると「どこまで確定したか」が分からなくなる。却下。

**`type="tel"`**: 古いブラウザでテンキーを出す定番の手だった。`inputmode` が使えるので今は理由がない。セマンティクスも嘘になる。却下。

**入力を数値パッド UI（自前のボタン）にする**: sanitization もキーボードの問題も全部消え、`.kb-open`（[キーボード表示中はボトムタブを隠す](../pwa/hide-tabs-when-keyboard-open.md)）も不要になる。しかし画面の大部分をパッドが占め、実装量も大きい。「非常にシンプル」から遠ざかるので却下。

**`f32` / `u32` の signal で持ち、空欄を `Option` で表現する**: 型で表現できるが、`"62."` のような**数値として同じだが文字列として異なる状態**が失われる。入力欄の表示が勝手に `62` に戻るので入力できない。却下。
