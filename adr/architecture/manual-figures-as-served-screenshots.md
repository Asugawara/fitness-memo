# マニュアルの図は `public/` に配信するスクリーンショットにし、`<img>` で参照する

- **状態**: 採用
- **日付**: 2026-09-09
- **カテゴリ**: architecture
- **関連**: [ヘルプの図を `assets/` の SVG に置き `include_str!` + `inner_html` で挿す](help-figures-as-included-svg.md), [使い方マニュアルを設定タブの節にし、章は 1 つだけ開く](../ux/manual-as-a-settings-section-with-one-open-chapter.md), [UI 関連パスを触ったコミットでだけスクリーンショットを撮り直す](../deploy/screenshots-in-pre-commit-on-ui-paths.md), [Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md), [クローラ向けメタデータを本番 URL のハードコードで持ち、オフラインシェルから外す](../seo/crawler-metadata-and-hardcoded-origin.md), [i18n crate を入れず、`src/i18n.rs` の struct + `const` 2 枚で文言を持つ](i18n-hand-rolled-string-table.md)

## 背景

[使い方マニュアルを設定タブの節にし、章は 1 つだけ開く](../ux/manual-as-a-settings-section-with-one-open-chapter.md) で、気づきにくい機能を説明する 8 章のマニュアルを設定タブに置いた。そのうち 5 章は**どこに何があるか**が主題なので、文章だけでは伝わらない。「グラフの下の読み取り欄」「カードのフッタにある ＋ メモ」「空の日にだけ出る候補リスト」はいずれも位置の話で、図が要る。

このリポジトリには既に図の載せ方の決定がある。[ヘルプの図を `assets/` の SVG に置き `include_str!` + `inner_html` で挿す](help-figures-as-included-svg.md) が、ホーム画面追加の手順シートの 3 枚について「`assets/` の SVG を wasm に埋め込む」と決め、**実機スクリーンショットを 3 つの理由で却下している**。

> **実機スクリーンショット（PNG / WebP）**: 忠実度は最高で、ユーザーが見る画面とそのまま一致する。しかし (1) 共有シート最上段の AirDrop 連絡先候補をトリミングし忘れると公開サイトに連絡先が出る、(2) ライト／ダークのどちらかと必ず明暗がずれる、(3) 1 枚数十〜数百 KB を 3 枚。却下。ただし差し替え点を 1 行に閉じてあるので、後から採る余地は残した。

したがって問題は「あの決定を覆すのか」ではなく、**被写体が違うことをどう扱うか**である。あちらの被写体は **iOS のブラウザクローム**（Safari の共有シート・ツールバー）で、こちらの被写体は**このアプリ自身の画面**である。

## 決定

**マニュアルの図は Playwright で撮った実機相当のスクリーンショットにし、`public/manual/{ja,en}/{id}.webp` に置いて素の `<img>` で参照する。** [ヘルプの図を `assets/` の SVG に置き `include_str!` + `inner_html` で挿す](help-figures-as-included-svg.md) は**置換しない**。被写体で棲み分ける。

|  | ヘルプの 3 枚 | マニュアルの 10 枚 |
|---|---|---|
| 被写体 | iOS のブラウザクローム（模式図） | このアプリ自身の画面（実物） |
| 置き場 | `assets/help/*.svg` | `public/manual/{ja,en}/*.webp` |
| 載せ方 | `include_str!` → `inner_html` | 配信物 → `<img src>` |
| テーマ | `var(--*)` で追従 | **ライト固定**（節の先頭で断る） |
| SW シェル | 乗る（wasm の一部） | **乗らない**（SHELL と BUILD_ID の両方から除外） |
| 作り方 | 手描き SVG | `scripts/shots.mjs`（[UI 関連パスを触ったコミットでだけスクリーンショットを撮り直す](../deploy/screenshots-in-pre-commit-on-ui-paths.md)） |

付随して 5 つを決める。

1. **要素単位のクリップで撮る。** viewport 全体ではなく `data-testid` の集合の外接矩形 + パディングを `page.screenshot({ clip })` に渡す。`src/` に撮影専用の testid を 1 つも足さずに済む
2. **`deviceScaleFactor: 2`、lossy WebP の `quality: 90`。** README の 3 枚（devices 既定の 3）からの意図した逸脱
3. **ja / en の 2 変種を持つ。** `<picture>` は使わない（テーマは固定なので変種は言語だけ）
4. **宣言寸法を `ChapterText::fig` に持ち、`<img width height>` に出す。** レイアウトシフトを防ぐと同時に、実ファイルとのずれを `cargo test` と E2E の両方で検出する
5. **`fig` は言語別に持つ。** クリップが外接矩形なので寸法は内容依存になる

```rust
<figure class="man-fig">
    <img
        src=format!("manual/{}/{}.webp", cur_lang().tag(), ch.id)   // ★ 先頭 / 禁止
        width=w height=h
        alt=text.fig_alt loading="lazy" decoding="async"
        data-testid="man-fig"
    />
</figure>
```

## 理由

- **却下理由 (1)（AirDrop の連絡先）は、この被写体には当たらない。** あちらが撮れなかったのは iOS の共有シートを撮る必要があったからで、最上段に実在の連絡先が並ぶ。**このアプリの画面には連絡先も個人情報も一切写らない。** 写るのは `scripts/shots.mjs` が localStorage へ直接注入した架空のトレーニング記録だけで、値はソースに直書きしてある。トリミング忘れという失敗モードそのものが存在しない。
- **却下理由 (2)（テーマずれ）は、固定 + 明示で扱える。** [`color-scheme` を宣言し、クラスなしの `<button>` を作らない](../ux/declare-color-scheme-for-ua-widgets.md) が既に「`shots.mjs` はライトで撮る」と決めており、README の 3 枚はそれで運用できている。マニュアルも同じライト固定にし、**節の先頭で「図はライトテーマの画面です。ダークテーマで使っていても配置は同じです」と断る**（`Manual::light_note`）。両テーマ 2 変種にすると図が 20 枚になり、pre-commit の撮影時間と blob が倍になる。あちらは「模式図に色トークンを与える」形が取れたのでテーマ追従が安く済んだが、こちらは撮り直しが倍になるだけなので、**同じ問題に別の解を当てるのが正しい**。
- **却下理由 (3)（サイズ）は、要素クリップ + dsf 2 + lossy WebP で桁が変わる。** あちらが想定していたのは「1 枚数十〜数百 KB」だが、実測は **10 枚で計約 190KB（1 枚 12〜32KB）**。参考として同じ被写体を lossless WebP で撮ると **10 枚で 569KB（約 3.0 倍）** になるので、`quality` の明示が桁を決めている。加えてこの 190KB は**オフラインシェルに乗らない**（下記）。
- **あの ADR が残した余地を、別の被写体に対して行使した。** 「差し替え点を 1 行に閉じてあるので、後から採る余地は残した」と書いてあるのは `views::help` の 3 枚の話である。**ヘルプの 3 枚は今も SVG のままで、1 行も差し替えていない。** 行使したのは「実機スクショという手段を採ってよい」という判断のほうで、対象は新しく増えたマニュアルの図である。あちらの状態は「採用」のまま据え置く。
- **アプリ自身の画面は模式図にできない。** ヘルプの図が模式図で成立するのは、伝えたいのが「共有ボタンは下のまん中」という**位置関係だけ**だからである。マニュアルは「グラフをタップすると読み取り欄が動く」「＋ メモ 1 つで 4 つ開く」という**実際の画面の状態**を見せるもので、模式図に描き直すと今度は「図と実物がずれていないか」を人間が保証し続けることになる。撮ってしまえば実物と一致する。
- **`public/` + `<img>` を採れるのは、テーマを固定したから。** あちらが `public/` + `<img>` を却下した理由は「外部参照された SVG に CSS 変数が届かずダークで破綻する」だった。ラスタ画像でテーマ固定なら CSS 変数を必要としないので、この理由は消える。
- **オフラインシェルから外せるのは、図が補助だからである。** マニュアルは章を開いたときだけ `<img>` を描くので、開かない人は 1 バイトも取りに行かない。約 1.0MB のシェルに 190KB を恒久的に足すのは、[クローラ向けメタデータを本番 URL のハードコードで持ち、オフラインシェルから外す](../seo/crawler-metadata-and-hardcoded-origin.md) が `og.png` について書いたのと同じ理由で割に合わない。除外の基準そのものを改訂したので、その記録は同 ADR と [Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md) への追記に置いた。
- **BUILD_ID からも外すのを実測で確認した。** `public/manual/` にファイルを追加・削除しても BUILD_ID は `5eefb38d25f5e488` のまま動かない。SHELL だけ外して BUILD_ID に残すと、図を 1 枚差し替えただけで**中身が同一のシェル**に新しいキャッシュ世代が切られ、全クライアントが約 1.0MB を無駄に再ダウンロードする。除外を片方だけにすると除外した意味が逆転する（`og.png` と同じ性質）。`scripts/stamp-sw.sh` の `shell_files()` に一本化して、片方だけ直す事故を構造的に潰した。
- **`src/` に撮影専用の testid を 1 つも足していない。** クリップを既存の `data-testid` の外接矩形から作っているので、撮影のためにプロダクションコードへ入る変更がゼロになる。撮影の都合が UI に漏れない。
- **寸法を宣言して二重に検証する。** `src/manual.rs` の `every_manual_figure_exists_with_the_declared_size` が `public/` の実ファイルを、`e2e/manual.spec.mjs` の「宣言寸法 = 実ファイル」が**配信物**を見る。前者は「ファイルが揃っているか」、後者は「配信経路まで含めて一致しているか」を担当する。同じテストを 2 回書いているのではなく、`copy-dir` を挟んだ前後を別々に押さえている。
- **`webp_size()` はチャンク走査で書く。** Playwright の出力は常に `VP8X(10) + ICCP(456) + VP8L`/`"VP8 "` の拡張形式で（`--force-color-profile=srgb` により sRGB プロファイルが 456 バイト挟まる）、byte 20 は `VP8X` の flags であって `VP8L` の signature ではない。offset 固定で読むと**たまたま通って別の数字を返す**形になる。

## 結果（トレードオフ）

- **`quality` を書き忘れると桁が変わる。** Playwright の `quality` 既定は 100 で、WebP の 100 は **lossless** である。実測でこの 10 枚は lossy q90 の 190KB に対し lossless で **569KB（約 3.0 倍）**。しかも lossless は PNG より大きい（別被写体の実測で 1179×600 の PNG 45,169 に対し lossless 88,950）。**「WebP にしたから小さい」は成り立たず、小さいのは lossy を選んだからである。** `scripts/shots.mjs` の `WEBP_QUALITY` に理由を書いてある。
- **`quality` を上げても色付き細線の滲みは取れない。** q85 / q90 / q95 を撮り比べて lossless と画素差を取ったところ、折れ線と部位ドット（彩度のある画素）で差 8 超の割合は **q85 65.9% / q90 60.9% / q95 60.4%** とほぼ動かない。WebP の lossy は品質に関わらず **4:2:0 のクロマサブサンプリング**を通すので、色の解像度は `quality` では戻らない。**したがって「滲みが気になったら quality を上げる」は効かない**（等倍では lossless と区別が付かないので実害は無いが、次に触る人が無駄に上げないよう記録する）。バイト数は q85 156KB / q90 190KB / q95 240KB で、**95 は 27% 払って何も買っていない。** 90 を採ったのは 85 との差が測定上わずかに残るためで、余裕を持たせた選択である。
- **`fig_alt` は iOS で 1 行に収まらないと描かれない。** WebKit の `RenderImage::paintMissingImageState` → `hasRoomForAltText` は alt 全文を 1 本の `TextRun` として測り、幅に収まらなければ**何も描かない**（折り返さない）。Blink は折り返して出すので Chrome で確認しても気づけない。したがって **ADR にも UI にも「オフラインでは alt が出る」と書いてはいけない。** 出るのは Blink だけである。対処として `fig_alt` を短い名詞句に限り、`every_language_has_the_same_manual_chapters` が言語別の上限（ja 20 字 / en 45 字、`chars().count()`）で固定した。上限の根拠は `.man-fig img` の 12px と、狭い端末（320px 幅）で `.screen` の左右 padding を引いた実効幅 290px。**この上限は机上の計算で、実機の WebKit で測ってはいない。**
- **図と本文の版ずれが起きる。** アプリ本体（本文と宣言寸法）は wasm の中にあり BUILD_ID で次回起動時に原子的に入れ替わるが、**図は `copy-dir` でハッシュの付かない固定 URL に置かれ、HTTP キャッシュ経由で配られる。** したがって次の 2 つが起きる。
  - **起動し直していない旧アプリが、新しい図を表示する**（旧 wasm の宣言寸法と新しい実ファイルがずれ、図が縦に伸び縮みして見える）
  - **新しいアプリが、10 分は旧図を表示する**（Pages の `max-age=600`）

  ずれる期間はマージから最悪 **20 分程度**（Pages のビルド + CDN 反映が約 10 分、そこに `max-age=600` が乗る）。**オフラインの端末では、次にオンラインになるまで続く**（図はシェルに無いので、機内モードのまま何日でも欠けたままになる）。`og.png` にこの問題が無かったのは、アプリが一度も参照しないからである。**受容する。** 図が 1 リリースずれても「どこに何があるか」の説明としては致命的でない。内容ハッシュをファイル名に付けて `MANUAL_CHAPTERS` に持たせる案（旧アプリは 404 になり「食い違い」が「欠け」に変わる）は、複雑さの割に得るものが小さい。`?v=` クエリは同じファイルが返るので効かない。
- **図はオフラインで出ない。** [Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md) の要件「完全にオフラインでも動作する」に対し、**図はこのアプリで初めての「オフラインで出ないもの」**である。緩和として (1) 本文だけで手順が完結するよう章を書き、(2) 節の先頭で `offline_note` として先に断り、(3) `e2e/manual.spec.mjs` の「オフラインで開くと本文は読めるが図は欠け、断りが伝わる」で機械的に固定した。
- **寸法が言語で違う章がある。** `accordions` は **ja 786×1030 / en 786×994** で、部位名の折り返し行数が違うぶん高さが 36px ずれる。言語非依存の `MANUAL_CHAPTERS` に `fig` を持たせていたら、どちらかの言語で必ずテストが落ちていた。`Chapter` には `has_fig: bool` だけを残し、寸法は `ChapterText` に置いてある。
- **`public/` の役割が増えた。** これまで `public/` は「配信されるもの」で、そのすべてが SW のシェルに載っていた（`og.png` を除く）。今後は「配信されるが**シェルには載らない**もの」が第 3 のカテゴリとして存在する。`scripts/stamp-sw.sh` の `shell_files()` に条件を一本化し、載せてよい条件を 5 つに落としてある。
- **wasm の増加は計測していない。** [ヘルプの図を `assets/` の SVG に置き `include_str!` + `inner_html` で挿す](help-figures-as-included-svg.md) は release wasm の前後を実測して「増加の 8 割は図ではなくコード」と書いたが、今回は**図を wasm に埋めていない**（`include_bytes!` を避けたのはまさにこのため）ので、増えるのは `src/manual.rs` と `src/views/manual.rs` のコードと 8 章 × 2 言語の文字列だけである。図そのものは 1 バイトも入らない。**前後比較の実測は取っていない**ので、「マニュアルで wasm がどれだけ増えたか」は未知のままである。必要になったら `--release` を 2 回踏んで測ること。
- **図の中身は日本語のシードで作られている。** en の図は `Exercise.name` が日本語のまま保存された `Db` を、表示だけ `ex_name` / `grp_name` で英語にして撮っている（[プリセット名は表示時に言語へ追従させ、改名したものだけ据え置く](../ux/preset-names-follow-the-ui-language.md) が保証する性質に乗っている）。**誰かが `Exercise.name` を素通しで描いたら en の図に日本語が写る。** `scripts/shots.mjs` が図ごとに「その図に写る文字列に日本語が含まれないこと」を撮影前に検査して落とす。
- **メニュー編集シートは撮れない。** `src/views/routine.rs` が `ex_name` / `grp_name` を通しておらず、en で日本語が写る既存バグがある。章 6（部位の折りたたみ）の図は 3 か所のうち「記録タブの追加シート」だけを被写体にした。**バグが直ったら図を足せる**が、それは別 PR。

## 検討した代替案

**ヘルプと同じく手描き SVG の模式図にする**: 既存の決定にそのまま乗れて、テーマにも追従し、SW シェルに載せるかどうかも考えなくてよい。しかし 5 枚の被写体はいずれも「実際の画面の状態」（グラフの読み取り欄が動く、4 つが一斉に開く、候補リストが並ぶ）で、模式図に描き直すと**図と実物が一致していることを人間が保証し続ける**ことになる。UI を触るたびに 10 枚の SVG を目で見比べる運用は続かない。却下。

**PNG のままにする**: `assets/*.png`（README のスクショ）と同じ扱いで、エンコーダの選択も `quality` の判断も要らない。しかし同じクリップの実測で PNG は lossy WebP のおよそ 2.5〜3 倍。pre-commit で撮り直して stage する設計（[UI 関連パスを触ったコミットでだけスクリーンショットを撮り直す](../deploy/screenshots-in-pre-commit-on-ui-paths.md)）では、そのまま git の肥大に直結する。Safari 14+ という前提（[ブラウザサポートは Safari を基準にし、polyfill を入れない](browser-support-policy.md)）では WebP に PNG フォールバックも要らない。却下。

**`cwebp` で PNG から変換する**: `-lossless` が Chromium の lossless の約 1/3 になるなど、エンコーダとしては優秀。しかし Playwright が `page.screenshot({ path: '….webp', quality })` で直接吐けるので、外部プロセスを 20 回起動する工程と `scripts/setup.sh` の導線が丸ごと不要になる。lossy 同士なら Chromium 直接出力と cwebp のサイズはほぼ同じ（別被写体の実測で 17,332 対 16,876）。**エンコーダが `@playwright/test` の exact pin に紐づく**ので決定性も強くなる。却下。

**図を `include_bytes!` で wasm に埋め込む（ヘルプと同じ載せ方）**: `public/` を触らずに済み、SW シェルの除外基準を改訂する必要もなく、オフラインでも図が出る。しかし **190KB がそのまま wasm に乗り、マニュアルを一度も開かない人も毎回ダウンロードする。** ヘルプの SVG が 4.3KB で成立した話と桁が違う。`src/manual.rs` が非 cfg モジュールなので、テストのために `include_bytes!` を書くだけでも同じことが起きる（テストは `std::fs::read` で読んでいる）。却下。

**ライトとダークの 2 テーマ × 2 言語 = 20 枚撮る**: ダークテーマの利用者にも自分の画面と一致する図が出せる。しかし撮影時間と blob が倍になり、pre-commit の 60 秒制約に直接効く。伝えたいのは配置であってテーマではないので、`light_note` の 1 行で足りると判断した。却下。

**`<picture>` + `prefers-color-scheme` で出し分ける**: 20 枚撮る前提での正しい実装。撮らないなら不要。却下。

**図のファイル名に内容ハッシュを付ける**: 版ずれが「食い違い」から「欠け」に変わり、旧アプリは 404 で図が出ないだけになる。しかしハッシュを `MANUAL_CHAPTERS` に持たせることになり、撮り直しのたびに Rust 側を書き換える箇所が寸法とハッシュの 2 つになる。ずれる期間が最悪 20 分であることに対して重い。却下。
