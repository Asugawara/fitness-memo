# 他アプリからの移行はスクショの文字起こしを貼り付けて受ける

- **状態**: 破棄
- **日付**: 2026-08-09
- **カテゴリ**: ux
- **関連**: [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](../storage/share-sheet-over-download.md)（書き出し経路）, [テキスト取り込みは「足すだけ」に固定し、部位を増やさず、`at` を書かない](../data-model/text-import-is-merge-only.md)（取り込みの規則）

## 破棄した理由（2026-08-09）

**実装して使ってみたが、狙った読み取りが成立しなかった。** 実機の「テキスト認識表示」から起こした文字列は、想定した「日付 → 種目名 → セット行」の並びで取れず、パーサが記録として拾えない。読めなかった行を画面に出す設計にしていたので黙って壊れはしないが、出てくるのが「読めなかった行」ばかりでは移行にならない。

**確認画面の操作量も移行 1 回に見合わない。** 未知の種目ごとに部位を選び、日付が読めない分の着地日を選び、読めなかった行を確かめる——移行は生涯に数回しか通らない導線なのに、そこだけ他のどの画面より操作が多い。**筋トレ中に最短距離で足せる**というアプリの前提から外れている。

読み取り精度を上げても操作量は減らず、操作量を削ると読み違いをそのまま取り込む。どちらに倒しても割に合わないので、機能ごと撤去した。

実装（`src/import_text.rs` と `BackupSheet` の `Pane::Text`）は削除済み。**この ADR は判断の記録としてのみ残る。** 以下の本文は当時のまま。特に「背景」の調査結果——iOS のサンドボックス・ショートカット・HealthKit・Web Share Target のどれも経路にならないこと——は今も有効なので、同じ経路を再検討するときはここから読む。

## 背景

別の筋トレアプリからこのアプリへ乗り換えたい。**移行元にエクスポート機能が無い。**

「iPhone に他アプリのデータを自動で読ませられないか」を先に潰した。結論は**読めない**。

- **iOS のサンドボックス**が他アプリのコンテナを一切見せない。PWA からはもちろん、ネイティブアプリでも他アプリの `Documents` は開けない
- **ショートカット**も同じ。移行元が App Intents を公開していない限り中身は取れず、個人開発の記録アプリはまず公開していない
- **HealthKit** には Web API が無いので PWA からは触れない。仮に触れても `HKWorkout` にセット・重量・回数は入らないので、移したいものがそもそも入っていない
- **Web Share Target** は Safari が実装していないので、共有シートから PWA へテキストを流し込む経路も無い

残る唯一の汎用手段が **iOS のテキスト認識表示（Live Text）**。移行元アプリの協力が一切要らず、スクリーンショット 1 枚から文字列を選択してコピーできる。

## 決定

**「他アプリから」ペインを `BackupSheet` に足し、貼り付けたテキストを解析して取り込む。**

移行元アプリ名に依存しない汎用パーサ（`src/import_text.rs`）を書き、日本語アプリの `1 60kg × 10` も海外アプリの `Bench Press / 60 kg x 10` も同じ `Draft` に落とす。英語の種目名はプリセットの日本語名に寄せる別名表を持つ。

```
前のアプリで記録の画面を出す → スクショ → 写真アプリで開く
 → 右下の「テキスト認識表示」→ すべてを選択 → コピー → 貼り付けて「読み取る」
```

## アプリの中で OCR しない

`tesseract.js` を wasm で載せる案は捨てた。

- 日本語の学習データだけで十数 MB。**完全オフラインで動くことがこのアプリの前提**（[Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md) のシェル一括入れ替え）なので、precache に十数 MB を足すことになる
- Shape Detection API の `TextDetector` は iOS 非対応
- **そして精度でも速度でも iOS 標準の Live Text に勝てない。** 端末に既に載っているものを、劣化させて再実装することになる

利用者の手数は「写真アプリで 2 タップ」増えるだけで、移行は生涯 1 回の操作。**割に合わない。**

## シートを増やさずペインを足した

`BackupSheet` の中に `Pane::Text` として置く。専用のシートを立てると、**自動退避（`storage::snapshot_current`）→ 適用 → 元に戻す の分岐が 2 本になる。**

このアプリでデータを失う経路はここ 1 本しかない、という状態は `views/backup.rs` の `apply` / `do_undo` を読めば検証できることで成り立っている。移行機能のために 2 本目を生やすと、次に片方だけ直す人が出る。

テキストペインが作るのは**確認画面の手前まで**で、`Db` を組み立てたら既存の `pending` に載せて読み込みペインへ渡す。控えを取るのも巻き戻すのも、これまでと同じ 1 本のコードが担う。

## 読み取れなかった行を必ず画面に出す

`Draft::ignored` に積んで、**「確認へ」より上**に折りたたみで出す。

黙って捨てると「移行できたつもり」で前のアプリを消される。それがこの機能で一番あり得ない結末で、しかも取り返しがつかない。「確認へ」より下に置かないのは、進んだ後に見せても取りこぼしに気づく前に押されているため。

セットが 1 つも続かなかった種目名（挨拶文や見出し）もここに落ちる。

## 結果（トレードオフ）

**全履歴の移行は現実的でない。** スクショの枚数が要る。**狙いは「種目リストと直近の重量」**で、次のトレーニングで `core::last_log_before` の「前回 60kg×10」が出れば移行は成功、と定義した。数年分のグラフを繋ぐ用途には応えない。

**読み取り違いは残る。** OCR は `0` と `O`、`6` と `8` を取り違える。だから[置き換えを選ばせず、足すだけに固定した](../data-model/text-import-is-merge-only.md)。読み違いは後から画面で直せるが、消えたデータは戻らない。

**書式の網羅は原理的に終わらない。** アプリごとに画面が違う。`src/import_text.rs` をターゲット非依存の純関数にして（[グラフの座標計算を `chart_layout` に切り出してテスト可能にする](../architecture/chart-layout-as-a-testable-module.md) と同じ立て付け）、実機で外した書式をテストとして足していける形にした。E2E は「読み取り結果の見せ方」しか見ない。

## 検討した代替案

**iPhone のバックアップから移行元の DB を抜く。** Mac に暗号化バックアップを取れば、アプリの `Documents` / `Library` が入っている。SQLite や plist で持っているアプリなら読める。**が、Mac が要る／移行元次第で失敗する／他人に配れない。** 自分の端末を 1 回だけ移す用途には有効なので、必要なら別途やる。この決定はそれを否定しない。

**移行元アプリごとの専用パーサ。** 汎用で試して実機で外した書式だけ足す方針を採った。最初から書式を決め打つと、そのアプリの画面更新で無言に壊れる。

**画像を直接受け取って解析する。** アプリ内 OCR と同じ理由で却下。`<input type="file" accept="image/*">` を置いても、読む手段がこちらに無い。
