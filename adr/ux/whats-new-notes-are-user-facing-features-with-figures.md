# 新機能のお知らせは「利用者の便益になる機能」だけを書き、画面に現れるものには図を付ける

- **状態**: 採用
- **日付**: 2026-09-22
- **カテゴリ**: ux
- **関連**: [新機能のお知らせバナーを画面最上段に置く](whats-new-banner-above-the-screen.md)（このお知らせ機能そのものの決定。`ReleaseNote` の形をここで `items` に変える）, [マニュアルの図は `public/` に配信するスクリーンショットにし、`<img>` で参照する](../architecture/manual-figures-as-served-screenshots.md)（撮り方・置き場・配信・検証を丸ごと踏襲する）, [UI 関連パスを触ったコミットでだけスクリーンショットを撮り直す](../deploy/screenshots-in-pre-commit-on-ui-paths.md)（`--only=` の対象と hook の対象を広げる）, [シートをネイティブ `<dialog>` にし、手動の重なり順から降りる](native-dialog-for-sheets.md)（`<Sheet>` 常時マウントの理由。図のゲートを `open` に直結しない根拠と同じ不具合クラス）, [Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md)（除外条件の 2 つ目の適用先）, [クローラ向けメタデータを本番 URL のハードコードで持ち、オフラインシェルから外す](../seo/crawler-metadata-and-hardcoded-origin.md)（除外の 5 条件そのものの出所）, [i18n crate を入れず、`src/i18n.rs` の struct + `const` 2 枚で文言を持つ](../architecture/i18n-hand-rolled-string-table.md)（お知らせ本文・図の代替文言をここに置く根拠）

## 背景

`RELEASES`（`src/i18n.rs`）には文言だけの項目が並んでいるが、いつの間にか利用者の便益にならないもの（推移タブの 2 段セレクタ化、種目追加のアコーディオン化、バナー自体の追加）まで混ざっていた。書く基準が無いまま項目を積んできた結果で、次の機能 PR の作者が「何を書き、何を書かないか」を毎回自分で判断している。

もう一つの欠落は図である。マニュアル（[使い方マニュアルを設定タブの節にし、章は 1 つだけ開く](manual-as-a-settings-section-with-one-open-chapter.md)）は 12 章すべてに図を持つのに対し、お知らせは文章だけで「どこに新しい設定行が現れたか」を伝えられていない。

3 つ目は運用の穴である。`scripts/release.sh` の `--check` は ADR と README に「rebase / GitHub マージ後の図のずれを捕む」と書いてあったが、`rg check scripts/release.sh` で確認すると実装が無かった。2026-09-09（[マニュアルの図は `public/` に配信するスクリーンショットにし、`<img>` で参照する](../architecture/manual-figures-as-served-screenshots.md) の日付）から本 PR（2026-09-22）まで、rebase やマージ後の図の実装ずれを捕まえる網は事実上存在しなかった。

## 決定

**「利用者が新しくできるようになったこと」だけを書く基準を `RELEASES` の doc コメントに固定し、その基準を満たす項目のうち画面に現れるものには図を 1 枚付けられるようにする。撮り方・置き場・配信・検証はマニュアルの図と完全に同じ形にする。**

### 書く基準

- **判定文**: 以前はどんな操作でもできなかったことができる、または得られなかった情報が得られる → 書く。同じ結果に別の操作で至るだけ → 書かない
- 書く: 設定の追加、新しい入力・記録の種類、新しい表示（それまで無かった情報）、言語追加（図なし）、エクスポート形式の追加
- 書かない: 既定値だけの変更、並び替え・アコーディオン化・セレクタ分割（負例: id 1 の 2 段セレクタ化、id 2 のアコーディオン化。**文言は触らない**）、スクロール位置・アニメーション・フォーカス、不具合修正、性能、内部構造、文言修正、ドキュメント、開発手順、テスト
- 1 項目 = 1 機能。本文は 1〜2 文（旧挙動・仕組みの説明は書かない。詳しい説明はマニュアルへ）
- 図: 新しい操作・設定が**指で指せる場所**にあるとき付ける（新しい設定行・チップ・グラフ）。画面に現れないものには付けない。図は**今の画面**を写す（そのときの画面ではない）
- `fig.id` は被写体のスラッグ。同じ被写体を別の項目で再び写すときは `<slug>-<release id>`（例 `weight-line-9`）
- 既存 id 1〜5 は基準より前のものなので触らない

### データ型

```rust
pub struct ReleaseFig {
    pub id: &'static str,        // ASCII スラッグ = ファイル名 public/whatsnew/{lang}/{id}.webp。全体で一意
    pub alt_ja: &'static str,    // 1 行に収まる名詞句。ja ≤ 16 字 / en ≤ 33 字
    pub alt_en: &'static str,
    pub size_ja: (u32, u32),     // 実測寸法（device px）。<img width height> に出す。言語別
    pub size_en: (u32, u32),
}
pub struct ReleaseItem { pub ja: &'static str, pub en: &'static str, pub fig: Option<ReleaseFig> }
pub struct ReleaseNote { pub id: u32, pub date: &'static str, pub items: &'static [ReleaseItem] }
```

`ReleaseNote { ja, en }`（言語ごとに文字列のリストを持つ形）から `ReleaseNote { items: &[ReleaseItem] }`（1 項目が日英両方を持つ形）へ変えた。既存 5 件は `ReleaseItem::plain(ja, en)` へ機械的に移し、文言は 1 文字も変えていない。id 5（体重の線の日ごと / 週平均設定）にだけ `fig` を付ける — 出荷時点で図がゼロだと図関連の E2E / `cargo test` が全部対象 0 件になるため、既存の中で最初に基準へ当てはまる項目に 1 枚置いた。

### 撮り方・置き場・配信・検証はマニュアルと同一

|  | マニュアルの図（24 枚） | お知らせの図（1 枚） |
|---|---|---|
| 置き場 | `public/manual/{ja,en}/*.webp` | `public/whatsnew/{ja,en}/*.webp` |
| 撮り方 | 要素クリップ / dsf 2 / lossy WebP q90 / ライト固定 | 同じ |
| SW シェル除外 | 5 条件を満たす | 同じ 5 条件を満たす |
| 撮影コンテキスト | ctx B/C（`FIGS`、順序依存あり） | **別コンテキスト ctx D/E**（`WN_FIGS`、順序非依存） |
| `--only=` | `manual` | `whatsnew`（+ カンマ区切りで複数種別） |

お知らせの図をマニュアルと別コンテキストで撮るのは、マニュアルの `FIGS` が順序依存（`copy-last` が当日にカードを生やす、`whats-new` が `release_seen` を書いて reload）だからである。混ぜると `--only=whatsnew:<id>` の単発撮影と全枚数撮影の絵が食い違いうる。

### 初回 open の `revealed` ラッチ

図は「一度でもシートを開いた」ラッチ `revealed: RwSignal<bool>` が真のときだけ描く。**`open.get()` を直接ゲートにしない。** 閉じた瞬間に `<figure>` が unmount され、退場アニメーション（`.sheet` の `translate` 0.22s）の途中でシートの高さが縮む — [シートをネイティブ `<dialog>` にし、手動の重なり順から降りる](native-dialog-for-sheets.md) と [新機能のお知らせバナーを画面最上段に置く](whats-new-banner-above-the-screen.md) が名指しした「退場中の DOM 消失」と同じ不具合クラスの縮小版である。`revealed` はバナーの `on:click` で `open` と同時に立て、閉じてもリセットしない（閉じる = 既読でバナーが消え、開き直す導線が無いため）。言語切替で部分木が作り直されると `false` に戻るので、そのときは開き直すまで図が無い。

### 壊れたときの代替とダークの断り

`on:error` で図の代わりに `<p>{t().releases.fig_missing}</p>` へ差し替える。**「圏外では」と断定しない** — `on:error` は 404（版ずれ: 旧 wasm が撤去済みの図を参照、Pages 反映の最悪 20 分）でも発火するため。ダーク利用者への断りは `unseen` に `fig` を持つ項目が 1 つでもあればシート本文の先頭に 1 行（`fig_light`。マニュアルの `light_note` と同じ役割・同じ CSS ゲート）。

### alt 上限 16/33（マニュアルの 20/45 より厳しい）

`.sheet-body` の実効幅と `.wn-fig img` の 12px から算出し、2 割以上余らせてある。根拠は AT 向けの短い名詞句と、`on:error` で代替表示に切り替わる保険であって、マニュアルの「WebKit は 1 行に収まらない alt を描かない」制約はここでは無関係 — 失敗時は `<img>` ごと `<p>` に差し替えるので alt が描かれない局面が無い。

### `scripts/release.sh` に `--check` を足す

```sh
DIST_DIR="$DIST_DIR" E2E_BASE="$PUBLIC_URL" node scripts/shots.mjs --check \
  || die "スクリーンショットが実装とずれています。リリースを中断します"
```

### 図の寿命と撤去規則

図は**今の画面**を写す（そのときの画面ではない）。被写体を消す・動かす改修をする PR は、同 PR で `WN_FIGS` の setup と `fig` を外し、ファイルを消す（**文言は残す**）。setup を追従修正して延命しない（無関係な UI 変更の pre-commit が `setupWeightLine` の throw で止まるのを防ぐ）。目安: 最新 3 件より古い項目の図は外してよい。図が 0 枚になったら `public/whatsnew/{ja,en}/.gitkeep` を置いて `copy-dir` を生かす（`.gitkeep` はドットファイルなので SHELL に載らない）。**`git add -- public/manual public/whatsnew` はディレクトリが無いと `fatal: pathspec` で hook が止まる**ので、ディレクトリを消すなら hook からも外す。

## 理由

- **書く基準を doc コメントに固定するのは、機能 PR の作者が最初に読む場所だから。** ADR は変更をする段になって初めて読まれるが、`RELEASES` の doc は項目を足そうとした瞬間に必ず目に入る。
- **既存 id 1〜5 の文言を変えないのは、この機能が「基準を新設した」のであって「過去のお知らせを検閲する」ものではないため。** 負例（id 1 の 2 段セレクタ化、id 2 のアコーディオン化）を doc に残すのは、次に似た変更をする人が「これは前例があるから書いていいはず」と誤読しないため。
- **`ReleaseItem` を 1 個の構造体にして日英を両方持たせるのは、`ja.len() == en.len()` を人力で揃える必要を型で消すため。** 旧形（`ReleaseNote { ja: &[str], en: &[str] }`）はリストを 2 本に分けており、片方だけ書き忘れてもコンパイルを通ってしまう。
- **`fig` を項目単位（`ReleaseItem`）に持たせるのは、1 項目 = 1 機能の基準と揃えるため。** リリース単位に持たせると id 4（3 機能で 1 リリース）のような場合に「どの機能の図か」が曖昧になる。
- **マニュアルと完全に同じ撮り方・除外条件を踏襲するのは、車輪の再発明を避けるため。** [マニュアルの図は `public/` に配信するスクリーンショットにし、`<img>` で参照する](../architecture/manual-figures-as-served-screenshots.md) が固めた 5 つの決定（要素クリップ / dsf2 + q90 / ja・en 2 変種 / 宣言寸法 / 言語別寸法）と SW 除外の 5 条件は、被写体が変わっただけでそのまま成立する。
- **ctx を分けるのは、マニュアルの `FIGS` が順序依存だから。** `copy-last` / `whats-new` は db や storage を書き換える setup を持ち、後続の図に影響する。お知らせの図を同じコンテキストに混ぜると、単発撮影（`--only=whatsnew:<id>`）と全枚数撮影で絵が変わりうる。
- **`revealed` ラッチが要るのは、`<Sheet>` の children が閉じていても評価されるため。** 無条件に `<img>` を置くと起動時に fetch が走り、[Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md) の除外条件 1（起動経路から参照されない）を破る。
- **`release.sh` に `--check` を足すのは、rebase / GitHub マージ後のドリフトを捕まえる網が実際には存在しなかったため。** [UI 関連パスを触ったコミットでだけスクリーンショットを撮り直す](../deploy/screenshots-in-pre-commit-on-ui-paths.md) は pre-commit が rebase やリモートマージでは走らないことを既に記録しており、`--check` はその唯一の受け皿として設計されていたが実装が無かった。

## 結果（トレードオフ）

- **図の枚数がお知らせ本数に比例して増える。** 再検討トリガー: 未読シート 1 枚に図が 5 枚を超えたら、`public/whatsnew/` が 300KiB を超えたら、または setup の修正が UI 変更のたびに要るようになったら、この方式を見直す。
- **古いお知らせの図も撮り直しの対象に残り続ける。** 上の撤去規則（最新 3 件より古い項目は図を外してよい）で抑える。
- **圏外・404 では図が出ず 1 行に置き換わる。** マニュアルと同じくオフラインで完結しない箇所が増える。
- **ダーク利用者にはライトの図が出る**（`fig_light` で断る。マニュアルと同じ妥協）。
- **既存 id 1〜4 は基準制定前なので触らない。** id 5 に 1 枚だけ付けて仕組みを実ファイルで固定した。
- **撮影の増分は実測 +1.3 秒**（`--only=manual` 7.2s → `--only=manual,whatsnew` 8.5s）。hook 全体の時間増とは別に読むこと（[UI 関連パスを触ったコミットでだけスクリーンショットを撮り直す](../deploy/screenshots-in-pre-commit-on-ui-paths.md) が同じ注意をマニュアルの図について書いている）。
- **同じマシンで並行する pre-commit と release.sh は `SHOT_PORT` を分ける必要がある**（既定 4274 の衝突を避けるため、開発中は明示的にポートを変えて走らせた）。

## 検討した代替案

**リリース単位で図を持つ**（`ReleaseNote` に `fig` を 1 つ）: id 4 のように 1 リリースに複数機能が入ると、どの機能の図かが曖昧になる。却下。

**マニュアルの図を参照・共有する**: 被写体と寿命の性質が違う（マニュアルは「今も存在する機能の説明」、お知らせは「その時点の新機能」で、撤去規則も別）。却下。

**圏外の断りを常時表示する**: シートでは 99% のオンライン利用者にノイズになる。ダークの断りは CSS でダーク利用者にしか出ないので採ったが、オフラインの断りは `on:error` 発火時にだけ出す形で十分。却下。

**`.notice` に相乗りさせる**: [新機能のお知らせバナーを画面最上段に置く](whats-new-banner-above-the-screen.md) が既に同じ理由（トーンと駆動源が違う）で却下している。却下。

**`src/releases.rs` を新設する**: [新機能のお知らせバナーを画面最上段に置く](whats-new-banner-above-the-screen.md) の代替案検討で既に却下済み（`i18n.rs` の外に表示用文言を置かない規約に反する）。却下。

**`loading="lazy"` を付ける**: 図は利用者がバナーを押した後にしか DOM に無く、枚数も少ない。lazy はスクロール容器内の判定と登場アニメーションに絡んで E2E を不安定にするだけ。却下。

**既存エントリを基準に合わせて書き換える・削除する**: 既存 id 1〜5 は基準制定前のものであり、文言は「触らない」と決めた。書き換えると過去のリリースノートの正確性を失う。却下。

**`fig.id` にリリース番号を前置する**: 図は「今の画面」を写すので、被写体そのものには番号が意味を持たない。同じ被写体を再度撮るときだけ `<slug>-<release id>` を付ければ足りる。却下（一律の前置はしない）。
