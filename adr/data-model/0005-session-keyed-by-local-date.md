# ADR-0005: セッションをローカル日付文字列で BTreeMap に持つ

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: data-model
- **関連**: [ADR-0006](0006-at-optional-same-day-only.md), [ADR-0008](0008-one-log-per-exercise-per-day.md)

## 背景

要件は「カレンダーに、どの日付にどの筋トレ項目をしたかを追加・閲覧できる」。カレンダー月グリッド、日別サマリ、過去日のバックフィルが全て「日」を単位に動く。

一方で「最後のトレーニングからの経過時間」は時刻を要求する。つまりモデルは日と時刻の両方に触る。

## 決定

**セッションを `BTreeMap<String, Session>` で持ち、キーはローカル日付の `"YYYY-MM-DD"` 文字列にする。**

```rust
pub struct Db {
    pub schema: u32,
    pub next_id: u32,
    pub groups: Vec<Group>,
    pub exercises: Vec<Exercise>,
    /// "YYYY-MM-DD" → 日付順が自動で保たれる
    pub sessions: BTreeMap<String, Session>,
}
```

日付は `Local::now().date_naive()`、epoch ms は `Local::now().timestamp_millis()` で統一する。書式は `core::DATE_FMT = "%Y-%m-%d"` の 1 箇所に置き、`date_key()` / `parse_date_key()` を通す。

**1 日 = 1 セッション、日付はローカル日付**を境界規則として明文化する。

## 理由

- **ゼロ埋め ISO 形式なので辞書順 = 時系列順になる。** `BTreeMap` に入れるだけで日付順が保たれ、`range(..date_key(before)).rev()` で「指定日より厳密に前」を後ろから走査できる。`last_log_before` と `elapsed_since_last` はこの性質だけで実装されており、ソートも二分探索も書いていない。
- **`String` キーにしたのは JSON の制約から。** `serde_json` のオブジェクトキーは文字列なので、`NaiveDate` をキーにすると独自の直列化が必要になる。[ADR-0014](../storage/0014-defer-export-import.md) で「`Db` の JSON がそのままエクスポート形式になる」ことを前提にしたので、人間が読める日付キーであることにも意味がある。
- **`chrono` の default features を絶対に削らない。** default は `["clock","std","oldtime","wasmbind"]` で、`wasmbind` が wasm32 でブラウザの実タイムゾーンを引く。サイズ削減の定石で `default-features = false` にすると wasm32 はフォールバックに落ち、`Local::now()` が黙って UTC を返す。**コンパイルも通りパニックもせず、日付キーだけが 9 時間ズレる**（JST では朝 9 時までの記録が前日に入る）。「1 日 = 1 セッション」というモデルの根幹への無音の破壊で、E2E でも時間帯依存でしか出ない。`Cargo.toml` に警告コメントを置いた。
- **レジューム中の「今日」を再評価する必要がある。** iOS のホーム画面 PWA は再起動されず何日もレジュームされるので、mount 時に決めた「今日」を持ち続けると月曜に開いたアプリで水曜のトレーニングを月曜に記録してしまう。`DateCtx { today, selected }` を `provide_context` で配り、`visibilitychange` の visible 復帰時とタブ切替時に `resync()` で引き直す。日付キー設計はこの再評価と組み合わせて初めて正しく動く。

## 結果（トレードオフ）

日付キーにすることで、次の 3 つを割り切りとして受け入れる。要件上いずれも許容範囲と判断した。

- **深夜 0 時を跨いだトレーニングは 2 日に分かれる。** 23:30〜00:30 のセッションが 2 レコードになる。
- **タイムゾーン移動は現地日付に従う。** 日本で記録して渡米すると、現地の日付でキーが振られる。
- **朝と夜のトレーニングは同じ日に合流する。** 1 日 2 部練が 1 セッションになる。部位が違えば種目カードが並ぶだけなので実用上は問題にならないが、「朝の分」「夜の分」を分けて見ることはできない。

その他:

- **キーが `String` なので不正な値を型で防げない。** `"2026-8-3"`（ゼロ埋めなし）や壊れた文字列が入ると辞書順の前提が壊れる。`core::migrate()` で**キーを再正規化し、パースできないキーのセッションは捨てる**ことで境界を固めた。正規化で同じキーに落ちた 2 セッションはマージする。この挙動はテストしてある。
- **`parse_date_key` が全ての走査で走る。** `sessions_in` や `elapsed_matching` は毎回文字列をパースする。10 年で 2,000 セッション程度なので実測上問題ないが、`NaiveDate` キーなら不要なコストである。
- **未来日のセッションを作れてしまう。** `elapsed_matching` は `range(..=date_key(today))` で未来日を除外し、負の経過時間を出さないようにしている（テスト済み）。除外を忘れた場所があると「−3 日前」のような表示になる。

## 検討した代替案

**`Vec<Session>` に `date: NaiveDate` を持たせる**: 型で日付を守れる。しかし日付での検索が線形探索になり、「指定日より前で最も新しい」を毎回ソート済みに保つ責任が実装側に移る。`BTreeMap` が無料でくれる性質を手で書くことになるので却下。

**`BTreeMap<NaiveDate, Session>`**: 型安全で正規化も不要。`serde_json` のオブジェクトキーは文字列なので、`serde` の `with` 属性で日付を文字列化する層が必要になる。結局同じ文字列表現を扱うことになり、JSON を人が読めなくなるリスクだけが増える。却下。

**epoch ms 1 本を真実源にして日付は導出する**: 時刻の精度を常に持てるが、過去日バックフィルで「いつトレーニングしたか」が表現できなくなる。この問題は [ADR-0006](0006-at-optional-same-day-only.md) で `at: Option<i64>` として別に解いた。

**セッションの境界を「午前 4 時」にずらす**: 深夜トレーニングが分断されなくなる。実装は容易だが、カレンダー表示・グラフの日付・「今日」の定義がすべて 4 時間ずれた独自の暦になり、要件の「非常にシンプル」から遠ざかる。却下。
