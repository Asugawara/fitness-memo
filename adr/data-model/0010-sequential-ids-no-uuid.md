# ADR-0010: ID を `next_id` の連番にし uuid を使わない

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: data-model
- **関連**: [ADR-0003](../architecture/0003-wasm-target-scoped-dependencies.md), [ADR-0011](../storage/0011-localstorage-single-key-json.md)

## 背景

`Group` と `Exercise` は ID を持つ必要がある。`ExerciseLog.exercise_id` が種目を参照し、`Exercise.group_id` が部位を参照するので、種目名を変えても過去ログが追随できなければならない（要件「種目名は自由に編集・追加できる」の帰結）。

素直な選択肢は `uuid` クレートだが、**wasm32 で `uuid::Uuid::new_v4()` を使うには `getrandom` のバックエンド設定が必要**になる。`getrandom` 0.3 は wasm32-unknown-unknown で明示的なバックエンド指定（`wasm_js` feature と `RUSTFLAGS` の cfg）を要求し、設定を忘れるとリンクエラーか実行時パニックになる。

## 決定

**ID は `u32` の連番とし、`Db.next_id` を唯一の採番口にする。`uuid` は使わない。**

```rust
impl Db {
    /// 唯一の ID 採番口。プリセット投入もユーザー追加もここを通す。
    pub fn alloc_id(&mut self) -> u32 {
        let id = self.next_id;
        self.next_id = self.next_id.saturating_add(1);
        id
    }
}
```

規則を 3 つ置く。

1. **`Group` と `Exercise` は同じ番号空間を共有する。** 部位 ID と種目 ID が衝突しない
2. **`presets.rs` は固定 ID を持たない。** プリセット投入も `alloc_id()` を通すので、種目タブの「プリセットを追加」で再投入しても既存 ID と衝突しない
3. **`0` は使わない。** 未採番の番兵として空けておく（`next_id` の初期値は 1）

`core::migrate()` は復元時に `next_id` を「既存 ID の最大値 + 1」まで繰り上げる。参照先が消えたログの `exercise_id` も最大値の計算に含める。

## 理由

- **`getrandom` のバックエンド設定という無音の失敗源を持ち込まない。** leptos 0.8.20 の `csr` feature は `getrandom?/wasm_js` という**弱依存**なので getrandom を有効化しない。つまり uuid を使うなら自分で設定する必要があり、設定は `Cargo.toml` だけでは完結せず `RUSTFLAGS` にも及ぶ。ビルド環境の設定に依存する箇所を増やさない方針（[ADR-0003](../architecture/0003-wasm-target-scoped-dependencies.md)）と一致する。
- **単一ユーザー・単一デバイス・単一ストレージなので、ID の衝突が起きる経路がない。** `Db` は 1 キーの JSON（[ADR-0011](../storage/0011-localstorage-single-key-json.md)）で、複数の書き手がマージされることがない。uuid が解く問題（分散生成された ID の衝突回避）が存在しない。
- **JSON が小さく読みやすい。** uuid だと 1 参照あたり 36 バイト、`u32` なら 1〜5 バイト。`exercise_id` は全セッションの全ログに出るので差が積み上がる。エクスポート形式をそのまま人が読む前提（[ADR-0014](../storage/0014-defer-export-import.md)）でも、`"exercise_id": 10` のほうが追いやすい。
- **`migrate` で `next_id` を修復できる。** 連番なら「既存 ID の最大値 + 1」という明確な回復規則がある。壊れた `next_id`（例えば 1 に戻っている）を放置すると新規種目が既存 ID と衝突し、過去ログが別の種目を指すという最悪の壊れ方をする。ログの `exercise_id` まで最大値の計算に入れているのは、参照先が消えた ID を再利用しないため。
- **番号空間を共有するのは、`alloc_id` を 1 本にしておくため。** 部位用と種目用でカウンタを分けると `next_group_id` / `next_exercise_id` の 2 つを常に正しく修復する必要があり、修復漏れの余地が増える。ID の重複は `presets.rs` のテストで検証している。

## 結果（トレードオフ）

- **ID を見ただけでは部位か種目か分からない。** 番号空間を共有しているので、`10` が部位なのか種目なのかは文脈で決まる。型エイリアス（`GroupId` / `ExerciseId`）を付けているが、どちらも `u32` なので**コンパイラは取り違えを検出しない**。`db.group(exercise_id)` と書いても通ってしまう。newtype にすれば防げたが、`serde` の実装と `format!` の手間が全体に波及するので採らなかった。
- **`u32` の上限に達すると `saturating_add` で止まる。** その後 `alloc_id()` は同じ ID を返し続けるので ID が重複する。1 日 100 個作っても 11 万年かかるので実害はないが、`saturating_add` は「静かに壊れる」方向の選択である。`checked_add` で `Option` を返せば呼び出し側が扱えるが、全呼び出し箇所にエラー処理が波及するので採らなかった。
- **「プリセットを追加」で改名済みのプリセットが別種目として復活する。** `presets::seed` は名前一致でスキップするので、「ベンチプレス」を「ベンチ」に改名した後に再投入すると「ベンチプレス」が新しい ID で追加される。ID を固定しておけば防げたが、固定 ID はユーザー作成の種目と衝突するので採れない。**既知の限界として受け入れる**（改名した種目を再度アーカイブすればよい）。
- **ID の再利用はしない。** 部位を削除しても番号は空くだけで、`next_id` は戻らない。過去ログが消えた種目を指していても、その番号が別の種目に割り当たることがないので、参照が silently 別のものに繋がる事故が起きない。

## 検討した代替案

**`uuid` クレート（v4）**: 分散生成でも衝突しない。しかし wasm32 で `getrandom` のバックエンド設定が必要になり、設定は `RUSTFLAGS` にも及ぶ。単一デバイス・単一ストレージのアプリで解く必要のない問題のために、ビルド環境依存の失敗源を持ち込むことになる。却下。

**`Local::now().timestamp_millis()` を ID にする**: 依存を増やさずほぼ一意になる。しかし同一ミリ秒内に 2 つ作ると衝突し、プリセット 34 件の一括投入がまさにそれに当たる。カウンタとの併用が必要で、それなら連番のほうが単純。却下。

**種目名そのものを ID にする**: 参照が人間可読になる。しかし「種目名は自由に編集できる」という要件が正面から壊れる（改名すると過去ログが全て迷子になる）。却下。

**部位と種目で番号空間を分ける**: ID から種類が判別できる。しかしカウンタが 2 つになり `migrate` の修復も 2 系統になる。共有空間で失うのは「見た目で判別できる」だけなので、修復の単純さを取った。
