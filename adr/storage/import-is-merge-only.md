# 取り込みは「足すだけ」に固定する

- **状態**: 採用
- **日付**: 2026-08-15
- **カテゴリ**: storage
- **関連**: [書き出しを TSV にし、保存形式（JSON）と分ける](tsv-export-for-spreadsheets.md), [書き出し / 読み込みを 1 画面に畳む](../ux/one-screen-export-import.md), [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md), [パース失敗時は上書きせず退避する](quarantine-on-parse-failure.md)

## 背景

取り込みには 2 つのモードがあった。

- **置き換える**（既定）— 丸ごと入れ替える。移行と復旧
- **足すだけ** — 既存を 1 つも書き換えず、無い分だけ足す。2 台の統合

確認画面は「現在」と「読込後」の件数を並べ、[それが「記録 0 日のファイルで全部消す」事故を止める唯一の道具](share-sheet-over-download.md)だと位置づけていた。裏を返すと、**既定が「置き換える」である限り、全損は 1 タップの距離にあり続ける**。

## 決定

**取り込みを `core::merge_db`（足すだけ）に固定し、モード選択を UI ごと外す。**

併せて、確認画面の「読込後」を「**取り込み後**」に改める。出す数字は `summarize(merge_db(現在, 取り込む側))` — つまり**マージ済みの結果**で、取り込むファイル自身の要約ではない。

## 理由

### merge は減らさない（コードを読んだ実測）

- **部位 / 種目は push のみ。** 既存の `archived` を書き換える枝が無い
- **セッションは追加のみ。** 同じ日の同じ種目でセットが食い違うときは `log_rank` の大きいほうを採るが、`log_rank` の第 1 要素は**セット数**なので減らない
- **体重は元の値を残す**（`Conflict::BodyWeight`）

したがって「種目 N ・ 記録 D 日 ・ S セット」は**単調非減少**になる。「記録 0 日のファイルで全部消す」は、確認画面が止めるのではなく**構造的に起きなくなる**。

### 置き換えが要る場面が実は無い

- **Safari タブ → ホーム画面 PWA の移行**（README が挙げている経路）: 移行先は初期状態なので、merge の結果は replace と同じ。プリセットが[全端末共通の固定 ID](../data-model/random-ids-for-safe-merge.md) を持つので、種目が二重にもならない
- **機種変更後の復旧**: 同上
- **2 台の統合**: もともと merge
- **特定時点まで巻き戻す**: これだけは merge でできないが、そのための道具は別にある（取り込み直後の「元に戻す」）

### 確認画面の役割が変わる。だから数字を直す必要がある

止める対象が消えたので、確認画面の役割は「全損を止める」から「**このファイルで合っているか / 何が増えるか**」に移る。

このとき、旧実装のまま「読込後 = 取り込むファイルの要約」を出し続けると**嘘になる**。1 日分の TSV を 42 日分の記録に足すとき、「読込後 記録 1 日」は取り込み後の姿ではない。**事故を止める唯一の道具が嘘をつくのが最悪**なので、マージを確認時に 1 回だけ走らせ、その結果を確認画面と適用の両方に使う。

副産物として:

- 表示した数字と実際に入る `Db` が**同じ計算の産物**になり、2 回計算して食い違う経路が構造的に消える
- `MergeReport` を押す**前**に持てるので、「7 日分 ・ 67 件の記録 を追加します」を予告できる
- `apply` が `db.set(merged)` + `replace_now` の 2 行になり、破壊的操作の本体が読み切れる長さになる

コストは stage 時の `Db` クローン 2 回。10 年分 1.24 MB でも数 ms で、年に数回の操作。`merge_db` は `IdGen` も時刻も使わない純関数なので、2 回走らせても副作用が無い。シートは `<dialog>` の modal（背景 `inert`）なので、確認中に `db` が変わる経路も無い。

## 結果（トレードオフ）

- **壊れた現データを丸ごと入れ替える道が UI から消えた。** 「今のデータを捨てて、このファイルの状態にする」ができない。取り込み直後なら「元に戻す」で戻せるが、任意の時点への巻き戻しは経路が無い
- **`Conflict::SetsDiverged` は残る。** 「絶対に何も変わらない」ではない — 同じ日の同じ種目でセットが食い違うと、取り込む側が勝つことがある。だから確認画面は残す
- **`Conflict` の 4 バリアントが全部、常時到達可能になった。** 置き換えでは 1 つも出なかったので、これは実質的に新しい表示経路。文言が複数行になるため `.backup-note { white-space: pre-line }` を足した（**これが無いと今も改行が潰れて読めていない**）
- **取り込み前の自動退避（`.pre-`）は残す。** merge が減らさないと言っても、`SetsDiverged` と「そもそも取り込みたくなかった」がある

## 検討した代替案

**置き換えを隠しオプションとして残す。** 折りたたみの中に置く案。却下 — 使う場面が無いものを、いちばん危険な操作として残すことになる。必要になったら「保管中のデータ」ごと別の形で作り直すほうがいい。

**現在のデータが空のときだけ置き換えを出す。** 空なら merge と結果が同じなので、出す意味が無い。

**確認画面も外して 1 タップにする。** `SetsDiverged` と `NameMatched` を見せる唯一の場所なので残した。ここは年に数回の導線で、1 タップ削るために「何が起きたか分からない」を買う取引にはならない。
