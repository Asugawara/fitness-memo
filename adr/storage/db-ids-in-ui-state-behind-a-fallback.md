# UI の状態に `Db` の ID を置いてよい条件を決める（寛容な受け口と既定への受け皿）

- **状態**: 採用
- **日付**: 2026-08-25
- **カテゴリ**: storage
- **関連**: [UI の状態を `Db` に入れず別キーに置く](ui-state-in-separate-key.md)（条件 1 をこの ADR で改訂）, [推移タブの対象を「部位 + 種目」の 2 セレクタにする](../ux/progress-target-as-group-plus-exercise-selects.md)（この条件を使う唯一の利用者）, [localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md), [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](share-sheet-over-download.md)

## 背景

[UI の状態を `Db` に入れず別キーに置く](ui-state-in-separate-key.md) は `fitness-memo/ui/v1` に 3 つの条件を課している。

1. **`Db` を一切参照しない。ID も日付キーも入れない**
2. 失われても害がない内容だけを置く
3. 移行も退避も持たせない

そのうえで同 ADR の「結果（トレードオフ）」節は、条件 1 が型で強制できないことを認めたうえで **`last_selected_exercise: ExerciseId` を「前提が崩れる例」として名指しで却下**している（「`Db` から種目が消えたときに宙に浮く」）。`src/views/mod.rs` の `OpenGroupCtx`（設定タブで開いている部位）も、この条件を根拠に**永続化せずプロセス内の寿命に留めて**ある。

[推移タブの対象を「部位 + 種目」の 2 セレクタにする](../ux/progress-target-as-group-plus-exercise-selects.md) の「最後に見た部位と種目を次回起動時に復元する」が、この却下例と同じ形で正面から当たった。

## 決定

**条件 1 を、次の 2 つを両方満たす場合に限って緩和する。**

1. **受け口が寛容であること。** `UiState` のフィールドは `Option<String>` で受け、`Id` への `FromStr` を通すのは `core` の純関数側でやる。壊れた値・知らない値で `UiState` 全体の deserialize が落ちてはならない
2. **宙に浮いた ID の受け皿が画面側に構造として存在すること。** 保存値が候補から消えていたら既定へ寄せ直す経路があり、それが `cargo test` と E2E の両方で固定されていること

満たす場合、そのフィールドは `Db` の ID を持ってよい。満たさない場合は今までどおり `OpenGroupCtx` のようにプロセス内の寿命に留める。

```rust
// storage: 生の文字列で持つ。検証はしない
#[serde(default)] progress_group: Option<String>,
#[serde(default)] progress_exercise: Option<String>,
pub fn saved_progress_pick() -> (Option<String>, Option<String>);
pub fn save_progress_pick(p: core::Pick);

// core（ホストのテストが届く側）: パースと「今も候補にあるか」の検証はここだけ
pub fn restore_pick(db: &Db, group: Option<&str>, exercise: Option<&str>) -> Pick;
```

## 理由

- **条件 1 の狙いは「宙に浮いた ID で壊れること」であって「ID を持つこと」自体ではない。** 元 ADR が守ろうとしたのは、[localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md) と同じ「参照整合性を実行時に検証するコードを増やさない」ことである。**検証を 1 箇所（`core::restore_pick`）に閉じ、そこがホストのテストで固定されているなら、増えるコードは 1 関数で済み、増えた分は型ではなくテストが押さえる。** 方針の文言ではなく方針の理由に照らして判断した（元 ADR 自身が単一キー方針に対して使った論法と同じ）。
- **受け皿は後付けではない。** 推移タブには**この改修より前から**「表示中の種目の記録を全部消すと候補から外れるので既定へ寄せ直す」`Effect` があった。ID を保存するために新しい安全網を足したのではなく、**既にある安全網の入口に保存値を 1 つ足しただけ**である。要件が「あるべき構造」を歪めていない。
- **`Option<String>` で受けるのは `lang` / `history` と同じ規律。** `Id` の `FromStr` は **12 文字ちょうどの Crockford base32 しか受けない**ので、手で編集された値や schema 2 以前の数値 ID の残骸が入っていると deserialize が失敗し、**`UiState` 全体のパースが落ちて `lang` と `history` と `install_hint_dismissed` まで巻き添えで消える**。`lang` が `Option<Lang>` でなく `Option<String>`、`history` が `Option<u8>` でなく `Option<i64>` なのとまったく同じ理由で、寛容な型で受けて丸め・検証を `core` に寄せる。
- **条件 2（失われても害がない）と条件 3（移行も退避も無し）は今までどおり満たす。** 消えても「記録がある先頭の種目」に戻るだけである。だから [パース失敗時は上書きせず退避する](quarantine-on-parse-failure.md) の退避も [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](storage-key-per-schema-generation.md) の世代切りも要らない。**回復手段の要否は、失ったときに何が起きるかで決まる**（元 ADR の判断基準をそのまま適用した）。
- **候補から落ちた ID は保存値からも落とす。** 読み替えるだけで放置すると、その種目の記録をもう一度作った瞬間に**選択が黙って戻る**（消したはずの対象が復活する）。復元時に「解いた結果が保存値と違えば書き戻す」を 1 行入れてある。一致していれば書かないので、ふつうのマウントで `localStorage` は触らない。
- **エクスポートに混ざらない性質は変わらない。** ID は `Db` を指すが、置き場所は `Db` の外なので [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](share-sheet-over-download.md) の TSV には載らない。**UI の状態は端末に属していてデータに属していない**という元 ADR の線は動いていない。

## 結果（トレードオフ）

- **レビューで見る点が 1 つ増えた。** 「ID を入れない」という単純な禁止が「ID を入れてよいが受け口と受け皿が要る」になった。禁止のほうが読み違えようがないぶん強かったが、要件を満たせない禁止を残すより、条件を書いて満たしたことをテストで示すほうがよいと判断した。
- **`storage` が `core::Pick` を知ることになった。** `save_progress_pick` は `Pick::ids()` を呼ぶので、`storage` → `core` の依存が 1 本増える。`history_count` で既にある向きなので新しい依存方向ではない。
- **別端末へ移らない。** バックアップを取って復元しても、最後に見ていた対象は移らない。今回の内容では望ましい（端末ごとに見たいものが違う）が、「移ってほしい UI 設定」が出てきたらこの置き場では扱えないのは元 ADR のままである。
- **`OpenGroupCtx` / `SettingsPageCtx` は非永続のまま。** 条件を満たせないからではなく、**満たす必要が無い**からである（記録⇄設定の往復に耐えればよく、アプリの再起動をまたぐ要求が無い）。同じ条件を機械的に全部へ広げると、`localStorage` の書き込みだけが増える。
- **E2E で「`Db` に混ざっていないこと」を固定した。** `fitness-memo/v3` の JSON に `progress_exercise` が含まれないことをテストしている。これが無いと、後から誰かが `Db` へ移しても気付けない。

## 検討した代替案

**永続化せず、プロセス内のコンテキストに留める**（`OpenGroupCtx` と同じ）: この ADR 自体が不要になり、元 ADR の条件 1 も無傷で済む。しかしタブの往復には耐えてもアプリの再起動には耐えないので、要件「最後に見た部位と種目を保存する」を満たさない。却下。

**ID ではなく種目名 / 部位名を保存する**: 文字列なので「`Db` の ID を入れない」の文面には触れない。しかし改名した瞬間に切れるうえ、**同名の種目を区別できない**（部位が違えば同名を作れる）。「宙に浮く」問題が消えるどころか、静かに別の種目を指す形に悪化する。却下。

**部位・種目の添字（`order` や並び順の位置）を保存する**: 数値なので受け口は寛容にできる。しかし並べ替えたときに**別の対象を指すのに検証は通ってしまう**。宙に浮いて既定へ落ちるほうが、黙って別物を出すよりはるかに良い。ID より悪い。却下。

**`Db` に `last_progress_pick` を足す**: 保存も読み込みも既存経路に乗り、参照整合性も `Db` の中で閉じる。しかし [JSON エクスポート/インポートを v1 に入れない](defer-export-import.md) が明示した「`Db` に UI 都合のフィールドを足さない」に正面から反し、書き出しに UI 状態が混入する。元 ADR が却下済み。却下。

**保存値の検証を `storage` 側でやる**（`saved_progress_pick` が `&Db` を受けて `Pick` を返す）: 呼び側は 1 行で済む。しかし `storage` は wasm32 専用なので、**検証ロジックにホストの `cargo test` が届かなくなる**。条件 2 の「テストで固定されていること」が成立しなくなるので、この ADR の前提そのものを壊す。却下。

**マウントのたびに検証結果を無条件で書き戻す**: 「候補から落ちた ID を残さない」を分岐なしで実現できる。しかし推移タブを開くたびに `localStorage` へ書くことになる。差分があるときだけ書く形で同じ結果が得られるので、無条件にする理由がない。却下。
