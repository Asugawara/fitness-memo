# ADR-0004: グラフライブラリを使わず SVG を自前で描く

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: architecture
- **関連**: [ADR-0001](0001-rust-leptos-csr-trunk.md), [ADR-0009](../data-model/0009-group-metric-is-set-count.md), [ADR-0045](0045-chart-layout-as-a-testable-module.md)（下の弱点を解消）, [ADR-0044](../ux/0044-body-weight-second-axis-always-on.md)（第2軸を追加）

> **一部改訂。** 下の「結果」に書いた `layout()` のテストが無いという弱点は
> [ADR-0045](0045-chart-layout-as-a-testable-module.md) で解消した（`src/chart_layout.rs` へ移設）。
> 描画の規則には [ADR-0044](../ux/0044-body-weight-second-axis-always-on.md) が
> 「体重を第2軸に常時重ねる」を足している。ライブラリを使わない決定そのものは有効。

## 背景

要件は「仕事量（レップ数×重さ）をグラフ化して過去と比較できる」。必要なのは折れ線 1 本、Y 軸グリッド、X 軸ラベル、タップで値を読む、これだけである。

Rust/WASM のグラフライブラリは `plotters`（canvas バックエンド）が代表的で、leptos 向けのラッパーもいくつかある。JS のライブラリ（Chart.js など）を `wasm-bindgen` 経由で呼ぶ選択肢もある。

## 決定

**ライブラリを使わず、`src/views/chart.rs` に SVG を自前で描く。**

```rust
const VIEW_W: f64 = 320.0;
const VIEW_H: f64 = 160.0;
const X0: f64 = 40.0;              // 左は Y ラベルのぶん空ける
const X1: f64 = VIEW_W - 10.0;
const Y0: f64 = 12.0;
const Y1: f64 = VIEW_H - 22.0;     // 下は X ラベルのぶん
```

`viewBox="0 0 320 160"` + `width:100%; height:auto` でレスポンシブにする。入力は `Vec<(NaiveDate, f64)>` と単位文字列だけで、部位別（セット数）も種目別（volume / 回 / 秒）も同じコンポーネントで描く（[ADR-0009](../data-model/0009-group-metric-is-set-count.md)）。

描画の規則を 5 つ置いた。

- **X は時間軸に比例配置**（等間隔ではない）
- **点数が 40 を超えたら `<circle>` を省略**し `polyline` と最新点のみ描く
- **「全期間」は週単位に集約**する（`core::aggregate_weekly`）
- **タップは点ではなく X 座標の最近傍点へスナップ**する
- 0 件は「記録がありません」、1 件は点のみ

## 理由

- **必要な機能が少なく、SVG で直接書くほうが短い。** `chart.rs` は 326 行で、レイアウト計算（`layout()`）と描画が分かれている。ライブラリを入れると設定 API の学習と、やりたいことが API で表現できるかの調査が発生する。
- **SVG は DOM なので leptos の signal で素直に更新できる。** canvas ベース（`plotters`）だと再描画を自分で管理し、要素のイベントも自前でヒットテストすることになる。`polyline` の `points` 属性を signal で差し替えるだけで済むほうが単純。
- **CSS 変数でダークモードに追随できる。** 見た目は極力 CSS クラスに寄せ（`--accent` などのトークンを使う）、SVG 属性には座標だけを置いた。canvas だと色を Rust 側にハードコードするか、`prefers-color-scheme` を JS で読んで渡すことになる。
- **バンドルサイズを増やさない。** [ADR-0001](0001-rust-leptos-csr-trunk.md) で WASM サイズを気にしている構成で、グラフのために依存を増やす理由が薄い。
- **X を時間軸に比例配置したのは要件のため。** 等間隔に並べると「3 週間休んだ」ことがグラフから消える。休んだ期間が空白として見えることが「これまでの比較」に合う。
- **タップのヒット領域を透明な `<rect>` の帯にしたのはタップターゲット規約のため。** `r=3` の `<circle>` は実機で直径約 7px しかなく、`min-height: 44px` の規約に反する。各点に「隣接点との中点まで」の帯（`band_x` / `band_w`）を持たせ、プロット領域の全高を覆う透明 `<rect>` で受ける。

## 結果（トレードオフ）

- **自前なのでエッジケースを全部自分で塞ぐ必要がある。** 実際に必要だったもの: 全値が 0 のときのゼロ除算（`y_max` に下駄を履かせる）、1 点だけ / 全部同じ日のとき X が定義できない（中央に置く）、0 件のとき（空表示に分岐）。ライブラリなら踏んでいない。
- **`view!` の名前空間の罠がある。** leptos_macro は要素名から HTML/SVG を解決する。`svg` / `g` / `line` / `polyline` / `circle` / `rect` / `text` / `tspan` は SVG リストに入っているので正しく解決されるが、**`<title>` / `<a>` / `<script>` は曖昧要素**で、親コンテキストが不明だと HTML 要素になる。SVG のアクセシブルネームに `<title>` を使うと、軸ラベルを別関数の `view!` に切り出すリファクタで無言に壊れる。**`role="img"` + `aria-label` を使って罠自体を回避した。**
- **SVG 属性は無検査で `setAttribute` される。** `view_box` や `stroke_width` のような snake_case のタイポは**コンパイルエラーにならず実行時に黙って無視される**（グラフが表示されないだけで、エラーも出ない）。綴りは `viewBox` / `stroke-width` / `text-anchor`。この 2 つの罠は `chart.rs` の冒頭にコメントとして残した。
- **点数が多いときの表示は妥協である。** 40 点超で `<circle>` を省くと、タップは効くが「どこに点があるか」が見えなくなる。1 年分を週集約すれば 52 点なので、この閾値では「全期間」以外は円が出る。
- **軸のラベル数を 3 個に固定した。** 期間が長いと粗く、短いと物足りない。自動調整は入れていない。
- グラフの見た目は E2E で検証しにくい。`chart.rs` のロジックは `layout()` に集めてあるが、wasm32 専用モジュールなので `cargo test` の対象外である。**`layout()` のテストが無いのは弱点で**、`core.rs` に移せばホストでテストできた（座標計算は純粋な関数である）。
  → [ADR-0045](0045-chart-layout-as-a-testable-module.md) で `src/chart_layout.rs` へ移設し解消した。`core.rs` ではなく別ファイルにしたのは、SVG の viewport 定数を「`Db` を読む純ロジック」に混ぜないため。

## 検討した代替案

**`plotters` の canvas バックエンド**: Rust では定番で、軸・凡例・複数系列が揃っている。しかし canvas なので再描画を自分で管理し、タップのヒットテストも座標計算から自前でやることになる（SVG なら DOM 要素にイベントを付けられる）。ダークモード対応も色を Rust 側に持つ形になる。必要な機能は折れ線 1 本なので割に合わない。却下。

**Chart.js を `wasm-bindgen` 経由で呼ぶ**: 機能は最も豊富。しかし JS 依存が 1 つ増え、`index.html` にスクリプトを足す必要があり、Service Worker の precache 一覧にも入る。Rust から使うためのバインディングを書く手間もある。却下。

**HTML の `<div>` を積んだ棒グラフ**: SVG より単純で、CSS だけで描ける。しかし X を時間軸に比例配置できず（休んだ期間が空白として見えない）、要件の「これまでの比較」が弱くなる。却下。

**スパークライン程度の簡易表示にする**: 「非常にシンプル」の要件には合う。しかし値を読めないグラフでは「同じかそれ以上をやる」という判断に使えない。タップで値を読める最小限は必要と判断した。
