# 種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない

- **状態**: 採用
- **日付**: 2026-08-09
- **カテゴリ**: data-model
- **関連**: [メモは種目カードのトグル 1 つで開き、閉じても薄字で残す](../ux/exercise-and-set-notes-behind-one-toggle.md)（画面側）, [「1日1種目1ログ」を不変条件にする](one-log-per-exercise-per-day.md), [`at` を `Option<i64>` にし当日入力時のみ埋める](at-optional-same-day-only.md), [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md), [localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md), [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md)

## 背景

自由記述を置ける場所は `Session.note`（その日の体調メモ）だけだった。「今日のベンチはフォームが崩れた」「3 セット目でセーフティに当てた」を書く場所が無い。

粒度が 2 つ要る。**種目単位**（その日のその種目）と**セット単位**。日単位のメモに「3 セット目で〜」と書くのは、どの種目の 3 セット目かを本文で言い直すことになる。

## 決定

### 1. 種目メモは `ExerciseLog.note`、セットメモは `SetEntry.note`。どちらも `String`

**種目マスタ（`Exercise`）には置かない。** 種目側に置くと毎日同じ注記が出て「今日そこがどうだったか」が書けない。`Session.note` が日単位である理由と同型。

`Option<String>` にしない。「`None`」と「`Some("")`」の 2 通りの空が生まれ、判定が全経路に散る。`Session.note` が `String` である先例に合わせる。

### 2. `SCHEMA` は 3 のまま。`storage::KEY` も切らない

`model.rs` の方針は「**フィールドを消す**変更は前方互換を壊す」であり、[保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md) の背景も `Exercise.kind` を**削除**したことが起点だった。今回は追加のみで、しかも:

- 旧版の serde は `deny_unknown_fields` を持たない（`model.rs` で意図的に不採用）ので、新版が書いた JSON を旧版は `note` を無視して読める。`migrate` が `Err` にならない = **退避パスに落ちない = 全損経路が発生しない**
- 決定 3 により、メモを使っていない利用者の JSON は**バイト単位で今までと同一**

KEY を切る積極的な害もある。v4 に切ると全利用者が「v3 から読んで v4 へ写す」経路を 1 回通り、失敗し得る移行を無駄に増やす。さらに v3 が読み取り専用で凍結され、localStorage を 1 世代分余計に食う（[localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md) の見積りに世代数が掛かる）。

### 3. 空のメモは JSON に書かない（`skip_serializing_if = "String::is_empty"`）

容量と互換の両方のため。空メモを毎セット書くと 1 セット ≈ 25 → 35 bytes（+40%）になり、[localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md) の「1 セット ≈ 30 bytes・10 年で約 1.1MB」に直接効く。

より重いのは互換のほう。`e2e/calendar.spec.mjs` と `e2e/backup.spec.mjs` の 3 箇所が `expect(session.logs[0].sets).toEqual([{ weight: 60, reps: 10 }])` で保存形式を固定している。`toEqual` は定義済みの余剰キーを不一致にするので、`"note":""` を常に書く実装にすると 3 本とも落ちる。**書き換えてしまえば、以後「保存形式が変わっていない」ことを誰も主張しなくなる。**

`Session.note` は昔から `"note":""` を書いており、そちらは**変えない**（既存の保存形式を今回の変更で動かさない）。

### 4. `SetEntry` から `Copy` を外す

`String` を持つので不可避。**全経路を洗ったうえで外している** — 本番コードで壊れた箇所は 1 つも無かった（参照する側は全て `&SetEntry` か `Vec<SetEntry>` の move / clone を通っている）。直したのはテスト内の構造体リテラルだけ。

### 5. セットが 0 本でもメモだけのログは残す。ただし「トレした日」にはしない

`Session::is_empty()` は既に「体重やメモだけが入っているセッションは空ではない（破棄するとコンディションのみの記録が消える）」と決めている。種目単位で逆の規則を採る理由が無い。

製品方針（トレ中の最短距離）で見ると、**許さない側が壊れる**。トレ中に「肩が痛いのでやめた」と種目メモに打つ。セットは 0 本。メモの commit とセットの commit は別の入口から来るので、`sets.is_empty()` でログを消す規則のままだと**次の 1 回のセット commit（行の ✕、`+ セット`、他の行の打鍵）でログごと消える**。カードの集合は `load_cards` が `session.logs` から引くので、カードごとその日から消える。

`core::dedupe_logs` の最終フィルタを `!l.is_empty()`（セットもメモも無い）に変えた。**ここは読み込みのたびに走る**ので、`!l.sets.is_empty()` のままだと画面に出ているメモが次回起動で消える — 保存と表示が食い違う最悪の形になる。

**一方で「メモがある」と「トレした」は別。** `Session::is_trained()` は `!sets.is_empty()` のままにし、カレンダーのドット・月フッタ・グラフ・経過日数・「前回」・`copyable`・`DbSummary` が見るフィルタは**1 つも変えていない**。`ExerciseLog.at` も、セットが 1 本以上あるときだけ押す（メモを書くのはトレーニングではないので、[`at` を `Option<i64>` にし当日入力時のみ埋める](at-optional-same-day-only.md) の「記録は起きたとおりに持つ」に従う）。

### 6. 「重量も回数も空でメモだけの行」は保存しない

`commit` の `parse_reps(&r.reps)?` フィルタはそのまま。通すと `0×0` のゴーストセットが生まれ、指標・`fmt_set` の「0」・`is_trained` のドット・コピーでの複製が全部汚染される（[数値入力に `type="number"` を使わない](../ux/text-input-not-number.md) が `Option` で潰した経路の復活）。

**セットメモはセットの付属物**という型の意味そのまま。「3 セット目がキツかった」は 3 セット目が無ければ指すものが無い。セットに紐づかないメモの置き場所は種目メモとして用意してあるので、逃げ道が上の階層にある。黙って捨てず、行に「回数を入れると保存されます」を出す。

### 7. `copy_day` / `copy_last` / `+ セット` はメモを複製しない

`copy_day` の既存コメント「体重と体調メモは複製しない。どちらもその日の観測値であってメニュー構成ではない」がそのまま当たる。「肩が痛い」「セーフティ 2 穴目」は**その日の観測**で、複製すると翌日に嘘の記録が生える。

`l.sets.clone()` は**メモまで運ぶ**ので、明示的に落としている。

重量をプリフィルするのとは扱いが違う。重量は**次のセットの計画値**、メモは**そのセットで起きたことの観測値**。[セット追加は直前行の重量をコピーして回数欄へフォーカスする](../ux/set-entry-prefill-and-focus.md) が引き継ぐ理由はメモには当たらない。

### 8. メモの合流規則は `append_note` の 1 本にする

`merge_db` が `Session.note` に持っていた重複ガード（`contains` で既出なら足さない）を関数に切り出し、`merge_same_day` / `dedupe_logs` / `merge_db` の 3 箇所で共有する。2 本目の規則を書いた瞬間にどれかが冪等でなくなる。

`merge_db` には**メモが消える経路が 2 つあった**ので、同時に直した:

- `existing.sets == log.sets` の早期 `continue` が取り込む側のメモを一切見ていなかった。`core::same_sets`（重量・回数のみを見る）に変え、一致するときはセットメモを**位置で**埋める
- `*existing = log` が取り込み先の種目メモを上書きで消していた。`std::mem::take` で持ち越す

`SetEntry` の `PartialEq` にメモが入ったので、**「同じセットか」の判定に `==` を使ってはいけない**。`==` のままだと「セットは同じでメモだけ違う」が食い違い扱いになり、`log_rank` が同点なので差し替えの分岐にも入らず、取り込む側のメモが `Conflict` も出さずに黙って捨てられる。将来「セット列が同じか」を問う箇所を足すときも `same_sets` を通すこと。

`log_rank` は**変えない**。メモの有無で「どちらのセットを採るか」が変わってはいけない（2 セットのログがメモ 1 個で 5 セットのログに勝つ形は論外）。

### 9. `MergeReport` に `notes_added` を足す。`DbSummary` は変えない

`MergeReport::is_noop()` が「新しく取り込むものはありませんでした」を出す。メモだけが追記されたケースでこの文言が嘘になるので数える。**追記は `conflicts` に出ない**ので、メモの冪等性を数で見る唯一の口でもある。

`DbSummary` にはメモ件数を足さない。あれは「取り込み事故を止める唯一の道具」で、守っているのは記録の規模（種目数 / 実施日数 / セット数 / 期間）。4 番目の数を足すと、事故を実際に止めている 3 つの数が 1 行の中で薄まる。メモだけの DB は `0 日・0 セット` と表示されるので、本物を置き換えようとした利用者には**明らかに異常に見える** = 確認が機能する側に倒れる。

## 理由

**「空白 = 無い」を 1 箇所で決める。** `normalize` に `blank_notes_to_empty` を足して、session / log / set の 3 階層の空白だけのメモを空文字にする。これが無いと `" "` が `skip_serializing_if` をすり抜けて保存され続け、`trim` する `is_empty()` と JSON の見え方がずれる。

**`legacy` は現行の `SetEntry` を再利用したまま。** schema ≤2 の JSON にメモは存在しないが、`note` が `#[serde(default)]` なので欠けていても読める。これが成り立つのは**`SetEntry` に足すフィールドが常に default を持つ**あいだだけなので、その条件をコードのコメントに書いた。破れば schema 1 / 2 の移行テストが `missing field` で落ちる。

## 結果（トレードオフ）

**旧版へロールバックして 1 操作すると、メモだけが落ちた JSON で上書きされる。** セット・重量・体重・体調メモは無傷なので、[保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md) が「全損 vs 巻き戻り」で許容した範囲より軽い。

**`append_note` のガードは部分一致なので、既存メモの部分文字列になる短いメモは足されない。** 「痛」が「肩が痛い」の中にあると新しいメモでも足されない。`Session.note` の既存挙動をそのまま踏襲したもので、冪等性のほうが短いメモの取りこぼしより重いと判断した。

**`drop_unrepresentable_weights` が捨てるセットのメモも一緒に消える。** メモはセットの付属物なので正しいが、無言の欠落なのでテストで固定した。発火するのは `3.5e38` のような壊れた取り込みだけで、UI からは入らない。

**`merge_db` でセットが食い違ったときは、負けた側のセットメモが失われる。** 種目メモは持ち越すが、セットメモはセットに従属するので一緒に置き換わる。

**「メモだけのログ」という新しい状態が増えた。** `is_trained` / `is_empty` の使い分けを間違えると退行する。`cargo test` の 27 本と E2E の 14 本が網。特に `migrate_keeps_a_log_that_only_has_a_note` と E2E の「種目メモだけの種目もカードとして残り、外すときは確認を経由する」は、`dedupe_logs` のフィルタを戻すと両方落ちることを実際に確認してある。

## 検討した代替案

**`ExerciseLog` に `set_notes: Vec<String>` を平行配列で持ち、`SetEntry: Copy` を守る。** `sets.len() == set_notes.len()` という不変条件を**全変更経路**が維持することになる。特に `drop_unrepresentable_weights` の `retain` は述語がインデックスを見ないので同期できず、**「メモが別のセットに付く」という無警告のデータ破損**を作る。`Copy` 1 個と引き換えにできる性質ではない。`BTreeMap<usize, String>` も同じ理由で却下。

**`SCHEMA` を 4 に上げて `storage::KEY` を v4 に切る。** 前方互換は壊れていないので得るものが無く、決定 2 の害だけが残る。

**空メモも `"note":""` として常に書く。** E2E 3 本を書き換えることになり、書き換えたあとは保存形式の不変を誰も主張しなくなる。容量も +40%。

**`legacy` に独自の `SetEntry` を切って凍結を厳格化する。** `#[serde(default)]` がある限り再利用は安全で、破れば schema 1 / 2 のテストが落ちる。`upgrade_from_sequential`（このファイルで最も繊細な関数）に写像を 1 段増やすリスクのほうが大きい。

**`log_rank` の tie-break にメモを足す。** 同点のときメモがあるほうを採ると、`*existing = log` で自分側のセットメモを失う。位置で埋める（決定 8）ほうが情報を失わない。

**`Conflict` にメモ用の variant を足す。** メモは常に追記で上書きしないので、「食い違い」が存在しない。
