# ID を 60 bit 乱数にし、プリセットには固定 ID を与える

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: data-model
- **関連**: [ID を `next_id` の連番にし uuid を使わない](sequential-ids-no-uuid.md)（置換）, [JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md), [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md), [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](../storage/share-sheet-over-download.md)

## 背景

データの書き出し / 読み込みを実装するにあたり、連番 ID（[ID を `next_id` の連番にし uuid を使わない](sequential-ids-no-uuid.md)）が**壊れることが分かった**。

同じ種目を登録順だけ変えて登録した 2 台を考える。

| | 端末 A | 端末 B |
|---|---|---|
| id=1 | 胸 | 背中 |
| id=2 | ベンチプレス | デッドリフト |

A の `exercise_id = 2`（ベンチプレス）のログを B に取り込むと、B では id=2 = デッドリフトを指す。**`migrate()` はこれを正常なデータとして受理する**のでエラーも警告も出ず、気づくのは数か月後にグラフを見たときになる。

さらに悪いのは形式の固定化である。**`"exercise_id": 10` を含むファイルが 1 つでもユーザーの iCloud Drive に保存されたら、その形式をアプリの寿命の間ずっとサポートし続けなければならない。** localStorage のキーは世代を切れる（[保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md)）が、ユーザーの手元のファイルにはバージョン交渉の手段がない。**ID 移行はエクスポート機能より前にしか実施できない。**

## 決定

**ID を 60 bit の乱数にする。** `Copy` な newtype で持ち、JSON では 12 文字の Crockford base32 **文字列**として直列化する。

```rust
pub struct Id<T>(u64, PhantomData<T>);
pub type GroupId = Id<GroupTag>;
pub type ExerciseId = Id<ExerciseTag>;
```

同時に 3 つを決める。

1. **予約領域を作る。** `RESERVED_MAX = 1024` 未満は `IdGen` が引かず、プリセット 34 件の固定 ID に充てる。部位ごとに 16 個ずつのブロック（胸 = `0x10`、ベンチプレス = `0x11`…）
2. **部位 ID と種目 ID を型で区別する。** `db.group(exercise_id)` がコンパイルエラーになる（[ID を `next_id` の連番にし uuid を使わない](sequential-ids-no-uuid.md) が既知の欠陥として挙げていた点）
3. **`schema` を 3 に上げ、保存キーを `fitness-memo/v3` に切る**（[保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md) の作法どおり）

## 理由

### なぜ固定プリセット ID が本体なのか

[ID を `next_id` の連番にし uuid を使わない](sequential-ids-no-uuid.md) は「固定 ID はユーザー作成の種目と衝突するので採れない」と書いていた。この制約は予約領域を持つ乱数 ID では消える（乱数が予約領域を引かないので、構造的に衝突しない）。

**固定 ID が無ければ、乱数化する意味はほとんど無い。** 別々に初期化された 2 台では「ベンチプレス」の ID が違うので、マージは名前突合に落ちる。片方で改名していれば別種目として重複し、履歴が 2 本に割れる。固定 ID があれば、プリセット由来の種目（実データの大部分）は 2 台で構造的に同一 ID になり、改名していても ID で追跡できる。

つまり **ID の乱数化は「衝突を防ぐ」ためであり、固定 ID は「同一性を保つ」ため**で、両方揃って初めてマージが成立する。

### なぜ UUID v4 ではないのか

| | JSON 10 年 | 衝突確率 (N=10⁴) | views への影響 |
|---|---|---|---|
| 現行 u32 | 1.10 MB | — | — |
| **12 文字 base32** | **1.24 MB** | **4×10⁻¹¹** | **約 20 行** |
| UUID v4 | 1.47 MB | 9×10⁻³⁰ | 同上 |

サイズは決定要因ではない（5 MiB 上限に対してどちらも十分小さい）。12 文字を選んだのは**デバッグ時に目で読めるから**で、衝突確率 230 億分の 1 は端末が壊れる確率より低い。

### なぜ JSON で数値にしないのか

u64 は 2^53 を超えるので、`JSON.parse` → `JSON.stringify` の往復で丸められる。`e2e/smoke.spec.mjs` は実際にこの往復をやっており、**数値にしていたらテストハーネス自身がこのバグを踏む**。文字列ならこの経路が構造的に消える。

### なぜ `Copy` な newtype なのか

`menu.rs` の `Editor` と `progress.rs` の `Target` が `#[derive(Copy)]` で ID を保持しており、`move ||` クロージャは実測 187 個ある。`String` にすると `Copy` を失って `.clone()` が広範囲に波及する。newtype なら views の変更は約 20 行に収まった。

### 乱数の種

`storage::crypto_seed` が `getRandomValues`（iOS 6.1+）から 1 回だけ引く。`randomUUID`（Safari 15.4+）ではなく前者を使うのは対応幅が 9 年広いため。

**種を `Db` に入れてはいけない。** 入れるとエクスポートで PRNG の状態ごと複製され、2 台が同じ ID 列を生成するようになる（それは連番より悪い）。`thread_local!` に置く。

`crypto` が使えない環境のフォールバックに**時刻だけを使ってはいけない**。2 台が同じミリ秒に初回起動するとシードが一致し、以後まったく同じ列を生成する。高精度時刻とアドレスを混ぜて分岐させる。

## 結果（トレードオフ）

- **`core` は純ロジックのまま。** `IdGen` を引数で受け取るので `web-sys` に触れず、`IdGen::from_seed(定数)` でホストの `cargo test` が決定的に回る（新しい trait も `#[cfg]` 分岐も導入していない）
- **`next_id` と `Db::alloc_id` が消えた。** 採番は `storage::alloc_id`（wasm）か `IdGen`（テスト・移行）を通る
- **JSON が 12% 増える**（10 年で 1.10 → 1.24 MB）。5 MiB 上限に対しては変わらず十分
- **v2 → v3 の移行時、名前がプリセットと一致する種目 / 部位を固定 ID へ寄せる。** ただし **一致が「ちょうど 1 件」のときだけ** — `rename_exercise` / `rename_group` に重複チェックが無いので同名 2 種目が存在しえて、両方を同じ固定 ID に寄せると**別々の種目の履歴が無警告で 1 本に合流する**（この移行が潰そうとしているバグと同型）
- **プリセットの固定 ID は二度と変えられない。** 変えると既存ユーザーの端末で同じ種目が 2 つになる
- **`seed()` の判定を名前から固定 ID に変えた。** 名前で見ていた頃の「改名済みプリセットが別種目として復活する」は軽微な挙動だったが、固定 ID の下では**同一 ID の種目が 2 つできる**不変条件違反に化ける

## 検討した代替案

**u32 のまま、マージ時に取り込む側の ID 空間へ再採番する**: 正しさは完全で、実装は約 60 行、マイグレーション不要。ただし**インポートのたびに ID が捨てられる**。iPhone → iPad へ移行すると iPad の「ベンチプレス」は別 ID になり、そこで改名して iPhone へ戻すと ID も名前も一致せず、履歴が 2 本に割れる。「衝突を防ぐ」だけなら足りるが「同一性を保つ」には足りない。却下。

**端末プレフィックス + 連番**: 全置換インポートで端末 ID ごと複製され、以後 2 台が**確定的に**同じ ID を生成する。今より悪い。却下。

**ULID / KSUID**: 生成に時刻が要り、`core` の `cargo test` が実行時刻に依存する。時系列は `order` と日付キーで足りている。却下。

**`#[serde(untagged)]` で数値と文字列の両方を受ける**: 機械的には書けるが、数値 → Id の写像が決定的である以上、A の `f(2)` と B の `f(2)` が同じ値になる。**移行が済んだように見えてマージのバグだけが生き残る**、最悪の結果になる。却下。

## 補足: [ID を `next_id` の連番にし uuid を使わない](sequential-ids-no-uuid.md) の技術的根拠について

[ID を `next_id` の連番にし uuid を使わない](sequential-ids-no-uuid.md) は uuid を避ける理由として「`getrandom` は `wasm_js` feature に加えて `RUSTFLAGS` の cfg を要求する」と書いていたが、現在の `Cargo.lock` の getrandom は 0.4.3 で、**cargo feature だけで足りる**（`RUSTFLAGS` は不要）。当時の記述は 0.3 系に基づくもので、今は成立しない。

ただし本 ADR は `getrandom` も `uuid` も使わない（`web-sys` の `Crypto` feature 1 行のみ、新規クレートはゼロ）ので、結論に影響はない。
