# ADR を `adr/` にカテゴリ別で置く

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: process
- **関連**: [GitHub Pages の branch deploy（`release` / `docs`）を使う](../deploy/github-pages-branch-deploy.md), [実装前に敵対的レビューを回す](adversarial-review-before-implementation.md)

## 背景

このプロジェクトには「動くコードを読んでも分からない判断」が多数ある。

- `chrono` の default features を削ってはいけない
- `web-sys` の feature を leptos 任せにしてはいけない
- Service Worker で `cache.put` してはいけない
- `git switch --orphan` で `release` を作ってはいけない
- リポジトリ設定の Actions 機能を無効化してはいけない

いずれも**やってしまうと動くところまでは行って、後で静かに壊れる**類のもので、コードには「やらなかったこと」が残らない。コメントで断片的に残してはいるが（実際 `Cargo.toml` と `sw.js` には警告コメントがある）、理由の全体と却下した代替案までは書けない。

文書の置き場所として一般的なのは `docs/adr/` である。しかしこのプロジェクトでは使えない。

## 決定

**ADR を `adr/` に置き、カテゴリごとにディレクトリを分ける。番号は全カテゴリ通し番号にする。**

```
adr/
├ README.md                    索引
├ architecture/  0001-0004     技術選定と全体構造
├ data-model/    0005-0010     データ構造と不変条件
├ storage/       0011-0014     永続化
├ pwa/           0015-0020     オフライン動作と iOS 実機
├ ux/            0021-0024     画面と操作
├ deploy/        0025-0029     配信とブランチ運用
└ process/       0030-0032     進め方
```

各 ADR のフォーマットは「メタ情報（状態 / 日付 / カテゴリ / 関連）+ 背景 / 決定 / 理由 / 結果（トレードオフ）/ 検討した代替案」の 5 節。状態は `採用` / `置換済み` / `破棄`。

## 理由

- **`docs/` が使えない。** GitHub Pages の branch deploy は公開ディレクトリが `/` か `/docs` の 2 択で、本プロジェクトは `release` ブランチの `/docs` をビルド成果物の配信元にしている（[GitHub Pages の branch deploy（`release` / `docs`）を使う](../deploy/github-pages-branch-deploy.md)）。さらに `scripts/release.sh` は毎回 `rm -rf docs` で作り直し、`.githooks/pre-commit` は `main` への `docs/` コミットを拒否する。**`docs/` に文書を置くとコミットできず、仮に入っても消される。** 慣習より機構が優先する。
- **カテゴリ別ディレクトリにしたのは、判断の性質が大きく異なるため。** データモデルの不変条件と git のブランチ運用は、読む場面も読む人も違う。「デプロイで詰まった」ときに `deploy/` の 5 本だけ読めばよい形にした。
- **番号は通し番号にした。** カテゴリ別に振り直す（`data-model/0001`）とカテゴリをまたぐ参照が `data-model/0001` と `deploy/0001` で曖昧になる。通し番号なら「[`visibilitychange` の hidden で debounce を flush する](../storage/flush-on-visibilitychange.md)」だけで一意に指せる。
- **「検討した代替案」を必須の節にしたのが最も重要である。** ADR の価値は決定内容ではなく、**なぜ他の案を採らなかったか**にある。決定内容はコードを読めば分かるが、却下理由は消える。実装者が「これ、こうしたほうが良くない?」と思ったときに、既に検討して却下した理由が読めるかどうかで再検討のコストが桁違いになる。[実装前に敵対的レビューを回す](adversarial-review-before-implementation.md) の敵対的レビューで却下された案が大量に記録されているので、素材はある。
- **「結果（トレードオフ）」も必須にした。** 良いことしか書いていない ADR は役に立たない。実際に受け入れたコスト（`Db` 全体のクローン、`u32` の型が取り違えを防がない、部位別グラフでは強くなったか分からない、`SKIP_HOOKS=1` で CI を飛ばせる）を書いておかないと、後から見て「この決定は完璧だった」と誤読される。
- **`関連` でリンクを張るのは、判断が連鎖しているため。** 「`localStorage` の同期 API を選んだ」→「だから hidden で flush できる」→「だから最後のセットが消えない」のように、1 つの決定が別の決定の前提になっている。リンクがないと個々の判断が孤立して見える。

## 結果（トレードオフ）

- **一般的な慣習（`docs/adr/`）から外れる。** ADR ツール（adr-tools など）は既定で `doc/adr` や `docs/adr` を見るので、そのまま使えない。ツールを使わず手で書いているので実害はないが、外部から見て見つけにくい。`README.md` の冒頭に理由を書いた。
- **索引（`adr/README.md`）を手で維持する必要がある。** ADR を追加したら索引にも行を足す。自動生成していないので、ずれる余地がある。実際に索引を先に書いて本文を後から書く運用（このプロジェクトの並列実装）では、**索引にあって本文が無い期間が存在する**（リンクが 404 になる）。
- **番号が通し番号なので、カテゴリの途中に追加できない。** 後から storage の 5 本目を書くと `0033` になり、`storage/` の中で `0011-0014, 0033` と番号が飛ぶ。カテゴリ内の連続性は保証されない。
- **ADR が 32 本ある。** 全部読むのは負荷が高い。カテゴリ分割と索引でナビゲートできるようにしたが、「まずどれを読むべきか」の指針はない。データモデル（0005-0010）と storage（0011-0014）が最も踏みやすい落とし穴を含んでいるので、そこから読むのが実用的である。
- **実装と ADR がずれる可能性がある。** ADR は実装を読んで事実を確認してから書いているが、その後に実装が変われば ADR が古くなる。状態に `置換済み` を用意したが、更新の強制力はない。
- **書くコストが実際にかかっている。** 32 本 × 40〜80 行で、実装 1 フェーズ相当の分量である。このプロジェクト固有の事情（技術スタックの落とし穴が多い、並列実装で複数のエージェントが同じ判断を再発明しうる、利用者が後から読む）を踏まえて割に合うと判断した。落とし穴の少ないプロジェクトなら過剰である。

## 検討した代替案

**`docs/adr/` に置く（慣習どおり）**: ツールとの互換性があり、外部から見つけやすい。しかし `.githooks/pre-commit` が `main` への `docs/` コミットを拒否し、`release.sh` が `rm -rf docs` するので**物理的に置けない**。選択肢として成立しない。

**コード内のコメントだけで済ませる**: 判断が使われる場所の隣にあるので、読み飛ばされにくい。実際に `Cargo.toml` / `sw.js` / `storage.rs` には警告コメントを置いている。しかし「却下した代替案」と「トレードオフ」はコメントに収まる量ではなく、しかも複数ファイルにまたがる判断（例: `localStorage` の同期性 → flush → 最後のセットが消えない）を 1 箇所に書けない。**併用**が正解で、コメントは「これを消すな」の警告、ADR は「なぜそうしたか」の記録という役割分担にした。

**計画書 1 ファイルをそのまま残す**: 既に存在する（`~/.claude/plans/…`）ので追加コストがゼロ。しかし計画書は時系列で書かれており、「storage の判断を知りたい」という引き方ができない。またリポジトリ外にあるので、コードと一緒に配布されない。ADR はその再構成として、判断単位で引けるようにしたものである。

**GitHub の Discussions / Issues に書く**: 議論の経緯が残り、コメントも付けられる。しかしリポジトリを clone しただけでは読めず、オフラインでも読めない。コードと同じ場所にある文書のほうが陳腐化に気づきやすい。却下。

**カテゴリを分けず `adr/0001-….md` とフラットに置く**: 索引が 1 つで済み、番号と場所が一対一になる。32 本がフラットに並ぶと目的の 1 本を探しにくいので、カテゴリで分けた。ADR が 10 本程度ならフラットで足りた。
