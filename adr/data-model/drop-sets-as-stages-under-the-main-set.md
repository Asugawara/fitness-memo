# ドロップセットをメインセットにぶら下がる段（`SetEntry.drops`）として持つ

- **状態**: 採用
- **日付**: 2026-09-09
- **カテゴリ**: data-model
- **関連**: [ドロップセットの段はメインセットの下の箱に出し、推移では既定で外す](../ux/drop-sets-as-a-box-under-the-main-set.md)（画面側）, [種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md), [ランダム ID で安全にマージする](random-ids-for-safe-merge.md), [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md), [取り込みはマージのみ](../storage/import-is-merge-only.md), [書き出しの見出しは UI の言語に従う](../storage/tsv-header-follows-the-ui-language.md), [コピーは種目メモとセットメモを持ち込む（体調メモと体重は持ち込まない）](../ux/copy-carries-the-notes.md)

## 背景

ドロップセット（限界まで挙げてから重量を落として続けるやり方）を記録する手段が無かった。

普通のセットとして入れると **推移タブの数字が実際より大きく出る**。ボリュームは落とした段のぶん膨らみ、セット数も増える。「前回と同じかそれ以上をやる」ためにグラフを見ているのに、その基準値が日によって膨らむ。かといって記録しなければ、その日やった仕事が残らない。

セットの種類を表す概念はこれまで持っていなかった。schema 2 で `Exercise.kind`（加重 / 自重 / 時間）を**削除**しており、その理由は「種目名を見れば分かることをユーザーに選ばせる意味が無かった」。今回は種目の属性ではなくセットの属性で、しかも種目名からは分からない（同じベンチプレスの 3 セット目が落とした段かどうかは、やった本人にしか分からない）。

**利用者の言葉**: 既存のセット行はメインセットで、ドロップセットはそれとは別に出てくるものであってほしい。

## 決定

### 1. `SetEntry.drops: Vec<DropStage>`。**メインセットの下に段がぶら下がる**

`DropStage` は `{ weight: f32, reps: u32 }` だけ。メインセットの重量・回数は `SetEntry` の `weight` / `reps` のままで、`drops` には**落とした段だけ**が入る。

一度は「落とした段も普段どおり 1 セットとして記録し、`drop: bool` の印を立てる」形で作ったが、**画面の意味が合わなかった**。既存のセット行はメインセットとして読まれるので、そこに印を立てる形は「このセットはドロップだ」と言うことになり、「メインセットから落とした」という関係が残らない。関係が残らないと:

- 3 セット目から落としたのか 1 セット目から落としたのかが記録に無い
- 同じ種目で 2 回ドロップしたときに区別できない
- 「メインセットは推移に残し、落とした段だけ外す」を**印の付け方の運用**で守ることになる（トップセットに印を付けてしまえば壊れる）

段としてぶら下げれば、その 3 つが構造で決まる。**推移から段を外してもメインセットは必ず残る。**

### 2. `SCHEMA` は 3 のまま。`storage::KEY` も切らない

[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) の決定 2 とまったく同じ理由。`model.rs` の方針は「**`#[serde(default)]` を持つフィールドの追加では上げない**」で、ここで上げると旧版が `RestoreError::Unsupported` で退避するので **前方互換を積極的に壊す側になる**。

`mod legacy`（schema ≤2 の JSON）が現行の `SetEntry` を再利用しているので、**default を持たないフィールドは足せない**という制約もそのまま効いている。`Vec` は `#[serde(default)]` で空になる。

### 3. 段の無いセットの JSON はバイト単位で今までと同一（`skip_serializing_if = "Vec::is_empty"`）

`note` と `Db::routines` と同じ。`e2e/smoke.spec.mjs` の「メモを使っていないデータの保存 JSON に note キーが増えていない」と `calendar` / `pwa` の `toEqual([{ weight: 60, reps: 10 }])` が、`toEqual` が余剰キーを不一致にする性質を使って保存形式を固定している。**書き換えてしまえば、以後「保存形式が変わっていない」ことを誰も主張しなくなる。**

### 4. 段数の上限は 4（`MAX_DROPS`）

実際のドロップセットは 1〜3 段で、4 段目から先は「セットを分けたほうが読める」領域。上限があること自体は `MAX_PINS` と同じ理由で、取り込みの門番であり、localStorage 単一キーの見積りを無制限にしないため。

### 5. `set_volume` はメインセットぶんだけ。段は `counted_drops` が別に数える

**`set_volume` に段を足し込まない。** `Metric::Sets` は本数を数えるので、1 セットの値を 0 にするやり方では設定が効かない。`log_value_of(m, l, Drops)` が 3 指標すべてで段の扱いを揃える:

| | Exclude | Include |
|---|---|---|
| Volume | Σ メインセット | + Σ 段 |
| Sets | メインセットの本数 | + 段の数 |
| Reps | Σ メインセットの回数 | + Σ 段の回数 |

**`Exclude` は段を入れる前の挙動とビット単位で同じ**（既存データに段は無いので）。既存の `log_value` は `log_value_of(.., Drops::Include)` として残し、記録タブ・カレンダー・`log_rank` が何も書き換えずに従来どおりになる。

`Sets` だけ段を数えないような食い違いを作ると、同じ設定で「ボリュームは増えたのにセット数は変わらない」が起きて、利用者は設定が効いているのか壊れているのか区別できない。**分岐は `counted_drops`（`Exclude` なら空スライスを返す）に畳んである**ので、3 つの腕はどれも「メインセット + 段」の同じ形になり、腕を足したときに片方だけ数え忘れられない。重量 × 回数の式も `volume()` の 1 本を共有する（`max(1.0)` の単調性を 2 箇所で持たない）。

### 6. 落とし幅（%）を設定に持ち、**1 段目の重量だけ**を先に計算して入れる

`core::dropped_weight(main_weight, pct)` が `メインセットの重量 × (1 − pct/100)` を小数点以下 1 桁で返す。既定は 20%（60 → 48 / 100 → 80 という最も普通の刻み）。

- **落とし幅を掛けるのは 1 段目だけ。** 2 段目以降は**前の段の重量をそのままコピー**する。もう一度掛けると、実際の刻みは段ごとに変わる（20% → 20% とは限らない）ので当たらない数字になる。前の段を持ってくれば「同じか、そこから下げる」のどちらでも打ち直しが最小になる（`views::day` の `add_row` が前の行の重量を引き継ぐのと同じ規則）
- **回数は入れない。** まだ挙げていないので観測が存在しない（`add_row` がメモをプリフィルしないのと同じ線）
- **重量の無いメインセット（自重種目）は `None`。** 掛ける相手が無いので、0 を入れるより空のままにする
- **自由入力。** 刻みは人によって違う（10 / 12.5 / 20 …）ので、選択肢を先に決めると必ず外れる。ただし `0..=MAX_DROP_PCT`（95）に `clamp` する — 100 を通すと計算結果が 0kg になり、`set_volume` の「重量なし = 重量 1」に化けて自重種目の扱いになる

### 7. 「同じセットか」の判定に段を入れない

`core::same_sets` / `same_sets_unordered` / `log_rank` は重量と回数だけを見る。**`note` とまったく同じ扱い。**

入れると `merge_db` で次のことが起きる。段の差だけで「食い違い」の枝に落ち、しかも `log_rank` は同点なので差し替えの分岐にも入れない。結果、取り込む側のセットメモが `Conflict` も出さずに黙って捨てられる。これは `same_sets` が `==` ではなく専用関数である理由そのもの。

### 8. その代わり、取り込みでは**段が空のセットにだけ**入れる

識別から外した以上、合流の一手が無いと他端末で入れた段が黙って消える。`merge_db` の 2 つの枝で運ぶ:

- `same_sets`（並びも同じ）: 位置対応の `zip` の中で、`mine.drops` が空なら `theirs.drops` を入れる
- `same_sets_unordered`（並べ替えただけ）: `merge_set_drops_unordered`

**両方に段があって中身が違うときは取り込み先を残す。** `append_note` の「同じ文が既に入っていれば足さない」と同じ、足さない側に倒す判断。`Conflict` も出さない — 出すと同じファイルを 2 回入れるたびに同じ食い違いを報告する。

`log_rank` の枝は `*existing = ExerciseLog { note, at, ..log }` で `sets` を丸ごと差し替えるので、**勝った側の段が残る**。今のセットメモとまったく同じ扱い（負けた側のセットメモも同様に消える）。`dedupe_by_exercise` の `*existing = log` も同じ。

### 9. 合流は **2 段**でやる。1 段だと同じデータを初めて取り込んだだけで段が増える

`merge_set_notes_unordered` を真似て「段付きの相手を、同じ重量・回数の未使用な先頭に入れる」と 1 段で書くと壊れる:

```text
mine   = [(60,10,"A"), (60,10,段あり), (70,5)]
theirs = [(70,5),      (60,10,段あり), (60,10,"A")]   // 並べ替えただけの同じ記録
```

あちらの段付き `(60,10)` がこちらの **段の無い** `mine[0]` に当たり、段が 2 セットに付く。同じ重量・回数の行が並んでいる記録は珍しくないので、これは日常的に踏む。

だから順序を決める。

1. `theirs` の段付きを、**まず同じ段を既に持っている**未使用の一致に消費する（何も変えないので数えない）
2. 余ったものだけが、段の無い一致に入る

`merging_the_same_data_does_not_invent_a_drop_stage` がこれを固定している。

> **メモ側のパスは鏡像の同じ欠陥を持っている。** `mine = [(60,10,""), (60,10,"A")]` / `theirs = [(60,10,"A"), (60,10,"")]` でメモが両方の行に付く。`append_note` の冪等ガードがあるので 2 回目以降は増えないが、1 回目の付き先は任意。**今回は直さない**（範囲外で、しかも `notes_added` の期待値を変える）。「メモと同じやり方で」を新しいフィールドの手本にしないこと。

### 10. `MergeReport.drops_added` を足す

段だけが増えたマージは `conflicts` に出ない（決定 7 でそう決めたので）のに、**推移タブの数字が動く**。数えないと `is_noop` が真になり、画面が「新しく取り込むものはありませんでした」と嘘をつく。`notes_added` がまさにこれを防ぐために存在している。`views::backup::added_text` にも同時に足す — 片方だけだと `is_noop` が偽なのに文言の部品が空になる。

### 11. `normalize` で回数 0 の段と上限超えを落とす

`prune_empty_drops` を `blank_notes_to_empty` の隣に置く。**「段が在る」を 1 箇所で決める。**

実体は `clean_drops`（`clean_pins` / `clean_interval` の隣）で、**回数 0・`f32` で表せない重量・上限超え**の 3 つをまとめて落とす。`prune_empty_drops` はそれを呼ぶだけ。

これが無いと、取り込みや手編集で入った `reps: 0` の段が `drops` を非空にして、推移タブの注記（「ドロップセットの段は含めていません」）が**何も外していないのに出る**。`"weight":null` を落とさなければ次回起動の `Db` のパースが丸ごと落ちる（メインセットで潰した経路と同型）。

★ **`parse_drops_cell` は上限を切らない。** `parse_tsv` は最後に必ず `normalize` を通るので、パーサ側で切ると規則が 2 本に割れる（`parse_interval` が上限で丸めないのと同じ理由）。

### 12. TSV は 1 セル。`50×5 40×4` のように半角空白で並べる

足さないと、書き出しで段が静かに消える。消えたぶんは推移に混ざり直すので、**機種変更のあとでグラフが勝手に増える**。

- **`ピン` 列と同じ流儀**（1 セル 1 要素にせず空白で並べる）。段は 1 セットに最大 4 個なので、列を段数ぶん増やすより 1 セルに畳むほうが「1 セット 1 行」を壊さない
- **位置は `回数` の隣。** セット単位の列なので、種目単位の `ピン` / `インターバル秒` と並べるとシートを縦に読んだときに意味の階層が崩れる。位置が動いても取り込みは `tsv_header` が名前で引く（`TsvCols` は位置フォールバックを明示的に持たない）ので、旧 14 列のファイルも新版も往復が閉じる
- **見出しは `ドロップ` / `Drop set`。** `Drop` 単独にしないのは、`is_known_header_cell` が `NotDb`（うちのファイルではない）と `NoHeader`（うちのファイルだが壊れている）を分けるのに見出し配列を使うので、ありふれた列名を入れると無関係な TSV が「壊れたうちのファイル」に化けるため。`Drop` と `ドロップセット` は**読み取り専用の別名**として受ける（`重量` と同じ手）
- **取り込みの綴りは書き出しより広い。** 区切りは空白 / タブ / 読点 / カンマ / セミコロン、掛け算記号は `×` `x` `X` `*`。読めない要素は黙って捨てる（行ごと落とすほどではない）

### 13. コピーの 3 経路は段を運ぶ

`copy_day` / `apply_routine` / `views::day` の `copy_last` すべて。[コピーは種目メモとセットメモを持ち込む（体調メモと体重は持ち込まない）](../ux/copy-carries-the-notes.md) と同じ 1 本の規則にする。

コピーは「過去のログを再現する」操作で、しかも**段はメモを閉じていても行に見える**（画面側 ADR の決定 5）ので、違えばその場で消せる。**`+ セット` は運ばない** — あちらが作るのはまだ起きていない次のセットで、段が勝手に入ると既定で推移から外れる重量が黙って生まれる。

`Seed::carry` は **`SetEntry` まで分解して組み直す**ようにした。`ExerciseLog` の分解ガード（「足した新しいフィールドがここを黙って素通りするのを止める」）が 1 階層下で破れていて、`sets.clone()` は新しいフィールドを判断なしに運んでいた。

## 理由

**`Vec<DropStage>` を `SetEntry` の中に置く。別のトップレベルの型にしない。** 段はメインセットが無ければ意味を持たない（何から落としたのかが決まらない）ので、参照ではなく所有で持つ。`Session.logs` が `Vec<ExerciseLog>` を所有しているのと同じ形で、宙に浮いた段が構造的に作れない。

**`DropStage` にメモを持たせない。** 段ごとに書くことが実際に無い（書きたいことはメインセットの `note` に付く）。持たせると `merge_set_notes_unordered` と同型の合流ロジックが段の階層にもう 1 本必要になる。

**段の数え方を 3 指標で揃える理由**は上の決定 5 に書いたとおりだが、もう 1 つある。`Metric::Sets` で段を数えないと「Volume だけ増える」ので、`Sets` を見ている人には設定が**存在しないように見える**。設定が効いていないのか自分の理解が違うのかを、画面から区別できない。

**落とし幅を `Db` ではなく `fitness-memo/ui/v1` に置く。** [指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md) と同じ立ち位置 — 記録された事実ではなく、次の入力を楽にするための好み。消えても既定に戻るだけなので、退避も世代切りも要らない（[UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md) の 3 条件を満たす）。

## 結果（トレードオフ）

- **2 段目以降は前の段のコピーなので、下げるときは必ず打ち直す。** 段ごとに「前の段から N%」を連鎖させる案もあったが、実際の刻みは段ごとに変わる（20% → 20% とは限らない）ので、当たらない数字を作ることになる。コピーなら「同じ重量で回数だけ落ちた」段は打ち直しゼロで済む
- **落とし幅が 1 つしか無い。** 種目ごとに違う刻みを使う人には合わない。種目に持たせる案（`Exercise.interval_sec` の先例）はあるが、設定 1 つで足りるかを先に確かめる
- **両方に段があるときは取り込み先が勝つ。** 端末 A で 3 段、端末 B で 2 段にしたときに B から取り込んでも A は 3 段のまま。`Conflict` も出ないので気づけない。メモの合流と同じ「足さない側に倒す」判断で、**捨てるより残すほうがまし**という選択
- **`log_rank` の枝では負けた側の段が消える。** セットメモが同じ条件で消えているのと同じで、新しく作った穴ではない
- **TSV の列が 15 本になった。** 見出しは足した時点で永久の外部仕様になる（[書き出しの見出しは UI の言語に従う](../storage/tsv-header-follows-the-ui-language.md)）。`回数` の直後に挿したので、既存のシートで `体重kg` 以降を位置で参照している数式はずれる。取り込みは名前で引くので往復は閉じる
- **`SetEntry` のリテラルを書くテストが 42 箇所あった。** `..Default::default()` に寄せたので、次にフィールドを足すときは本番コードの 2 箇所だけがコンパイルエラーになる（そちらは判断を通す価値がある）

## 検討した代替案

- **`drop: bool` の印を既存のセット行に立てる** — 一度作って捨てた。決定 1 の理由。記録の手数は最小（普段のセット追加 + 1 タップ）だが、「メインセットから落とした」という関係が残らず、「トップセットに印を付けない」を運用で守ることになる
- **セットの種類を enum にする（`SetKind::{Working, Warmup, Drop, ...}`）** — 将来ウォームアップや RPE を足すときに拡張しやすいが、**今欲しくないものを先に決めることになる**。schema 2 で `Exercise.kind` を消したのは「ユーザーに区別を選ばせる形は意味が伝わらなかった」からで、選択肢を増やす方向は同じ失敗の入口
- **段を自由記述のメモにする** — 打つのは楽だが数値として読めないので、「推移に含める」設定そのものが作れない（グラフに一切乗らない）。この機能の動機は「推移の数字が膨らむ」を直すことなので、それでは目的を満たさない
- **識別に段を入れて、違えば `Conflict` を出す** — 決定 7 の理由で却下。利用者から見て食い違っていないものを食い違いとして報告するのは嘘で、しかも `log_rank` が同点なので実際には報告すらされずセットメモが消える
- **TSV に段を別行として書く（`ドロップ` 列に親のセット番号を入れる）** — シートで縦に読めるが、`1 セット 1 行` が壊れて `parse_tsv` の `staged` の組み方（セット番号で並べ直す）を作り直すことになる。1 セルに畳めば既存の経路がそのまま通る
- **TSV に列を足さない** — JSON のバックアップ（`views::backup`）は段を運ぶので全損はしない。しかし TSV はスプレッドシートで開く用途の外部仕様で、そこで消えるということは**シート経由で戻した人のグラフが勝手に増える**ということ
- **落とし幅をセグメント（10 / 15 / 20%）で選ばせる** — 刻みは人によって違うので、選択肢を先に決めると必ず外れる。設定タブの他の節が全部 `.segmented` なので形は揃うが、揃えるために当たらない選択肢を出すのは逆
