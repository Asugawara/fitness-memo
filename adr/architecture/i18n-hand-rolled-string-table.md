# i18n crate を入れず、`src/i18n.rs` の struct + `const` 2 枚で文言を持つ

- **状態**: 採用
- **日付**: 2026-08-19
- **カテゴリ**: architecture
- **関連**: [グラフライブラリを使わず SVG を自前で描く](no-chart-library-hand-rolled-svg.md), [ルーターを使わずタブを enum signal で切り替える](no-router-tab-enum-signal.md), [UI 依存を wasm32 の target 別 dependencies に置く](wasm-target-scoped-dependencies.md), [グラフの座標計算を `chart_layout` に切り出してテスト可能にする](chart-layout-as-a-testable-module.md), [言語はブラウザに従い、選んだらそれを優先する](../ux/language-follows-the-browser-then-the-setting.md)

## 背景

日本語専用で作ってきたアプリを英語にも対応させることになった。UI に出る文字列リテラルは
production だけで 324 箇所（ユニーク 264）あり、`src/views/settings.rs` に 43、
`src/views/backup.rs` に 42、`src/views/day.rs` に 33 と、view のほぼ全ファイルに散っている。

移行で一番怖いのは**文言の取りこぼし**である。264 個を人力で日英突き合わせると、
必ずどこかが片方の言語で欠ける。しかもその欠けは「その画面をその言語で開いたときだけ」
出るので、テストで全部踏むのは現実的でない。**機械が漏れを見つけてくれる形が要る。**

もう 1 つの制約は置き場所である。文言は `views/` だけの話ではない。
`src/core.rs` が `Metric` のラベル・`ImportError` のメッセージ・経過時間の表現
（「今日 / 昨日 / N日前」）・TSV の見出しを持っており、`src/presets.rs` は部位と種目の名前を持つ。
`core.rs` は「純ロジック / 実行環境非依存」を宣言していて `cargo test` がホストで検証する層なので、
ここが leptos に依存する仕組みを引くわけにはいかない
（[UI 依存を wasm32 の target 別 dependencies に置く](wasm-target-scoped-dependencies.md)）。

## 決定

**外部 crate を入れず、`src/i18n.rs` に「struct 定義 + `const JA` + `const EN`」の形で手書きする。**

```rust
pub enum Lang { Ja, En }

pub struct S {
    pub common: Common,   // views/mod.rs
    pub day: Day,         // views/day.rs
    pub settings: Settings,
    pub core: Core,       // core.rs
    // …ソースファイルと 1:1
}

const JA: S = S { common: JA_COMMON, day: JA_DAY, /* … */ };
const EN: S = S { common: EN_COMMON, day: EN_DAY, /* … */ };
```

付随して 5 つを決める。

1. **`src/i18n.rs` は `lib.rs` の cfg なしブロックに置く。** `leptos` も `web_sys` も import しない。
   依存は `serde` だけ。`core` と `presets` が引くので wasm32 に閉じられない
2. **サブ struct はソースファイルと 1:1 にし、`struct` → `const JA_X` → `const EN_X` を隣接させる。**
   264 フィールドの `const` リテラルを 1 枚にすると差分レビューが成立しない
3. **引数が要る文言は表に置かず `impl Lang` のメソッドにする**（約 30 箇所）
4. **表示用の日本語リテラルを `i18n.rs` の外に置かない。** 例外は開発者向けの
   `expect` / `debug_assert!` と、`presets.rs` の `Names`（あちらは文言ではなくデータ）
5. **`core` へは `Lang` を引数で渡す。** グローバルにしない

## 理由

- **`const JA: S = S { .. }` は構造体リテラルなので、フィールドを 1 つでも書き忘れると
  コンパイルが通らない。** これが決め手だった。264 個の突き合わせを人間がやらずに済む唯一の形で、
  「英語だけ欠けている文言」が原理的に存在できなくなる。しかも新しい文言を足すときも同じ強度が効く
  — フィールドを 1 つ足せば両方の `const` を直すまでビルドが赤いままになる。
- **`enum Key` + 巨大 `match` は同じ強度を出せない。** 腕を落としても `_ =>` があれば黙って通るし、
  無くても「両言語ぶんの腕」が要るので記述量は変わらない。呼び側も `t(Key::DayAddSet)` になって、
  view の中で何の文字が出るのか読めなくなる。`HashMap<&str, &str>` はキーの typo が実行時。どちらも却下。
- **`format!` はフォーマット文字列がリテラルでなければならない。** 表から引いた `&'static str` は
  渡せないので、引数付きは別扱いが要る。`fn(&str) -> String` をフィールドに持つ案は
  `(t.day.last_log)(&when)` と括弧が要って 30 箇所で醜い。`impl Lang` のメソッドなら
  `match self` の腕落としがコンパイルエラーで、引数の数と型もコンパイラが見て、
  呼び側は `lang.last_log(&when)` と自然に読める。**表と同じ強度をメソッドでも得られる。**
- **助詞で部品を繋いでいる文は、組み立てごとメソッドに畳む。** グラフの `aria-label` は
  `"{期間}" + "の推移。最大 {n} {単位}" + "。体重 {min}〜{max} kg"` という形で、
  語順も接続詞も違う英語には移せない。`Lang::chart_summary(span, metric, weight, smoothed)`
  として値を渡し、組み立ては言語ごとに書く。日本語の腕は元の文を 1 文字も変えずに再現してある。
  同じ扱いをしたのは他に `db_summary`（取り込み前後のサマリ）と `added_*`（増える件数の列挙）。
- **`core` に `Lang` を引数で渡すのは、`tz` と同じ理由。** `export_tsv(db, tz)` が
  `chrono::Local` を呼ばずオフセットを受けているのは、実行環境非依存を保って
  ホストのテストで検証できるようにするためだった。言語も「呼び側が決めて渡すもの」として同じ扱いにする。
  グローバルにすると `humanize_days` のテストが暗黙の状態に依存し始める。
- **`i18n.rs` を全ターゲットでビルドするのは、コストではなく利点。** `&'static str` の定数なので
  ホストビルドに害がなく、逆に `cargo test` が「TSV の見出しが日英で衝突しない」
  「プリセット名が両言語で一意」といった不変条件を検証できるようになる。
  [グラフの座標計算を `chart_layout` に切り出してテスト可能にする](chart-layout-as-a-testable-module.md) と同じ発想。
- **crate を入れない判断は、この repo の一貫した方針に沿う。** グラフライブラリも
  （[グラフライブラリを使わず SVG を自前で描く](no-chart-library-hand-rolled-svg.md)）
  ルーターも（[ルーターを使わずタブを enum signal で切り替える](no-router-tab-enum-signal.md)）
  入れずに済ませてきた。2 言語・264 文言・翻訳の外注予定なしという規模で、
  ビルドスクリプトと外部ファイル形式を持ち込む理由がない。
- **英語の単複は辞書を持たず、呼び側が 2 語を書く。** `plural(n, "day", "days")` の形。
  不規則変化まで面倒を見る仕組みは要らないし、呼び側が両方書けば規則も不規則も同じ扱いで済む。

## 切り替えの反映

**`App` の `view!` の中に 1 箇所だけ反映境界を置き、そこで画面を丸ごと作り直す。**

```rust
{move || {
    let l = lang.get();
    CURRENT_LANG.set(l);   // ★ view! を組む前に更新する
    let t = l.strings();
    view! { /* .notice + <main> + <nav> */ }
}}
```

各画面は `views::t()` で文言を**非リアクティブに**読む。264 箇所を `move ||` で包むのは
現実的でないので、購読するのはここ 1 箇所だけにして、変わったら作り直す。
言語切り替えは一生に一度の操作なので、全画面の再構築は割に合う。

さらに **`t()` はコンテキストではなく thread-local のキャッシュから読む。**
`use_context` はリアクティブな owner の中でしか引けず、文言が要る場所は
イベントハンドラ（書き出しボタン、ファイル選択のコールバック）にもある。
そこで `use_context` を呼ぶと `None` が返って `expect` で落ちる
— 実装中に「壊れたファイルの取り込み」で実際に踏んだ。読み取りを owner から独立させて、
この失敗クラスごと無くす。グローバル可変状態だが **UI 層に閉じている**ので、
`core` / `presets` / `i18n` が引数で受ける性質は失われない。

**キャッシュの更新は `Effect` ではなく描画クロージャの中で行う。** 描画クロージャは
signal の変更で同期に走るのに対し `Effect` は DOM を作り終えた後に走るので、
`Effect` に任せるとボトムタブ（クロージャの `l` を直接使う）だけが新しい言語になり、
その下の画面が前の言語で残る。**これも実装中に E2E が実際に検出した。**

## 結果（トレードオフ）

- **言語を切り替えるとコンポーネント局所のシグナルがリセットされる。** 編集シートの開閉、
  カレンダーの表示月、推移タブの対象 / 指標 / 期間が既定に戻る。`DbCtx` / `DateCtx` /
  `TabCtx` / `SettingsPageCtx` / `OpenGroupCtx` は `App` が持つので残り、切り替えた人は
  「設定 > 言語」に留まる。一生に一度の操作なので受容する。
- **文言は購読しないので、`App` の境界を経由しない経路で言語が変わると反映されない。**
  今は `pick` ハンドラ 1 つしか `lang.set` を呼ばないので問題にならないが、
  別経路を足す人はこの前提を知らずに壊せる。`LangCtx` の doc に書いてある。
- **wasm が両言語ぶんの文字列を持つ。** 使わない言語の文言も配信物に入る。
  実測で数 KB 程度なので、遅延ロードの仕組みを持ち込む理由にならない
  （[読み込みと操作は実測して、何も入れないと決めた](measure-before-optimizing-and-do-nothing.md)）。
- **翻訳を外注できない。** `.po` も `.ftl` も無いので、翻訳者に渡せるファイルが存在しない。
  3 言語目、あるいは翻訳を人に頼む段になったらこの決定を見直すことになる。
- **`impl Lang` のメソッドが 30 本以上になり、表とメソッドで文言の置き場が 2 つになった。**
  「引数があるかどうか」という機械的な基準で分かれるので迷いはしないが、
  ある文言を探すときに 2 箇所見る必要がある。
- **grep でしか規約を守れない。** 「表示用の日本語リテラルを外に置かない」は型で強制できない。
  `rg '"[^"]*[ぁ-んァ-ヶ一-龠]' src/ -g '!src/i18n.rs'` の残りが
  コメントと `expect` / `debug_assert` / `Names` だけになることを、レビューで見るしかない。

## 検討した代替案

**`leptos_i18n`**: leptos 公式に近く、コンパイル時にキーを検証してくれる。しかし
**leptos に閉じているので `core.rs` から使えない。** `Metric` のラベルも `ImportError` の
メッセージも TSV の見出しも core にあるので、core 用に別の仕組みを併設することになり、
文言の置き場が 2 系統に割れる。却下。

**`fluent` / `rust-i18n` / `gettext`**: いずれも外部ファイル（`.ftl` / YAML / `.po`）に文言を置く。
翻訳の外注には強いが、**キーの欠落が実行時**になるものが多く、今回一番欲しかった
「264 個の漏れをコンパイラが見つける」が得られない。ビルドスクリプトと配信物への
埋め込み方も増える。2 言語・翻訳の外注予定なしという規模に対して重い。却下。

**`macro_rules!` で `key => "日本語", "English";` と 1 行に両言語を並べ、struct と 2 枚の const を生成する**:
JA と EN が隣接するのが最大の利点で、翻訳漏れも構造上起きない。しかし
**この repo には `macro_rules!` が 1 つも無い**（`grep -rn macro_rules! src/` は 0 件）。
最初の 1 本を i18n のために入れるのは、読む人に新しい語彙を要求する割に得るものが少ない。
サブ struct をファイル単位に割ったことで「編集箇所が 40 行以内に収まる」ところまでは近づけた。
却下、ただし文言が数倍に増えたら再検討してよい。

**全文言を `Signal` にして細粒度に更新する**: 言語を切り替えても局所状態が飛ばない。
しかし 264 箇所すべてを `move || t().foo` で包むことになり、view の可読性が落ちるうえ、
シグナルの購読者が 264 個増える。一生に一度の操作のために払う代償として釣り合わない。却下。

**`Db` に言語を持たせる**: 保存経路が既存のものに乗る。しかし
[UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md) に正面から反し、
エクスポートファイルに UI 設定が混入する。別端末へインポートしたときに、
その端末の言語が相手の言語に書き換わる副作用まで付く。却下。
