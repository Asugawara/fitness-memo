# 書き出しを TSV にし、保存形式（JSON）と分ける

- **状態**: 採用
- **日付**: 2026-08-15
- **カテゴリ**: storage
- **関連**: [localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md)（「保存形式 = 書き出し形式」を上書き）, [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](share-sheet-over-download.md)（運び方は変えない）, [取り込みは「足すだけ」に固定する](import-is-merge-only.md), [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md)（外に出た形式は永久にサポートする）

## 背景

書き出しは `core::export_json` が吐く compact JSON 1 本で、[共有シート](share-sheet-over-download.md)から iCloud Drive / Google Drive に置ける。運ぶところまでは動いている。

**が、置いたファイルをスプレッドシートで開けない。** Google スプレッドシートも Numbers も Excel も JSON を表として読まないので、Drive に残した数年分の記録は「アプリでしか読めない塊」のまま眠る。書き出しの動機は「機種変更で消えないように」だけではなく、**貯めた記録を眺めたい**でもある。

[localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md) は「**エクスポート形式 = 保存形式**をこの 1 関数に固定する。別形式を作ると、保存側の変更に追随し忘れて『書き出したファイルが読み戻せない』が静かに起きる」と書いていた。この判断を再検証した。

## 決定

**書き出しは TSV（`.tsv` / `text/tab-separated-values`）にし、`localStorage` の保存形式は JSON のまま据え置く。**

1 セット 1 行の 1 枚の表。ヘッダ 1 行、LF、末尾改行あり、BOM なし。

```
日付	部位	種目	セット	重量kg	回数	体重kg	セットメモ	種目メモ	体調メモ	時刻
2026-08-01	胸	ベンチプレス	1	60	10	72.5			よく寝た	18:32
2026-08-01	胸	ベンチプレス	2	62.5	8		きつい
```

加えて:

- **`parse_import` は TSV と JSON の両方を受ける。** 先頭が `{` か ` ``` ` なら JSON の枝
- **`repair()` を TSV に通さない**（全角引用符の一括置換がメモを黙って書き換える）
- **体重・種目メモ・体調メモは、そのまとまりの先頭 1 行にだけ書く**
- **重量 0 は空セル**
- **「時刻」列は書き出し専用**（取り込みでは読まず、`at` は常に `None`）
- **末尾に「種目マスタ行」**（日付が空の行）。未使用の自作種目と、種目を持たない部位を残す。手つかずのプリセットは書かない
- **メモの `\t` `\r` `\n` は半角空白に潰す**

## 理由

### CSV ではなく TSV

- **貼り付けても列に分かれる。** スプレッドシートは TSV をタブ区切りとして受けるので、共有シートが使えない端末の「文字でコピー」経路でも、シートに貼れば表になる。CSV は 1 列に落ちる
- **クォート規則が要らない。** メモにカンマは普通に入るが、タブは入らない（入るのは `append_note` の `\n` だけで、それは出力時に潰す）。RFC4180 のクォート / エスケープを実装しないぶん、パーサが小さく壊れにくい
- `.csv` のほうが「どのアプリでもダブルクリックで開く」度合いは高いが、**このアプリの保存先は Google スプレッドシート**で、そこは `.tsv` を直接開く

### 「保存形式 = 書き出し形式」を崩す代償と、その埋め方

[localStorage の単一キーに JSON 全体を持つ](localstorage-single-key-json.md) の懸念は正しい。**TSV は `Db` の全部を持てない** — ID、`Group.color`、`Group.order` / `Exercise.order`、`Exercise.archived`、`ExerciseLog.at`、`schema` が落ちる。

埋め方は 3 つ:

1. **落ちるものを「名前から作り直せるもの」だけに限った。** 色と並び順は見た目、`archived` は表示設定。ID は[名前とプリセット固定 ID から引き当てる](#idの引き当て)
2. **往復をテストで固定した。** `cargo test` の `tsv_round_trips_every_record_except_the_clock` が「`at` 以外は一致する」を主張し、`importing_the_same_tsv_twice_adds_nothing` が冪等性を数で見る。「書き出したファイルが読み戻せない」は**静かには起きず、テストが落ちる**
3. **JSON の取り込みを永久に残す。** [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md) が「一度ユーザーの手元に出たファイル形式はアプリの寿命の間サポートし続ける必要がある」と書いているとおり。加えて `.pre-` 退避が保存形式（JSON）なので、機能的にも外せない

### 版番号を持てないので、進化規則を文章で固定する

TSV には `schema` に当たる欄が無く、`ImportError::Unsupported` を返す手段が**原理的に無い**。古いアプリが新しいファイルを読んだとき「新しすぎる」と言えない。

代わりに規則を置く:

1. **列は足すだけ。既存の列名と意味は永久に変えない**
2. **取り込みは列を名前で引き、知らない列は無視する**（位置で読まない）
3. **足す列は「無くても読める」ものだけにする**

規則 2 の実行部が `tsv_header()` で、見出しを名前で引いて `TsvCols` に落とす。**見出し無しのファイルを位置で読むフォールバックは作らない** — 列順を推測すると「回数を重量として取り込む」が黙って通り、しかも数字なので画面を見ても気づけない。

### 体重を毎行書かない

1 セット 1 行に体重を毎回書くと、シート側の `AVERAGE(G:G)` が「**セット数で重み付けした平均**」になる。体重グラフを作った瞬間に嘘の値が出るので、日の先頭 1 行にだけ書く。種目メモ・体調メモも同じ理由（`COUNTA` が実際の本数と合わなくなる）。

並べ替え耐性は出力側ではなく**パーサ側**で確保した（日付でグルーピングして最初の非空を採る）ので、シートで行をソートして書き戻しても壊れない。

### 「時刻」を往復させない

4 つの理由があり、どれも単独で十分:

- **`HH:MM` → epoch ms の復元にはローカルタイムゾーンが要る。** `core.rs` に `chrono::Local` を持ち込むと、書き出しも取り込みも**実行環境の TZ 依存**になり、`cargo test` が動かすマシン次第で落ちる。この repo は `elapsed_since_last(db, now_ms, today)` のように**環境を引数で受ける**流儀で、`export_tsv(db, tz)` もそれに揃えた
- **分未満が落ちる**ので `Db → TSV → Db` の厳密一致が成立せず、往復テストが「`at` だけ特別扱い」を抱える
- **スプレッドシートが `18:32` を時刻セルに変換**し、`18:32:00` や小数シリアル値（`0.7722…`）で書き戻すことがある。読まないと決めれば、この変形は**構造的に無害**になる
- [テキスト取り込みは「足すだけ」に固定し、部位を増やさず、`at` を書かない](../data-model/text-import-is-merge-only.md)（破棄済み）の決定 3 と同じ規範に乗る。外から来たセットは過去日のバックフィルなので時刻を持たない

失うのは「同じ暦日に再取り込みしたとき `humanize` が『3 時間前』ではなく『今日』になる」だけ。しかも既存ログとセットが一致すれば `merge_db` は既存に触らないので、**自分の端末に戻す限り `at` は保持される**。

出力側は「`at` のローカル日付が行の日付と一致するときだけ書く」。壊れたデータ由来の矛盾した `at`（`elapsed_since_last` が既に想定している状態）を、シート上で前日の行に時刻として並べないため。

### 重量 0 を空セルにする

`set_volume` は 0 を「重量なし」として扱い（`max(1.0)`）、`fmt_set` も回数だけを出す。**アプリ自身が 0 を「無い」と表示している。** シートでも空セルは平均・グラフから外れるので、意味が一致する。取り込みは空も `0` も受けるので曖昧さは無い。

### 種目マスタ行を末尾に置く

一度も記録していない自作種目と、種目を持たない部位は、記録の行に一度も出てこない。書かないと**黙って消える**。このアプリでいちばん避けたい失敗は「移行できたつもり」なので、日付が空の行として残す。

先頭ではなく末尾なのは、シートを開いた第一画面が空行だらけの定義行にならないため。手つかずのプリセット（名前も ID もそのまま）を書かないのは、新規インストールに必ず同じ固定 ID で居るので、書かなくても失われないから。

### <a id="idの引き当て"></a>取り込みは名前と固定 ID で ID を引き当てる

`parse_import` に**取り込み先の `Db`** を渡す。ID を持たない TSV をそのまま `merge_db` に流すと 2 つ壊れる:

- `merge_db` は同名一致のたびに `Conflict::NameMatched` を無条件に積むので、**自分のファイルを戻すだけで確認画面が「〇〇は同じ種目とみなしました」で埋まる**（`is_noop` は真なのに 30 行の注意書きが出る）
- 同名が取り込み先に 2 つあると、片方に寄って残りが `dedupe_by_exercise` で黙って落ちる

解決の梯子は、破棄済みの [テキスト取り込みは「足すだけ」に固定し、部位を増やさず、`at` を書かない](../data-model/text-import-is-merge-only.md) の決定 4（「既存の種目に当たったら取り込み先の `Exercise` をそのまま複製する」）を踏襲した:

1. `mine` に (部位名, 種目名) が**ちょうど 1 件** → その `Exercise` を複製（`merge_db` は ID 一致の枝を素通りし、conflict が出ない）
2. `mine` に 種目名 が**ちょうど 1 件** → 同上
3. **プリセット名に一致 → 固定 ID**
4. それ以外 → 新規採番

**3 が要る理由**: 端末 A の TSV を、プリセットを改名した端末 B（「ベンチプレス」→「ベンチプレス（スミス）」）に取り込むと、名前照合が当たらず **B に「ベンチプレス」が新規追加されて履歴が 2 本に割れる**。[ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md) が固定 ID を導入して潰した壊れ方そのもの。

**1・2 が「ちょうど 1 件」なのは `core::pin_presets` と同じ理由。** 画面に重複名チェックが無いので、自作の「ベンチプレス」がプリセットと別に存在しうる。両方を同じ ID に寄せると**別種目の履歴が無警告で合流する**。曖昧なら新規に倒す。

### メモのサニタイズが必須

`core::append_note` は合流時に `\n` を挟むので、**改行入りのメモは実在する**（`<input type="text">` から入るので改行は打てない、は誤り）。潰さないと行が崩壊し、その日の記録が丸ごと壊れる。

潰すと元の文字列と変わるので、**`append_note` の重複判定を空白畳み込みで行う**ように直した（保存する文字列は畳まない）。これが無いと、`"A\nB"` を持つ端末が自分の TSV を読み戻したときだけメモが `"A\nB\nA B"` に 1 度伸びる。副産物として既存 4 呼び出し全部の冪等性が上がった。

## 結果（トレードオフ）

- **`fmt_weight` / `parse_weight` / `parse_reps` を `views/mod.rs` から `core.rs` へ移した。** TSV の重量整形がホストの `cargo test` から検証できるようになる。`views` は再輸出するだけなので呼び出し側は無変更
- **`COLOR_CHOICES` を `views/menu.rs` から `presets.rs` へ移した。** 取り込みが作る新規部位にも画面と同じ色を振るため。「部位を作る」全経路で 1 本になった
- **TSV は ID・色・並び順・`archived`・`at` を持たない。** 取り込み時に名前とプリセット固定 ID から作り直す。色と並び順は既定に戻る
- **スプレッドシートで編集して戻す経路は best effort。** CRLF / `YYYY/M/D` / `62,5` / 列の増減 / 行の並べ替えは吸収するが、**`=` `+` `-` `@` で始まるメモがシート上で数式になる**のは直さない。`"` を含むメモの再クォートも扱わない。README に明記した
- **`ImportError` が 2 つ増えた**（`NoHeader` / `NoRecords`）。`NotJson` は JSON の枝でしか返らなくなったが、名前は変えていない（変えると文言まで曖昧になり、テストと E2E の diff が増える）
- **実機で未確認**: iOS の共有シートが `.tsv`（UTI `public.tab-separated-values-text`）に「ファイルに保存」を出すか。`can_share_file()` のプローブを `probe.json` から `probe.tsv` へ揃えたのはこのため（違う型で可否を判定しない）

## 検討した代替案

**CSV にする。** 「どのアプリでもダブルクリックで開く」度合いは上。却下したのは、クリップボード経路で列に分かれないことと、RFC4180 のクォート実装を抱えること。保存先が Google スプレッドシートである以上、TSV で困らない。

**JSON と TSV を 2 ファイル書き出す。** 完全な backup と読める表を両立できる。却下 — `navigator.share` に 2 ファイル渡したときの iOS の挙動が未検証で、しかも「どちらを読み込めばいいか」を利用者に判断させることになる。**復旧が要る瞬間にいちばん選ばせてはいけない選択肢**。

**TSV を 2 つの表に分ける（種目マスタ + 記録）。** 空行区切りで 1 ファイルに 2 表を置く形。パーサが状態を持つことになり、シートで行を並べ替えると区切りが壊れる。日付が空の行という 1 つの表に畳んだ。

**先頭にコメント行で版番号を書く（`# fitness-memo v1`）。** スプレッドシートで開くと 1 行目にゴミが出るうえ、シートから書き戻すと消える。版番号は持たず、進化規則で縛るほうが実際に守れる。
