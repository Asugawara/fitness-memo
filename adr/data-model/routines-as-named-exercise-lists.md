# トレーニングメニューを「名前 + 種目 ID の並び」だけのデータにする

- **状態**: 採用
- **日付**: 2026-08-15
- **カテゴリ**: data-model
- **関連**: [保存したメニューから始める](../ux/start-from-a-saved-routine.md) / [1 日分のメニューは候補リストから 1 タップで丸ごとコピーする](../ux/copy-whole-day-menu.md) / [「1日1種目1ログ」を不変条件にする](one-log-per-exercise-per-day.md) / [種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) / [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md) / [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](random-ids-for-safe-merge.md)

## 背景

種目の組み合わせに名前を付けて保存できるようにする（[保存したメニューから始める](../ux/start-from-a-saved-routine.md)）。そこで必要になるデータの形を決める。

「メニュー」という語はこのリポジトリで既に 2 つの意味を持っていた。設定タブ（旧・種目タブ、`views::settings`）と、過去の日の種目構成（`core::MenuCandidate` / `recent_menus`）である。3 つ目を同じ語に載せると、コードのどこを読んでも「どのメニューの話か」が判別できなくなる。

## 決定

**Rust 側の型名は `Routine`、UI 表記は「トレーニングメニュー」にする。** 持つのは 3 つだけ。

```rust
pub struct Routine {
    pub id: RoutineId,
    pub name: String,
    pub exercises: Vec<ExerciseId>,
}
```

`Db` には `#[serde(default, skip_serializing_if = "Vec::is_empty")] pub routines: Vec<Routine>` として足す。**`SCHEMA` は 3 のまま。`storage::KEY` も切らない。**

正規化・マージ・展開の規則は以下のとおり。

## 理由

### なぜ `Routine` という名前か

| 却下した案 | 理由 |
|---|---|
| `Menu` | 上記 3 義と衝突する。`views::settings` と `MenuCandidate` の両方に当たる |
| `Workout` | このアプリでは 1 日の記録（`Session`）こそが workout。最も紛らわしい |
| `Template` | 「訓練」の含意が無く、UI のコードでは view template と読まれる |
| `Plan` | 日付・スケジュールを含意する。日付を持たない設計なので嘘になる |
| `Preset` | `presets.rs`（初期投入データ）と衝突。しかも後述のとおりプリセットのメニューは作らないので二重に悪い |
| `Program` | 週単位のピリオダイゼーションを含意する |

`core.rs` の「メニューのコピー」節の冒頭に、3 義の対応表をコメントで置いた。改名より安く、誤読を確実に潰せる。

### なぜセットの重量・回数を持たないのか

**目標値を持つと腐る。** 記録が伸びても目標が古いまま残り、画面に出る数値が前回の実績と食い違う。このアプリの唯一のループは「前回を見て同じかそれ以上をやる」なので、そこが食い違った時点で機能全体が意味を失う。

数値は展開時に種目ごとの `last_log_before` から引く。これはカード内の「前回をコピー」（[「前回をコピー」はセットが空のときだけ出す](../ux/copy-button-only-when-empty.md)）とまったく同じ「前回」の定義で、2 つの導線が同じ数値を出すことが保証される。

副次的に、[1 日分のメニューは候補リストから 1 タップで丸ごとコピーする](copy-whole-day-menu.md) が却下した「『予定』の概念をデータモデルに足す」という代償も避けられる。`Session::is_empty` / `is_trained` / `migrate` はいずれも無変更で済んだ。

### なぜ `order` を持たないのか

`Vec` の順を表示順とする。`Session::logs` が既に「Vec の順 = ユーザーが決めた順」で、`dedupe_logs` のコメントが「初出の順序は保つ」を仕様と明言している。

`Group` / `Exercise` が `order` を持つのは、`exercises` が全部位ぶん 1 本の `Vec` に混在していて部位内順序を `Vec` 位置で表せないため。メニューは平坦な 1 本のリストなのでその制約が無い。`order` を足すと「一意性・詰め直し」という正規化義務が増えるだけになる。

### なぜ `archived` を持たないのか（＝物理削除でよい）

**メニューを参照する記録は 1 つも無い。** 種目がアーカイブ（論理削除）なのは、過去ログの `exercise_id` 参照を保つためだった。メニューを消しても過去のログは 1 バイトも欠けないので、その理由が当たらない。

### なぜプリセットのメニューを作らないのか

`presets::seed()` は「固定 ID が無ければ足す」を**毎起動**やる。種目はアーカイブしかできないので復活しないが、**メニューは物理削除できるので、プリセットにすると削除しても毎起動で復活する。** 消せない行が永久に残るのは論外なので作らない。

系として、`RoutineId` は予約領域（`RESERVED_MAX` 未満）を使わない。`IdGen::alloc` は元から予約領域を返さないので追加の対処は不要だが、「共通の固定 ID を与えれば 2 台で同じメニューが 1 本になる」という発想でここを触ってはいけない（上記の復活問題がそのまま戻る）。

### なぜ schema を上げないのか

[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) が確立した「default 付きの追加のみなら上げない」にそのまま乗る。両方向を検証した。

**後方互換（新版が旧 JSON を読む）**: schema 3 の旧 JSON に `routines` が無ければ `#[serde(default)]` で空 `Vec`。schema ≤2 は `legacy::Db` にそもそもフィールドが無く、`upgrade_from_sequential` が `routines: Vec::new()` を書く（`legacy` モジュールには一切触っていない）。

**前方互換（旧版が新 JSON を読む）**: `model.rs` は `deny_unknown_fields` を意図的に採っていないので、旧版の serde は `routines` を未知フィールドとして無視する。したがって旧版の `migrate` は `Err` を返さず、`storage::load` の退避パス（`.bak-`）に落ちない。

[保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md) の起点は `Exercise.kind` の**削除**（旧版が `missing field` で落ちた）であって、追加ではない。

さらに `skip_serializing_if = "Vec::is_empty"` により、**メニューを 1 本も作っていない利用者の JSON は今までとバイト単位で同一**になる。`e2e/backup.spec.mjs` の `toEqual(parsed)` などが「保存形式は変わっていない」ことを主張し続ける（この不変を E2E に 1 本足した）。

### 正規化（`core::normalize_routines`）

`normalize` のシグネチャを `fn normalize(db: &mut Db, ids: &mut IdGen)` に広げた。呼び出し元は `migrate` の 1 箇所だけ。

1. 空白だけの名前を空文字にする（`blank_notes_to_empty` と同じ。**trim はしない** — 両端の空白を削るのはユーザーが打った文字の書き換えになる）
2. `exercises` を初出順で dedupe する。残すと展開時に同一 `exercise_id` のログが 2 本でき、[「1日1種目1ログ」を不変条件にする](one-log-per-exercise-per-day.md) が破れる
3. 名前も種目も無いメニューを落とす。**名前だけ / 種目だけは残す**（名前を打って種目を選ぶ前に閉じた状態を消さない。`ExerciseLog::is_empty` がメモだけのログを残すのと同じ理由）
4. ID が重複しているメニューに `ids.alloc()` で採番し直す

**存在しない種目・アーカイブ済み種目への参照は消さない。** 理由は 3 つ。

- このアプリに種目の物理削除は無い（`views::settings` にあるのは `set_archived` だけ）ので、宙に浮いた参照は「他端末のデータ」しか作らない。つまり**後から相手のファイルを取り込めば生き返る**種類の参照で、読み込みのたびに消すと生き返らせる機会をユーザーから奪う
- `upgrade_from_sequential` が既に「宙に浮いた参照は宙に浮いたまま残す。偶然有効にするほうが危ない」という立場を採っている。同じファイルに逆の規則を置くと、次に読む人がどちらが正か判断できない
- 消すのは不可逆（メニューから 1 種目が黙って減る）。残しても被害は「候補に出ない / 編集画面に出ない」だけで可逆

「押しても何も起きない死んだボタンを作らない」責任は、読み出し側の `expandable` が全部持つ（`copyable` が `recent_menus` と `copy_day` の両方を通っているのと同じ形）。

ID の重複だけは放置できない。画面が `<For key=id>` に使うので重複キーは keyed diff を壊し（wasm では panic = アプリが死ぬ）、削除は `retain(|r| r.id != id)` なので**片方を消すと両方消える**。捨てずに採番し直すのは、名前を付けて組んだリストを黙って失わないため。

### マージ（`core::merge_db`）

種目ループの直後・セッションループの前に置く（`exercise_alias` の完成待ち）。判定は:

```
ID 一致 → (同名 かつ 写像適用後の種目列が完全一致) → 新規追加
```

**同名でも中身が違えば寄せない。** 種目とはここだけ規則を変えている。

種目で同名を寄せるのは、**種目には履歴がぶら下がっている**から。寄せないとグラフの系列が 2 本に割れ、[ID を 60 bit 乱数にし、プリセットには固定 ID を与える](random-ids-for-safe-merge.md) が潰そうとした壊れ方が復活する。

メニューには**何もぶら下がっていない**ので、天秤が逆になる。

| | 被害 |
|---|---|
| 寄せて外す | 取り込む側のリストがどこにも残らず消える（不可逆・不可視） |
| 寄せずに残す | 「胸の日」が 2 行並ぶ（可視・1 タップで消せる） |

ID が違って名前だけ同じになるのは「2 台で独立に作った」ときだけで、それは本当に別のオブジェクトである。中身が完全一致するときだけ寄せることで、純粋な重複（同じものを両方で作った / 同じファイルを 2 度入れた）は潰しつつ、内容の異なるリストを 1 本も失わない。

写像は `exercise_alias` を通し、**適用後に dedupe する**。写像は単射とは限らず（取り込み先で改名済みの種目と、取り込む側の同名の別種目が同じ ID に落ちる）、同じ `exercise_id` が 2 回入ると展開時に「1 日 1 種目 1 ログ」が破れる。セッション側の `dedupe_by_exercise` とまったく同じ危険。同名判定に使う種目列も**写像適用後**のものにする（前で比べると、同じ種目を指しているのに ID が違うだけで「別物」と判定される）。

`MergeReport.routines_added` と `Conflict::RoutineDiverged { name }` を足した。`is_noop()` に数えたものは `views::backup::report_text` にも必ず出す（片方だけだと `is_noop` が偽なのに文言の部品が空になり、画面に「 を追加しました」だけが出る）。

### なぜ `DbSummary` を変えないのか

[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) が確立した規則をそのまま適用する。あの 3 つの数（種目 / 実施日 / セット + 期間）は「取り込み事故を止める唯一の道具」で、4 番目を足すと**事故を実際に止めている数が 1 行の中で薄まる**。

## 結果（トレードオフ）

- **旧版へロールバックして 1 操作すると、保存したメニューだけが消える。** `routines` が落ちた JSON で現行キーが上書きされるため。セット・重量・体重・メモは無傷なので、[保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md) が「全損 vs 巻き戻り」で許容した範囲より軽く、メニューは数タップで作り直せる（記録は作り直せない）
- **「置き換える」で古いファイルを取り込むとメニューが消えるが、プレビューの数字は 1 つも動かない。** メモが黙って消えるのと同じクラスの損失で、退路も同じ（取り込み直前に `storage::snapshot_current()` が `.pre-` へ raw JSON を退避しており、メニューごと復元できる）。将来ここを埋めるなら `DbSummary` ではなく **Replace の確認文言**に足すこと
- 2 台を混ぜると同名のメニューが並びうる。設定タブから 1 タップで消せる
- `Vec<ExerciseId>` を `Vec<RoutineItem>`（要素を構造体に）へ変える日が来たら、JSON が「文字列配列 → オブジェクト配列」に変わる。そのときは serde の `untagged` で両方読むか schema を上げることになる

## 検討した代替案

**`SCHEMA = 4` に上げて `storage::KEY` を `fitness-memo/v4` に切る**: 得るものが無い（前方互換が壊れていない）うえに害だけ残る。全利用者が「v3 から読んで v4 へ写す」失敗しうる移行を 1 回通り、v3 が読み取り専用で凍結されて localStorage を 1 世代余計に食う。さらに悪いことに、**上げた瞬間に旧版が `RestoreError::Unsupported(4)` を返して `.newer-4-` へ退避し、プリセット入りの空 DB を表示する** — schema を上げるほうが前方互換を積極的に破壊する。却下。

**`normalize` で宙に浮いた参照を落とす**: JSON は綺麗になるが、`storage::load` は起動のたびに `migrate` を通るので、**相手のファイルを取り込む前に参照が消える**。救済不能になる。却下。

**マージで種目列を union する（追加のみだから正しい、という論法）**: 冪等ではあるが、「この端末では意図的にチェストフライを外した」が毎回の取り込みで無言に戻る。削除を表現する手段がデータモデルに無い以上、union は「消したものが復活し続ける」を確定させる。`merge_db` が同じ理由でセットを連結しないのと同型。却下。

**マージで ID 一致時に種目列の「強いほう」を採る**: どちらが強いかの意味がメニューには無い（10 種目のリストが 3 種目のリストより良いとは限らない）。却下。

**`created_at` / `updated_at` を持つ**: `core` は時計を持たない（`copy_day` が `at` を引数で受けるのと同じ理由）。どの画面も作成日時で並べないので、持つと使われない時刻を全コンストラクタに配線することになる。却下。

**`note`（メニューのメモ）を持つ**: 「予定のメモ」と「その日の観測メモ」の 2 概念が混ざる。[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) が「種目マスタにメモを置かない」と決めた理由と同型。却下。
