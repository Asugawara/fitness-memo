# ラベルの定義を種目に置き、ログには ID の印を 1 つだけ付ける

## 背景

ベンチプレスで HPS トレーニング（Hypertrophy / Power / Strength）のように、**同じ種目で毎回狙いを変えて重量とレップを変える**やり方がある。この使い方では「前回」が役に立たない。`core::last_log_before` は直近 1 件だけを見るので、Power の日に Hypertrophy の記録（`70×10`）が出てくる。数値がまるで違うので参照にならず、「前回を見て同じかそれ以上をやる」という唯一のループが切れる。

必要なのは「その日その種目が**どの狙いだったか**」を記録し、「前回」をその狙いの中だけから引くこと。狙いの名前は各利用者が決める（HPS は一例で、「高重量ローレップ」「ドロップセット」「フォーム確認」も同格）。

置きたい情報は 2 つに分かれる。**定義**（この種目にはどんな狙いがあるか）と**印**（この日はどれだったか）。前者は種目に貼り付いて日をまたぐ設定で、[マシンのピンは種目に持たせ、メモのトグルに相乗りさせる](../ux/machine-pins-on-the-exercise.md) が扱った性質と同じ。後者はその日の観測で、[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) の `ExerciseLog::note` と同じ。**この 2 つを 1 つのフィールドで表そうとすると必ず壊れる**ので、最初から分けた。

## 決定

### 1. 定義は `Exercise.labels: Vec<Label>`、印は `ExerciseLog.label: Option<LabelId>`

```rust
pub struct Label { pub id: LabelId, pub name: String }

// Exercise（ピン / インターバルと同じ「種目に貼り付く」棚）
#[serde(default, skip_serializing_if = "Vec::is_empty")]
pub labels: Vec<Label>,

// ExerciseLog（note と同じ「その日のログ」の棚）
#[serde(default, skip_serializing_if = "Option::is_none")]
pub label: Option<LabelId>,
```

**ラベルは種目ごとに独立して定義する。共通プールを作らない。** ベンチプレスの「P」とスクワットの「P」は別のものでよく、共通にすると片方を改名したときにもう片方の意味が変わる。さらに重要なのは、**参照の解決を必ず「そのログの種目の `labels` の中」で行える**ことで、種目をまたいだ宙に浮いた参照が構造的に起きない（`core::label_name` がこの 1 本しか道を持たない）。

**粒度は「その日その種目に 1 つ」。** `SetEntry` には持たせない。狙いはセッション全体の性質で、1 セットごとに変わるものではない。[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) が「その日のこと」と「そのセットのこと」を分けた軸に対して、これは**3 つ目の軸**（「その日の狙い」）を `ExerciseLog` の側だけに足したことになる。

**「ラベルなし」は `Option` が言う。** `Id::default()`（`Id(0)` 番兵）は使わない。番兵にすると `label_name` が引けなかったときと区別できず、`serde` の `skip_serializing_if` も書けない。

### 2. `SCHEMA` は上げない。`storage::KEY` も切らない

`model.rs` の `SCHEMA` の doc の規則そのままで、`#[serde(default)]` 付きのフィールド追加では上げない。旧版は `deny_unknown_fields` を付けていないので未知フィールドを黙って無視し、`migrate` が `Err` を返さないので退避パスにも落ちない。**上げると逆に旧版が `RestoreError::Unsupported` で退避し、前方互換を積極的に壊す側になる。**

`skip_serializing_if` により、ラベルを使わない利用者の JSON は**今までとバイト単位で同一**（`exercise_omits_empty_labels_from_its_json` / `exercise_log_omits_an_unset_label_from_its_json` がリテラルで固定している）。ピンとインターバルを足したときとまったく同じ判断。

### 3. 名前ではなく ID で参照する。**改名では ID を変えない**

この機能の目的が「数か月にわたる Power の履歴」なので、`P` → `Power` の改名で過去ログが全部外れる形は採れない。**これは実装上の細部ではなく機能の要件そのもの**なので、3 箇所で守っている:

- `core::clean_labels` は**重複 ID だけ**採番し直し、それ以外の ID は保持する
- `core::set_labels` は `Label.id` を呼び側から受け取る（自分で採番しない）
- `views::settings` の `LabelRow` は `LabelId` を持ち、`＋` のときだけ `storage::alloc_id()` を振る

`LabelRow` を `PinRow { key, value }` の形（ID を持たない）で写すと、`set_labels` に渡す `Label.id` を毎 commit 採番するしかなく、**1 文字打つごとに全ラベルが新 ID になって `ExerciseLog.label` が全部宙に浮く**。敵対的レビューが「破壊的」と判定した唯一の箇所で、`renaming_a_label_keeps_its_id` と `e2e/label.spec.mjs` の 10 番が両側から網を張っている。

名前で参照すれば「2 台で独立に定義した `P` が自動で寄る」という利点があるが、それは決定 6 の合流の梯子（ID 一致 → 同名 → 新規）で回収できる。**改名で履歴が外れる損失は回収できない**ので、天秤は一方に倒れる。

### 4. プリセットに既定ラベルを配らない。`RESERVED_MAX` も触らない

`H` / `P` / `S` をベンチプレスに配ると便利に見えるが、[指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md) が「加重 / 自重の区別をユーザーに宣言させる意味が無い」として `Exercise.kind` を捨てた判断を逆走する。HPS は一つの流派で、全員の使い方ではない。

**副産物として、定義が 0 本の種目では画面が 1px も動かない**（画面側の決定は [チップでラベルを選ぶと履歴とコピーが切り替わる](../ux/label-chips-switch-the-history-and-the-copy.md)）。プリセット 28 種目は全部ラベル 0 なので、既存利用者の体験が変わらないことが**データの側で保証される**。

### 5. 同一判定（`same_sets` / `same_sets_unordered` / `log_rank`）にラベルを入れない

入れるとラベルの差だけで「セットが食い違った」枝に落ち、しかも `log_rank` は同点なので差し替えの分岐にも入らず、**取り込む側のセットメモが `Conflict` も出さずに黙って捨てられる**。[種目メモとセットメモを `ExerciseLog` / `SetEntry` に持たせ、空のメモは書き出さない](notes-on-logs-and-sets.md) の決定 8 が ★ で警告しているのと同型の壊れ方で、`note` と同じ扱いにする（`a_label_difference_alone_is_not_a_set_conflict` が固定している）。

ログの `label` の合流は**「空のときだけ埋める」**（`mine` 優先。[取り込みは「足すだけ」に固定する](../storage/import-is-merge-only.md)）。挿入位置は `append_note` の隣で、**あとに回してはいけない** — 下の `*existing = log` が上書きして消す。`log_rank` の勝ち枝では**明示的に持ち越す**（`..log` に任せると勝った側で上書きされ、`mine` 優先が壊れる）。

`dedupe_logs` にも `existing.label = existing.label.or(log.label)` の 1 行が要る。無いと重複ログを畳むときに後発の `label` が黙って落ちる。

### 6. 定義の合流は種目と同じ梯子。**写像のキーは `(ExerciseId, LabelId)` の組**

`core::merge_labels` の判定は ID 一致（何もしない）→ **同名がちょうど 1 件**（別名写像に積む）→ 新規追加（`MAX_LABELS` まで）。種目の梯子とまったく同じ形で、「ちょうど 1 件」なのは `resolve_exercise` / `pin_presets` と同じ理由 — 曖昧なら新規に倒す（同名が複数あるときに片方へ寄せると別の狙いの履歴が無警告で合流する）。

**呼ぶのは `fill_pins` / `fill_interval` と同じ 2 枝**（ID 一致 と 同名寄せ）。3 つ目の新規追加枝は `..e` なので `labels` が自動で乗る。**この手当てが無いと最悪の形になる**: プリセットは固定 ID を持つので新品端末への復元は必ず「ID 一致」の枝を通り、その枝は取り込み側の `Exercise` を丸ごと捨てる。つまり**記録は全部戻るのにラベル定義だけ落ち、ログには宙に浮いた `label` が残って履歴が全部「どのラベルにも属さない」になる**。`fill_pins` の ★ と同型で、被害はこちらのほうが大きい（`merging_into_a_fresh_device_keeps_the_labels`）。

**写像のキーを `LabelId` 単独にしてはいけない。** 同じ `LabelId` が取り込み側の 2 種目に居る場合（手編集 JSON、または `clean_labels` が種目内の重複しか再採番しないので種目をまたぐ重複は生き残る）、後の `insert` が前を上書きし、**種目 A のログが種目 B のラベルへ張り替わって宙に浮く**。キーを `(写像後の ExerciseId, LabelId)` の組にすればこの経路が構造的に消える（`merge_does_not_confuse_the_same_label_id_used_by_two_exercises`）。

### 7. `MergeReport.labels_added` は数える。`labels_dropped` は数えるが `is_noop()` に入れない

**`labels_added` は必須。** ラベルだけが増えたマージは `conflicts` に出ないのに**チップが増えて履歴の見え方が変わる**。数えないと `is_noop()` が真になり、画面が「新しく取り込むものはありませんでした」と嘘をつく。定義の追加とログへの付与を合算した 1 本のカウンタにした（`notes_added` が既に異種混合の先例）。`is_noop` に足したものは `views::backup::added_text` にも必ず足す。

**`labels_dropped`（`MAX_LABELS` 超過で取り込めなかった定義の数）は `is_noop()` に入れない。** 何も増えていないので、`is_noop` の意味（新しく取り込むものがあるか）としては真が正しい。しかし黙って進めてはいけない — 落ちた定義を指すログは取り込み直しても二度と生き返らない宙に浮いた参照になる。

そこで **`views::backup::Pending` に `conflicts` とは別の `warnings` を持たせた**。3 つの理由でこちらに出す:

1. **`conflicts` に積むと確認画面が嘘をつく。** `change_text` は `conflicts.is_empty()` で「入れ替わる記録があります」に分岐するが、記録は 1 件も入れ替わらない。`change_text` の doc が「確認画面が嘘をつくのが最悪」と書いている形そのもの
2. **`Conflict` の腕も足さない。** あれは「記録の食い違い」を並べる型で、`SetsDiverged` / `BodyWeight` / `RoutineDiverged` はどれも既存の値が入れ替わったことを言う。ラベル定義が上限で落ちたのは別の種類の事象
3. **出す位置は `change_text` / `imported_*` の結果と独立に併記する。** 「上限で落ちただけ」のマージは `nothing_new`（「新しく取り込むものはありません」）に落ちる — 取り込むものが無いのは事実なので嘘ではないが、そこに混ぜると落としたことが画面から消える

文言（`Lang::dropped_labels`）は**責めずに「何が起きたか」と「何をすれば直るか」まで書く**（`Day::weight_missing` の「回数を入れると保存されます」と同じ作法）。記録は消えず「指定なし」で見られることも言う。

### 8. TSV は末尾（15 列目）に `ラベル` / `Label`。セルは ID ではなく名前

**位置は末尾。** `e2e/backup.spec.mjs` が `r.split('\t')[2] === 'ベンチプレス'` と位置参照しているので、既存 14 列のインデックスを動かさない（[表計算で開ける TSV で書き出す](../storage/tsv-export-for-spreadsheets.md) の進化規則 1「列は足すだけ」）。

**セルは名前。** TSV の存在意義がスプレッドシートで読めることなので、既に全 ID を落として名前から作り直している。

**書くのは「そのログの最初の行」だけ**（`種目メモ` と同じ「使ったら空にする」）。**`ex_meta_written` に相乗りさせない** — あれは種目粒度（その種目がファイル中で最初に現れた行）で、ラベルは**日ごと**に変わる。相乗りさせると 2 日目以降が全部落ちる（`export_tsv_writes_the_label_once_per_log_not_once_per_exercise`）。

取り込みは `core::resolve_label` が `resolve_exercise` の梯子を 1 階層下でなぞる（mine のその種目に同名がちょうど 1 件ならその ID → `out` に作った同名はキャッシュから → それ以外は採番）。**`LabelCache`（キーは `(ExerciseId, String)`）は必須** — 無いと行ごとに採番して 1 種目に数百ラベルが生える（`tsv_import_allocates_one_label_id_for_thirty_rows`）。`MAX_LABELS` は `parse_import` 末尾の `normalize` が効かせる。

### 9. **未使用のラベル定義は TSV に載らない。** よって種目マスタ行の判定にも足さない

ラベル列は記録行にしか出ないので、1 度も使っていない定義は書き出しに現れない。[表計算で開ける TSV で書き出す](../storage/tsv-export-for-spreadsheets.md) の基準「落ちてよいのは名前から作り直せるもの」を満たす — 未使用ラベルは打ち直せば完全に戻り、**ぶら下がる記録が 0 件**。使ったラベルは各ログ行が名前を運ぶので必ず復元され、履歴も繋がる。JSON バックアップは定義も全部運ぶ。

**この非対称の帰結として、種目マスタ行のプリセット除外判定に `labels.is_empty()` を足さない。** ピンとインターバルはマスタ行自身のセルが値を運ぶので、記録もメニューも無いプリセットに付けた設定を守るために判定へ入っている。ラベルはマスタ行が運べないので、足しても**空のマスタ行が 1 本増えるだけ**で何も守れない。将来「ピンに倣って足す」修正が入らないよう、ここに理由を残す（`export_tsv_leaves_the_label_empty_where_it_has_no_meaning` が固定している）。

### 10. 上限は取り込みの門番。長さは **char** で数える

`MAX_LABELS = 6` / `MAX_LABEL_LEN = 12`。どちらも `MAX_PINS` / `MAX_PIN_LEN` と同じ立場で、**UI の制限ではなく取り込んだ JSON への門番**。長さを**バイトではなく char で数える**のは、バイトで切ると UTF-8 の途中で割れて panic するため（`MAX_PIN_LEN` と同じ）。12 文字は `"Hypertrophy"`(11) と「高重量ローレップ」(8) が収まる幅。

正規化は `core::normalize_exercises` と `core::set_labels` が `clean_labels` を**共有する**（`clean_pins` の先例）。2 経路に分けると「画面で消えたはずの値が取り込みで生き返る」「取り込みで落ちた値が画面からは入る」が起きる（`set_labels_normalizes_the_same_way_as_normalize` が唯一の主張）。

`clean_labels` の規則: 名前を **trim しない**（[トレーニングメニューを名前付きの種目リストとして持つ](routines-as-named-exercise-lists.md) の `normalize_routines` の規則）が空白だけの要素は落とす / **`split_whitespace` しない**（ピンが分割するのは TSV のセル内が空白区切りだからで、ラベルは 1 セル = 1 名前。「高重量 低レップ」を許したい）/ **同名は潰さない**（merge が正当に生む）/ **並べ替えない**（`Vec` 順 = 表示順）。

### 11. 削除は物理削除。過去ログの `label` は宙に浮いたまま残す

[トレーニングメニューを名前付きの種目リストとして持つ](routines-as-named-exercise-lists.md) の `normalize_routines` の doc がそのまま当たる — 「存在しない参照は消さない。後から相手のファイルを取り込めば生き返る。消すのは不可逆で、残しても被害は『候補に出ない』だけ」。設定タブの 1 タップで歴史的記録の一括書き換えを起こさない。

`Exercise` のように `archived` を持たせないのは、**ラベルの宙に浮いた参照では記録そのものが完全に無傷で可視**だから（種目の宙に浮いた参照は記録を「削除された種目」にする）。読み出し側が門番になり、画面は「指定なし」として見せる（`normalize_leaves_a_dangling_label_on_the_log`）。

## 理由

**分けた 2 つのフィールドが、この機能の 2 つの寿命に対応している。** 定義は種目の生涯にわたって数個で、印は日ごとに 1 つ。1 つのフィールド（例えば `ExerciseLog.label: String`）で表そうとすると、定義の一覧を「過去のログを全部走査して集める」ことになり、改名が不可能になる（過去のログを一括書き換えするしかない）。

**ID で参照し、改名で ID を変えない**という選択が、機能の目的（数か月の履歴を 1 本の線として見る）を型で守っている。名前参照の利点（2 台で寄る）は合流の梯子で回収できるので、天秤は明確に一方へ倒れた。

**`SCHEMA` を上げず、`skip_serializing_if` でバイト同一を保つ**のは、この機能を使わない利用者にとってこのリリースが**存在しないのと同じ**であるべきだから。プリセットに既定を配らない決定も同じ動機で、[指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md) が示した「宣言させる意味が無いものを持たせない」に従っている。

**同一判定に入れないこと・合流を 2 枝で呼ぶこと・写像のキーを組にすること**の 3 つは、どれも既存の ADR が一度踏んだ壊れ方の再演を防いでいる。新しい判断ではなく、既に払った授業料の適用先が 1 つ増えただけ。

**`labels_dropped` を `conflicts` と別の出口に出す**のは、`is_noop` と `change_text` がそれぞれ別のことを言うために存在しているから。数を `is_noop` に入れると「増えていないのに増えた」と言い、`conflicts` に積むと「入れ替わらないのに入れ替わる」と言う。どちらも確認画面の信頼性を削るので、3 つ目の出口を作るほうが安い。

## 結果（トレードオフ）

**ラベルは種目をまたいで共有できない。** 「Power」を 10 種目で使うなら 10 回打つことになる。共通プールを作らないことで得た構造上の安全（種目をまたぐ宙に浮いた参照が起きない）の対価。

**同じ名前で作り直しても過去の記録は戻らない。** ID が変わるので、削除したラベルの履歴は「指定なし」でしか見えない。**本物の罠**なので削除の確認文言に明記した。

**未使用のラベル定義は TSV では失われる。** JSON バックアップには入る。決定 9 の明示的なトレードオフ。

**TSV が 15 列になる。** 既存のシートで列幅や数式の範囲を設定していた人は作り直しになる（インターバルを足したときと同じ）。

**`MAX_LABELS` は 6 で、7 本目以降は取り込みで落ちる。** 落ちたことは警告文に出るが、落ちた定義を指すログは取り込み直しても生き返らない。上限を上げるのは後方互換なので安いが、カードの高さの予算（決定は [チップでラベルを選ぶと履歴とコピーが切り替わる](../ux/label-chips-switch-the-history-and-the-copy.md)）を確かめてからになる。

**`normalize_exercises` が `&mut IdGen` を取るようになった。** 重複 ID の再採番に要る。`normalize` は既に `ids` を持っているので呼び出しは 1 行だが、テストからの直接呼び出し 2 箇所は書き換えた。

**推移タブはラベルを見ない。** グラフも記録テーブルも全ログを混ぜて描く。別 PR（`exercise_series` / `pick_series` / `UiState.progress_*` に一切触っていない）。

> **改訂**（2026-09-10）: その別 PR が [ラベルに色を持たせ、推移タブのデータ点をその色で描く](../ux/label-colour-on-the-progress-dots.md)。`Label` に `color: String`（`#rrggbb`、`#[serde(default)]`、`skip_serializing_if` なし）が加わり、推移タブがチップでラベルを絞れるようになった。**この ADR の不変条件はどれも変わっていない** — 定義は種目に貼り付いたまま、参照は ID のまま、ラベルだけのログは書かないまま、TSV には色列を足していない（部位の色と同じ扱い）。既定色の門番は `clean_labels` の 1 箇所で、`Exercise.labels` を書く 5 経路がすべてそこに寄る。

## 検討した代替案

**ラベル名を文字列で `ExerciseLog.label: String` に持つ。** 定義のテーブルが要らず、TSV の往復も名前だけで閉じる。しかし改名が過去ログの一括書き換えになり、`P` → `Power` で「今日から別のラベル」になる（または全 sessions を走査して書き換える不可逆な移行が要る）。この機能の目的そのものを壊すので却下。

**全種目で共通のラベルプールを `Db.labels` に持つ。** 「Power」を 1 度定義すれば全種目で使える。しかし (a) ベンチの「P」とスクワットの「P」が同じものになり片方の改名がもう片方の意味を変える、(b) 参照の解決が「そのログの種目の中」で閉じなくなり種目をまたぐ宙に浮いた参照が起きる、(c) 種目ごとに関係ないラベルがチップ行に並ぶ。却下。

**`SetEntry` にもラベルを持たせる（セット単位の狙い）。** ドロップセットやピラミッドを 1 日の中で表せる。しかし「前回」の引き方が「そのラベルのセットだけを集める」になり、`ExerciseLog` を返せなくなる（`fmt_set` / `log_value` / コピーが全部セット列を前提にしている）。狙いはセッション全体の性質なので、粒度を 1 段細かくして得るものが無い。却下。

**プリセットに H / P / S を配る。** 初回起動で機能が見つかる。[指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md) の判断を逆走し、HPS を使わない大多数のカードが 50px 高くなる。却下。

**`SCHEMA` を 4 に上げる。** 「新しい形式である」ことを明示できる。しかし旧版が `RestoreError::Unsupported` で退避するようになり、**前方互換を積極的に壊す側になる**（`SCHEMA` の doc が明記している）。却下。

**`LabelFilter` に `Unlabeled`（ラベルなしのログだけ）を足す。** 「指定なし」の意味が厳密になる。しかし 6 か月ラベルなしで記録 → 今日 H/P/S を定義 → 以後全部付ける、という利用で「指定なし」を押すと**半年前の記録が出る**。`Any` なら昨日が出る。既存利用者の体験を変えないという要件はこちらでしか満たせないので却下（画面側の決定は [チップでラベルを選ぶと履歴とコピーが切り替わる](../ux/label-chips-switch-the-history-and-the-copy.md)）。

**`ExerciseLog::is_empty()` にラベルを入れる（ラベルだけのログを保存に値するとする）。** 選択がリロードを越えるようになる。しかしセット 0 本のログが `has_logs_on` を真にして、**その日が候補リストから永久に外れる**（`apply_routine` の ★ と同じ壊れ方）。逆に入れないと `dedupe_logs` が消すが、画面側が**そもそも空ログを作らない**設計なので食い違いも起きない。却下（`a_log_with_only_a_label_is_still_empty` が固定）。

**削除を `archived`（論理削除）にする。** 消したラベルを戻せる。種目でこれを採ったのは、宙に浮いた `exercise_id` が記録を「削除された種目」にして参照不能にするから。ラベルでは**記録が完全に無傷で可視**なので、同じ重さの対価が無い。物理削除 + 宙に浮いた参照を残すほうが、`Label` に状態を 1 つ増やさずに同じ可逆性（相手のファイルを取り込めば生き返る）を得られる。却下。

**同一判定（`log_rank`）にラベルを入れて、狙いが違うログを別物として扱う。** 「1 日 1 種目 1 ログ」の下では同じ日に 2 つの狙いを持てないので、入れても表現力が増えない。増えるのは決定 5 に書いた壊れ方だけ。却下。

**`labels_dropped` を `Conflict::LabelsDropped { n }` として積む。** 出口を増やさずに済み、既存の描画経路にそのまま乗る。しかし `change_text` が `conflicts.is_empty()` で分岐するので、記録が 1 件も入れ替わらないマージで「入れ替わる記録があります」が出る。確認画面が嘘をつくのは `change_text` の doc が最悪と呼ぶ形なので却下（決定 7）。

**種目マスタ行の除外判定に `labels.is_empty()` を足す。** ピン / インターバルとの対称性が保たれ、コードが読みやすい。しかしマスタ行にラベル列を書く手段が無いので、**空のマスタ行が 1 本増えるだけで何も守れない**。対称性のために無意味な行を出すほうが読み手を混乱させる。却下（決定 9）。
