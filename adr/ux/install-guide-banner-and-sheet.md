# ホーム画面への追加の案内を記録タブ末尾のバナー + 手順シートにする

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: ux
- **関連**: [JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md), [ルーターを使わずタブを enum signal で切り替える](../architecture/no-router-tab-enum-signal.md), [localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md), [記録タブをカレンダー + 選択日エディタの単一画面にする](record-tab-calendar-with-day-editor.md), [ヘルプの図を `assets/` の SVG に置き `include_str!` + `inner_html` で挿す](../architecture/help-figures-as-included-svg.md), [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md)

## 背景

iOS では Safari のタブと、ホーム画面に追加した standalone PWA とで `localStorage` が共有されない。先に Safari のタブで記録すると、ホーム画面に追加したあとで全部見えなくなる（[JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md)）。書き出し／読み込み（[書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](../storage/share-sheet-over-download.md)）が入った今は移せるが、**それを知らずに「消えた」と受け取る**経路は残るので、そもそも先に追加してもらうほうが早い。

[JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md) はこのリスクを受容する条件として「`display-mode: standalone` が false のとき控えめなバナーを出す」と決め、実装は `views::calendar` の 1 行テキストになっていた。

```rust
{(!is_standalone()).then(|| view! {
    <p class="install-hint" data-testid="install-hint">
        "記録を付ける前にホーム画面に追加してください。Safari のタブで付けた記録は引き継がれません"
    </p>
})}
```

このバナーには 4 つの問題があった。

1. **やり方が書いていない。** 共有ボタン → リストをスクロール → 「ホーム画面に追加」→ 右上「追加」の 4 手を知らない人は詰む。[JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md) が言う「読まなかった人は同じ穴に落ちる」より手前に、「読んだが実行できない人」がいた。
2. **standalone になると二度と見られない。** 機種を変えたとき、人に勧めるときに手順を確認できない。
3. **Android にも出る。** `is_standalone()` は OS を見ないので Android Chrome のタブでも出る。Android はタブと PWA でストレージを共有するので、この警告は**事実として偽**である。
4. **記録の導線の真上にあって邪魔。** 記録タブは「カレンダー → 選択日の入力欄 → 種目を追加」を 1 画面に載せた画面（[記録タブをカレンダー + 選択日エディタの単一画面にする](record-tab-calendar-with-day-editor.md)）で、その最上部に常駐する警告は毎回目に入る。筋トレ中に最短距離で記録するという前提に反する。

## 決定

**押せるバナー + 手順シートの 2 層にする。ボトムタブは 3 つのまま増やさない。**

### 層 1: 記録タブ**末尾**のバナー（本命の導線）

`<p class="install-hint">` を押せるようにし、押すと手順シート（[ヘルプの図を `assets/` の SVG に置き `include_str!` + `inner_html` で挿す](../architecture/help-figures-as-included-svg.md) の図解つき）が開く。表示条件は `!is_standalone() && storage_may_split()`。

**置き場所は `DayEditor` の外側の末尾**、つまり `<section class="calendar">` の最後の子である。`DayEditor` の中に入れると `.add-wrap`（「種目を追加」）の `position: sticky` な帯に覆われて読めない。sticky は `<section class="day">` で完結するので、その後ろなら干渉しない。

バナーには **✕（今後表示しない）を付ける。** 押すと二度と出ない。フラグは `Db` ではなく UI 専用キーに置く（[UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md)）。

箱は `<div>` で、「シートを開く」と「今後表示しない」を兄弟のボタンにする。`<button>` の入れ子は不正な HTML なので、バナー全体を 1 つのボタンにしたままでは ✕ を内側に置けない。

### 層 2: 種目タブ**冒頭**のリンク（保険と読み返し）

`.link-btn` から同じシートを開く。`storage_may_split()` では絞らない。

置く位置は冒頭の `.menu-note` の直後。末尾は `.add-wrap` の sticky に覆われるうえ、`ArchivedSection` が条件付きなのでアーカイブの有無で縦位置が動く。

### 判定は「iOS を当てる」のをやめ、「分離しないと分かっている環境を除く」に反転する

```rust
pub fn storage_may_split() -> bool {
    window()
        .navigator()
        .user_agent()
        .map(|ua| !ua.contains("Android"))
        .unwrap_or(true)
}
```

### トーンは枠線 + CTA の色だけに持たせ、本文は通常の文字色にする

`border: 1px solid var(--warn)` と CTA の `color: var(--warn)`。見出しは `--text`、2 行目は `--muted`。

## 理由

- **手順を必要とする人は、必ずバナーが「描かれる」状態にいる。** standalone で起動できている人にこの案内は要らず、できていない人には必ず描かれる。人に勧めるときも渡すのは URL なので相手側に出るため、勧める本人が手順を覚えている必要はない。だから導線としては 1 層で足りる。**ただし「描かれる」は「見える」ではない**（下記）。
- **記録の導線より下に置く。** [JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md) は「控えめなバナー」と書いていた。上に置いた常駐警告は控えめではない。末尾に落とせば、毎日使う人の視界からは外れる。**「気付かせる」と「邪魔しない」の両立を強さではなく位置で図った**が、この取引には後述の代償がある。
- **iPad を落とさないために判定を反転した。** iPadOS 13+ の Safari は既定で desktop-class の UA（`Macintosh; Intel Mac OS X …`）を出すので、`iPhone` / `iPad` を探しにいく実装は **iPad で false になる**。ストレージ分離は iPad でも同じく起きるので、それは改修前より保護が減る。除外側（Android）だけを列挙すれば iPad も未知のブラウザも自動的に警告対象に入る。`is_standalone()` が `match_media` の失敗を false（＝警告を出す側）に倒しているのと同じ方針である。
- **Chrome/Firefox on iOS を UA で分岐させない。** `CriOS` / `FxiOS` も UA に `iPhone` を含むのでバナーは出る。それらでも記録の分離は起きるので出るのが正しい。手順が Safari 専用である点は、手順①の注記「**Safari で開いてください。**他のブラウザだとこの手順は使えません」1 行で吸収する。図解を 2 種類持つより安い。
- **本文を `--warn` にしないのはダークモードで読みづらいから。** ダークの `--warn` は淡橙 `#e2a06a` で、`#0b0b0c` 上の輝度比は約 8.9 ある。だが 13px の日本語を橙一色で 2 行流すと実際に読みにくい。**輝度比が足りていることは読みやすさの証明にならない。** 警告であることは枠線と CTA の色で足りる。
- **`.notice` のようなベタ塗りにしない。** `.notice` は復元通知を起動時に 1 回だけ出す枠で、✕ で消せる。常駐するものに同じ強さを与えると、どちらが緊急かが読めなくなる。
- **ボトムタブを増やさない。** 記録・推移・種目はすべて日常操作で、ヘルプは一生に 1 回開く画面。ルーターを持たない構成（[ルーターを使わずタブを enum signal で切り替える](../architecture/no-router-tab-enum-signal.md)）ではタブが唯一の最上位ナビゲーションなので、その 1/4 を使い切る価値がない。
- **✕ を付けられるのは、種目タブに導線が残っているからである。** 消せるようにすると「消したあと Safari で記録して全損する」経路が開く。それでも入れられると判断した根拠は、**✕ が消すのはバナーだけで手順そのものは消えない**という点にある。層 2 を「保険」として最初から持っていたことがこの決定の前提条件になっている。もし層 2 が無ければ ✕ は入れられない。

## 結果（トレードオフ）

- **バナーは初期表示では折り返しの下にあり、スクロールしないと見えない。** これが末尾へ移したことの代償であり、この ADR で最も重い受容項目である。ビューポート 393×659・記録ゼロの実測で、バナーの上端は **685px**（ビューポート下端 659px より下）。記録が増えるほど遠のく（3 種目で文書高 1671px）。

  しかも `.add-wrap`（「種目を追加」）は sticky で常に画面内に留まる設計なので、**記録を始めるのにスクロールは要らない。** つまり守るべき対象＝「Safari のタブで初めて記録しようとしている人」は、バナーを 1px も見ずに記録を始められる。改修前の最上部バナーは邪魔ではあったが確実に見えていたので、**データ損失の防止という機能面では後退している。**

  それでもこの位置にしたのは、最初の画面に常駐する警告が記録の導線を邪魔するためである。**この ADR は「気付かせる」を「邪魔しない」に対して意図的に譲った記録である。** 後から「やはり届いていない」となったときは、位置を戻すのではなく「選択日にログが 0 件のときだけ `DayEditor` の直前に出す」など、対象を絞って可視域へ戻す方向を検討すること。
- **これは「気付かせる」だけの機能で、救済は別の仕組みが担う。** [JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md):39 の「注意書きであって解決策ではない。読まなかった人は同じ穴に落ちる」は**この ADR の範囲では今も真である**。ただし救済側は [書き出しは共有シートを主経路にし、iOS では `<a download>` を使わない](../storage/share-sheet-over-download.md) の書き出し／読み込みが埋めた。シートの「すでに Safari で記録してしまった場合」は独立したブロックに切ってあり、そこを「Safari のタブのまま書き出し → アプリ側で読み込み」に差し替えてある。**この案内の役割は「そもそも落ちない」ようにすることで、落ちたあとの救済ではない。**
- **[JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md):35 の「控えめなバナー」という文言からは逸脱している。** 枠線を `--warn` に上げ、押せるようにし、手順シートを足した。位置を末尾に落としたことで「控えめ」の意図（記録の邪魔をしない）は満たしているが、見た目の強さは上がっている。
- **PC ブラウザと、Android の「PC 版サイト」表示にも出る。** `storage_may_split()` は UA の `Android` だけを除くので、Mac/Windows のブラウザに加えて、**Android Chrome のデスクトップモード（UA が `X11; Linux x86_64` になり `Android` を含まない）でも出る**。どちらもタブと PWA でストレージを共有するので警告は事実として偽である。iPad を救うために採った除外リスト方式の裏側で、**誤りは必ず「余分に警告する」向きに出る**（保護が減る向きには出ない）ので受容した。精度が要るようになったら `navigator.maxTouchPoints` を足せる。
- **副産物として E2E が pre-commit に載った。** Desktop Chrome の UA には `Android` が入らないのでバナーが出る。`.githooks/pre-commit` が回すのは `--project=chromium --project=harness` だけなので、肯定側のテストがフィードバックループに入る。UA は `test.use({ userAgent })` で明示し、project ごとの UA に暗黙に依存させない。
- **コントラストは light 側が本文・CTA とも下限に近い。** CTA（`--warn` `#b4560c` on `#f7f7f8`）が約 **4.58**、本文（`--muted` `#6b7280` on `#f7f7f8`）が約 **4.52**。どちらも 13px で AA（4.5）のぎりぎり上なので、**フォントを小さくすることも背景を明るくすることもできない。** dark 側は CTA 約 8.88 で余裕がある。
- **✕ を押した人は、以後この警告を受け取れない。** 消したあとで Safari のタブに記録すれば全損する経路が開いたままになる。バナーは「気付かせる」役なので、✕ はその役を降ろす手段である。手順は種目タブ冒頭から読めるので手段は残るが、**能動的に探しに行かないと届かなくなる**点は受容したリスクである。
- **バナーは 1 度きりの評価でリアクティブではない。** `MediaQueryList` の change を購読していないので、ホーム画面に追加した直後の**同じタブ**では消えない。タブを切り替えれば `match tab.get()` が `Calendar` ごと作り直すので再評価される。standalone は別プロセスで起動するため実害はない。
- **シートは 2 箇所からインスタンス化される。** 記録タブと種目タブは排他レンダリングなので同時にマウントされることはないが、`RwSignal<bool>` の宣言が 2 箇所に重複する。`TabCtx` に並ぶ 5 つ目のコンテキストを増やすより安いと判断した。
- **種目タブが意味的に最良の置き場ではない。** インストール方法を探す人が「種目」を見ることはない。3 タブに設定画面が無いので「アプリ全体の説明の唯一の置き場」という消極的な理由で選んでいる。設定画面ができたらそちらへ移すべきである。

## 検討した代替案

**4 つ目の「ヘルプ」タブを作る**: 恒久的な置き場としては最も分かりやすい。`.tab-btn { flex: 1 }` なので実装コストもほぼゼロ。しかし記録・推移・種目はすべて日常操作で、ヘルプは一生に 1 回開く画面である。筋トレ中の最短距離を最優先する方針で、最上位ナビゲーションの 1/4 を使い切る価値がない。却下。

**初回起動時のフルスクリーンオンボーディング**: 確実に読ませられる。しかし決定的な問題は**「見た」フラグの置き場が無い**ことである。`Db` に足すのは「`Db` の JSON がそのままエクスポート形式」という前提（[JSON エクスポート/インポートを v1 に入れない](../storage/defer-export-import.md):56）に反し、別の localStorage キーを切るのは単一キー方針（[localStorage の単一キーに JSON 全体を持つ](../storage/localstorage-single-key-json.md)）に反する。フラグを持たないと毎回全画面で邪魔になる。却下。

**記録を付けさせないゲート（追加するまで入力を塞ぐ）**: データ損失を完全に防げる唯一の案。しかし「ちょっと見てみたい」を阻害し、ストレージ分離が起きない Android/PC の閲覧者まで丸ごとブロックする。判定が偽陽性を出したときの被害が「読めない案内が出る」から「アプリが使えない」に跳ね上がる。却下。

**`.notice` を再利用する**: 枠が既にあり実装が最小。却下の理由は 2 つある。(1) `.notice` は `storage::load` の復元通知を出す専用の枠で、`App` が `Option<String>` 1 本で駆動している。同じ枠に相乗りさせると、破損復元とインストール案内が同時に出せない。(2) `.notice` の ✕ は `notice.set(None)` するだけなので**セッション限りで、次の起動では必ず復活する**。永久に消せる ✕ より鬱陶しく、かつ消えないことの保証にもならない。却下。

なお「不可逆なデータ損失の警告を消せるようにするのは設計として逆」という論点はあるが、**消せる邪魔さのほうが害が大きいと判断して ✕ を入れた。** 緩和は上記のとおり層 2 の導線で、E2E で「✕ を押しても種目タブから手順が開ける」ことを固定してある。

**記録タブの最上部に置いたまま強くする**: 気付く確率は最大。しかし記録タブは毎日開く画面で、警告は追加するまで消えない。毎回目に入る警告は 2 日で背景になり、そのうえ記録の導線を下へ押しやる。**強さで解こうとすると邪魔さも一緒に上がる。** 位置を末尾に落とすほうが副作用が小さい。却下。

**`manifest.webmanifest` に `description` を足す**: インストール UI にアプリの説明を出せる。しかし iOS の「ホーム画面に追加」シートはタイトル・URL・アイコンしか表示しないので**対象プラットフォームでの効果はゼロ**である。さらに `public/manifest.webmanifest` は `$TRUNK_STAGING_DIR` に入るので編集すると `scripts/stamp-sw.sh` が計算する BUILD_ID が変わり、**全インストール済みクライアントがシェルを再ダウンロードする**。効果ゼロのために全員に再取得させる取引になる。却下。

**UA を見ず `is_standalone()` だけで出し続ける（現状維持）**: 実装がゼロ。しかし Android Chrome のタブに「Safari のタブで付けた記録は引き継がれません」と出るのは事実として偽であり、偽の警告は他の警告の信頼も削る。除外 1 語で消せるコストなので却下。

**`navigator.platform == "MacIntel" && maxTouchPoints > 1` で iPad を積極的に判定する**: 精度は上がり、PC への誤表示も消える。しかし判定式が 3 つの API に増え、どれかが将来変わると**保護が静かに減る方向**に壊れる。除外リスト方式なら壊れても警告が余分に出るだけで、データは守られる。精度より壊れ方の向きを取った。却下（必要になったら足せる）。
