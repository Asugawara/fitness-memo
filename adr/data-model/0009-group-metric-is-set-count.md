# ADR-0009: 部位別の指標を volume ではなくセット数にする

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: data-model
- **関連**: [ADR-0007](0007-exercise-kind-explicit.md), [ADR-0004](../architecture/0004-no-chart-library-hand-rolled-svg.md)

## 背景

要件は「仕事量（レップ数×重さ）をグラフにして過去と比較できる」と「部位ごとに種目をグループ化する」。推移タブの対象セレクタは部位と種目の両方を選べる設計にした。

種目別は素直に `volume = Σ(weight × reps)` で出せる。では**部位別**は何を足せばよいか。

素直に「その部位の全種目の volume を合算する」とすると、[ADR-0007](0007-exercise-kind-explicit.md) で決めた `Kind` の混在が問題になる。

## 決定

**部位別の指標は volume ではなく「セット数」にする。**

```rust
/// 部位別の推移は **セット数**（Kind 非依存なので混在部位でも合算できる）
pub fn group_set_series(db: &Db, g: GroupId, from: NaiveDate, to: NaiveDate)
    -> Vec<(NaiveDate, f64)>;
```

要件の「レップ数×重さのグラフ」は種目別グラフ（`exercise_series`）が担う。部位別は「その部位をどれだけやったか」を見るための別の軸として位置づける。

## 理由

**volume を部位で合算すると意味を失う。**

- 体幹の部位はプランク（`Duration`）とクランチ（`Bodyweight`）が中心で、どちらも `weight = 0` が普通
- `Kind::Bodyweight` と `Kind::Duration` の指標は `Σ(reps)` なので、volume として合算すると 0 になる
- 結果として**体幹の部位グラフは恒常的にほぼ 0 の平坦な線**になり、実際には毎週鍛えているのに「何もしていない」ように見える

仮に `Kind` ごとの指標をそのまま足すと、もっと悪い。胸の部位で「ベンチプレス 1,080（kg·回）+ プッシュアップ 40（回）」を足して 1,120 という数字は単位を持たない。**次元の違う量の和**なので、増減の意味が読めない。

セット数を選んだ理由は 3 つある。

- **`Kind` 非依存なので混在部位でも合算できる。** `l.sets.len()` を足すだけで、単位は常に「セット」。
- **週あたりセット数は部位のトレーニング量として標準的な指標である。** 筋力トレーニングの文献やアプリで「部位あたり週 10〜20 セット」という形で広く使われており、利用者が既に持っている感覚と一致する。
- **部位別グラフの用途に合っている。** 部位を見るときの問いは「胸を十分やれているか」「脚をサボっていないか」であって、「胸の総 kg·回が伸びているか」ではない。伸びを見るのは種目別グラフの仕事である。

## 結果（トレードオフ）

- **部位別グラフでは強くなったかどうかが分からない。** セット数は量であって強度ではないので、同じ 12 セットを 60kg でやっても 80kg でやっても同じ高さになる。**要件の「これまでの比較」を部位別グラフは満たしていない**。この責務は種目別グラフに割り当てたうえで、推移タブの対象セレクタで両方を選べるようにしている。
- **同じ画面で 2 種類の単位が出る。** 対象が種目なら `kg·回` / `回` / `秒`、部位なら「セット」。Y 軸の意味が対象によって変わるので、選択中の対象と単位を明示する必要がある。
- **セット数はセットの重さも長さも区別しない。** 1 レップだけ入れたセットも 20 レップのセットも 1 セットである。空セット（`reps == 0`）は保存時に破棄されるので数に入らないが、「1 レップのセットを 20 個」のような入力をすれば量を偽装できる。個人用の記録アプリなので問題にしない。
- **`group_set_series` はアーカイブ済み種目も含める。** `Db::exercise_ids_of_group` がアーカイブ込みで返すのを使っている。含めないと過去のグラフだけが後から欠ける。この性質は部位の削除ガード（種目タブ）がアーカイブ済みを数えることと対になっている。
- 部位別と種目別で関数が 2 本に分かれるが、どちらも `Vec<(NaiveDate, f64)>` を返すので `chart.rs` は 1 つのままで済む。

## 検討した代替案

**部位別も volume で合算する**: 要件の文言に最も近い。しかし `Kind` が混在する部位で恒常的に 0 になり、次元の違う量を足すことになる。「動くが意味がない」グラフが 1 つ増えるだけなので却下。

**部位別を `Kind` ごとに 3 本の線に分ける**: 情報は失われない。しかし 1 つの部位に 3 本の線が出るのは「非常にシンプル」の要件から遠く、しかも `Weighted` だけの部位では 2 本が常に 0 になる。却下。

**総レップ数にする**: `Kind` 非依存で合算でき、セット数より粒度が細かい。しかし `Duration`（秒）が混ざると「プランク 60 秒 = 60 レップ」として胸のレップ数と同列に足されてしまう。セット数はこの汚染を受けない。却下。

**部位別グラフを作らない**: 種目別だけにすれば単位問題が消える。しかし「部位ごとにグループ化する」という要件が閲覧側で何の役にも立たなくなる（追加シートの並びだけになる）。経過時間は部位ごとに出しているのだから、量も部位ごとに見られるべきと判断した。
