# 有酸素の区間を SetEntry の任意フィールドとして持つ

- **状態**: 採用
- **日付**: 2026-10-27
- **カテゴリ**: data-model
- **関連**: [指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md)（種目に種類を持たせない方針の出所）, [ドロップセットをメインセットにぶら下がる段（`SetEntry.drops`）として持つ](drop-sets-as-stages-under-the-main-set.md)（セットへ任意の欄を足す前例）, [数値入力に `type="number"` を使わない](../ux/text-input-not-number.md), [有酸素のカードは 1 行 = 1 区間、欄は機種ごとに最大 3 つ](../ux/cardio-card-fields-per-machine.md)

## 背景

筋トレの記録は `SetEntry { weight, reps }` の 1 行 = 1 セットで、重量と回数が入る。有酸素（トレッドミル・エアロバイク・ローイングなど）は、時間・速度・傾斜・距離・レベルを記録したいが、筋トレの 2 欄には載らない。

マシンの有酸素は「途中で傾斜や速度を変える」のが普通で、区間ごとに値が変わる。終わってから合計だけを 1 件として残すと、途中で変えた傾斜が数字として残らない。

選択肢は大きく 2 つあった。**有酸素専用の記録の型を別に持つ**か、**既存の行（`SetEntry`）に任意の欄を足す**か。

## 決定

**有酸素の 1 区間を `SetEntry` の任意フィールド `cardio: Option<Cardio>` として持つ。** `Cardio` の欄はすべて任意。

```rust
pub struct SetEntry {
    pub weight: u32,
    pub reps: u32,
    /// 有酸素の区間。筋トレの行では `None` のままキーごと出さない。
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub cardio: Option<Cardio>,
    // …（既存のフィールドは変えない）
}

pub struct Cardio {
    pub sec: Option<u32>,    // 時間（秒）。UI は分で打つ
    pub m: Option<u32>,      // 距離（メートル）。UI は km（ローイングだけ m）
    pub kmh: Option<f32>,    // 速度（km/h）
    pub incline: Option<f32>, // 傾斜（%）
    pub level: Option<u32>,  // レベル
}
```

- 有酸素の行は `weight = 0`, `reps = 0` で保存する。
- 有酸素かどうかは **種目の部位が「有酸素」かどうかで決める**。種目に「加重 / 自重 / 時間」のような種類のフィールドは持たせない（[指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md) の方針を守る）。
- 欄を足すときは `#[serde(default, skip_serializing_if)]` を付け、**`SCHEMA` は上げない**。有酸素を使わない人の JSON はバイト単位で変わらない。
- 単位は保存側で固定する（時間は秒、距離は m）。表示と入力で分・km に直す（Hevy の公開 API も保存単位を m と秒に固定している）。

## 理由

**1 行 = 1 セットの形を崩さない。** 同じセットの判定（`same_set` / `same_sets`）、マージの順位（`log_rank`）、前回コピー、正規化、TSV の書き出しは、`SetEntry` の一覧を前提に書かれている。有酸素を別の `Vec` にすると、並べ替え・メモ・時刻・削除・前回コピー・マージを二重に持つことになる（[検討した代替案](#検討した代替案) (4)）。

**既存の任意欄の前例に乗る。** ドロップセットは `SetEntry.drops` を空なら出さない任意欄として足された（[ドロップセットをメインセットにぶら下がる段（`SetEntry.drops`）として持つ](drop-sets-as-stages-under-the-main-set.md)）。同じ規則に従えば、旧 JSON はそのまま読め、`SCHEMA` も変わらない。

**Garmin FIT と Android Health Connect が同じ形をしている。** どちらも「要約（セッション）と区間（lap / segment）」を持ち、区間は空でよい。1 行が普段の形で、区間は任意という分け方はこの業界の標準的な形に近い。Bluetooth FTMS のトレッドミル規格も、中核を速度・傾斜・距離・経過時間に置いており、欄の候補の根拠になる。

**保存単位を固定して表示で直す。** 単位を入力者の好みで保存すると、集計で単位が混ざる。wger のように回数欄へ「分」を入れる方法は、集計の単位が崩れるので採らなかった。

## 結果（トレードオフ）

**旧版のアプリで開いて保存すると `cardio` が落ちる。** 旧版は `Cardio` を知らないので、読んで書き戻す時に欄が消える。ドロップセットや打った時刻（`SetEntry::at`）と同じ性質で、新版で保存し直せば戻る。

**取り込み確認の「セット」数は区間も数える。** 集計の定義を変えず、画面上の「セット」という語に区間も入る。

**利用者が自作した同名の「有酸素」部位があると、部位が 2 つ並ぶ。** 印（`UiState::cardio_group_added`）は 1 回だけ足すための目印で、名前の衝突は防げない。

**区間の欄が増えると行の判定が複雑になる。** 同じセットの判定とマージの順位に `cardio` を入れた。欄を足す PR は、この 2 関数と正規化の対応を同時に見ること。

## 検討した代替案

**(1)「合計だけ」を記録する。** 全機種で固定の 4 欄（時間・距離・傾斜・速度）を 1 件として持ち、途中の変化はメモに書く。途中で変えた傾斜が数字として残らないので採らなかった。

**(2)「ライブ計測」にする。** 開始ボタンで時間を計り、± で区間を切る。マシンの上で操作が要り、押し忘れで区間がずれる。終わってから表示の値を写すほうが確実。

**(3) 種目に種類を持たせる（`Exercise.kind` を復活させる）。** [指標を種目の属性ではなくグラフの表示設定にする](metric-is-a-view-setting.md) で捨てた判断の逆走になる。

**(4) `ExerciseLog` に別の `Vec<Cardio>` を持つ。** 並べ替え・メモ・時刻・削除・前回コピー・マージを二重に持つことになる。

**(5) 時間と距離の切り替えボタンを置く。** 機種ごとに「設定した値」と「終わって写す値」を欄として分ければ、切り替えは要らない。
