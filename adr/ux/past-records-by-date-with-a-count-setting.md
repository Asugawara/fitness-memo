# 前回までの記録を日付で出し、何回分出すかを表示設定にする

- **状態**: 採用
- **日付**: 2026-08-23
- **カテゴリ**: ux
- **関連**: [「前回をコピー」はセットが空のときだけ出す](copy-button-only-when-empty.md)（「前回 —」の表記を本 ADR が改訂。コピーの挙動は変えない） / [メモは種目カードのトグル 1 つで開き、閉じても薄字で残す](exercise-and-set-notes-behind-one-toggle.md)（決定 4 が「`.last-row` の直下にメモを置かない」と決めていた。**本 ADR はそれを守る**） / [コピーは種目メモとセットメモを持ち込む（体調メモと体重は持ち込まない）](copy-carries-the-notes.md)（**運ぶことと履歴に並べることは別の要件**。コピーは今までどおり両方を運ぶ） / [UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md)（置き場の 3 条件） / [言語はブラウザに従い、選んだらそれを優先する](language-follows-the-browser-then-the-setting.md)（設定行 + サブページ + `.segmented` の型） / [設定タブの入口を節の一覧にし、中身は 1 階層下ろす](settings-as-a-list-of-sections.md)（6 行目の置き場所） / [指標を種目の属性ではなくグラフの表示設定にする](../data-model/metric-is-a-view-setting.md)（永続化する / しないの線） / [1 日 1 種目 1 ログにする](../data-model/one-log-per-exercise-per-day.md)（`Vec` になるのは日をまたぐ方向） / [チップでラベルを選ぶと履歴とコピーが切り替わる](label-chips-switch-the-history-and-the-copy.md)（決定 6 を守ったうえで 4 列目を足し、決定 4 の `first()` 規則を強めた相手）

## 背景

種目カードの `.last-row` は**前回の記録を 1 件だけ**、しかも**相対日数**で出していた。

```
前回 8日前  60×10 60×8   1,080
```

このアプリの中核は「前回何をどれだけやったかを見て、同じかそれ以上をやる」ループだが、
実際にトレ中に効く判断は**直近数回でどう動いているか**であることが多い。
60 → 60 → 60 と 3 回止まっているのか、55 → 57.5 → 60 と上げてきたのかで、
今日 62.5 に行くかどうかが変わる。1 件だけでは、その差がカードから読めない。

検討の途中で「その日のメモも一緒に出す」案を実装して実機で見た。**やめた。**
理由は下の「なぜメモを出さないのか」に書く。

## 決定

### 1. 表記を相対日数から日付にする

`views::fmt_date` をそのまま使う（`8/20 (水)` / `Aug 20 (Wed)`）。`Lang::last_log` は削除した。

### 2. 何回分出すかを設定にする。1〜3、既定 1

設定タブ 4 行目「表示数」→ `.segmented` で `1 回分 / 2 回分 / 3 回分`。
保存先は `fitness-memo/ui/v1` の `history` フィールド。

### 3. メモは出さない

`.last-row` に出すのは `日付 / セット列 / volume` の三つ組だけ。
その日の種目メモとセットメモは**今までどおりコピーで今日のカードへ運ばれる**が、
履歴としては表示しない。

### 4. 「前回」1 件しか見ない判断は必ず `first()` を通す

`show_copy` / `uses_weight` / `copy_last` の 3 つ。表示件数がいくつでも先頭 1 件だけを見る。

★ **`uses_weight` はこの規則から 1 段強くなった**（[チップでラベルを選ぶと履歴とコピーが切り替わる](label-chips-switch-the-history-and-the-copy.md)）。ラベルで履歴を絞れるようになったので、`history` の `first()` を見ると `[S]`（履歴 0 件）に切り替えたとたんに「重量未入力」の警告が全行から消える。「この種目は重量を使うか」は**種目の性質**でモードの性質ではないので、**無絞りの `core::last_log_before` を引く専用 Memo** に差し替えた。下の「表示設定は表示だけを変える」をラベルにも降ろしたもので、`show_copy` / `copy_last` は絞り込み後の `history` を読み続ける（そちらは「今この画面が見せているもの」に従うのが正しい）。

### 5. 並びは降順（新しい順）

`history[0]` が「前回」で、`core::last_log_before` と必ず一致する。

### 6. 3 列は subgrid で全エントリ揃える

`.last-rows` が `grid-template-columns: max-content 1fr max-content` を持ち、
各 `.last-row` が `grid-template-columns: subgrid` でそれを借りる。
日付は左揃え、指標は `justify-self: end` で右揃え。行間は親の `row-gap`。

★ **ラベル定義がある種目では 4 列になる**（[チップでラベルを選ぶと履歴とコピーが切り替わる](label-chips-switch-the-history-and-the-copy.md)）。ラベル名を `.when` と同じ span に入れると日付列の `max-content` がラベル名で決まってセット列の開始位置がずれ、**この決定が無効になる**。独立した 4 列目にすればラベル列の幅は全エントリのラベル名で 1 回決まり、日付列は日付だけで決まるので**桁は縦に揃ったまま**。列幅は `max-width: 4em` + ellipsis で cap する（cap しないと 12 文字のラベル 1 本で `.sets` が 234px → 80px になり `100×10` が 3 行に折り返す。`6em` でも `100×3` ×4 が 2 行になるので足りない — どちらも 393×852 の実測）。

★ **`data-labels` 属性と 4 つ目の span は必ず同じ Memo 1 本から出す。** subgrid 軸に implicit track は無いので、3 トラックの親に 4 セル入れると 4 個目が次の行へ落ち、4 トラックに 3 セルだと `.metric` が `1fr` 列に座る。定義が 0 本の種目では属性も span も出ないので、**既存カードは 1px も動かない**（`e2e/label.spec.mjs` が実測で固定している）。

## 理由

### なぜ日付で、経過日数を併記しないのか

**件数が可変になった時点で「前回 / 前々回 / 前々々回」は破綻する。** 3 番目を何と呼ぶかに
答えが無いし、設定で 2 に減らした人の画面から「前々々回」だけ消えるのも読みにくい。

では「3日前 / 10日前 / 17日前」かというと、それも違う。**縦に並べると引き算が要る。**
週次でやっている人にとって意味があるのは「毎週水曜にやっている」ことで、
それは `8/20 (水) / 8/13 (水) / 8/6 (水)` と並べれば**曜日が縦に揃って一目で出る**。
数字の列からは出てこない。

経過日数を捨てるわけではない。**ヒーロー（`elapsed`）と部位チップに残っている**ので、
「最後にトレしてから何日空いたか」はカードの外で読める。`core::humanize_days` も
そのまま残した。カードから消えるのは「その種目の前回から何日」だけで、
それは日付と今日を見比べれば分かる。

`views::progress` の記録テーブルが既に `日付 / 詳細 / 指標` の三つ組で同じことをしている。
**カードの履歴はそのミニチュア**になり、2 つの画面で同じ読み方ができる。

### なぜ最大 3 なのか（5 ではなく）

要件は「最大でも 5」だったが、`.last-row` は 12px の 1 行とはいえ、5 件並べると
カードの上半分が 5 行になる。

[メモは種目カードのトグル 1 つで開き、閉じても薄字で残す](exercise-and-set-notes-behind-one-toggle.md) が
「重量を打つ → 回数を打つ → `+ セット` の動線に何も割り込ませてはいけない」と決めており、
5 種目のカードに 5 行ずつ載ると**入力欄が下へ押し出される。** 3 なら
「伸びているか停滞か」を読むには足りる。それ以上は推移タブ（グラフ + 記録テーブル）の担当で、
既に専用の画面がある。**既定 1 / 上限 3 / 明示的なオプトイン**の三点セットで、
選ばなかった人のカードは 1px も動かない。

### なぜメモを出さないのか

**一度実装して実機で見てから外した。** 判断は絵を見るまで付かなかったので、経緯を残す。

出す案には筋があった。「グリップは広め」「肩に違和感」は次のセットの決め方に直接効くし、
[コピーは種目メモとセットメモを持ち込む（体調メモと体重は持ち込まない）](copy-carries-the-notes.md) で
**コピーは既に両方を運んでいる**ので、「運ぶのに見えない」という非対称もあった。

実機で崩れたのはここである。**この 3 行は数値を縦に読む場所だった。**

```
8/16 (日)   60×10  60×9  60×6      1,500
8/9  (日)   57.5×10  57.5×8         1,035
8/2  (日)   55×10  55×9               990
```

`.when` と `.sets` は `tabular-nums`、`.metric` は `margin-left: auto` で右端に揃う。
つまり左に日付の列、右に指標の列があって、**その 2 列を上下に走らせるために日付表記にした**
（この ADR の決定 1 そのもの）。ここへメモを挟むと行の間隔が空き、
列を目で追うのに視線が横へ逃げる。3 件で 6〜8 行になると、**日付表記にして得た
「毎週水曜にやっている」の読みやすさが、自由文で相殺される。**

そして [メモは種目カードのトグル 1 つで開き、閉じても薄字で残す](exercise-and-set-notes-behind-one-toggle.md) の
決定 4 は、まさにこれを禁じていた。

> `.last-row` の直下に置くと 12px `--muted` の行が 2 本続く。トークンが同一なので
> 「前回の記録の続き」に読める。

置くのが本当に前回の記録の続きなら誤読にはならない、と考えて一度は通した。
**誤読の問題は消えたが、列が崩れる問題が残った。** 決定 4 は守るのが正しかった。

非対称のほうは実害がない。コピーを押せばメモは今日のカードに入り、
そこでは `.ex-note-read` / `.set-note-read` として今までどおり読める。
**運ぶことと、履歴として並べることは別の要件だった。**

### なぜ「前回」1 件しか見ない判断を `first()` に固定するのか

`uses_weight`（「重量未入力」の警告）が `last` を読んでいた。素直に
`history.iter().any(..)` へ置き換えると、**表示件数という表示設定が警告の出方を変える。**

具体的には、加重懸垂を 3 週間前に 1 度だけやった人が件数を 3 にした瞬間、
もう何週間も自重でやっている懸垂の全行に「重量未入力」が戻ってくる。
`copy_last` も同じで、「どれがコピーされたか」が件数で変わってはいけない。

**表示設定は表示だけを変える。** これをコードのコメントと E2E 2 本
（`history.spec.mjs` の 8 / 9）で固定した。件数が 0 にならないこと
（`core::history_count` が `1..=MAX_HISTORY` を返す不変条件）がこの式の前提なので、
そちらもホストのテストで押さえてある。

### なぜ降順なのか

`views::progress` の記録テーブルが `rows.reverse(); // 新しい順` で降順にしている先例がある。
加えて、**件数 1 のとき現状とピクセル一致する**こと、そして
**カード見出し直下の行が常に「前回」**という不変条件が絵と一致することが決め手だった。
`first()` 規則の土台がそこにある。

### なぜ列を subgrid で揃えるのか

エントリごとに flex で組んでいたときの絵がこうだった。

```
8/23 (日)   60×10  60×9  60×6      1,500
8/22 (土)   57.5×10  57.5×8         1,035
8/9 (日)   55×10  55×9              1,045     ← 1 桁ぶん左にずれる
```

**日付の幅が桁数で変わるので、セット列の開始位置が行ごとに動く。** `tabular-nums` は
数字の幅を揃えるが、`8/9` と `8/23` の**文字数の差**は揃えない。1 件しか出していなかった
ころは存在しなかった問題で、複数行にした瞬間に出てきた。

これは細かい見た目の話ではなく、**この ADR の決定 1 を無効にする。** 相対日数をやめて
日付にしたのは「縦に並べたとき曜日が揃って週次のリズムがそのまま読める」からで、
セット列がぎざぎざなら数字を縦に追えない。日付を揃えても数値が揃わなければ半分しか効かない。

列の実体を親が 1 つ持ち、各エントリがそれを借りる形にすれば、
**列幅は 3 エントリ全体の max-content で 1 回決まる。** これが subgrid の定義そのものである。

- **`min-width` で日付列に固定幅を与える案**は却下した。`12/31 (月)` と `Aug 30 (Wed)` の
  両方に足りる値を言語ごとに手で置くことになり、フォントが変われば崩れる。
  max-content なら中身から決まる
- **`fmt_date` をゼロ埋め（`08/03`）にする案**も却下した。あれは日エディタの見出し・
  推移タブの記録テーブル・グラフの `aria-label` が共有しているので、
  履歴 3 行の都合で全画面の日付表記を変えることになる
- **日付を右揃えにする案**も却下した。列は揃うが、ブロックの左端がぎざぎざになって
  カードの内側余白と合わなくなる。桁数の差は日付列の**右**に出すのが正しい

`row-gap` を親に置いたので `.last-row` は margin を持たない。**gap は「間」だけに入るので、
件数 1（既定）のときは高さに 1px も乗らない。** subgrid は Baseline widely available
（Safari 16 / Chrome 117）なので、[ブラウザサポートは Safari を基準にし、polyfill を入れない](../architecture/browser-support-policy.md)
の方針どおりフォールバックを持たない。

### なぜ `UiState` に置き、なぜ `Metric` / `Period` は永続化しないのか

[UI の状態を `Db` に入れず別キーに置く](../storage/ui-state-in-separate-key.md) の 3 条件を満たす。
`Db` を参照しない（ただの数）、失われても既定 1 に戻るだけ、移行も退避も要らない。
`Db` に入れると書き出しファイルに混入し、別端末へ取り込んだときにその端末の好みが上書きされる。

推移タブの `Metric` / `Period` を永続化していないのとは線が違う。あちらは
**1 画面の中で見る角度を切り替えるもの**で、切り替えたこと自体がその場の操作である。
こちらは**毎日開くカードの常設の好み**で、開くたびに選び直させる意味がない。

**`Option<i64>` で持つ。** `Option<u8>` にすると `{"history": 999}` で deserialize が落ち、
**`UiState` 全体が飛んで `lang` と `install_hint_dismissed` まで巻き添えになる。**
これは [言語はブラウザに従い、選んだらそれを優先する](language-follows-the-browser-then-the-setting.md) が
`lang` を `Option<Lang>` ではなく `Option<String>` にした理由そのもので、
今は `lang` が同居しているぶん被害が大きい（言語選択が飛ぶ）。整数なら何でも受けて、
丸めは `core::history_count`（ホストの `cargo test` が届く側）でやる。

範囲外は捨てずに **`clamp`** する。`clean_pins` が上限を超えたピンを切り詰めるのと同じ規則で、
`DEFAULT_HISTORY` が下端と一致するので未設定・0・負がすべて 1 に落ちる。

### なぜシグナル（`HistoryCtx`）に載せるのか

`storage::history_count()` を直接呼ぶと、**`history` Memo は `Db` を購読していて
1 打鍵ごとに走る**ので、`localStorage.getItem` + `serde_json::from_str` が
打鍵 × カード枚数だけ走ることになる。起動時に 1 回読んでメモリに置くのは
`saved_lang` → `LangCtx` と同じ作法である。

`OpenGroupCtx` / `SettingsPageCtx` が永続化されないのとも違う。あちらが
プロセス内の寿命に留まるのは `Db` の ID を持つからで（種目が消えると宙に浮く）、
こちらはただの数なので置ける。

### 設定行を 4 行目に置く理由

現在の並びは**探しに来る頻度順**である。先頭のエクスポート / インポートは
「データを失う前に見つけてもらう」ため（[設定タブの入口を節の一覧にし、中身は 1 階層下ろす](settings-as-a-list-of-sections.md)）、
末尾の言語は「一生に一度の操作」だから
（[言語はブラウザに従い、選んだらそれを優先する](language-follows-the-browser-then-the-setting.md)）。
表示の好みはその中間で、データ（メニュー / 種目）の後・常設導線（ホーム画面追加）の前になる。

**行のラベルは「表示数」にする。** 最初は「前回までの記録」にしていたが、他の 5 行
（エクスポート / インポート・トレーニングメニュー・種目・ホーム画面への追加のしかた・言語）が
どれも 2〜10 文字の短い名詞なので、1 行だけ説明文めいて浮いた。**何の数かはラベルに書かない。**
右端に現在値（`1 回分`）が出ていて、入れば注記が説明する。
[設定タブの入口を節の一覧にし、中身は 1 階層下ろす](settings-as-a-list-of-sections.md) が
「4 行とも『押すと先がある』もので揃っている」を大事にしたのと同じで、**一覧は行の形が揃っていることが読みやすさそのもの**である。
ラベルを削ったぶん、`history_note` が説明を持つ。

**右端には件数ではなく現在値を出す。** 言語行が `endonym()` を出しているのと同じ形だが、
**素の数字だと「種目 28」「メニュー 0」と同じ件数に見えて意味が読めない**ので、
`3 回分` / `3 sessions` と単位を付けた。行の右端とセグメントのラベルに
**同じ `Lang::n_past_sessions` を使う**ので、2 つが食い違うことがない。

「日」ではなく「回」なのは、出すのが直近 N 日ではなく**その種目をやった直近 N 回**だから。
3 回分が 3 週間にまたがることは普通にある。

## 結果（トレードオフ）

- **メモだけ書いた日は履歴に出ない。** `last_logs_before` は
  [1 日 1 種目 1 ログにする](../data-model/one-log-per-exercise-per-day.md) 側で決まっている
  `!sets.is_empty()` を通す。「今日は肩が痛いので飛ばす」とだけ書いた日は
  実施日ではないので、ドット・月フッタ・グラフ・経過日数と同じくここにも出ない。
  外すと `apply_routine` が 0 セットのログを種に使い始めるので、フィルタは変えない。
- **体調メモ（`Session.note`）は出さない。** 日に属していて種目に属していないので、
  [コピーは種目メモとセットメモを持ち込む（体調メモと体重は持ち込まない）](copy-carries-the-notes.md) と同じ線を引いた。
- **年が出ない。** `views::fmt_date` は年を持たないので、1 月に 3 回分を見ていると
  `12/28 (土)` が去年か今年か絵からは読めない。`views::progress` の記録テーブルも
  同じ性質なので、ここだけ新しい書式を作ることはしなかった。
- **書き出しに載らない。** 別端末へ復元しても件数は移らず、既定 1 で始まる。
  `UiState` に置いた以上そうなる（同 ADR のトレードオフそのもの）。
- **`last_logs_before` は `limit` 件見つかるまで全セッションを走査する。**
  `find_map` は最初のヒットで止まっていた。ただし「1 件も無い」ケース
  （種目を追加した直後 = 最も頻繁な状態）は**現状も全走査している**ので、
  オーダーは悪化しない。
- **`data-testid="last-log"` が複数になった。** 従来は 1 カードに 1 つだったので、
  `toHaveText` に配列を渡す形に変わる。既存 E2E はこの testid を 1 度も参照していなかった。
- **設定タブが 6 行になった。** 56px × 6 + gap 8px × 5 = 376px でまだスクロール無しに収まるが、
  「5 行はスクロール無しで見える」と書いた

## 検討した代替案

**日付ではなく「前回 / 前々回 / …」を続ける**: 件数 1 のままなら最も自然だが、
3 番目を何と呼ぶかに答えが無く、件数を変えると呼び名が動く。却下。

**日付に経過日数を併記する（`8/20 (水) 3日前`）**: 情報を落とさないが、複数行で
「3日前 / 10日前 / 17日前」と引き算した数が並ぶ。393px 幅では折り返しも増える。
経過日数はヒーローと部位チップに残っているので、ここで二重に持つ必要がない。却下。

**最大を 5 にする**: 要件が許していた上限。`.segmented` は 5 択でも成立する
（推移タブの期間が実証済み）ので UI は作れるが、5 種目のカードに 5 行ずつ載ると
入力欄が下へ押し出される。3 行あれば「伸びているか停滞か」は読める。却下。

**その日のメモを記録の下に一緒に出す**: 一度実装して実機で見た。「グリップは広め」
「肩に違和感」は次のセットに効くし、コピーは既にメモを運んでいるので筋はあった。
しかし**数値を縦に読む場所に自由文が挟まると列が崩れ**、日付表記にして得たものを
相殺する（上記「なぜメモを出さないのか」）。却下。

**メモの件数を別の設定にする**: 「記録は 3 件、メモは 1 件」ができる。しかし
メモを出さないと決めた以上、そもそも数える対象が無い。設定行が 2 本になる分の
コストだけが残る。却下。

**前回のメモをメモのトグル（`＋ メモ`）の中に隠す**: 列は崩れない。しかし
そのトグルは**今日のメモを書くための入口**で、開くと入力欄が出る。そこに読み専用の
過去のメモが混ざると、どれが今日書いているものか分からなくなる。却下。

**昇順（古い順）に並べ、最新を入力欄の隣に置く**: 最新と今日の入力が近くなる。
しかし「前回」がカードのどこにあるかが件数で動き、`first()` 規則が絵と食い違う。却下。

**`.row-count` に素の数字（`3`）を出す**: 短い。しかし「種目 28」「メニュー 0」と
同じ件数に見えて、3 が何の 3 なのか読めない。却下。

**行のラベルを「前回までの記録」にする**: 何の数かがラベルだけで読める。しかし他の 5 行が
短い名詞で揃っている一覧に説明文めいた 1 行が混ざり、行の形が崩れる。何の数かは
右端の現在値と注記が担える。却下。

**推移タブの記録テーブルへ誘導して、カードは 1 件のままにする**: 新しい設定が要らない。
しかしトレ中にタブを移ってスクロールして戻るのは、このアプリが避けている動線そのもの。却下。
