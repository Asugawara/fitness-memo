# 表からの取り込みは利用者に何も聞かない

- **状態**: 採用
- **日付**: 2026-08-13
- **カテゴリ**: ux
- **関連**: [他アプリからの移行はスクショの文字起こしを貼り付けて受ける](migrate-by-ocr-paste.md)（破棄。撤去の理由がこの ADR の出発点）, [テキスト取り込みは「足すだけ」に固定し、部位を増やさず、`at` を書かない](../data-model/text-import-is-merge-only.md)（破棄。規則はここへ引き継ぐ）, [CSV を二次形式として足し、正は JSON のままにする](../storage/csv-as-a-secondary-lossy-format.md), [公開リンクの Google スプレッドシートを URL で取り込む](../storage/import-from-published-sheet-url.md), [部位別の指標を volume ではなくセット数にする](../data-model/group-metric-is-set-count.md)

## 背景

`src/import_text.rs`（1382 行 + 単体テスト 25 本）は**追加した 5 時間後に撤去された**。撤去の理由は読み取り精度ではなく**操作量**だった。

> 未知の種目ごとに部位を選び、日付が読めない分の着地日を選び、読めなかった行を確かめる。
> 移行は生涯に数回しか通らない導線なのに、そこだけ他のどの画面より操作が多い。
> 筋トレ中に最短距離で足せるというアプリの前提から外れている。

決定打はこう書かれている —「読み取り精度を上げても操作量は減らず、操作量を削ると読み違いをそのまま取り込む。**どちらに倒しても割に合わない**」。

表からの取り込み（[CSV を二次形式として足し、正は JSON のままにする](../storage/csv-as-a-secondary-lossy-format.md)）は、同じ画面に着地する別の入力である。**同じ穴に落ちないことを設計で保証する必要がある。**

## 決定

**確認画面で利用者に問いを出さない。** 未知の種目の行き先は表に書いてある部位から決め、決まらない行は**落として件数を報告する**。

| 種目名の状態 | 動作 |
|---|---|
| 既存の種目と**ちょうど 1 件**一致（空白・中黒・全角半角・大文字小文字を潰した後） | その ID を使う |
| 既存の種目と**2 件以上**一致 | **その行を落とす**（下記） |
| 未知 + 部位列が既存の部位と一致 | **その部位に種目を自動で作る** |
| 未知 + 部位列が空、または未知の部位 | **その行を落とし、行番号と理由を出す** |

加えて、[テキスト取り込みは「足すだけ」に固定し、部位を増やさず、`at` を書かない](../data-model/text-import-is-merge-only.md) の規則をそのまま引き継ぐ。

1. **新しい部位を作らない**
2. **`ExerciseLog.at` は常に `None`**
3. **既存の種目に当たったら、取り込み先の `Exercise` をそのまま複製して返す**
4. **黙って 0 件取り込まない**

## 理由

### なぜ「聞かない」が成立するのか

**表は自前の書き出しか、人が整えたものだから。** OCR の出力と決定的に違うのは、`部位` 列に何を書くかを人が決められる点にある。

- 自前の CSV を編集して戻す場合、部位は必ず既存のものに一致する。**問いは 1 つも発生しない**
- 他アプリから移す場合、利用者はスプレッドシート上で部位列を埋める。**表計算アプリのほうがアプリ内の確認画面より編集しやすい**（オートフィル、コピー、一括置換がある）

つまり `import_text.rs` が「アプリ内の確認画面でやらせようとしたこと」を、**表計算アプリに任せた**。整形の道具として、こちらのほうが優れている。

### 落とした行を数で出す

聞かない代わりに、**落としたことは必ず見せる**。確認画面に出すのは 3 つ。

```
新しく作る種目: レッグプレス・チンニング
取り込めない行: 4 / 120 件
7 行目: 「Bench Press」の部位「Push Day」がありません
9 行目: 日付「08/13/2026」が読めません（年から書いてください）
...ほか 2 件
```

行番号を出すのは**表の中で探せるようにする**ため。理由だけ出しても、120 行のどれかが分からなければ直せない。`SkipReason::message()` が理由ごとに直し方まで書く。

先頭 3 件で打ち切るのは、`.pre-` の控えを取ってから実行する構造（`storage::snapshot_current`）があるので、**全部読ませなくても取り返しがつく**から。

### 新しい部位を作らない

[部位別の指標を volume ではなくセット数にする](../data-model/group-metric-is-set-count.md) の下で**部位はグラフの集計単位**なので、増やすと過去の集計まで割れる。移行元の「Push Day」「胸・三頭」をそのまま部位にすると、プリセットの 6 部位と意味が重なった部位が並び、以後ずっと種目が二重に分かれる。

`import_text.rs` はここで「既存の部位から選ばせる」を選び、それが操作量の主因になった。**選ばせずに落とす**なら、直す場所は表の側になる — そこには一括編集の道具がある。

### 名前を寄せすぎない

突き合わせで潰すのは**空白・中黒・全角半角・大文字小文字だけ**にする。編集距離で寄せると「レッグカール」と「レッグエクステンション」を同一視しうる。

**間違って繋がった履歴は、間違いに気づけない。** グラフが滑らかに繋がってしまうので、見ても異常が分からない。落とすほうは画面に出るので気づける。`csv_import_does_not_merge_names_that_are_merely_similar` が固定している。

### どの行も「入る」か「報告される」かのどちらかにする

**`report.taken` は「読んだ行」であって「入った行」ではない。** ここがずれると、画面が「取り込みました」と言ったのに何も増えない、あるいは落としたと言った行の一部だけが残る。守る規則を 3 つ置いた。

1. **後段が捨てる値は行の時点で弾く。** `core::normalize` の `drop_unrepresentable_weights` は負の重量と f32 で `inf` になる値を黙って捨てるので、`sheet::parse` 側で先に見て `skipped` に出す
2. **重量も回数も種目メモも無い行は落とす。** `normalize` が「セットもメモも無いログ」を捨てるため、取り込んだことにすると黙って消える
3. **落とす行はセッションに触らせない。** 体重・当日メモの代入を種目の解決より**後ろ**に置く。前に置くと、取り込まないと言った行の体重だけが「記録のない日」として残り、**利用者が知らない休養日がカレンダーに生える**

3 は実際に踏んだ。`sessions.entry(...).or_default()` を行の先頭で呼んでいたのが原因で、`a_row_that_is_reported_does_not_leave_its_body_weight_behind` が固定している。

### 同名が 2 つあるときは選ばない

`rename_exercise` にも `rename_group` にも重複チェックが無いので、**利用者は「ベンチプレス」を 2 つ、「胸」を 2 つ作れる**。名前で引く以上、この状態では取り込み先が決まらない。

片方を勝手に選ぶと、上と同じ壊れ方になる — 別々の種目の履歴が 1 本に合流し、グラフが滑らかに繋がるので気づけない。だから落として

> 「ベンチプレス」という種目が 2 つ以上あります（種目タブで名前を分けてください）

と出す。**直し方が 1 つに決まる**ので、聞かない方針とも矛盾しない。

これは [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md) が v2 → v3 の移行で「名前がプリセットと一致する種目を固定 ID へ寄せるのは**一致がちょうど 1 件のときだけ**」と決めたのと同じ穴で、同じ答えを採った。

**部位にも同じ規則を掛ける。** `core::pin_presets` が部位と種目の両方に「ちょうど 1 件」を適用しているのと揃える。片方だけ守ると、新しい種目が意図しないほうの「胸」に入り、[部位別の指標を volume ではなくセット数にする](../data-model/group-metric-is-set-count.md) の集計が 2 つに割れる。

`csv_import_refuses_to_pick_between_two_exercises_with_the_same_name` と `csv_import_refuses_to_pick_between_two_groups_with_the_same_name` が固定している。

### 取り込み先の名前で出す

読み取った表記ではなく、`db` にある `Exercise` をそのまま複製して返す。読み取った表記を入れると `core::merge_db` が `Conflict::NameMatched`（同じ種目とみなしました）を種目の数だけ並べる。

**同じものを同じと言っただけで、改名は起きていない。** 起きていないことを報告に並べると、本当に見るべき `SetsDiverged` が埋もれる。`merging_a_parsed_sheet_does_not_report_renames` が `conflicts` が空であることを固定している。

## 結果（トレードオフ）

- **部位列を埋め忘れた行は取り込まれない。** 既定を「取り込まない」にしたので、埋め忘れると黙って入らない…とはならないよう、件数と行番号を必ず出す。**それでも「出したのに読まなかった人」は取りこぼす**
- **自動で作られた種目は、あとから部位を直す作業が残りうる。** 表の部位列が雑だと、意図しない部位に種目ができる。ただし種目タブで動かせるし、`.pre-` の控えから丸ごと戻せる
- **曖昧な日付は推測せず落とす。** `08/13/2026` と `13/08/2026` はどちらの解釈も成り立つ。推測して外すと記録が半年ずれた日に静かに入るので、落として報告するほうを選んだ。**アメリカ式の日付で書かれた表はそのままでは入らない**（表の側で `YYYY-MM-DD` に直してもらう）
- **確認画面が縦に伸びた。** 「現在 / 読込後」の数字に加えて内訳が入る。ただし出るのは落とした行か新規種目がある場合だけで、自前 CSV の往復では 1 行も増えない

## 検討した代替案

**未知の種目を「その他」部位に自動で入れる**: 部位を 1 つ増やすことになり、決定 1 と矛盾する。しかも自動で入ると、後から部位を直す作業がそのまま残る（`import_text.rs` の ADR が同じ理由で却下していた）。

**未知の種目ごとに部位を選ばせる**: `import_text.rs` がやって撤去された形そのもの。生涯数回の導線に、他のどの画面より多い操作を置くことになる。却下。

**部位列が無くても種目を作る（既定の部位に入れる）**: 「聞かない」は保てるが、どこに入るかが利用者から見えないまま増える。**落として報告するほうが、直す場所が明確**。

**落とした行を全部並べる**: 120 行の表で 40 行落ちたとき、確認画面が 40 行になる。控えを取ってから実行する構造があるので、先頭 3 件 + 件数で足りる。
