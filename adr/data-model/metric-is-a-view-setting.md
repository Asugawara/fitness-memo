# 指標を種目の属性ではなくグラフの表示設定にする

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: data-model
- **関連**: [指標の種類を種目の明示属性にする（データから推論しない）](exercise-kind-explicit.md)（置換）, [部位別の指標を volume ではなくセット数にする](group-metric-is-set-count.md)（置換）, [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md)

## 背景

[指標の種類を種目の明示属性にする（データから推論しない）](exercise-kind-explicit.md) は `Exercise.kind`（加重 / 自重 / 時間）を種目の明示属性として持たせ、指標の式と単位をそこから決めていた。狙いは「自重ディップスを 12 週記録した後にベルトで +10kg 付けると、推論方式なら系列全体が volume 指標へ切り替わり過去 12 週が潰れる」という事故の防止だった。

問題は実装ではなく前提にあった。懸垂が自重でプランクが時間だというのは種目名から読めることで、加重 / 自重の区別をユーザーに宣言させる意味が無い。しかも `Kind` は指標・単位・入力欄の有無・種目編集 UI・単位変更の確認ダイアログ・プリセット定義・部位別合算の可否まで波及しており、「意味の分からない選択肢」1 つのために UI が広範囲に複雑化していた。

そして **指標は記録の属性ではなく、見る側の関心である。** 同じ記録を「重量×回数」でも「セット数」でも見たいなら、それはグラフの表示設定にすればよい。

## 決定

**`Kind` を型ごと廃止し、代わりに `Metric`（画面の表示設定）を入れる。**

```rust
/// グラフに出す値の種類。**種目の属性ではなく画面の表示設定。**
pub enum Metric { Volume, Sets, Reps }

/// 1 セットのボリューム。**重量が入っていないセットは重量 1 として数える。**
pub fn set_volume(s: &SetEntry) -> f64 {
    f64::from(s.weight).max(1.0) * f64::from(s.reps)
}

pub fn log_value(m: Metric, l: &ExerciseLog) -> f64;
```

- 指標の式は 1 本。重量欄を空のままにすれば自重種目は総レップ数、時間種目は総秒数になる
- 単位は `Metric` だけで決まる（`Volume` は合成量なので単位なし / `Sets` = セット / `Reps` = 回）
- 推移タブが 3 指標のセグメントを持つ。対象種目を切り替えても軸の意味は変わらない
- `Db` の `schema` を 2 に上げる。旧 JSON の `"kind"` は serde が未知フィールドとして無視する

## 理由

**[指標の種類を種目の明示属性にする（データから推論しない）](exercise-kind-explicit.md) の問題を、種目に属性を持たせずに解ける。**

「自重種目に加重すると系列の意味が変わる」のが怖かったのは、系列の意味が種目定義から自動で決まり、ユーザーがそれを見ても分からなかったから。**どの軸で見るかをその場で選べる**なら、跳ねたグラフを見て「セット数」へ切り替えれば済む。判断の主導権が定義時ではなく閲覧時に移る。

**`max(1.0)` は単調性のため。** 素の積にすると 0.5kg のプレートを持った瞬間に指標が自重時より下がり（0.5×10 = 5 < 10）、グラフの上下が負荷の増減を表さなくなる。

**式が 1 本になると多くの分岐が消える。** `unit_of` / `reps_unit` / 種目編集の「種類」UI / 単位変更の警告 / プリセットの Kind 列 / カレンダー月合計の「加重種目のみ」絞り込み / 部位別をセット数に固定する制約（[部位別の指標を volume ではなくセット数にする](group-metric-is-set-count.md)）がまとめて不要になった。

## 結果（トレードオフ）

**schema 1 から値が変わる記録が 3 種類ある。** `core.rs` の `set_volume_changes_these_three_cases_from_schema_1` で固定してある。

| 記録 | 旧 | 新 |
|---|---|---|
| 自重 + 追加重量（ディップス +10kg × 8） | 8 | 80 |
| 加重種目で重量を空のまま保存した記録 | 0 | reps |
| 0 < 重量 < 1（0.5kg × 10） | 5 | 10 |

過去の点が遡及的に書き換わるわけではなく、式が単調なので順序は保たれる。1 は「実際に負荷が上がっている」ことの反映でもある。

**`+10×8` の「追加重量」表記が消える。** 重量が入っていれば `10×8` と出るだけになり、それが自重に足した 10kg なのかは読めない。`Kind` が無ければ区別する情報がそもそも無い。

**時間種目の「秒」が表記から消える。** プランクのセットは `60` とだけ出る。60 が秒だと分かるのは種目名からで、表記からではない — というのがこの ADR の立場そのものなので、一貫はしている。

**重量未入力の検出が難しくなった。** 新式では重量を入れ忘れると 600 が黙って 10 になる。`Kind::Weighted` という判定材料が消えたので、`day.rs` は「前回ログか同カードの他の行に重量があるか」という実データ由来の判定に置き換えた（全種目で警告を出すと懸垂 12 回の毎行に出て邪魔になる）。

**前方互換が壊れる。** フィールドを消したので旧版は新 JSON を読めない。対処は [保存キーを schema 世代ごとに切り、旧キーを読み取り専用で残す](../storage/storage-key-per-schema-generation.md)。

## 検討した代替案

**UI から「種類」の選択だけ消し、データ上の `Kind` は残す。** 表示上は言葉が消えるが、ユーザーが新規追加した自重種目の指標が常に 0 になる（既定の Weighted で重量が空のため）。「意味が分からない概念」が見えないまま挙動だけ支配するので、むしろ悪い。

**指標を総レップ数に統一する。** 単位が 1 つになり最もシンプルだが、重量の伸びがグラフから読めなくなる。「仕事量（レップ数×重さ）を比較する」という中核要件を落とす。

**データから `Kind` を推論する。** [指標の種類を種目の明示属性にする（データから推論しない）](exercise-kind-explicit.md) が却下したとおり、自重種目に加重した瞬間に系列全体の意味が切り替わる。`Metric` は式が常に同じで表示軸だけが変わるので、この問題を構造的に持たない。
