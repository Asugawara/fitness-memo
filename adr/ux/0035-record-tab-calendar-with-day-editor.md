# ADR-0035: 記録タブをカレンダー + 選択日エディタの単一画面にする

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: ux
- **関連**: [ADR-0024](0024-calendar-add-from-empty-day.md)（改訂）, [ADR-0022](0022-pre-workout-and-in-workout-exclusive.md)（置換）, [ADR-0002](../architecture/0002-no-router-tab-enum-signal.md)

## 背景

タブは「今日 / カレンダー / 推移 / 種目」の 4 つだった。[ADR-0024](0024-calendar-add-from-empty-day.md) は「記録が無い日でも『この日に記録する』を必ず出す」ことで要件（カレンダーに対して日付を指定して追加できる）を満たしたが、その導線は **カレンダーで日を選ぶ → ボタンを押す → 今日タブへ遷移 → 記録する → カレンダーへ戻って確認** というタブ往復だった。

実使用のフィードバックは **「当日タブいらん気がする。カレンダーとその下に種目」**。

「昨日記録し忘れた分を入れる」は最も典型的な使い方で、そのたびに往復するのは重い。しかも「今日」も `dates.selected` が今日を指しているだけの同じ画面なので、2 タブに分ける理由がデータ上も無かった。

## 決定

**タブを 3 つ（記録 / 推移 / 種目）にし、記録タブをカレンダー + その下の選択日エディタの 1 画面にする。**

```
月ナビ ‹ 2026年8月 ›
曜日ヘッダ + 月グリッド
月フッタ（実施 / 合計 / セット）
最後から 2日5時間 · 胸3d 背中5d …      ← 圧縮ヒーロー
──────────────────────────
8/8 (金) [今日]  ／ 8/5 (火) [今日へ戻る]
＋コンディション
種目カード…
[＋ 種目を追加]（sticky）
```

- **日セルをタップした時点で、下の入力欄がその日のものになる。** ボタンを挟まない
- 読み取り専用の日別サマリと「この日を編集 / この日に記録する」は削除
- **選択日は `DateCtx::selected` だけが持つ。** カレンダーのローカル `picked` は廃止
- 日セルのクリックは `DateCtx::open`（同値ガード付き）を通す

## 理由

**`picked` と `selected` の二重管理は必ずずれる。** 統合前は「グリッドの選択日」と「入力欄が書き込む日」が別シグナルでも、画面が分かれていたので破綻しなかった。同じ画面に並べた瞬間、片方だけ動くと嘘の表示になる。

**`RwSignal::set` は同値でも通知する。** 選択中の日セルを再タップしただけで `<ConditionRow />` が作り直され、体重欄に「62.」まで打った中間状態が確定値へ巻き戻る。`DateCtx::open` の `!=` ガードで防ぐ。

**同じ画面なので反映が即座に見える。** セットを打つとカレンダーのドットと月フッタが同時に動く。タブ往復では「戻って確認する」必要があった。

## resync の force を落とす

これが統合で一番危険だった点。

`DateCtx::resync(force)` は visible 復帰（`visibilitychange`）で `force = true` を渡し、**ユーザーが明示的に選んだ過去日でも無条件に今日へ戻して**いた。iOS のホーム画面 PWA は再起動されず何日もレジュームされるので、日付を跨いだ操作が前日に記録されるのを防ぐためだった。

これが安全だったのは、カレンダーの選択日が `picked` で resync の影響外にあったから。**選択日を一本化した今そのまま残すと、7 月の記録を見ている最中に通知からアプリへ戻るだけで、月表示ごと今日へ飛ぶ**（`month` が `selected` を追う `Effect` を持つため巻き添えになる）。

**`force` を削り、「当日を見ていたときだけ新しい当日へ追従する」に統一した。**

```rust
let selected = self.selected.get_untracked();
if selected == prev && selected != now {
    self.selected.set(now);
}
```

誤記帳の防止は、カレンダーのハイライトと `past-banner`（日付が常時見えている）が担う。

**不変条件: 明示的に選んだ日付は visible 復帰でも維持する。**

## 結果（トレードオフ）

**読み取り専用の日別サマリを失う。** 「1 行 = 1 種目」の密度で過去日を流し見できる唯一の画面だった。常時編集可能な入力フォーム（1 セット = 1 入力行）に置き換わるので、**過去日の一覧性は明確に下がり、閲覧のつもりのタップが編集操作になる**。ユーザー指示の直接の帰結として受け入れるが、意図的な損失として記録しておく。

**セット未入力のカード枠は日付切替で消える。** カードは `selected` の変化で `Db` から引き直す（`day.rs`）ので、まだセットを入れていない「先に種目を並べておく」枠はカレンダーを触ると消える。記録データ自体は無事。統合前は別タブだったので起きなかった動線。

**大きい経過ヒーローを置く余地が無くなった。** カレンダーが上に載って画面が縦に伸びたので、34px のヒーローと中央寄せチップは常時 1 行へ圧縮した。トレ前 / トレ中の出し分け（[ADR-0022](0022-pre-workout-and-in-workout-exclusive.md)）も意味を失ったので廃止。

**打鍵ごとの再計算が増える。** `calendar.rs` の `month_data` と `day.rs` の `before_today`（**`Db` 全体の clone**）が同一画面で併走する。記録が数年分になったら `before_today` の粒度を見直す。

## 検討した代替案

**カレンダーを今日タブの上に折りたたんで置く。** タブ構成を変えずに済むが、開閉状態という新しい状態が増え、「閉じているときに過去日を選ぶ」導線が結局必要になる。

**サマリと入力欄を切り替え式にする。** 一覧性は保てるが、「閲覧か編集か」をユーザーが宣言する操作が増える。往復を減らすのが目的なので本末転倒。
