# プリセット名は初回投入の言語で固定し、ユーザーデータとして扱う

- **状態**: 置換済み → [プリセット名は表示時に言語へ追従させ、改名したものだけ据え置く](../ux/preset-names-follow-the-ui-language.md)
- **日付**: 2026-08-19
- **カテゴリ**: storage
- **関連**: [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md), [取り込みは「足すだけ」に固定する](import-is-merge-only.md), [テキスト取り込みは「足すだけ」に固定し、部位を増やさず、`at` を書かない](../data-model/text-import-is-merge-only.md), [言語はブラウザに従い、選んだらそれを優先する](../ux/language-follows-the-browser-then-the-setting.md)

> **置換済み。** この ADR は「プリセット名は初回投入の言語で固定し、言語を切り替えても
> 一切変えない」と決めたが、**利用者から「表示を切り替えたい」という要望があり反転した。**
> 新しい決定は [プリセット名は表示時に言語へ追従させ、改名したものだけ据え置く](../ux/preset-names-follow-the-ui-language.md)。
>
> **下の「理由」の中身は、そのほとんどが新しい決定でもそのまま生きている** —
> 保存名を書き換えないこと、固定 ID がマージの鍵であること、lookup が日英両対応で
> あることは変わらない。変わったのは**表示のときだけ**言語の綴りを引くようになった点で、
> `Db` は一切触らない。この ADR が却下した「表示時に翻訳」の破綻理由
> （下の「検討した代替案」）にどう答えたかは新しい ADR に書いてある。

## 背景

6 部位 28 種目のプリセットは初回起動時に `Db` へ書き込まれる。英語対応にあたり、
**言語を切り替えたときにこれらの名前をどうするか**を決める必要がある。

素朴に考えると「英語にしたら Bench Press に変わってほしい」となる。しかしプリセット名は
投入された瞬間から `Db` の中のただの `String` で、ユーザーが自由に改名できる。
`seed` は既に「改名済みプリセットを復活させない」という規則を持っていて
（判定が名前ではなく固定 ID なのはそのため）、テストもそれを固定している。

## 決定

**`seed(db, lang)` は初回（と復元失敗時）に、その時点の言語の綴りで投入するだけ。
以後アプリが既存の名前を書き換えることは一切しない。**

```rust
pub struct Names { pub ja: &'static str, pub en: &'static str }

pub struct PresetGroup {
    pub id: GroupId,
    pub name: Names,
    pub exercises: &'static [(ExerciseId, Names)],
}
```

**固定 ID は 1 文字も動かさない。** 名前は言語で変わるが ID は変わらない。

**`preset_exercise_id` / `preset_group_id` は日英どちらの綴りでも固定 ID を返す。**

## 理由

- **改名は正当な操作で、アプリが勝手に戻してはいけない。** 「ベンチプレス」を
  「ベンチプレス（スミス）」に変えた人の名前を、言語設定を触ったという理由で
  「Bench Press」に書き換えるのは記録ではなく破壊である。`seed` が既に
  「改名済みプリセットを復活させない」を守っているのと同じ原則。
- **言語切替で名前を書き換えると、マージが全種目を衝突として報告する。**
  `merge_db` は名前の違いを `Conflict::Renamed` として数える。端末 A が日本語、
  端末 B が英語なら、片方のファイルを取り込むたびに 34 件の衝突が並ぶ。
  ID で寄せているのに名前で騒ぐという、一番読みにくい状態になる。
- **名前が変わっても ID が変わらないので、日英の端末のデータを混ぜても種目が割れない。**
  これは [ID を 60 bit 乱数にし、プリセットには固定 ID を与える](../data-model/random-ids-for-safe-merge.md) の
  狙いがそのまま効く場所で、予約領域の固定 ID を持っていたおかげで
  「多言語対応でデータモデルを触る」必要が一切なかった。
- **lookup が両言語を見るのは必須。** 英語で初期化した端末が書き出した TSV には
  "Bench Press" が入る。片方しか見ないと、日本語の端末で取り込んだときに固定 ID へ寄らず
  **同じ種目が 2 本に割れる**。`Names::matches` が両方を比べる。
- **`Names` は `i18n.rs` ではなく `presets.rs` に置く。** これは文言ではなくデータで、
  投入されたら `Db` の中のただの名前になる。`i18n.rs` の「表示用の日本語リテラルを
  外に置かない」という規約の例外として、明示的に除外してある。
- **`v1` / `v2` からの移行（`pin_presets`）も両言語で照合する。** 旧世代は日本語しか
  持たないので実質日本語しか当たらないが、規則を 1 本にしておくほうが後から読んで迷わない。

## 結果（トレードオフ）

- **既存の日本語ユーザーが英語に切り替えても、種目名は日本語のまま。** 英語 UI に
  「ベンチプレス」が並ぶ状態が普通に起きる。手で改名するしかない。
  意図した挙動なので、言語サブページに注記を出して先に伝えている。
  README の「現時点の制限」にも書いた。
- **英語のプリセット名も、出した時点で永久の外部仕様になった。** TSV に書き出されて
  他端末で `preset_exercise_id` に引かれるので、後から "Bench Press" を
  "Barbell Bench Press" に変えると、古いファイルが固定 ID に寄らなくなる。
  日本語名と同じ重みで凍結される。
- **プリセット名の一意性を日英を跨いで守る必要が生じた。** 片方の言語で衝突していなくても、
  日英で同じ綴りがあれば `Names::matches` が 2 つのプリセットに当たる。
  68 個すべてが一意であることを `cargo test` で固定した。
- **`seed` の引数が増えた。** `storage::load(lang)` から渡す形になり、`App` が
  `LangCtx` を provide する前に言語を解決する順序制約ができた。`App` にコメントで書いてある。

## 検討した代替案

**固定 ID をキーに、未改名のものだけ表示時に翻訳する**: 「Bench Press のまま使っている人」には
言語切替が効いて、改名した人の名前は守られる。理想的に見えるが、破綻が多い。
TSV に何を書き出すのか（表示名か実体か）が決まらず、書き出したファイルを取り込むと
表示名が実体として保存される。グラフの凡例・検索・`merge_db` の名前照合も
「実体」と「表示」のどちらを見るかを全部決め直すことになる。
**「未改名」の判定自体も、初回投入の言語の綴りと一致するかで見るしかなく、
言語を 2 回切り替えると壊れる。** 却下。

**言語切替時に、未改名のプリセットを一括で改名する**: `Db` を実際に書き換えるので
表示・書き出し・マージの整合は取れる。しかし他端末とマージしたときに
`Conflict::Renamed` が 34 件並ぶし、「設定を触ったらデータが書き換わった」という
挙動そのものが、記録アプリとして踏んではいけない一線だと判断した。却下。

**プリセットを英語名だけにして、日本語は表示時に引く**: 実体が 1 つになるので
上の破綻は起きない。しかし既存の全ユーザーの `Db` に日本語名が入っているので、
移行で全員の種目名を書き換えることになる。得るもの（新規英語ユーザーの整合）に対して
払うもの（既存ユーザー全員のデータ書き換え）が釣り合わない。却下。
