# 実装前に敵対的レビューを回す

- **状態**: 採用
- **日付**: 2026-08-08
- **カテゴリ**: process
- **関連**: [Herdr の波状並列でファイル所有権を分けて実装する](herdr-wave-parallelism.md)

## 背景

このプロジェクトは greenfield で、コミット 0 の空リポジトリから始まった。技術スタック（Rust + leptos + trunk + wasm32 + PWA + GitHub Pages）はどれも「動かしたことがある人には自明だが、初見では細部で必ず躓く」種類のものである。

しかも失敗のコストが非対称である。データモデルの誤りは、実装が進むほど直すコストが上がる。デプロイ機構の誤りは、実装が終わってから初めて分かる。

計画を書いた時点では、次のような「もっともらしいが間違っている」判断が含まれていた。

- `chrono` の `default-features = false`（サイズ削減の定石）
- `[profile.release] strip = "symbols"`（同）
- Service Worker の「ミス時はネットワーク → 成功なら `cache.put`」（定番のパターン）
- `release` ブランチを `git switch --orphan` で作る
- 種目の指標を「全記録が `weight == 0` なら総レップ数」と推論する

いずれもレビューなしで実装すれば、動くところまでは行って**後で静かに壊れる**。

## 決定

**実装に着手する前に、計画に対して敵対的レビューを 3 系統回す。** 観点を分けて並列に走らせる。

1. **要件 / UX / データモデル** — 要件を満たしているか、モデルが将来のデータを壊さないか
2. **Rust / leptos / trunk** — API 名と feature、ビルド設定が実在するか
3. **PWA / デプロイ** — SW とキャッシュ、Pages と git 操作が実際に成立するか

**指摘は一次ソースで裏取りしてから計画に反映する。** crates.io の実 tarball、docs.rs 0.8.20、trunk v0.21.14 のソース、Homebrew formula、WebKit / Chrome / MDN、GitHub Docs、`curl -I` の実測。

## 理由

- **「もっともらしいが間違っている」判断は、レビューでしか捕まらない。** 上記の 5 つはいずれも一般的なベストプラクティスの形をしている。テストでは捕まらないものが多い（`chrono` の UTC 化はコンパイルもパスもするし、時間帯依存でしか出ない）。
- **観点を分けると見落としが減る。** データモデルを見ている視点は SW のキャッシュ順序を疑わない。3 系統に分けたのは、単一の視点で全部を見ようとすると必ず薄くなるからである。
- **一次ソースでの裏取りが不可欠だった。** レビューの指摘自体も間違いうる。実際に「`leptos::ev::visibilitychange` を使えばよい」という提案が出たが、docs.rs 0.8.20 を確認すると 404 で、typed event として存在しなかった（`window_event_listener_untyped` を使う）。**指摘を無検証で採ると別のバグが入る。**
- **greenfield は方針転換のコストが最も低い瞬間である。** コードがない時点なら、データモデルの変更は文書の書き換えで済む。実装後なら移行コードとテストの書き換えが必要になる。

## 実際に捕まった主な指摘

| 当初案 | 問題 | 反映 |
|---|---|---|
| `chrono` の default features を削る | wasm32 で `Local::now()` が黙って UTC になり、日付キーが 9 時間ズレる | 削らない（[セッションをローカル日付文字列で BTreeMap に持つ](../data-model/session-keyed-by-local-date.md)） |
| `strip = "symbols"` | wasm 生成物を壊す（rust-lang/rust#93294 は現在も open） | 書かない |
| `web-sys` の feature を leptos 任せ | tachys は `Storage` を有効化しない。`local_storage()` が生成されない | 自前で全宣言（[UI 依存を wasm32 の target 別 dependencies に置く](../architecture/wasm-target-scoped-dependencies.md)） |
| SW のミス応答を `cache.put` | Pages の `max-age=600` により v2 キャッシュに v1 index.html が固定化され白画面 | 格納しない（[Service Worker はシェル全体を BUILD_ID で原子的に入れ替える](../pwa/sw-atomic-shell-swap.md)） |
| `caches.keys()` を無差別に削除 | オリジン共有なので他プロジェクトの Pages キャッシュを壊す | prefix で絞る |
| `git switch --orphan release` | unborn ブランチ / unrelated histories / `.gitignore` 消失の 3 重の欠陥 | `main` から派生（[`release` を `main` から派生させ orphan 運用にしない](../deploy/release-branch-from-main.md)） |
| Actions 機能を無効化 | Pages の branch deploy が内部で Actions を使うのでデプロイ不能 | 機能は有効のまま（[ワークフローファイルを書かない（ただし Actions 機能は無効化しない）](../deploy/no-workflow-files.md)） |
| `weight == 0` から指標を推論 | 加重カリステニクス移行で過去データが遡及的に壊れる | `Kind` を明示属性に（[指標の種類を種目の明示属性にする（データから推論しない）](../data-model/exercise-kind-explicit.md)） |
| `type="number"` で数値入力 | WebKit の sanitization で中間状態が読めない | `type="text"` + `inputmode`（[数値入力に `type="number"` を使わない](../ux/text-input-not-number.md)） |
| キーボード対策なし | standalone では `interactive-widget` が無視され、毎セットタブバーが被る | `.kb-open`（[キーボード表示中はボトムタブを隠す](../pwa/hide-tabs-when-keyboard-open.md)） |
| WebKit で SW の E2E を走らせる | Playwright の WebKit は SW 非対応。release ゲートを永久に通過できない | Chromium 系のみ |

## 結果（トレードオフ）

- **実装開始が遅れる。** レビュー 3 系統と一次ソースでの裏取りに相当の時間を使った。ただし上記のうち 1 つでも本番まで流れれば、原因究明に同等以上の時間がかかる（しかも「なぜか日付がずれる」「なぜか白画面になる」という形で現れる）。
- **計画書が長くなる。** 却下した案とその理由が全部書かれているので、実装者が読む量が増える。一方でその記録があるおかげで、実装中に「これ、こうしたほうが良くない?」が出たときに再検討のコストが下がっている。この ADR 群自体がその記録の再構成である。
- **レビューが指摘しなかったことは依然として穴である。** 3 系統に分けても、誰も見ていない領域は残る。実際に残った未確認事項（iOS Safari が SW メインスクリプトの更新フェッチで HTTP キャッシュをバイパスするかの一次資料、`release` 不在で `POST /pages` を叩いたときの正確なエラーコード）は計画に「残るリスク」として明記した。**「レビュー済みだから安全」ではない。**
- **レビューの指摘を検証するコストが発生する。** 無検証で採ると別のバグが入るので省略できない。実際に `leptos::ev::visibilitychange` の件で必要だった。
- レビューはあくまで文書に対するものなので、実装時の判断（例: シートがボトムタブに隠れる）は捕まらない。実装フェーズでの検証（E2E と実機）が別に必要である。

## 検討した代替案

**そのまま実装して動かしながら直す**: 最も速く動くものが見える。しかし上記の指摘の多くは「動いてしまう」バグなので、動かしても見つからない。データモデルの誤りは実装後に直すコストが最も高い。却下。

**レビューを 1 系統だけ回す**: コストが 3 分の 1 になる。しかし単一の視点で要件・Rust API・PWA・git 操作の全てを見ると必ず薄くなる。実際に捕まった指摘は 3 系統に散っており（データモデル / ビルド設定 / SW とデプロイ）、1 系統では取り逃していた。却下。

**プロトタイプを作ってから計画する**: 実測に基づけるので確実である。しかしプロトタイプで確認したいこと（`chrono` の TZ、SW のキャッシュ順序、Pages のデプロイ）は**プロトタイプを本番相当まで作らないと現れない**。それは実装そのものである。却下。

**レビューの指摘を無検証で全部採る**: 速い。しかし指摘自体が間違っている場合に別のバグが入る（実例あり）。一次ソースでの裏取りは省略できない。
